## CR-1 — Make the five-failure token limit atomic

`DeploymentSetupService.CountFailureAsync` reads the current token, increments `FailedAttempts` in memory, and saves it (`DeploymentSetupService.cs`, lines 116–128; the increment is line 120). Concurrent invalid setup requests can read the same value and overwrite one another, so five failures need not produce five stored attempts or void the token. That violates the approved security contract.

Revise the failure transition so concurrent invalid requests are serialized or updated atomically in the database. Required behavior:

- the fifth committed failure voids the current token;
- a correct token is refused afterwards;
- exactly one `SetupTokenRejected` audit row is produced for that transition;
- later failures do not create more rejection rows; and
- no raw token or attempted credential enters logs or audit details.

Add a focused concurrency test using separate contexts/requests that submits at least five invalid attempts simultaneously and proves the outcomes above. Retain the existing sequential boundary test for four versus five failures.

## CR-2 — Close the missing S21 unreachable-server proof

The approved S21 contract includes proving that an unreachable database/server terminates its readiness decision within the configured timeout/retry bound. R01 explicitly lists this as untested and nevertheless reports acceptance as 5/5.

Add the narrow automated proof. It may be a focused process/API test rather than another full browser walkthrough, but it must exercise the real retry/timeout path, establish an upper time bound, and prove the application does not hang or silently migrate/create anything. Record the measured duration and exact command in R02.
