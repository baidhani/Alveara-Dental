## Blocking findings and corrections

### ALV-002-C01-R02-01 — P2: The real audit API omits the entity metadata that the viewer expects

**Locations:** `src/Alveara.Api/Controllers/AuthController.cs:212`–226; `src/alveara-client/src/services/authApi.ts:42`–51; `src/alveara-client/src/pages/AuditLogPage.tsx:78`; `AuditLogPage.test.tsx`; `e2e/auth-real-backend.spec.ts:149`.

The shared service stores EntityType, Reason and CorrelationId. The client AuditLogEntry contract requires their nullable JSON equivalents, and the viewer renders entityType. However, GetAuditLog still projects only Id, EventType, TargetUserAccountId, PerformedByUserAccountId, Details and TimestampUtc. It never serializes the three new fields. Thus even a new UserAccount audit event with its type recorded reaches the viewer without that type and displays a dash; this is not just legacy rows legitimately lacking metadata.

The handoff explicitly claims the endpoint now returns richer entity/reason/correlation metadata, but the actual controller was not extended. The component test supplies entityType in a mocked response the real endpoint cannot produce. The new real-browser test checks event names, not the entity column, and consequently passes despite the contract mismatch.

An independent reviewer-only real-API/database integration probe staged a synthetic event through AuditService.Record with EntityType = UserAccount and non-null reason/correlation. Its authenticated GET succeeded, but the assertion failed: **“Real audit API omits entityType required by the viewer contract.”** Source inspection additionally confirms reason and correlationId are omitted by the same projection. This is a reproduced contract defect.

**Correction:** Return the shared nullable metadata from the existing read endpoint while preserving its permission enforcement and original fields. Keep nulls honest for legacy entries. Add an API contract test round-tripping entity type, reason and correlation, and strengthen real-browser coverage to assert the visible entity type of an actual newly generated event. Update handoff/evidence to describe the real behavior. No audit-edit permission or new domain workflow is needed.

### ALV-002-C01-R02-02 — P2: Viewer claims 500 events but requests only 100

**Locations:** `src/alveara-client/src/pages/AuditLogPage.tsx:49`; `src/alveara-client/src/services/authApi.ts:215`–216; `src/Alveara.Api/Controllers/AuthController.cs:212`–217.

The page says it shows “the most recent 500” events. getAuditLog() requests `/api/auth/audit-log` without a take parameter, so GetAuditLog uses its default 100. Once more than 100 entries exist, events 101–500 are omitted despite the description claiming that window. The server's maximum of 500 does not make its default response 500.

**Correction:** Make the actual requested limit and visible description agree, for example by requesting `take=500`, or explicitly describing the smaller window. Keep the server bound. Add coverage with more than 100 events or equivalent request/limit contract coverage so the same mismatch cannot recur. Filtering/pagination is not required by this correction.
