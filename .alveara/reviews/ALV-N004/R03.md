## Blocking finding

### ALV-N004-R03-01 — P1 — “Verify only” promotes a known contradictory archive to fully verified and increases confidence

**Source evidence:** `src/Alveara.Api/Architecture/Backup/BackupRestoreService.cs:300` (`VerifyFullAsync`) decrypts the archive, checks inventory/deployment asset agreement and runs SQL Server `RESTORE VERIFYONLY`. It does not inspect the database's recorded deployment invariants. At line 325 it sets `FullyVerified` and clears the verification failure. The database/manifest agreement check at line 469 is reached only through the restore drill. `src/Alveara.Api/Architecture/Backup/BackupService.cs:463` includes every `FullyVerified` row in confidence evidence; line 466 calculates its successful-verification count. A failed drill records its own failure but does not prevent the subsequent verify-only promotion.

**Independent reproduction:**

1. Create a real SQL Server-backed encrypted backup whose captured database records the normal Chicago deployment.
2. Use the same authenticated altered-archive mechanism exercised by the submitted hardening tests: change manifest and deployment asset to Tokyo, update the component hash, leave the captured database unchanged, and re-encrypt using the test recovery material. Configure the recovery provider for Tokyo.
3. Run an actual restore drill. Assert and observe `Failed` / `restore_validation_failed` (the new database-agreement check correctly rejects it).
4. Call the actual `VerifyFullAsync` on that same archive.
5. Observe **`FullyVerified` and `SuccessfulVerificationCount = 1`**, despite zero successful drills and the known deployment contradiction.

The reviewer test `A_contradictory_database_cannot_become_fully_verified_after_its_drill_fails` fails with: `Actual verification=FullyVerified; confidence count=1`. Initial reproduction and the follow-up confidence measurement both show the defect. Evidence is retained outside the product repository in `review-verification/ALV-N004-R03/reviewer-confidence-probes.trx` and `ReviewerR03Tests.cs.txt`.

**Impact and requirement:** SQL media readability is narrower than application-state consistency. The runbook legitimately distinguishes verify-only from application-start proof; retaining that distinction is appropriate. However, this attempt explicitly claims a contradictory backup cannot become fully verified, and the previous required correction included verification/trust state. A backup already proven internally inconsistent can still earn confidence and eventually satisfy the probation count through the weaker path. This violates truthful history/verification and the recovery confidence contract. The submitted 7/7 acceptance claim therefore remains overstated.

**Required correction:** Make verification/trust state accurately reflect the scope and failure evidence. Either validate captured database/manifest agreement before granting the relevant full-verification/trust credit, or retain media-only verification as a distinct state that cannot override a failed application-consistency check or earn application-recovery confidence without the required proof. A known failed consistency drill must invalidate that archive's recovery credit, and a later weaker check must not erase the failure. Preserve the useful verify-only workflow and clearly explain what its result proves.

**Required regressions:** Cover contradictory archive → verify only; verify only → failed consistency drill; failed consistency drill → verify only; and resulting confidence/probation state in each order. Include missing/unreadable restored deployment records and manifest/asset/database agreement. Keep valid-media, valid-drill, history-free recovery, isolated-target cleanup, non-default time-zone and legacy MFA compatibility behavior passing. Do not fix this merely by changing the prose claim while continuing to count a known contradictory archive toward trust.
