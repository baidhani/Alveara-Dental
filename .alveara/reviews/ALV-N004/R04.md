## Blocking finding

### ALV-N004-R04-01 — P1 — A file-hash check erases a known archive defect and bypasses its verification guard

**Code evidence:** `src/Alveara.Api/Architecture/Backup/BackupService.cs:392` (`VerifyHashAsync`) has no known-defect guard. When bytes match their recorded hash, lines 411–413 replace a failed state with `HashVerified` and clear `VerificationFailureCode`. Its failure branch can likewise replace the stronger known failure code with a different hash/environment failure. `BackupRestoreService.cs:310` (`HasKnownArchiveDefect`) depends on the mutable combination `VerificationFailed` plus an intrinsic code; after the hash action it no longer recognizes the defect. `VerifyFullAsync` then sets `FullyVerified` and clears the failure at line 347.

This is an exposed operator workflow: `POST /api/backup/backups/{id}/verify-hash` calls that service; the Backup history UI offers the file-hash action and displays the failure reason only while the verification state is failed. Permission/CSRF protection does not preserve the stronger integrity fact.

**Independent reproduction:** Create a real encrypted SQL-backed backup; use the authenticated altered-archive mechanism from the hardening tests to make manifest and deployment asset say Tokyo while the captured database records Chicago. A real drill correctly fails with `restore_validation_failed`. Then run the real `VerifyHashAsync`, followed by `VerifyFullAsync` on unchanged archive bytes.

`ReviewerR04Tests.A_known_archive_defect_survives_weaker_checks(hashFirst: True)` fails with **`Actual verification=FullyVerified; confidence count=0`**. The corresponding case without the intermediate hash check passes. The archive has not been repaired; the weaker checks have erased its known defect. Result/probe source are retained outside the product repository under `review-verification/ALV-N004-R04/reviewer-probes.trx` and `ReviewerR04Tests.cs.txt`.

**Practical limit of the finding:** The reproduced sequence does **not** regain recovery confidence; the new restore-proof separation keeps count zero. Also, the historical failed drill/audit entries remain. The defect is loss of the known failure in current backup state and bypass of the claimed permanent-failure protection, not deletion of immutable audit history or a demonstrated renewed trust count.

**Requirement and impact:** The acceptance item requires truthful distinction of success/failure/verification state. The R03 required correction says a later weaker check must not erase a known consistency failure. R04's runbook and acceptance evidence explicitly claim permanent, visible archive defects. An unchanged backup already proven unusable can instead return to the contents-verified label with its failure reason cleared. That known limitation is inside the story's recovery/history contract and prevents approval.

**Required correction:** Preserve intrinsic archive-defect evidence independently of the mutable latest-check status, or consistently enforce the same preservation rule across every mutation path. A quick hash pass/failure, media-only verification, wrong supplied material or temporary destination error must not erase a stronger recorded archive defect. Keep useful narrower check results separately if desired, with the known defect still visible and operative. Review all writes to verification status/failure/proof, including hash, verify-only, history/archive drills and failure paths, so this is not fixed only for one direct call order. Keep the new restore-proof separation.

**Required regression evidence:** At minimum: failed consistency drill → hash pass → verify-only; failed consistency drill → hash failure/environment error → later weaker success; and direct failed drill → verify-only. Assert persistence of the intrinsic reason in durable backup state and its visible history/API representation, zero confidence and no restore proof. Retain valid hash/media/drill behavior, wrong-key/server-mismatch distinctions, media-damage credit revocation, history-free archive recovery, cleanup, startup guard, non-default time-zone and legacy MFA compatibility.
