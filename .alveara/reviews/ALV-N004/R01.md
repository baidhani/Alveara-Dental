## Required corrections

### ALV-N004-R01-01 — P1: Recovery requires the database/history that the backup is supposed to recover

**Locations:** `Architecture/Backup/BackupRestoreService.cs:41`, `:181`, `:223`–225; `Controllers/BackupController.cs` restore routes; `pages/backup/RestoreWizard.tsx`; runbook disaster-recovery steps.

Preflight, verification and restore all start by finding a BackupRecord in the currently running database. The controller accepts only that record's ID; the wizard starts from an existing history row. There is no archive import/discovery or offline recovery entry point. Copying an intact `.abk` file to a replacement server does not create its history record.

**Real-database reviewer reproduction:** create an actual encrypted backup with representative accounts/blobs; retain the archive and correct offline private key/passphrase; create a fresh, migrated replacement database with no old history; call the provided restore service for that retained backup. The operation throws **BackupException: Backup not found** at line 225 before any archive validation or restore. The runbook's instruction to run the drill from a fresh installation therefore cannot be followed through the provided UI/API. The submitted full-state drill starts while the original backup history is still available and does not prove this disaster scenario.

**Correction:** Provide a supported, protected recovery entry point that accepts/discovers a retained archive without relying on lost database rows, verifies its authenticated metadata and contents, then restores only to a safe isolated target. A recovery tool or an authorized import-and-restore workflow is acceptable; document and test the actual operator path. Do not require manual database-row fabrication, a hash copied from the lost database, or the original server. Prove recovery using only the supported application/tool, retained encrypted archive and externally held recovery material against a fresh installation; start the recovered application and validate records, assets and MFA.

### ALV-N004-R01-02 — P1: The encrypted backup container violates the explicit no-custom-format requirement

**Location:** `Architecture/Backup/BackupCrypto.cs:24`–36 and its EncryptAsync/DecryptAsync/BuildAad framing code.

The Execution Plan explicitly says **“do not implement custom encryption, key derivation or custom cryptographic formats”**. The Reference independently forbids **“custom authenticated-encryption formats”**. The implementation defines its own `ALVBK` magic, version/header, wrapped-key layout, nonce prefix/counter, chunk lengths, AAD and final-chunk interpretation, then implements the corresponding parser and authentication rules. This is an application-defined authenticated-encryption format even though AES-GCM, RSA and PKCS#8 themselves use platform primitives.

The handoff candidly discloses this deviation. Tamper/reorder/truncation tests are useful, but do not satisfy or waive the prohibition. This finding is a demonstrated specification violation; this review does not claim the AES primitive is broken or that an exploit has been proven.

**Correction:** Replace the custom encrypted framing/parser with a maintained, reviewed library/platform facility implementing a documented authenticated file/container format, including its large-file handling. Preserve the externally held recovery-material strategy, wrong-key/authentication failures and bounded resource use. Record the selected facility and format, and add round-trip/interoperability, tamper, truncation, wrong-key and realistic multi-chunk/large-file coverage. Update the runbook/UI/evidence as needed; do not silently redefine the master requirement to permit the current format.

### ALV-N004-R01-03 — P1: The Data Protection application-name change makes existing MFA secrets unreadable

**Locations:** `Program.cs:87`; `Architecture/Backup/BackupRestoreService.cs:333`; existing AccountService MFA protection/unprotection paths.

Before this attempt the host persisted its key ring using its existing application discriminator. R01 unconditionally adds `SetApplicationName("Alveara.Dental")` without a compatibility reader or migration of existing protected values. Keeping the same key files does not preserve decryption when that discriminator changes.

**Reviewer reproduction:** build the old host's Data Protection registration, persist its key ring and protect an existing MFA payload using AccountService's real protector purpose; construct the R01 registration with the same content root/key ring and unprotect the payload. It fails with **CryptographicException: The payload was invalid**. AccountService uses this boundary for enrolled MFA secrets, so the failure affects existing enrolled accounts. Fresh enrollment/drill tests use the new discriminator on both sides and cannot detect this upgrade regression. The handoff acknowledges the break and proposes re-enrollment; the absence of production data is not authorization to invalidate previously completed authentication behavior or discard protected state.

**Correction:** Preserve existing payload compatibility or implement an explicit, tested upgrade that reads old protected values with their original discriminator and safely re-protects them under the portable identity before switching. Cover active/pending MFA and other persistent protected payloads that exist. Preserve key custody and failure recovery; do not clear factors, manufacture completion or require every existing user to enroll again as a substitute. Test an account enrolled before this implementation through upgrade, successful MFA authentication and a restore into a different folder/server identity. Revalidate ALV-001-C01's affected authentication behavior.

### ALV-N004-R01-04 — P1: The claimed full-state set omits the practice time-zone deployment invariant

**Locations:** `Program.cs:51`, `:107`–108; `Architecture/Backup/BackupEntities.cs:164`; `BackupSupport.cs:16`; `Architecture/Configuration/ConfigurationEntities.cs:7`–8; runbook recovered-application/promotion configuration.

The backup covers the database, blob directory and Data Protection keys. Its manifest stores versions/counts/component inventory but no effective practice time zone, and no source captures critical application configuration. ALV-N003 explicitly keeps time zone out of database columns: `PracticeTimeZone` is deployment configuration consumed by IPracticeClock. On a replacement host Program defaults it to America/Chicago. The runbook tells the operator to restore connection/storage/key paths but does not recover or check this invariant.

Therefore, an installation configured for another time zone can pass the current full-state drill and reopen its restored practice-local schedules under a different zone. This consequence follows from the inspected configuration and recovery code; this review did not run a separate non-default-zone archive probe. SQL backup of configuration tables alone cannot preserve this deployment-owned value. The scope expressly requires critical configuration/state as those assets exist.

**Correction:** Inventory and capture the effective non-secret deployment settings essential to interpreting restored data, beginning with PracticeTimeZone. Restore/apply them or block recovery pending explicit compatible configuration; validate them in the recovered application. Use an explicit allowlist and safe rebinding of machine-specific paths rather than blindly archiving credentials or raw environment/configuration files. Add a real non-default-time-zone backup/recovery test proving the same practice-local-to-UTC scheduling result after recovery. Update asset coverage and the runbook so “full state” cannot report complete while a required invariant is missing.
