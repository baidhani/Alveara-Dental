## Blocking findings

### ALV-N004-R02-01 — P1 — Domain requests are allowed before deployment verification

**Evidence:** `src/Alveara.Api/Architecture/Backup/DeploymentSettings.cs:111` initializes status to `Unchecked`. `DeploymentInvariantMonitor` verifies asynchronously and retries initial database failures (approximately lines 128–151). `DeploymentGuardMiddleware.InvokeAsync`, at line 225, blocks only `Mismatch`; `Unchecked` reaches the domain handler.

**Independent reproduction:** Construct a fresh `DeploymentInvariantStatus`, invoke the actual middleware for `/api/config/scheduling`, and track whether its downstream delegate executes. `Domain_requests_wait_until_deployment_invariants_are_verified` fails with `Expected: False; Actual: True`. The response is not the required pending-verification refusal. This is a deterministic middleware reproduction, not a claim that every normal startup exhibits a measured timing window.

**Impact:** A recovered server can process domain requests while its time-zone/Data Protection invariant check is pending or retrying, before a mismatch becomes visible. That contradicts the stated protection against interpreting restored data under the wrong deployment settings.

**Required correction:** Require a positively verified matching state before domain APIs proceed. Return an explicit, truthful unavailable/pending-verification response while initial verification is incomplete or fails. Preserve the operator endpoints necessary for health, status, authentication and recovery. Add delayed/failed initial-check coverage, matching-state allowance and mismatch refusal coverage; ensure recovery access still works. Do not resolve this only by making the test wait until the monitor finishes.

### ALV-N004-R02-02 — P1 — A successful restore drill can contain contradictory deployment settings

**Evidence:** `BackupService.cs:242` writes `deploymentSettings.Current` into the manifest; `DeploymentSettings.cs:74` onward writes the same running settings into the deployment asset. Backup APIs remain allowed during mismatch. `BackupRestoreService.cs:260` compares manifest settings to the running recovery server, while `ValidateRestoredApplicationAsync` at line 421 checks schema, records/assets and restored MFA protection but does not compare the captured database's `DeploymentInvariants` to the manifest/asset. Lines 396–399 can then mark the drill `Succeeded` and history backup `FullyVerified`.

**Independent reproduction:** Seed a real test database with a recorded `America/Chicago` deployment invariant and representative accounts/audit; change the running deployment provider to `Asia/Tokyo`; create a real SQL Server-backed encrypted backup and restore it using the same Tokyo provider. `A_drill_cannot_report_success_for_a_manifest_that_conflicts_with_the_restored_database_invariant` fails: expected outcome other than `Succeeded`, actual `Succeeded`. The target is cleaned up after the assertion. The probe establishes an actual backup/drill contradiction; it does not claim to boot the recovered app in this particular probe.

**Impact:** The archive recommends Tokyo while its restored database records Chicago. Applying the manifest's settings would cause the recovered monitor to reject the deployment once it checks. The drill's success therefore overstates readiness of the recovered application and undermines verification/trust state.

**Required correction:** Prevent creation of a trusted backup from an unverified/mismatched deployment, or derive authoritative recorded settings from the consistent captured state with an explicit recovery policy. Ensure manifest, deployment asset and captured database agree. Validate that agreement after restore before reporting `Succeeded`/`FullyVerified` or advancing confidence. Handle missing legacy invariant records explicitly. Add the real mismatched-host backup/drill regression and a contradictory-archive rejection check, retaining non-default-time-zone, history-free recovery and legacy Data Protection compatibility regressions.
