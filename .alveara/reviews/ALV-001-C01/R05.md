## Blocking findings and required corrections

### ALV-001-C01-R05-01 — P1 evidence gap: Step-up test still relies on scheduler luck and does not exercise both required orderings

**Location:** `src/Alveara.Api.Tests/AccountServiceMfaTests.cs:609`–678.

The corrected test now starts at four failed attempts, so the competing failure can reach the threshold. It then starts two ordinary tasks and accepts either `null` or `AccountLockedOutException` for the correct step-up. No barrier or fault hook controls whether the fifth failure acquires the database row lock before or after the step-up's conditional reset, and no assertion proves that both branches ran. Repeating the same uncontrolled test three times does not establish either ordering; all three runs can take the same benign step-up-first path.

R04 explicitly required deterministic coordination sufficient to exercise both permitted orderings rather than scheduler luck. R05's evidence does not meet that requirement, even though the production row-count check is present.

**Correction:** Add deterministic tests for both orderings. One must pause the correct step-up after its preliminary check/password verification, allow the fifth failure to lock and commit, then resume step-up and prove zero affected rows, `AccountLockedOutException`, and no pending secret/codes. The other must let step-up's conditional reset win and commit before the failure proceeds, then prove the pending set exists and the later failed attempt remains recorded. Use a narrow test seam/interceptor or database coordination appropriate to the repository; do not depend on repeated uncontrolled scheduling.

### ALV-001-C01-R05-02 — P1 evidence gap: New recovery tests can pass without executing the rollback branch

**Locations:** `AccountService.cs:355`–404; `AccountServiceMfaTests.cs:768`–848.

The production branch at `rows == 0` now calls `RollbackAsync`, which is the intended correction. The submitted tests do not deterministically execute it:

- In `When_a_recovery_code_race_is_lost...`, the test marks the recovery row used **before** calling `CompleteMfaChallengeAsync`. The service's initial query selects only `UsedAtUtc == null`, so that row is excluded and the method never verifies it, never consumes the challenge in the recovery transaction, and never reaches the conditional update or rollback. The challenge remains usable simply because the critical branch was bypassed.
- In `Two_distinct_challenges_racing...`, the losing request may perform its initial query after the winner commits. In that ordering the used row is excluded and the rollback branch is again bypassed. The final-state assertions are identical whether rollback worked or was never needed, so the test can pass without proving the fix.

This falls short of R04's requested controlled losing-race/rollback evidence.

**Correction:** Deterministically pause both requests after they have loaded and verified the same unused recovery code, allow one request to commit consumption, then resume the other so its conditional update provably returns zero after its own challenge was conditionally consumed in the transaction. Assert that this precise transaction rolls back, the losing challenge remains unconsumed, its privacy-safe failure audit is recorded, and it can subsequently complete with another code. Add a controlled failure after both conditional updates but before commit to prove rollback restores both challenge and recovery state. The test must demonstrate branch entry, not infer it only from a compatible final state.
