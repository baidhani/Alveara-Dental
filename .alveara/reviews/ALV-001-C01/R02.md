## Blocking findings and required corrections

### ALV-001-C01-R02-01 — P1: MFA challenge and TOTP replay creates multiple authenticated sessions

**Locations:** `src/Alveara.Api/Architecture/Identity/AccountService.cs:291`–339; `src/Alveara.Api/Controllers/AuthController.cs:117`–125; `src/Alveara.Api.Tests/AccountServiceMfaTests.cs`.

`MfaChallengePayload` contains account ID, security stamp and expiry, but no challenge identifier backed by consumable server state. The authenticator-code success path verifies TOTP, writes audit entries and returns the account without atomically consuming either the challenge or accepted TOTP time step. Nothing changes between a first and second submission. Otp.NET can report the accepted time window, but this implementation ignores it.

**Independent live reproduction:** against a fresh migrated reviewer database and the unchanged real API, the reviewer bootstrapped an account, enrolled and confirmed TOTP, obtained one MFA challenge through password login, computed one current standards-compatible TOTP, and submitted the identical challenge-token/code body twice. The first response was HTTP **200** and the second response was also HTTP **200** (`SAME_CHALLENGE_REPLAY_ACCEPTED=True`). Each response issued an authentication cookie. Only synthetic reviewer credentials/data were used, and the database was deleted afterward.

This directly leaves unmet the R01 correction: “Use a one-time or replay-controlled challenge lifecycle.” The existing recovery-code test proves only that a recovery code is one-time; no test repeats a successful authenticator-code challenge.

**Correction:** Give each protected challenge a cryptographically random identifier tied to durable, short-lived server state and atomically mark it consumed on successful TOTP or recovery-code completion, or implement an equivalent atomic replay-control design. Concurrent duplicate submissions must produce exactly one success. Preserve security-stamp and expiry checks. Add service and HTTP tests for sequential replay, concurrent replay, replay after recovery-code completion, expiry, and revocation. Audit one successful completion and the rejected replay without logging the token or code.

### ALV-001-C01-R02-02 — P1: MFA replacement password verification is not rate-limited or lockout-coupled

**Locations:** `AccountService.cs:384`–405; `AuthController.cs:199`–217; `Program.cs:141`–163.

Replacing an established factor now correctly requires the current password, but `/api/auth/mfa/enroll` does not carry the `AuthAttempts` rate-limit policy. Its direct password verification also does not use the login failure/lockout lifecycle. An attacker with a stolen authenticated cookie can therefore make unlimited online guesses at the account password through this endpoint; each request performs a fresh PBKDF2 comparison and returns a distinguishable `invalid_current_password` result. The IP limiter covers register, bootstrap, login, MFA challenge and reset completion, but not this newly added authentication step.

**Correction:** Put the step-up verifier inside an explicit throttling policy and an account-aware failure boundary appropriate to authenticated reauthentication. It must not allow this endpoint to become a password-oracle bypass around login lockout/rate limits. Return a bounded public result, audit privacy-safe step-up failures, and add HTTP tests proving repeated attempts are throttled and cannot bypass the intended account protection. Preserve the established active factor throughout all failed attempts.
