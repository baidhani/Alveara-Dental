## Blocking findings and required corrections

### ALV-001-C01-R03-01 — P1: Correct MFA step-up can proceed after a concurrent request locks the account

**Location:** `src/Alveara.Api/Architecture/Identity/AccountService.cs:430`–471.

After verifying the correct replacement password, `BeginMfaEnrollmentAsync` conditionally resets the shared failure counter only where the account is not locked. Unlike `LoginAsync`, it does not inspect the affected-row count. It proceeds to generate and persist a pending MFA secret and recovery-code set even when the update affected zero rows because a concurrent failed login or step-up request crossed the lockout threshold after the earlier check.

The comments say this path matches login's stale-success protection, but login explicitly rejects when its conditional clear affects zero rows. R03 tests cover an account locked before step-up and ordinary counter sharing; none races a correct step-up against the threshold-triggering failure. This leaves the same concurrent stale-success class the authoritative prompt explicitly requires the authentication boundary to prevent.

**Correction:** Require the correct step-up path's conditional reset to affect exactly one eligible row. If it affects zero, reload the authoritative lock state and reject without creating or replacing pending MFA material. Add a real two-context concurrency test that races a correct step-up with the failure that reaches lockout threshold and proves the only permitted outcomes: the correct step-up completes before the lock and the later failure state is retained, or lockout wins and no new pending secret/recovery set is created. Retain the current IP limiter and shared counter tests.

### ALV-001-C01-R03-02 — P1: Challenge consumption is not atomic with its security audit/state change, and replay rejection is unaudited

**Locations:** `AccountService.cs:326`–400; `AuditLogEntry.cs`; `AccountServiceMfaTests.cs:375`–500.

`TryConsumeChallengeAsync` executes and commits its conditional database update before `CompleteMfaChallengeAsync` opens the transaction used for `MfaChallengeSucceeded`/`LoginSucceeded`. In the recovery path, it likewise consumes the challenge before the separate transaction that consumes the recovery code and writes audits. A failure after challenge consumption but before the later commit leaves a consumed security artifact without the corresponding audit and, for recovery, without the recovery-code state transition. That contradicts the project's transactionally coupled security-audit requirement carried from R01.

When `TryConsumeChallengeAsync` returns false for the exact replay case, the method throws immediately and writes no privacy-safe rejection event. R02 explicitly required one successful completion and the rejected replay to be audited. The new replay tests assert only the exception/status and do not examine audit evidence.

**Correction:** Place conditional challenge consumption, recovery-code consumption where applicable, and success audits in one database transaction. A rollback must restore all of them. Record a privacy-safe rejection event for a consumed/replayed challenge without logging token or code material; keep public replay/expired/revoked responses indistinguishable. Add targeted transaction-failure tests plus sequential and concurrent audit assertions proving exactly one success audit and appropriate rejected-attempt evidence.
