## Blocking findings and required corrections

### ALV-001-C01-R01-01 — P1: Starting re-enrollment immediately removes established MFA protection

**Locations:** `src/Alveara.Api/Architecture/Identity/AccountService.cs:343`–369; `src/Alveara.Api/Controllers/AuthController.cs:197`–215; `src/Alveara.Api.Tests/AccountServiceMfaTests.cs`.

`BeginMfaEnrollmentAsync` replaces the protected TOTP secret, sets `MfaEnabled = false`, deletes all existing recovery codes, creates replacements, and saves before any replacement factor is verified. The authenticated `/mfa/enroll` endpoint calls it directly. Therefore any currently authenticated session can turn off an account's confirmed MFA and invalidate all working recovery codes simply by beginning enrollment and abandoning confirmation. The security stamp is not rotated at that point, so existing sessions remain valid. The tests cover initial enrollment only; they do not cover re-enrollment of an already protected account or failed/abandoned replacement.

**Correction:** Model pending enrollment separately from the active factor. Keep the current verified secret and recovery codes active until the replacement code is successfully confirmed, then atomically swap the factor/recovery set, rotate the security stamp, and audit the change. Require suitable reauthentication/step-up for changing an established factor. Test successful replacement, wrong code, abandoned enrollment, concurrent confirmation, and preservation of the old factor until atomic completion.

### ALV-001-C01-R01-02 — P1: Session revocation and password reset do not invalidate outstanding MFA login challenges

**Locations:** `AccountService.cs:276`–306 and 480–503; `AuthController.cs:115`–123.

The protected MFA challenge payload contains only the account ID and expiry. Completion checks current disabled/MFA state but does not bind the challenge to the account's `SecurityStamp`. Password reset and explicit session revocation rotate that stamp, yet a challenge issued before either action remains usable for up to five minutes and can create a fresh authenticated cookie. This defeats the stated session-revocation boundary during the password-to-MFA login interval.

**Correction:** Bind every MFA challenge to the account's current revocation/security stamp and reject completion after any stamp-changing operation. Use a one-time or replay-controlled challenge lifecycle appropriate to the selected maintained MFA facility. Add HTTP/service tests proving password reset, role/status change, factor replacement, and explicit revocation invalidate an already issued challenge and cannot mint a new session.

### ALV-001-C01-R01-03 — P1: The TOTP implementation violates the project's proven-cryptography rule

**Locations:** `src/Alveara.Api/Architecture/Identity/Totp.cs:8`–112; Engineering/Product Reference v2 lines 246–247 and 1514.

`Totp.cs` implements Base32 encoding, RFC 4226 dynamic truncation, TOTP windowing, and verification directly. Its own comment describes this as a direct implementation with no external package. The authoritative reference says not to design custom cryptographic algorithms or ad-hoc derivation and requires maintained, well-reviewed platform/library facilities. Correct-looking vectors and an independent Python demo do not replace a maintained implementation boundary.

**Correction:** Replace the hand-written TOTP/Base32 implementation with a maintained, reviewed library or suitable platform facility. Keep secrets protected at rest and preserve offline operation. Add interoperability tests against published standards vectors and exercise enrollment/challenge/recovery through the production abstraction.

### ALV-001-C01-R01-04 — P1: Security-sensitive MFA/recovery changes are not fully audited

**Locations:** `AccountService.cs:260`–268, 285–390; `Architecture/Identity/AuditLogEntry.cs:24`–38; packaged `ACCEPTANCE_EVIDENCE.md` section 7.

The audit vocabulary has `MfaEnabled` but no recovery-code-use/replacement or completed-MFA-login event. A recovery code is consumed at lines 323–334 without an audit entry. Beginning enrollment replaces the secret and recovery set without an audit entry. A password-correct attempt is recorded as `LoginSucceeded` before the second factor succeeds, while successful challenge completion is not recorded. The package's statement that MFA/recovery changes are audited is therefore broader than the implementation.

**Correction:** Audit factor enrollment/replacement, recovery-set generation/replacement, one-time recovery-code consumption, challenge success/failure at the appropriate privacy-safe granularity, and any MFA disable/reset operation. Record password verification awaiting MFA as a distinct non-success state; record successful authentication only after the second factor completes. Keep audit writes transactionally coupled to the state change and never log raw secrets or codes. Add direct and HTTP-level audit tests.

### ALV-001-C01-R01-05 — P1: Required security UI and configurable session control are incomplete

**Locations:** Execution Plan item 5 lines 589 and 593–600; `src/alveara-client/src/App.tsx`; `pages/AdminUsersPage.tsx`; `services/authApi.ts`; `IdentityEntities.cs:25`; `AuthController.cs:346`.

The client supplies login, MFA challenge, password-reset completion, and a user table. It has no MFA enrollment/replacement screen or client call to `/api/auth/mfa/enroll` and `/confirm`; no permission-matrix screen or client call to `/api/auth/permission-matrix`; and no user-detail workflow. `SessionTimeoutMinutes` exists on the entity and is enforced when issuing a cookie, but there is no authorized API or UI to configure it and no validation of its range. Consequently the implementation does not satisfy the requested configurable session timeout or the security-administration UI for users, roles, and permission visibility.

The submitted demo explicitly states that no live rendered click-through or real-browser test was performed. Component tests are useful but do not fulfill the authoritative visible-workflow demonstration rule for a user-facing vertical slice.

**Correction:** Complete the user-facing flows for MFA enrollment/replacement and recovery-code presentation, permission visibility, and security administration, including a validated authorized session-timeout setting. Provide truthful loading, empty, error, denied, expired, and disconnected states where applicable. Exercise the actual rendered application in a real browser against the real API/database and capture reproducible evidence without secrets. Add focused browser coverage for the critical flows; keep unit/component tests.
