## Blocking findings and required corrections

### ALV-001-C01-R04-01 — P1 evidence gap: The new step-up race test never reaches the lockout threshold

**Location:** `src/Alveara.Api.Tests/AccountServiceMfaTests.cs:609`–655.

The test says three priming failures leave the account “one below” a five-attempt threshold and that one racing failure crosses it. Three plus one is four. `MaxFailedLoginAttempts` remains five. Consequently the racing login cannot lock the account, the `AccountLockedOutException` branch is not exercised, and the test normally proves only that a correct step-up can run near a non-locking failed request. Its assertions permit the always-successful result, so the test passes vacuously while the handoff claims a real threshold race.

The production row-count check is directionally correct, but the R03 decision required a real two-context test in which the concurrent failure reaches the threshold and proves either valid ordering without lost failure state or lockout with no pending factor material. R04 does not supply that evidence.

**Correction:** Prime exactly four failed attempts, then race the correct step-up against the fifth failing login/step-up attempt. Assert the full outcome-specific invariants, including final failed-attempt/lockout state when step-up wins and absence of pending secret and pending recovery codes when lockout wins. Make the synchronization deterministic enough to exercise both permitted orderings, or use targeted coordination/fault hooks rather than relying on scheduler luck. Correct the handoff/test prose and rerun the full suite.

### ALV-001-C01-R04-02 — P1: Recovery-code losing race still separates challenge consumption from its audit outcome

**Location:** `src/Alveara.Api/Architecture/Identity/AccountService.cs:355`–401.

On the normal recovery path, challenge consumption, recovery-code consumption and success audits now share a transaction. But two different valid challenges can concurrently submit the same still-unused recovery code. Both can verify its hash before either transaction updates it. Each then consumes its own challenge. The winner updates the recovery code and succeeds. For the loser, the recovery-code conditional update affects zero rows at lines 377–380; lines 386–387 explicitly commit that challenge consumption with no audit in the transaction, then the method later opens a separate transaction and records `MfaChallengeFailed`.

This recreates the exact partial-state window R03 required R04 to close: failure/crash between those commits leaves a consumed challenge with no corresponding outcome audit. It also burns the losing request's otherwise valid challenge instead of rolling back the failed multi-record transition. The new tests cover same-challenge replay and sequential recovery replay, not two distinct challenges racing on one recovery code or injected transaction failure.

**Correction:** Treat conditional challenge consumption, conditional recovery-code consumption and the resulting success/failure audit as one atomic decision. If recovery-code consumption loses, roll back challenge consumption before recording the privacy-safe rejected attempt, or use an equivalent single transactional design that cannot leave an unaudited consumed challenge. Add a two-context test with distinct challenges racing the same recovery code, plus a controlled failure/rollback test. Prove exactly one recovery success/login audit, one privacy-safe rejection/failure audit, one consumed recovery code, and no partially consumed unaudited challenge.
