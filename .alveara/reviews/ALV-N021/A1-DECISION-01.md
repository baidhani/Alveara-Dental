## Evidence and ruling

The actual repository confirms that `FinancialDocumentBuilder.AgeDays` subtracts UTC dates, that statements include age/bucket in canonical content, and that `BillingService.Documents.BuildAsync` does not dispatch using the issued document's stored template version. A direct substitution would invalidate affected statement reprints. The builder also uses the shared template version for receipts, and `BillingService.Timeline.cs` calls `AgingAt` for live aging.

Authorize practice-local calendar-day aging for new version-2 documents within ALV-N021 A1. Preserve the exact version-1 content contract for issued statements AND receipts. Keep amounts, balances, ledger operations, bucket thresholds and service-date/amendment cut-offs unchanged. This narrowly extends the financial-date exclusion in the briefing to this identified aging calculation and its compatibility plumbing only.

## Mandatory implementation contract

1. Dispatch rebuilds by the document's stored template version, for reprint and export. Version 1 preserves original canonical fields, ordering, formatting, UTC aging and template-version value. Do not rewrite old hashes or issued rows. Unknown versions fail explicitly; never fall back silently to the current builder.
2. Version 2 subtracts the practice-local calendar dates of the as-of and service instants, clamped to zero as before. Convert each instant using its own applicable zone offset; do not use the server/browser zone or one fixed current offset across DST. Keep the existing 0–30, 31–60, 61–90 and over-90 thresholds.
3. Freeze the version-2 aging basis for issued documents. Reprints must not depend on the current practice zone or mutable time-zone rules. Persist sufficient non-monetary date-conversion metadata with the existing immutable document envelope (for example, as-of local date and per-charge service local dates plus zone provenance). Bind that metadata to the preview/issue content check and validate it against the document cut-offs. Do not store a second monetary ledger. A zone change between preview and issue must require a fresh preview when it changes the bound basis; a zone change after issue must not change the issued content/hash. An identifier alone, re-resolved against mutable zone rules at reprint, does not fully freeze the basis.
4. Preserve preview/issue equality and idempotent issue replay. An unissued version-1 preview is stale after rollout and requires re-preview; retrying an already-issued version-1 request with its original key must still return that original document. Do not inadvertently reject the replay because it has an older version.
5. Apply the current practice-local policy to the live aging caller in `BillingService.Timeline.cs` so new statement aging and live aging agree for the same snapshot/cut-offs. Historical issued documents continue to show their original policy. Inspect all builder callers and document the version selected for each.
6. Existing version-1 receipts must remain canonical-byte/hash identical even though they contain no aging buckets. Changing the shared constant alone changes receipt content too. Maintain the existing export and hash-verification safeguards.
7. Use the existing envelope storage if compatible; this ruling authorizes the bounded metadata/serialization and version-dispatch change, not an unreviewed database migration. If a schema change proves necessary, disclose its concrete design before implementing it.

## Focused proof for the A1 handoff

- A version-1 statement and receipt produced by the pre-change builder reprint with identical canonical bytes and stored hashes after the upgrade. Use baseline fixtures/original-builder evidence, not expected hashes regenerated by the new implementation.
- Version-2 cases cover the evening mismatch, each 30/31, 60/61 and 90/91 boundary, both DST transitions, year boundary, and zones ahead of and behind UTC. Verify unchanged amounts and totals.
- Version-2 reprint remains identical after practice-zone change; frozen conversion metadata remains authoritative. A preview/issue zone-basis mismatch is rejected.
- Unsupported version refusal, stale unissued v1 preview, successful already-issued v1 idempotent replay, issued export compatibility, and live/new-statement aging agreement.
- Negative control: routing a boundary-affected v1 document through v2 changes its canonical content and fails the immutable-reprint check.

No broad/full regression is requested. The existing five-minute standing permission and explicit permission for longer/unknown-duration runs remain in force. Return this change in the normal A1 Stage 1 handoff with focused evidence; there is no need for another design round if the implementation stays within this contract.
