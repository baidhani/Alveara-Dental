## Blocking findings and required corrections

### ALV-N009-R02-01 — P1: Background authorization polling prevents an idle sliding session from timing out

**Locations:** `src/alveara-client/src/contexts/AuthContext.tsx:29`–32 and 74–94; `src/Alveara.Api/Program.cs:90`–138.

R02 calls the authenticated `/api/auth/permissions` endpoint every 30 seconds while signed in. Cookie authentication does not set `SlidingExpiration`, so the installed ASP.NET Core 10.0.12 runtime default is active; independent runtime inspection confirms `CookieAuthenticationOptions.SlidingExpiration == true`.

With sliding expiration enabled, authenticated requests after the renewal midpoint renew the cookie. The poll therefore manufactures continuous activity even when the person has left the browser untouched. A five-minute session, for example, is polled roughly every 30 seconds and renewed around its midpoint; continued polling can repeat that indefinitely. The boundary logic then receives a renewed session instead of the 401 it expects. This defeats the configured session timeout and the required expiry behavior. This renewal consequence is inferred from the inspected polling code and verified runtime configuration; the review did not run a multi-minute idle-cookie renewal reproduction.

The new fake-timer test mocks a 401 after the timestamp; it does not exercise cookie middleware or prove that an idle real session can expire while the poll is running.

**Correction:** Choose and enforce an explicit session policy that preserves the configured timeout under background revalidation. Acceptable designs include disabling sliding renewal for these sessions, suppressing renewal for machine-generated permission probes, or replacing the continuous poll with revalidation tied to real user activity while retaining a trustworthy local expiry boundary. Add integration evidence proving that an idle session actually expires with the final revalidation mechanism active and that legitimate renewal, if retained, updates the client expiry without letting background traffic keep the session alive forever.

### ALV-N009-R02-02 — P1: An older successful refresh can restore protected state after a newer 401

**Location:** `src/alveara-client/src/contexts/AuthContext.tsx:47`–68, 74–94 and 96–105.

Poll, focus, visibility and expiry callbacks can all invoke `refresh()` concurrently. `refresh()` applies every response in completion order without a request generation, single-flight guard, abort signal or terminal invalidation epoch. A request validated just before a role change can therefore return its old 200 after a newer request has received 401. The unauthorized handler and newer refresh first clear the session; the older response then calls `setState({ kind: "signed-in", ... })` and restores stale identity and permissions.

A reviewer-only deterministic probe forced that ordering: initial sign-in, older deferred refresh, newer 401 and signed-out transition, then completion of the older 200. It failed with expected `signed-out`, received `signed-in`. The temporary probe was removed afterward.

**Correction:** Serialize refreshes or apply monotonic request/invalidation ordering so no response started before a later 401/logout/expiry decision can restore authenticated state. Add a deterministic test for the exact ordering above and prove permissions remain cleared. Apply the same protection to explicit logout so an in-flight refresh cannot restore state after the user signs out.

### ALV-N009-R02-03 — P2: The packaged status snapshot comes from an unlisted supplemental commit

**Locations:** Git commits `4bb653a...` and `25aa26c...`; `.alveara/EXECUTION_STATUS.json`; `.alveara/HANDOFF_SCHEMA.md:30`–40.

The schema defines an implementation commit, an evidence/status commit, then a validated ZIP. It says a committed file is never required to contain its own commit SHA; the generated manifest and Git-state evidence record both SHAs afterward. This removes the need for a supplemental SHA-recording commit; it does not itself expressly prohibit every additional control-only commit.

R02 created evidence commit `4bb653a...`, then added commit `25aa26c...` solely to write `4bb653a...` into `EXECUTION_STATUS.json`. The ZIP manifest still declares `4bb653a...` as the evidence SHA, but its packaged status file matches `25aa26c...`; the status blobs differ. The supplemental commit is not identified in the manifest. Packaged `evidence/GIT_STATE.md` also leaves the evidence SHA as “recorded in EXECUTION_STATUS.json once made” rather than recording both full SHAs as required by the schema. Source is unchanged and the exact difference is verified, so this is a traceability issue rather than an unidentified implementation change.

**Correction:** Preserve R02 and this decision. For R03, use the documented implementation/evidence sequence and record the evidence SHA in generated manifest/Git-state evidence after the evidence commit exists. Leave that SHA absent from committed status where necessary until review closure. Ensure the package clearly identifies the commit from which its repository snapshots were obtained; avoid an unnecessary supplemental SHA-recording commit.
