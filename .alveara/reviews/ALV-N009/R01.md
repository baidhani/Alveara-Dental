## Blocking findings and required corrections

### ALV-N009-R01-01 — P1: Passing the known session expiry leaves protected UI mounted and the caller marked signed in

**Locations:** `src/alveara-client/src/contexts/AuthContext.tsx:81`–96; `src/alveara-client/src/contexts/AuthContext.test.tsx:41`–81.

The context polls the server-provided `sessionExpiresAtUtc` every 15 seconds, but the callback only computes `sessionExpiringSoon`. Once `remainingMs <= 0`, it sets the warning to `false`; it never changes `state` to `signed-out`. `RequireAuth` therefore continues rendering the shell and any protected page, including data already loaded into an edit screen, until an unrelated future API call happens to return 401.

The submitted tests cover "within the warning window" and "comfortably in the future," but never cross the expiry boundary. A reviewer-only fake-timer probe started with an expiry 30 seconds in the future and advanced 45 seconds without another API request. It failed with expected `signed-out`, received `signed-in`, directly reproducing the missing transition.

This violates both “Session expiry/sign-out removes protected application state” and the required “Session expires during edit” failure path.

**Correction:** When the authoritative expiry is reached, clear the signed-in identity/permissions and protected UI state immediately so `RequireAuth` redirects to the reauthentication path. Add a deterministic fake-timer test that crosses the expiry and proves protected content unmounts. Reconcile this with cookie sliding renewal: either make the server expiry fixed for the issued session or refresh the authoritative expiry often enough that the client does not expire a genuinely renewed ticket based on a stale timestamp.

### ALV-N009-R01-02 — P1: Permission/session changes are not revalidated during a signed-in visit

**Locations:** `src/alveara-client/src/contexts/AuthContext.tsx:41`–61; `src/alveara-client/src/App.tsx:25`–64.

`refresh()` is called on `AuthProvider` mount and explicitly after successful login/MFA operations. It is not called on route navigation, on window focus, or on any bounded interval. `AuthProvider` is outside `BrowserRouter`, so it cannot currently observe location changes itself. Contrary to the R01 handoff statement that the “next ... refresh (on any subsequent navigation)” reflects a permission change, ordinary navigation between Dashboard, Showcase, and System Status performs no permissions request.

Role and account-state changes rotate the server security stamp, so server enforcement remains safe. However, a user whose access changed can continue seeing the old identity, old navigation and already-mounted protected state indefinitely while moving among routes that do not fetch protected data. The stale state clears only if a later API call returns 401. That does not satisfy the explicit “Permission changes while user is signed in” failure path.

**Correction:** Add a bounded revalidation trigger appropriate for the shell, such as route navigation plus focus/visibility or a modest poll, and use the response to update capabilities or clear the session when the rotated stamp produces 401. Add a deterministic test that changes the mocked server authorization state after initial sign-in, triggers the chosen revalidation event, and proves stale navigation/protected content is removed without requiring an unrelated protected action first.

### ALV-N009-R01-03 — P2: Deep-link return is lost when reauthentication requires MFA

**Locations:** `src/alveara-client/src/pages/LoginPage.tsx:36`–56; `src/alveara-client/src/pages/MfaChallengePage.tsx:11`–13 and 44–53; `src/alveara-client/src/App.routeGuards.test.tsx:69`–113.

`RequireAuth` correctly stores the denied location and password-only login returns there. If login returns `mfaRequired`, `LoginPage` navigates to `/mfa-challenge` with only the challenge token. `MfaChallengePage` has no destination field and always navigates to `/` after success. An MFA-enabled user reauthenticating from a protected deep link therefore loses the intended destination. The route-guard test covers only the password-only path.

**Correction:** Carry the validated internal destination through the MFA challenge state and return there after successful MFA completion. Add a route test for direct protected URL → login → MFA challenge → original URL, including permission enforcement at the destination.
