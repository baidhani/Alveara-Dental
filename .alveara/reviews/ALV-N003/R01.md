## Required corrections

### ALV-N003-R01-01 — P1: A delayed response can show one provider's schedule under another provider

**Locations:** `src/alveara-client/src/pages/configuration/AvailabilityTab.tsx:61`–107, including loadSchedule, chooseProvider and saveSchedule.

loadSchedule applies every response to the same rows/saved/blocked/loading state, without checking whether its provider is still selected. Provider switching is enabled while requests are pending. A deterministic reviewer probe selected A, left A's response pending, selected B and loaded B's 13:00 start, then completed A's older 09:00 response. The picker still identified B while the editor showed 09:00 from A. Expected 13:00; received 09:00.

The displayed mismatch is directly reproduced. A subsequent wrong-provider write is the consequence of the inspected saveSchedule code: it submits those shared rows using the currently selected providerId, so editing the stale rows can replace B's hours with values loaded from A.

**Correction:** Bind requests, drafts and responses to a provider identity and request generation; cancel or discard superseded results. Clear/disable stale editor state while loading the selected provider. Protect schedule and blocked-time load/save completion paths from updating a different selection. Add deterministic out-of-order response tests and prove no save can submit another provider's rows. Retain dirty-change confirmation during provider switching.

### ALV-N003-R01-02 — P1: Concurrent whole-schedule replacements can merge into overlapping windows

**Locations:** `src/Alveara.Api/Architecture/Configuration/StaffProviderService.cs:185`–211; `ReplaceAvailabilityRequest` and the availability PUT in `Controllers/ConfigurationController.cs`.

Replacement validates each submitted set, loads existing rows, removes them and inserts the new set. It neither requires the schedule revision read by the caller nor changes a versioned aggregate during the replacement. The handoff discloses last-writer-wins, but the actual race is worse: two replacements of an initially empty schedule can both read no existing rows and commit their inserts, creating the union of both sets rather than either replacement.

A real SQL Server reviewer probe used two independent contexts and a SaveChanges interceptor barrier to ensure both replacements had finished reading before either committed. One submitted Monday 09:00–12:00, the other 11:00–14:00. Both succeeded, and a fresh context found **two overlapping windows**. Neither caller requested that combined schedule, and an equivalent combined request would be rejected by the service's own overlap validation.

**Correction:** Treat the provider's weekly schedule as a versioned aggregate. Require the caller's observed revision and perform revision comparison/update, row replacement and audit atomically, or use an equivalent design that rejects stale writes and serializes the aggregate correctly. Return the established conflict representation to a stale editor rather than merging or silently overwriting. Wire the revision/conflict recovery into the availability UI. Add deterministic races for initially empty and populated schedules, stale-editor rejection, valid persisted final state, and audit/business rollback on conflict. Per-call SaveChanges atomicity alone does not fix the observed race.

### ALV-N003-R01-03 — P2: Main navigation bypasses unsaved-change protection

**Locations:** `src/alveara-client/src/hooks/useUnsavedChangesWarning.ts`; `pages/ConfigurationHubPage.tsx`; shell/router navigation.

The hook only subscribes to beforeunload. Explicit discard checks guard cancel, row/provider switches and configuration tabs, but not React Router route transitions through the main shell. Such transitions do not fire beforeunload.

A reviewer probe opened the real App route at /admin/configuration, typed a dirty practice name, and clicked the Dashboard navigation link with window.confirm configured to refuse discard. The discard confirmation was **never called**. The handoff acknowledges unavailable route blockers with the current BrowserRouter, but that implementation limitation does not waive the required unsaved-change protection.

**Correction:** Guard voluntary navigation away from dirty configuration through shell links and browser back/forward, or preserve the draft across those transitions. A canceled discard must keep the page and draft intact. Extend coverage beyond tab/cancel handlers. Forced session expiry or authorization loss must still clear protected state; a navigation guard must not retain revoked protected UI.

### ALV-N003-R01-04 — P2: DST-fold availability check accepts a slot partly outside weekly hours

**Location:** `src/Alveara.Api/Architecture/Configuration/SchedulingConfiguration.cs:57`–79.

The check compares only local endpoint times with `window.StartLocal <= startTime && endTime <= window.EndLocal`. It assumes local wall-clock time advances monotonically across the elapsed slot, which is false during the fall-back hour.

A real-database reviewer probe configured Sunday 01:30–02:00 in America/Chicago, then checked a 30-minute slot starting at **2026-11-01 06:50 UTC**. This is 01:50 CDT; its end is **07:20 UTC**, or 01:20 CST. The slot crosses the repeated 01:00–01:20 period outside the 01:30 opening, yet the service returned Available = true. The probe expecting false failed. This differs from the existing blocked-time DST-input rejection tests, which do not exercise this scheduling-consumer calculation.

**Correction:** Evaluate the entire elapsed slot against the practice-local weekly window with an explicit DST policy, or conservatively reject such transition-crossing slots. Do not infer interval containment from these two endpoint inequalities alone. Add the exact fall-back reproduction and appropriate normal-day/transition regressions while preserving blocked-time UTC overlap checks. Do not silently guess ambiguous local boundaries.

### ALV-N003-R01-05 — P2: Failed conflict reload closes the unsaved draft

**Location:** `src/alveara-client/src/components/ConfigEntityPanel.tsx:149`–163.

refresh returns null on load failure. reloadAfterConflict treats that null like a successful reload with no matching record, closes the form, clears editing and removes the conflict. Thus a failed recovery request makes the draft inaccessible instead of retaining it with a retryable error.

A reviewer component probe edited a record, received the real shared conflict shape, selected Reload current version, and forced the load request to fail. The Name input containing the draft disappeared; the assertion to retain its value received null. A successful reload may intentionally replace the edit, but a failed reload has not obtained a replacement version.

**Correction:** Preserve the form, draft and conflict on reload failure and provide retryable recovery feedback. Replace draft state only after obtaining a valid fresh record. Distinguish an actual missing/inactivated record from a network/read failure, and handle that explicitly. Add a failed-reload regression alongside the successful recovery test.
