Review covered the binding design decisions: atomic selected-set completion, canonical idempotency, plan-level stale protection, completed-procedure provenance and immutability, amendment concurrency, odontogram resolution, charge creation, server readiness, permissions/CSRF, and the approved temporary legacy-path boundary.

## Evidence accepted

- The ZIP hash is correct. The local implementation, evidence, and status commits form the declared ancestor chain, the checkout is at the declared AWAITING_REVIEW status commit, and the working tree was clean.
- CompletedProcedureService opens one explicit transaction for the complete operation. It reads the selected items, resolves chart effects before writes, stages completion state/history/audit records, creates immutable completion records, applies chart changes, charges billable procedures through IProcedureCharging, writes its audit record, and commits only after all saves succeed. The rollback paths clear the change tracker and preserve a safe error response.
- The plan root is loaded inside that transaction with the submitted row version as its original concurrency value, then touched and saved with the completion state. This is the required plan-level stale-token protection, including the newly added deterministic check for a plan changed between the earlier read and its persistence.
- Completion requests use a normalized UTC-millisecond timestamp and a sorted, duplicate-free item set in the canonical request hash. A same key/reasonable request replays without writes; a reused key with a changed request conflicts. The database uniqueness controls reinforce one completion record per plan procedure and one key per plan.
- The migration creates immutable CompletionSets, CompletedProcedures, and CompletedProcedureAmendments records and SQL guards for their relationships, patient/encounter provenance, source plan revision/catalog snapshot, time constraints, and amendment sequence. Amendments use an expected amendment number and their own idempotency key/hash, leaving the original procedure record unchanged.
- Chart resolution follows only a plan item's diagnosis link to a matching patient finding, checks tooth/surface, refuses ambiguity for the full selected set, and shares the resolution logic with the server readiness endpoint. Billable procedures use the plan-stored fee and create one charge through the billing contract; zero-fee procedures create none.
- The new write/read routes require the specified treatment-plan or clinical-documentation permission, and writes require CSRF. The STORY-008 state-only routes remain temporarily as the approved compatibility boundary, emit only the internal non-identifying legacy-use log, and are labelled in the UI as legacy. Their removal is separately scheduled as ALV-008-C02 before Gate D.
