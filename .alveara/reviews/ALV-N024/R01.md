## CR-1 — make payer eligibility identical at every enforcement layer

`BillingService.EligiblePayersAsync` offers and accepts only active related people (`p.IsActive`), but the widened database trigger 51142 accepts a guarantor or household member regardless of active status. A direct insert can therefore record a payer the service/UI intentionally exclude. This contradicts the approved requirement that the server and database enforce the same bounded payer set.

The default correction is to retain the current active-only service/UI rule and make 51142 enforce the same rule for every non-patient payer category. If the product instead intends inactive related people to be eligible, remove the active-only service/UI filter and explicitly document that policy; do not leave the layers different.

Add focused server and direct-SQL migration proof for active and inactive guarantor, household, and recorded-responsible cases, for both payment and correction writes. A refused direct insert must prove 51142; an eligible active related payer must still succeed. Record the final rule in the handoff.
