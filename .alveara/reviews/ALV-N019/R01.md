## Required corrections before R02 Stage 1 resubmission

1. **Implement the approved O-1 / PD-32 clock seam, or obtain a new scope decision before substituting a different design.**
   The approved decision was a separate chain host with production `Program.cs` unchanged.  The approved acceptance table requires proof that production registers the real `PracticeClock`, the chain host uses only its injected test clock, and each record states the clock mode.  R01 deliberately builds no chain host or injected clock and marks PD-32 NOT MET.  A `clockMode: real` label alone does not establish the required isolation.

2. **Complete the runner self-test and resilience acceptance assertions.**
   Add focused, deterministic evidence for: refusal when the target database already exists; interrupted/mid-run API cleanup proving the owned database and run folder are removed; dirty-tree labeling; and a meaningful resumed-run label/path if that capability is claimed.  Preserve the existing refusal/containment tests.  Do not solve this by weakening the safety gate or by deleting non-owned leftovers.

3. **Complete the E10 assertion.**
   The approved acceptance criterion requires evidence that the COPY_ONLY checkpoint exists, no restore is invoked, and the live chain database is unchanged.  R01 proves only backup creation and `RESTORE VERIFYONLY`.  Add a before/after invariant appropriate to the chain database and retain it in the evidence record.

4. **Meet the exact F-003 test commitment.**
   The approved plan calls for normal validation/no unintended change when injection-like values are submitted through every user-controlled merge/unmerge input, including any free-text reason if exposed.  The R01 boundary test is useful but does not replace that commitment merely because identifier fields are GUIDs.  Add the applicable API/service-level negative-input coverage, or document a narrowly reviewed correction to the acceptance table if a claimed input does not exist.

5. **Complete the dependency advisory content required by the approved criterion.**
   The report must provide an evidence-backed disposition and reachability analysis for each advisory it discusses, not state that advisory content/reachability were not examined.  Do not upgrade packages in this correction without the separate PD-26 decision.  The vulnerable shipped `System.Security.Cryptography.Pkcs` dependency remains an OPEN blocker: the report must retain that fact and final closure still requires PD-26 remediation or explicit product-owner risk acceptance.  For the dev-only findings, prove the shipped-artifact boundary and state the resulting disposition; account for the documented Vite development-server caveat.

6. **Provide the required product-browser brand evidence.**
   Add a focused real-browser assertion showing the DentalKeep login page, signed-in header, and document title.  The Stage 0 sign-in pass without these assertions and without screenshots/equivalent captured assertions does not meet the approved brand-browser criterion.

7. **Resubmit as a new Stage 1 attempt.**
   Keep this R01 package immutable.  Package focused evidence for the corrections, update acceptance counts accurately, and do not run the frozen full backend/Stage 2 contract before a new independent Stage 1 decision.  The known intermittent walkthrough observations and the uncommitted architecture-map control-file mismatch must remain disclosed; neither is grounds to hide a product failure.
