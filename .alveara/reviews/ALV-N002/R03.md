## Blocking findings and required corrections

### N002-R03-01 — P1: The local-server package and required LAN/offline/security acceptance remain incomplete

**Locations:** `src/Alveara.Api/Program.cs:78`–95; `src/Alveara.Api/Alveara.Api.csproj`; `src/alveara-client/.gitignore`; packaged `MANIFEST.json`; packaged `evidence/ACCEPTANCE_EVIDENCE.md` items 1 and 7; packaged `evidence/DEMO_EVIDENCE.md`.

The attempt itself reports only **7 PASS + 2 PARTIAL**. ALV-N002's acceptance list is a stop condition, not a menu from which required items may remain partial at approval. The two partial items are the story's explicit first-release topology requirements: a LAN client using the production shell with no public internet, and proof that clients use the API rather than direct database/storage access. `blockingIssues: []` and `blockers: []` are inconsistent with those unmet stop conditions.

The static-hosting implementation also does not produce a runnable published server. It looks for `../alveara-client/dist` relative to the server content root, while the client `dist` directory is ignored and the API project has no build/publish rule that includes it. An independent clean `dotnet publish` to a reviewer-owned directory succeeded, but the output contained neither `index.html` nor `dist`. Running that published application produced:

- `/api/health` → HTTP 200;
- `/` → HTTP 404;
- `/system-status` → HTTP 404.

Thus the claimed production shell works only from the repository layout after a separate client build; it is absent from the deployable server output.

The revised TLS demonstration is also not a deployable LAN trust strategy. `curl --resolve localhost:<port>:<server-LAN-IP>` forces the certificate name `localhost` to the server's LAN address on the same machine. A real LAN client must not resolve `localhost` to another computer. The test proves that the locally trusted development certificate validates for its own `localhost` name, but it does not prove a server LAN hostname/certificate trust path.

`StorageIsolationTests` prove that blob bytes are outside the HTTP static-file surface. They do not establish Windows filesystem ACLs or show that an ordinary LAN/client identity lacks direct access to the storage root. Likewise, the R02 SQL role test is useful application-role evidence but does not provision or exercise the actual least-privilege server service identity and maintenance boundary required by the story.

**Correction:** Produce a repeatable server build/publish output that includes the client and prove `/`, SPA fallback, assets and API work from that clean output. Exercise a real server LAN hostname whose certificate name and trust chain a separate or meaningfully isolated client validates without rewriting `localhost`. Disable public-internet reachability while preserving LAN access for the required shell walkthrough. Configure and test concrete service/maintenance identities plus database and storage-root permissions, including a negative direct-access check from an ordinary client identity. A polished installer remains ALV-N013 scope; the ALV-N002 runtime/topology/security foundation and stop-condition proof do not. If the necessary environment or authorization is genuinely unavailable, return a truthful `BLOCKED` attempt and obtain it rather than requesting approval with partial acceptance.

### N002-R03-02 — P1: Framework database logging still bypasses the PHI-safe diagnostic boundary

**Locations:** `src/Alveara.Api/appsettings.json:2`–6; `src/Alveara.Api/Architecture/BackgroundWork/BackgroundJobRunner.cs:211`–224 and `299`–309; `src/Alveara.Api.Tests/BackgroundJobTests.cs:485`–520.

The application-owned background-job path is corrected: the R02 reviewer harness now shows both concurrent enqueue calls succeeding on one row, and the synthetic handler message no longer reaches `LastError`. The runner's own logger also emits a safe summary.

That test captures only the injected `ILogger<BackgroundJobRunner>`. The normal application logging pipeline still allows Entity Framework to log complete database exceptions at the default `Information`/error configuration. An independent reviewer-owned real LocalDB test inserted a user named `SyntheticAliceExample`, attempted a duplicate value, and captured the configured EF log events. The synthetic value appeared in ordinary log output. SQL Server includes conflicting key values in unique-index exception text, so replacing `ex.Message` at one runner call site does not establish the story-wide “no unnecessary PHI in ordinary logs” convention.

The clean published-process check independently showed full EF/SqlClient exception objects and connection details written before the hosted service's own safe type-only summary. No real PHI was used or observed.

**Correction:** Apply the PHI-safe boundary to framework/database logging in the actual host configuration, not only to one application logger. Preserve safe operational signals while preventing SQL/EF exception text and values from reaching ordinary sinks. Add a host-level logging integration test using synthetic patient-like/identity values and the real configured providers/categories, proving those values and raw exception messages are absent from all captured ordinary logs.
