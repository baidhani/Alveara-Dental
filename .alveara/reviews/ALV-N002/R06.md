### N002-R06-02 — P1: Acceptance items 1 and 7 are not backed by independently reviewable infrastructure evidence

**Locations:** packaged `evidence/DEMO_EVIDENCE.md`; packaged `evidence/ACCEPTANCE_EVIDENCE.md`, items 1 and 7; ALV-N002 acceptance items 1 and 7 and required no-public-internet/direct-database-access tests.

The package contains prose descriptions and selected console-output snippets, but no sanitized command transcript, result files, screenshots, exported configuration, or repeatable verification script. The current host independently confirms two distinct running bridged VMs at the claimed addresses (`192.168.1.216` and `192.168.1.109`). Their visible consoles corroborate an ordinary-account storage denial on the server and cleanup/restoration activity on the client. Those observations do not independently establish all of the claimed conditions:

- that the real API process ran as `svc-alveara-api`;
- that its active SQL connection used `alveara_app_login` with only `db_datareader` and `db_datawriter`;
- that its configured storage root was the ACL-protected path and the process could read/write it;
- that the client could not reach SQL or storage directly;
- that public internet was unavailable from that same client at the same time the shell, static asset, health endpoint, and status endpoint succeeded with normal TLS validation.

At review time the two VMs were running, but the claimed HTTPS service was not listening from the reviewer host, so these conditions could not be replayed. The narrative may be accurate, but the project instructions explicitly prohibit treating an implementation agent's success claim as sufficient evidence.

**Correction:** Make R07's operational verifier produce sanitized, timestamped evidence from both machines. Record the server process identity, resolved storage path and ACL, successful API storage/database operation, SQL role membership, unrelated-account denial, client SQL-port and storage-share denial, certificate-validated LAN requests, failed client public-internet probe, and successful shell/static/API requests during the same isolation window. Package the generated outputs without credentials, private keys, or other secrets. Leave the environment in a safe restored state afterward.
