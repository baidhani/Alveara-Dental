## Blocking findings and required corrections

### N002-R02-01 — P1: The required LAN production-shell and least-privilege deployment model is still not established

**Locations:** `src/Alveara.Api/Program.cs`; `src/Alveara.Api/Properties/launchSettings.json`; `src/alveara-client/vite.config.ts`; `src/alveara-client/playwright.config.ts`; packaged `evidence/ACCEPTANCE_EVIDENCE.md` items 1 and 7; packaged `evidence/DEMO_EVIDENCE.md`; packaged `review/NEXT_STORY_IMPACT.md`.

The R02 demonstration reaches only the API health endpoint from the server machine through its own NIC address. It does not exercise the production shell from a LAN client, and public-internet access was not disabled. The API does not serve the built client: `Program.cs` has no static-file/fallback hosting, the production browser tests use a localhost Vite preview, and checked-in launch settings bind to localhost. Therefore the evidence cannot establish the acceptance requirement that a LAN client can use the production shell with no public internet.

The HTTPS check uses `curl -k` with the ASP.NET development certificate. That proves encryption bytes were negotiated while explicitly bypassing server-certificate validation; it does not establish a trusted LAN transport strategy. The package itself acknowledges that no separate client, production service account, or trusted LAN certificate was established, yet `MANIFEST.json` still reports `acceptance: { total: 9, passed: 9 }` with no blockers.

The SQL test usefully proves that `db_datareader` plus `db_datawriter` can perform the current CRUD and cannot perform the sampled DDL/backup operations. It does not configure or exercise the actual server/service identity, SQL Server Express runtime connection, storage-root ACL, or an approved maintenance identity. No storage-permission check proves that an ordinary client cannot read/write the blob root directly.

**Correction:** Within ALV-N002, define a runnable local-server profile that serves or routes the production shell and API for LAN use; document and exercise certificate issuance/trust and hostname/address validation without bypassing validation; configure a concrete least-privilege service identity and separate maintenance boundary for SQL and the storage root; and prove an ordinary client identity cannot directly access either. Exercise the shell from a separate or explicitly isolated client while public internet is unavailable and LAN access remains available. A polished installer remains ALV-N013 scope, but the runtime, topology and security model explicitly required by ALV-N002 cannot be deferred. If the required environment is unavailable, report the acceptance item as not established instead of passed.

### N002-R02-02 — P1: Raw exception text still crosses the PHI-safe diagnostic boundary

**Locations:** `src/Alveara.Api/Architecture/BackgroundWork/BackgroundJobRunner.cs:179`–189 and `251`–255; `src/Alveara.Api.Tests/BackgroundJobTests.cs`; `.alveara/BUILD_STATE.md` PHI-safe logging claim.

R01 explicitly required diagnostic error codes/correlation identifiers instead of raw potentially sensitive payloads, plus a synthetic sensitive-error test through the real failure/logging path. R02 did not implement that correction. The runner still writes `ex.Message` verbatim to persisted `BackgroundJob.LastError`, and the hosted service still passes the complete exception object to ordinary logging.

An independent reviewer-owned test job threw `InvalidOperationException("Synthetic patient Alice Example, treatment detail")`. After the actual runner processed it, `LastError` contained `Alice Example` verbatim. This uses synthetic data and demonstrates the privacy boundary failure without alleging exposure of real PHI. The submitted test instead asserts that a raw simulated exception message is retained, which entrenches the unsafe behavior.

**Correction:** Persist a bounded, non-sensitive error code/state and correlation identifier. Log only an approved safe diagnostic representation; do not assume arbitrary handler/database exception messages are PHI-free. Add negative tests using synthetic patient-like content through both persisted failure status and the configured logging sink, proving the sensitive text is absent while operators retain enough safe information to correlate and troubleshoot the failure.

### N002-R02-03 — P1: Concurrent enqueue violates the queue's idempotency contract

**Locations:** `src/Alveara.Api/Architecture/BackgroundWork/BackgroundJobRunner.cs:27`–53; `src/Alveara.Api.Tests/BackgroundJobTests.cs`.

R01 required a concurrent-enqueue test. R02 adds concurrent claim coverage but not concurrent enqueue coverage. `EnqueueAsync` still performs a read followed by an insert. The unique database index prevents two rows, but when two callers read the same absent key before either insert commits, one `SaveChangesAsync` fails rather than returning the existing job as the interface contract promises.

The independent harness synchronized two real LocalDB callers immediately after their key lookup. One call failed with `DbUpdateException`; one row remained. This prevents duplicate rows, but it is not an idempotent enqueue API and can turn a harmless duplicate submission into an observable failure.

The external-effect guidance in the same file also suggests check-marker-then-act for a non-transactional external action. A crash after the external action and before its marker commits still allows a duplicate. Future external handlers need a stable idempotency token honored by the target or a suitable outbox/inbox protocol; a local pre-check alone is not sufficient.

**Correction:** Make the enqueue operation converge under a unique-key race, for example by safely resolving the unique conflict and returning the committed existing job with a clean context, or by using an appropriate atomic database pattern. Add a deterministic real-database concurrent-enqueue test in which both callers succeed and receive the same durable job. Correct the external-effect contract so it does not instruct future handlers to rely on an unsafe check-before-act sequence.

### N002-R02-04 — P2: The claimed halfway migration-failure rollback is not actually exercised

**Locations:** `src/Alveara.Api.Tests/MigrationUpgradeTests.cs:106`–131 and `168`–180; packaged migration acceptance claims.

The populated-database upgrade test is a meaningful correction and passes. The separate failure migration, however, contains only one statement, and that statement fails immediately because it references a nonexistent column. No schema/data change succeeds earlier in that migration, so the test cannot demonstrate that an actually partially executed migration is rolled back rather than left half-applied. It verifies only that an immediately failing migration is not recorded and pre-existing data remains.

The repository also does not document the operational migration owner, schema-readiness behavior, or recovery action after a failed upgrade; the application itself does not apply migrations or report schema version/readiness. ALV-N013 will later own the complete install/upgrade workflow, but R01 specifically required the applicable ALV-N002 migration failure policy and an exercised partially failing upgrade.

**Correction:** Make the test migration perform a successful observable DDL/DML change and then fail in the same migration; assert that the earlier change is absent after failure, the migration is not recorded, and representative existing data remains. Document the current migration execution/ownership and safe failure/recovery boundary without claiming automatic rollback or restore beyond what is tested.
