## Blocking findings and required corrections

### N002-R05-01 — P1: The browser client was not demonstrated with public internet unavailable

**Locations:** packaged `evidence/DEMO_EVIDENCE.md`, Part 3; packaged `evidence/ACCEPTANCE_EVIDENCE.md`, item 1; ALV-N002 acceptance item 1 and required no-public-internet smoke test.

The firewall exercise blocks outbound public-internet traffic on the **server host** and proves the bridged VM can still request the shell over the LAN. The evidence does not block or test public-internet access from the VM where the browser/client runs. The acceptance condition says a LAN client can use the production shell with no public internet; leaving that client online does not demonstrate that condition and cannot detect a runtime browser dependency on a public resource.

The earlier source scans are useful supporting evidence but are not the required deployed smoke test. The R05 transcript shows the VM's LAN requests succeeding while the host cannot ping `8.8.8.8`; it provides no corresponding failed public-internet probe from the VM and no browser/network observation that the client workflow issued only LAN requests.

**Correction:** In the real bridged-client setup, block public-internet access for the VM/client while retaining its local-subnet route, or isolate both client and server from the public internet while retaining their LAN. From that same client, prove a public target is unreachable and then exercise the built shell, SPA route, static assets, health and status API successfully. Record the simultaneous negative public-internet result and positive LAN workflow without leaving a persistent firewall change.

### N002-R05-02 — P1: The actual server service/database/storage permission boundary is still not exercised

**Locations:** packaged `evidence/DEMO_EVIDENCE.md`, Part 4; packaged `evidence/ACCEPTANCE_EVIDENCE.md`, item 7; `src/Alveara.Api/Program.cs` storage/database configuration; ALV-N002 security requirement for least-privilege service configuration and restricted database/storage permissions.

The two Windows accounts and ACL-protected `AlveaaraStorageDemo\blobs` folder exist on the **client VM**, while the API demonstrated in Parts 2 and 3 runs on the host at `192.168.1.180`. The folder is expressly described as “storage-root-equivalent.” The API was not run under `svc-alveara-api`, did not write a blob to that folder, and did not connect to SQL under a corresponding deployed least-privilege identity. The ordinary-account denial proves generic NTFS ACL mechanics, not the permissions of the actual server runtime.

Current host inspection corroborates the gap: no `svc-alveara-api` local account exists on the server host. The actual source-tree `src/Alveara.Api/App_Data/blobs` inherits its ordinary development ACL, including read/execute access for `CodexSandboxUsers`; it is not restricted to a dedicated API service identity plus maintenance administrators. The earlier SQL test proves current CRUD can work with a restricted SQL login, but the demonstrated running server still uses its configured development identity rather than that principal.

The LAN client also did not attempt and fail direct database access. HTTP non-exposure of blob bytes proves the application does not serve the storage directory, but it is not a filesystem/network permission check.

**Correction:** Exercise a coherent server deployment boundary. Run the published API on the server under a dedicated non-administrative service identity; point it at the actual configured storage root protected for that identity and approved maintenance administrators; prove the running API can write/read there; and prove an ordinary local/server identity cannot. Connect the running API through the tested least-privilege database principal and prove the LAN client cannot directly reach/authenticate to the database or storage while API access succeeds. Disposable accounts/folders are acceptable, but they must be the identities and paths used by the demonstrated server process rather than an unrelated stand-in on the client.
