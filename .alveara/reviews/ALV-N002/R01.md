## Blocking findings and required corrections

### N002-R01-01 — P1: Restart can duplicate consequential job effects; the claim is not atomic

**Locations:** `src/Alveara.Api/Architecture/BackgroundWork/BackgroundJobRunner.cs:90`–120; `src/Alveara.Api/Data/AlveraDbContext.cs`; `BackgroundJobTests.cs`.

The runner commits InProgress, invokes the handler, then separately commits Succeeded. A crash after a handler's durable effect and before the final status save leaves an InProgress job. Recovery resets it to Pending and invokes the handler again. A unique enqueue key prevents duplicate rows; it does not prevent duplicate effects from re-executing the same row. No durable effect receipt, transactional completion boundary, or demonstrated idempotent-handler protocol closes that window.

**Independent reproduction against a fresh real LocalDB database:** Seeded one synthetic persisted effect and the associated InProgress job with an old start timestamp, representing precisely that crash boundary. A new runner recovered and processed it using an ordinary handler that persisted its effect. The effect count became **2**, and the job was completed. Only synthetic reviewer data was used.

The existing restart test seeds InProgress without any preceding effect, so its execution count of one cannot prove the required post-effect crash case. Additionally, the comment that the Pending→InProgress update prevents concurrent dispatch is unsupported: jobs are read as Pending and later saved without an atomic conditional claim, row version or other ownership mechanism. Two readers can both hold the same pending job. That concurrency issue is a source finding; the reviewer did not claim a concurrent-dispatch runtime reproduction.

**Correction:** Define and implement the minimal durable execution contract appropriate to local work: atomic claim/ownership, a durable idempotency key/receipt at the side-effect boundary, and transaction coupling where the effect and completion share the database. For effects outside that transaction, explicitly require and exercise an idempotent handler/outbox-style contract rather than claiming the runner alone guarantees exactly-once behavior. Test interruption after the effect but before completion, concurrent attempts to claim a job, and concurrent enqueue of the same key. Do not build a distributed broker or future domain workflows to satisfy this.

### N002-R01-02 — P1: A quick restart leaves interrupted jobs stranded indefinitely

**Locations:** `BackgroundJobRunner.cs:58`–77 and `BackgroundJobHostedService.ExecuteAsync` at lines 136–151.

Recovery selects only InProgress rows older than five minutes. The hosted service calls recovery once at startup; its later loop only processes Pending rows. If the service restarts within five minutes of claiming a job, recovery skips it. Aging later does not help because recovery is never called again.

**Independent reproduction:** A newly started InProgress job gave `startup recovery count=0`. After moving its timestamp past the cutoff to represent time passing, the regular poll processed **0** jobs and its status remained **InProgress**. This follows the actual hosted-service call sequence and does not require waiting five wall-clock minutes.

**Correction:** Use safe startup ownership recovery and/or periodic lease-expiry recovery, with an explicit active-owner policy. Preserve the protection against duplicate effects from finding 01. Enforce MaxAttempts across recovered/crashed attempts as well as caught handler failures; recovery currently resets Pending without an exhaustion check. Test a quick restart, delayed recovery, final-attempt interruption, and truthful visibility of unrecoverable/failed jobs.

### N002-R01-03 — P1: Database outage at startup stops the host; status polling can also remain stale

**Locations:** `BackgroundJobRunner.cs:136`–141; `Program.cs`; `Controllers/SystemStatusController.cs`; `src/alveara-client/src/hooks/useSystemStatus.ts:21`–40.

The initial recovery query executes outside the hosted service's guarded polling loop. A database exception escapes the background service and stops the application host. The endpoint's own catch around CanConnectAsync cannot help once the host has stopped.

**Independent real-process reproduction:** Launched the unchanged API on reviewer-only port 5191 with a syntactically valid connection string naming a deliberately nonexistent LocalDB database, `AlvearaReviewMissing_9b661291`. It initially reported listening, then the recovery query threw SQL error 4060, the background service failed, and the process logged **“Application is shutting down...”** and exited. No existing database was changed or removed. This contradicts the claimed graceful unavailable-database status behavior. A WebApplicationFactory request that succeeds before background shutdown is insufficient evidence of sustained degraded service.

The new client status hook also has no per-request timeout, cancellation, overlap prevention or response-shape validation. A hanging request can leave old healthy cards visible indefinitely, or a late response can replace a newer observation. It does not reuse the bounded health-check behavior established in ALV-N001.

**Correction:** Contain initial recovery failures, preserve a truthful degraded status endpoint, retry safely and report runner/database errors without fabricated health. Add a real-process cold-start-with-database-unavailable test, a sustained degraded request after the initial failure, and recovery when the database becomes available. Bound/coalesce/cancel status polls, reject invalid response shapes, and explicitly show stale/unavailable observations rather than retaining healthy data indefinitely. Test hanging, delayed and out-of-order requests as well as outright rejection.

### N002-R01-04 — P1: The measurement privacy/version boundary accepts arbitrary nested payloads

**Locations:** `Architecture/Measurement/MeasurementEvent.cs`, `MeasurementEventValidator.ValidateProperties`; `Architecture/Measurement/IMeasurementEventSink.cs`, `RecordAsync`; `BackgroundJobRunner.cs:115` and 155.

The validator checks only top-level property names. Allow-listed values may be arbitrary objects, arrays or free text; EventName and schemaVersion are also unrestricted. Therefore the allow-list does not enforce the claimed privacy-minimized event contract or a meaningful versioned schema.

**Independent reproduction against the fresh review database:** `RecordAsync("review.synthetic-privacy", 0, new { category = new { patientName = "SYNTHETIC_TEST_ONLY" } })` succeeded and persisted. The nested disallowed field bypassed validation, and version zero was accepted. This is synthetic evidence of the bypass, not real PHI exposure.

The failure path also stores raw handler exception messages in LastError and logs exception objects from the poll loop. A helper that formats IDs does not by itself establish that these diagnostics cannot retain sensitive caller payloads. No actual patient content was used or found during this review.

**Correction:** Define the small supported event name/version/property schema, validate value types/ranges/lengths and bounded categorical values, and reject unexpected nested/free-text structures by default. Do not add a speculative event framework. Validate schema versions and separate diagnostic error codes/correlation identifiers from raw potentially sensitive payloads. Add nested-object/array/free-text/version negative tests and synthetic sensitive-error tests through the actual failure/logging paths, not only the correlation helper.

### N002-R01-05 — P1: Required LAN deployment, no-internet and service-permission evidence is absent

**Locations:** packaged ACCEPTANCE_EVIDENCE items 1 and 7; `NoPublicInternetDependencyTests.cs`; `tests/no-direct-db-access.test.mjs`; `Program.cs`, existing launch profile, and NEXT_STORY_IMPACT.

The package equates a localhost request and an API URL-literal scan with a LAN client operating without public internet. `http://localhost:5072` is loopback, notwithstanding the evidence's “non-loopback-only” description. A source scan of `.cs` URL literals does not exercise built client assets, configuration-supplied/dynamic endpoints, transport, or a separate client. The lack of a SQL driver/connection string in browser source is useful but does not verify database/storage permissions or network exposure.

The implementation/evidence does not supply the story-required least-privilege service configuration, restricted database/blob permissions, or a documented and exercised secure LAN transport strategy. Existing localhost CORS and HTTPS-redirection scaffolding are not that evidence. Deferring a polished installer to ALV-N013 is legitimate; deferring the explicitly required ALV-N002 runtime/topology/security model and acceptance proof is not.

**Correction:** Define a concrete runnable local Windows-server configuration: application/client serving and API routing, LAN binding, TLS/certificate trust strategy, service identity, database rights, storage ACLs and approved maintenance boundaries. Exercise the shell/API from a LAN client or an explicitly documented equivalent isolated-client setup while public-internet access is unavailable, preserving LAN access. Verify ordinary clients cannot directly access the database/storage. Record actual configurations, commands, environment and results without secrets. If the environment/input needed for a required check is unavailable, report that limitation truthfully rather than converting a source scan into a runtime PASS. Do not alter the user's network/firewall without appropriate authorization.

### N002-R01-06 — P2: Migration upgrade/failure and interrupted-storage behavior are not established

**Locations:** `MigrationTests.cs`; `Architecture/Storage/IBlobStorage.cs:49`–52; Program/configuration and packaged acceptance items 2 and 9.

Migration coverage consists of initial migration, rerunning an already-applied migration, and a unique-index violation during ordinary data insertion. Rerunning a migration as a no-op is not an upgrade test, and a data insert failure is not a migration failure. No explicit migration failure/recovery policy or exercised partially failing upgrade is supplied. The transaction rollback tests correctly prove their own data transaction scenario but cannot stand in for all schema/storage failure paths.

Blob writes create the final-name file directly and do not remove it when copying fails. In an independent synthetic interrupted-stream check, StoreAsync threw an IOException and left **one partial file** in the storage root. It did not falsely return success, and no linked authoritative record was corrupted in this check, but there is no tested atomic publication/cleanup policy for the partial artifact. Existing storage tests cover ordinary round-trip/integrity, not disk-full/read-only or interrupted writes.

**Correction:** Document and test the applicable schema-upgrade and failed-migration recovery policy, including preservation of existing representative data and honest schema readiness. A test-only migration fixture can exercise this without inventing a new product domain. Define and test interrupted/full/read-only storage behavior, including temporary-file publication/cleanup or an explicit recoverable orphan policy and bounded errors. Do not simulate successful recovery by dropping/recreating existing authoritative data. Add database unavailable/corrupt/schema-mismatch coverage appropriate to the actual chosen engine rather than claiming all failures from one rollback test.
