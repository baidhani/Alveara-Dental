### N002-R07-02 — P1: The server summary is not raw output produced by the committed verification harness

**Locations:** `ops/deployment-verification/Invoke-ServerVerification.ps1:131` and `:152`–`:166`; packaged `artifacts/server/20260928-235600-SUMMARY.json`; packaged `artifacts/server/20260928-235600-svc-write-result.txt`; `DEMO_EVIDENCE.md`.

The checked-in server script does not perform the positive service-account write. It prints a command for an operator to run manually, unconditionally sets `serviceWriteRead` to `MANUAL STEP REQUIRED`, and immediately writes `SUMMARY.json`. It never re-reads the later result or changes that verdict to `PASS`.

The packaged summary nevertheless reports:

`"serviceWriteRead": "PASS: SUCCESS: written by svc-alveara-api at 2026-09-28T23:56:58.8658701-05:00"`

Its own `capturedAtUtc` is `2026-09-29T04:56:05.1593759Z`, which is about 53 seconds **before** the referenced write at `04:56:58.8658701Z`. Therefore this summary cannot be the raw, unedited, machine-generated output of the committed script, contrary to the manifest, handoff, and demo-evidence claims.

The positive result file is also not self-authenticating: its text says “written by svc-alveara-api,” but that account name is a string interpolated into the child script. The child does not capture its actual Windows identity. A manually generated file with that text does not independently establish who executed the write.

**Correction:** Make the R08 server harness execute the positive check itself under a supplied `PSCredential` or another explicit service-identity mechanism, wait for completion, and have the child record its actual runtime identity (for example, `WindowsIdentity.GetCurrent().Name`) along with write/read success. Only then should the parent compute and write the final summary. The summary timestamp must follow every result it incorporates. Package the untouched outputs from one complete run; do not manually patch verdicts.

### N002-R07-03 — P1: The SQL evidence does not prove that the running API uses the least-privilege login

**Locations:** `Invoke-ServerVerification.ps1:99`–`:110`; packaged `artifacts/server/20260928-235600-sql-role-membership.txt`; packaged client route files; `ACCEPTANCE_EVIDENCE.md`, item 7.

The server harness accepts `-SqlLogin alveara_app_login` as an operator-supplied string and uses an administrative `Invoke-Sqlcmd` connection to show that this database principal belongs to `db_datareader` and `db_datawriter`. That proves the login exists with those roles. It does not inspect the API process's runtime configuration or a SQL session created by that process.

The client route sweep proves `/api/systemstatus` returned HTTP 200 but does not retain the response body showing database reachability, and it does not link a database session to `alveara_app_login`. The process-identity artifact records only the executable command line. As a result, R06's required correction — prove the real running API connects through the tested least-privilege database principal — remains unestablished.

**Correction:** In R08, force a database-backed request and capture sanitized evidence tying the resulting SQL session/configuration to the running API and `alveara_app_login`, without exposing the password or full connection string. A privileged verifier can, for example, correlate an active SQL session's `login_name`, host/process/application identity, and the API PID while the request is in progress. Also retain the `/api/systemstatus` response body, or a sanitized parsed subset, showing `database.reachable: true` and the runner state. Continue to retain the role-membership query as separate least-privilege evidence.
