## Blocking findings

### N001-R01-01 — P1: The shell treats Vite's HTML fallback as a healthy API

**Locations:** `src/alveara-client/src/hooks/useConnectionStatus.ts:22`–23; `src/alveara-client/vite.config.ts`; `src/Alveara.Api/Properties/launchSettings.json`.

The hook fetches the relative URL `/api/health` and sets `connected` solely from `res.ok`. The Vite configuration has no API proxy, and the API is a separate process/origin. CORS configuration does not route a relative client request to that process.

**Independent runtime reproduction:** With only Vite running on `http://127.0.0.1:5173` and no listener on the configured/reported API ports 5072, 7180 or 5199, `Invoke-WebRequest http://127.0.0.1:5173/api/health` returns **HTTP 200, Content-Type text/html**, beginning with `<!doctype html>` and the Vite React-refresh script. This is the client index fallback, not the API health response. The actual hook therefore evaluates it as connected, and AppShell suppresses the disconnected banner even though the API is unavailable. This conclusion follows directly from the observed HTTP response and the hook; it is not presented as a browser screenshot observation.

The passing disconnected test mocks `fetch` to reject, so it cannot detect this wiring defect. The default test setup mocks any request as `{ok:true}`, which also accepts the false-positive path.

**Required correction:** Connect the client to the actual configured API through a development proxy or an explicit environment-configured API base URL. Document consistent startup ports. Validate the expected health payload rather than accepting arbitrary 200 HTML. Bound each check with a timeout and avoid accumulating overlapping hung checks: the current controller is aborted only on unmount, so a stalled server can also leave the previous status indefinitely. Add regression coverage for API up/down/recovery, HTML or invalid-payload 200 responses, and timeout. Demonstrate the real shell's banner appearing when the actual API stops and clearing after recovery.

This is within ALV-N001's explicitly required disconnected/local-server-unavailable failure path and truthful status UI. It must not be deferred to ALV-N002.

### N001-R01-02 — P2: Responsive usability and the visible demonstration have not been established

**Locations:** `src/alveara-client/src/App.responsive.test.tsx:8`–19; packaged `evidence/ACCEPTANCE_EVIDENCE.md`, item 3; `evidence/DEMO_EVIDENCE.md`.

The two responsive tests assert DOM landmarks and the presence of the text `@media (max-width: 820px)` in a CSS file. Neither renders layout at a desktop or tablet width, measures clipping/overflow, or exercises long labels. No agreed/tested viewport dimensions are recorded. A CSS-breakpoint string cannot prove the acceptance criterion that the shell is usable at the specified widths.

DEMO_EVIDENCE explicitly substitutes jsdom plus HTTP requests for a visible browser demonstration. This confirms component structure and that servers return content, but cannot establish rendered layout, readable text, visible focus, or the real client/API interaction. In fact, N001-R01-01 passes those checks. A screenshot framework is not mandatory; a genuine, recorded browser walkthrough or browser-based checks are.

**Required correction:** Declare the desktop/tablet viewports used for this story and run the actual UI in a rendering browser. Record results for navigation, showcase, keyboard focus/skip link, unknown route, validation, notifications, connected/disconnected/recovery and both themes. Exercise the explicitly required empty module registry and long-label/constrained-tablet cases, with representative fixtures, and check that controls remain reachable without unintended clipping/overflow. Include reproducible browser/test instructions and actual outcomes in the new attempt's demo and acceptance evidence. Do not label DOM-only checks as proof of responsive usability.

The reviewer's browser-tool attempt returned `Transport closed`; no independent visual pass is claimed. That tool limitation does not establish a UI defect by itself. This finding rests on the required evidence missing from the submitted package and the actual scope of its tests.

### N001-R01-03 — P2: Dark-theme primary controls use low-contrast text

**Locations:** `src/alveara-client/src/styles/tokens.css:19`, 112–113; `src/alveara-client/src/components/Button.css:9`, 23–27.

Dark mode changes the primary background to `#5fa2c7` and hover background to `#7fb8d8` while retaining white `--color-primary-contrast`. The normal primary-button label size is `0.8125rem`. Independent relative-luminance calculations give white-text contrast ratios of approximately **2.808:1** and **2.154:1** respectively. These are below the 4.5:1 normal-text threshold, and even below 3:1. This affects enabled primary actions in the implemented dark theme. See [W3C's contrast-minimum guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

The submitted accessibility test checks only the dashboard in jsdom; it does not demonstrate readable showcase/action colors in both themes.

**Required correction:** Define a suitable dark-theme foreground token or adjust the primary backgrounds; verify normal and hover text contrast. Run accessibility smoke checks against actual rendered interactive controls in both themes, including the showcase and unknown-route action, and record the results. This is a concrete shell accessibility defect, not a demand to complete the later production accessibility gate now.
