## Non-blocking evidence limitations

- The submitted E2E connectivity test intercepts `/api/health` and reloads for recovery. The reviewer independently verified actual API down/up/down polling without reload. Keep that distinction; the submitted suite alone is not a backend integration test.
- The submitted long-text test checks ordinary description-box width, not genuinely long labels or their text overflow. Representative label evidence is supplied above. Preserve such a fixture in future UI regression work; no R03 is required solely to duplicate this completed reviewer check.
- The handoff names `VALIDATION_RESULTS.md`, which exists in repository evidence but is not packaged. The ZIP still contains all mandatory story members. Future prose should distinguish repository-only supplemental evidence from package members.
- The test title saying notification coverage is “for each tone” exceeds its actual two-click Success/Warning coverage; the keyboard demo prose also overstates skip-link activation by the committed test. These wording issues do not negate the actual rerun and supplementary evidence reported here.
- The dark-theme contrast ratios in handoff prose are approximate; the passing tests' explicit calculations and actual rendered axe results are the evidence. This is smoke coverage, not complete accessibility certification.
- In development StrictMode, the effect's in-flight guard can defer the visible initial status until the next polling interval after effect cleanup/re-execution; live checks allowed that interval. This does not reproduce the false-positive API-health defect. The current 15-second poll cadence is not a real-time connection guarantee.
- A historical CHANGES_REQUIRED intermediate ledger state was not committed separately; the unchanged R01 rejection is durably stored in R02 evidence and the current ledger correctly reflects the new attempt awaiting review. No prior rejection was erased or self-approved.
