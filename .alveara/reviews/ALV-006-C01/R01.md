## Blocking finding

### ALV-006-C01-R01-01 — P1: The absent-tooth rule is not preserved when a finding becomes absent, and is not atomic for concurrent writes

**Locations:** `src/Alveara.Api/Architecture/Odontogram/OdontogramService.cs:38-90` and `:175-189`; `src/Alveara.Api/Migrations/20261004223713_AddConditionCatalogueAndLinks.cs:199-217`; `docs/ODONTOGRAM.md` / `HANDOFF.md`, Limits.

The story’s rule is that a tooth recorded as missing (an active Existing or Completed finding with the `Absent` effect) may not take any other active clinical finding except another absence/replacement finding. R01 checks that rule only during `RecordAsync`: it calls `EnsureToothPresentAsync` after a non-locking read and before inserting a new finding. `ChangeStateAsync` has no corresponding check.

Consequently, the following ordinary sequential API workflow can leave an invalid active chart:

1. Record `Missing` as `Planned` on a tooth.
2. Record active `Caries` on that tooth; this is currently allowed because planned absence does not yet block the tooth.
3. Change the Missing finding to `Completed`; this succeeds without revalidating the other active finding.

The chart then holds an active completed absence and active caries for the same tooth, contrary to the stated validation rule. In addition, two writers can each pass the `EnsureToothPresentAsync` read before either inserts a different finding; the migration has immutability triggers but no patient/tooth presence invariant or serialization mechanism. The handoff explicitly discloses that the absence check “is not transactional against a simultaneous write.” That is a material unsatisfied part of the prompt’s concurrency-safe tooth-update and integrity requirements, not acceptable deferred debt.

**Required correction for R02:**

1. Make every operation that can create or activate an `Absent` finding, and every operation that records a non-presence finding, serialize and validate against the same patient/tooth state. This includes recording a Missing/Extracted finding, moving one from Planned/Diagnosed to Existing/Completed, and recording another finding. A patient/tooth aggregate revision or lock row with an atomic transaction is a suitable design; an application-only pre-read is not sufficient.
2. Decide and implement the explicit correction path when a transition would make a tooth absent while other active clinical findings exist. The operation must refuse with a stable clinical conflict, or atomically apply a documented non-destructive lifecycle transition that preserves history. It must never silently leave incompatible active chart state.
3. Add real-SQL tests that prove: (a) Planned Missing → Caries → Missing Completed cannot persist the invalid state; (b) concurrent Missing/Extracted and Caries writes for the same tooth cannot both succeed into the invalid state; and (c) a permitted replacement/implant remains possible. Include API-level behavior and regression coverage for the original `STORY-006` workflow.
4. Update the handoff acceptance and limitations to state the final proved invariant. Do not retain the simultaneous-write disclaimer after claiming concurrency-safe tooth updates.
