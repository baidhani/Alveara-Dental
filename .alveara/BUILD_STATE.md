Confirmation atomically promotes pending to active (`ExecuteUpdateAsync` gated on the pending value still matching, so two racing confirmations apply at most once) and rotates `SecurityStamp`. Replacing an already-active factor requires the caller's current password as step-up reauthentication, sharing the exact same account-lockout boundary as an ordinary login (R03) — a wrong step-up password counts toward, and can trigger, the same lockout, and `mfa/enroll` carries the same IP rate limiter as every other auth-attempt endpoint. Every MFA challenge is backed by a durable, one-time-consumable `MfaChallenge` row (R03) — atomically marked consumed on success (`ExecuteUpdateAsync` gated on `ConsumedAtUtc == null`), so an identical challenge-token/code submission cannot be replayed to mint a second session, and is bound to the account's `SecurityStamp` at issue time (R02), rejected if that stamp has since rotated (password reset, role/status change, explicit revocation, or a factor replacement). Challenge consumption, recovery-code consumption (where applicable), and the resulting audit write happen inside one database transaction (R04); a rejected replay writes a privacy-safe `MfaChallengeReplayRejected` audit entry (never logging the token or code) instead of going unaudited (R04). When two DISTINCT valid challenges concurrently race the same still-unused recovery code, the losing challenge's own consumption is rolled back (not committed) if the recovery-code update it depends on affects zero rows — so a losing challenge is never left partially consumed with no owning audit, and remains genuinely completable afterward with a different valid code (R05). **R06:** the step-up counter-reset and the two-challenges-one-code rollback are now proven with deterministic tests - three narrow, test-only coordination seams on `AccountService` (`TestHook_BeforeStepUpConditionalReset`, `TestHook_AfterRecoveryCodeVerifiedBeforeConsumption`, `TestHook_AfterRecoveryCodeConsumedBeforeCommit`; each `internal Func<Task>?`, null and a no-op in production) let a test pause execution at the exact point a race window requires and force each critical branch to genuinely execute, closing an evidence gap where R04's and R05's own concurrency tests could pass through a benign scheduler ordering without ever exercising the stale-success rejection or the rollback branch they claimed to prove. `Totp.cs` delegates all cryptographic work to `Otp.NET` (a maintained, widely-used library) rather than implementing RFC 6238/Base32 itself.
