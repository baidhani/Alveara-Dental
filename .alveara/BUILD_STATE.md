## Authorization-aware navigation, session UX, and identity context (ALV-N009, COMPLETE — approved attempt R03)

R03 corrections (responding to R02's independent review, `.alveara/reviews/ALV-N009/R02.md`, decision `CHANGES_REQUIRED`):

- **Idle sessions can no longer be kept alive by background observation traffic.** `Program.cs`'s cookie-auth configuration now sets `options.SlidingExpiration = false` explicitly — ASP.NET Core's default (`true`) was silently renewing `ExpiresUtc` on every authenticated request past the renewal midpoint, including R02's own 30-second revalidation poll. The session deadline set at sign-in (`SessionTimeoutMinutes`) is now a fixed, honest ceiling regardless of what polls the session. This is a deliberate policy change: a genuinely active user's session now also expires at that fixed deadline rather than being pushed back by their own activity.
- **A stale, superseded async response can no longer resurrect a cleared session.** `AuthContext.tsx` gained a monotonic `requestSeqRef` guard: every `refresh()` call (poll, focus, visibility, expiry boundary, post-login/MFA) captures its own sequence number and only applies its result if nothing newer (a later refresh, `logout()`, or the reactive-401 handler) has superseded it; `logout()` and the 401 handler both bump the sequence synchronously before any state change.
- Three new deterministic tests prove each fix (one backend `dotnet test` proving repeated calls never extend the session expiry; two frontend fake-completion-order tests forcing the exact race the R02 review's probe used). 179 backend (up from 178) / 59 frontend (up from 57) / 8 real-backend Playwright, all passing. See `.alveara/handoffs/ALV-N009/R03-evidence/`.

## Authentication and security administration (ALV-001-C01, COMPLETE — approved attempt R06)

- **`src/Alveara.Api/Architecture/Identity/AccountService.cs`** — registration (`RegisterAsync`, no role parameter — self-service accounts are always `Role.Unassigned` + disabled), one-time offline-capable first-admin bootstrap (`BootstrapFirstAdminAsync`, atomicity via a fixed-PK `BootstrapState` singleton row, not application check-then-act), login with concurrency-safe rearming lockout and timing-safe unknown-user handling (`LoginAsync`), TOTP MFA via a maintained library (`Totp.cs`, a thin wrapper over `Otp.NET` — see below), admin-issued one-time password reset (no email/SMS dependency), account enable/disable, session timeout configuration (`SetSessionTimeoutAsync`, validated 5–1440 minutes, audited), and session revocation via `SecurityStamp` rotation.
- **MFA lifecycle (R02/R03/R04/R05/R06):** enrollment/replacement uses a pending-then-confirm model — `UserAccount.PendingMfaSecretProtected` and `MfaRecoveryCode.IsPending` hold a not-yet-confirmed factor completely separately from the active one, so starting (and abandoning) re-enrollment can never disable an established factor. Confirmation atomically promotes pending to active (`ExecuteUpdateAsync` gated on the pending value still matching, so two racing confirmations apply at most once) and rotates `SecurityStamp`. Replacing an already-active factor requires the caller's current password as step-up reauthentication, sharing the exact same account-lockout boundary as an ordinary login (R03) — a wrong step-up password counts toward, and can trigger, the same lockout, and `mfa/enroll` carries the same IP rate limiter as every other auth-attempt endpoint. The correct-password step-up path checks the affected-row count of its conditional lockout-counter reset, exactly like `LoginAsync`'s own success path (R04). Every MFA challenge is backed by a durable, one-time-consumable `MfaChallenge` row (R03) — atomically marked consumed on success (`ExecuteUpdateAsync` gated on `ConsumedAtUtc == null`), so an identical challenge-token/code submission cannot be replayed to mint a second session, and is bound to the account's `SecurityStamp` at issue time (R02), rejected if that stamp has since rotated (password reset, role/status change, explicit revocation, or a factor replacement). Challenge consumption, recovery-code consumption (where applicable), and the resulting audit write happen inside one database transaction (R04); a rejected replay writes a privacy-safe `MfaChallengeReplayRejected` audit entry (never logging the token or code) instead of going unaudited (R04). When two DISTINCT valid challenges concurrently race the same still-unused recovery code, the losing challenge's own consumption is rolled back (not committed) if the recovery-code update it depends on affects zero rows — so a losing challenge is never left partially consumed with no owning audit, and remains genuinely completable afterward with a different valid code (R05). **R06:** the step-up counter-reset and the two-challenges-one-code rollback are now proven with deterministic tests - three narrow, test-only coordination seams on `AccountService` (`TestHook_BeforeStepUpConditionalReset`, `TestHook_AfterRecoveryCodeVerifiedBeforeConsumption`, `TestHook_AfterRecoveryCodeConsumedBeforeCommit`; each `internal Func<Task>?`, null and a no-op in production) let a test pause execution at the exact point a race window requires and force each critical branch to genuinely execute, closing an evidence gap where R04's and R05's own concurrency tests could pass through a benign scheduler ordering without ever exercising the stale-success rejection or the rollback branch they claimed to prove. `Totp.cs` delegates all cryptographic work to `Otp.NET` (a maintained, widely-used library) rather than implementing RFC 6238/Base32 itself.
- **`src/Alveara.Api/Architecture/Identity/Permission.cs` / `PermissionMatrix.cs` / `RequirePermissionAttribute.cs`** — a genuine named-permission matrix mapped to the seven course-defined roles (dentist, hygienist, assistant, front desk, billing, office manager, admin), replacing a single hardcoded `[Authorize(Roles=Admin)]` gate. Also names clinical/scheduling/billing permissions no module enforces yet, for future stories to authorize against instead of inventing their own role checks.
- **Session security:** cookies are `HttpOnly`, `SameSite=Strict`, and `Secure` outside Development; a `SecurityStamp` claim is validated against the database on every request (`Program.cs`'s `OnValidatePrincipal`), giving real server-side "sign out everywhere" with no server-side session store. CSRF protection (double-submit via ASP.NET Core's `IAntiforgery`) covers every `[Authorize]`-protected state-changing auth endpoint. IP-based rate limiting (sliding window, configurable) covers every unauthenticated auth-attempt endpoint.
- **Audit (R02/R04):** the full MFA/recovery lifecycle is now audited (`MfaEnrollmentStarted`/`MfaReplacementStarted`, `MfaReplaced`, `MfaChallengeSucceeded`/`MfaChallengeFailed`, `MfaRecoveryCodeUsed`, `SessionTimeoutChanged`, alongside the R01 events). `LoginSucceeded` is recorded only once authentication genuinely completes — a password-verified-but-MFA-pending login records `PasswordVerifiedMfaPending` instead, correcting R01's premature success record. **R04:** a rejected challenge replay (already consumed, expired, or revoked) now writes a new `MfaChallengeReplayRejected` event, privacy-safe by construction (never logs the token or code), instead of going unaudited.
- **`src/alveara-client`** — `contexts/AuthContext.tsx` (re-derives session state from `GET /api/auth/permissions` on every mount), `services/authApi.ts`, and seven pages: `LoginPage`, `MfaChallengePage`, `ResetPasswordPage`, `AdminUsersPage` (user list, now with a "View" link per row), `AdminUserDetailPage` (R02 — per-user detail view including the session-timeout control), `MfaSettingsPage` (R02 — enrollment/replacement UI), `PermissionMatrixPage` (R02 — full role/permission visibility). ## Core architecture (ALV-N002, COMPLETE — approved attempt R08)

- **Database engine decision:** SQL Server Express for the actual local Windows server deployment; SQL LocalDB (the same SQL Server engine) for development and automated tests — a deliberate, documented choice, not a shortcut: both speak the same T-SQL/EF Core SqlServer-provider surface, so tests exercise real migrations/transactions/constraints, not an in-memory fake. Chosen (with the product owner) over SQLite specifically because a dental practice has multiple concurrent LAN writers (front desk, clinicians, billing) and SQLite serializes writes practice-wide.
- **`src/Alveara.Api/Data/AlveraDbContext.cs`** — the single EF Core DbContext; `src/Alveara.Api/Migrations/` holds two migrations (`InitialArchitecture`, `AddBackgroundJobEffectReceipts`), both applied and verified against a real SQL Server (LocalDB) database — including a genuine **upgrade** of an already-populated database from the first migration to the second (not just a fresh-database apply).
- **`src/Alveara.Api/Architecture/`** — the cross-cutting invariants this story exists to establish, each with its own tests:
  - `Time/PracticeClock.cs` — practice-timezone (`America/Chicago` by default, configurable) ↔ UTC conversion; explicitly rejects (or, when asked, explicitly resolves) DST spring-forward-invalid and fall-back-ambiguous local times rather than silently guessing.
  - `Money/Money.cs` — `decimal`-backed, USD/2dp, banker's-rounding (round-half-to-even) money type; never `double`/`float`.
  - `Identity/IdentityEntities.cs` — `UserAccount`, `StaffProfile`, `ProviderProfile` as three distinct, explicitly-linked entities. No authentication logic yet — that's STORY-001/ALV-001-C01.
  - `Storage/IBlobStorage.cs` — local-disk blob storage seam; stored identity is a generated Guid, never a caller-supplied filename; SHA-256 integrity verification; writes go to a temp file and are atomically moved into place only on success, so an interrupted write (disk full, cancellation) can never leave a partial file under a real blob id. No document module yet — that's ALV-N010/ALV-010-C01.
  - `Backup/IBackupSnapshotProvider.cs` — `SqlServerBackupSnapshotProvider` uses real `BACKUP DATABASE`, not a raw file copy. Consumed later by `ALV-N004`.
  - `BackgroundWork/BackgroundJobRunner.cs` — durable, persisted background-job mechanism with an explicit crash-safety contract: **atomic claim** (a single conditional `UPDATE`, not read-then-write, so two runner instances can never both own the same job), a **durable effect receipt** (`BackgroundJobEffectReceipt`) written in the *same database transaction* as a handler's local-database effect and the job's `Succeeded` status — so a crash between "effect happened" and "job marked done" is structurally impossible, not just unlikely. Recovery (`RecoverStuckJobsAsync`) runs on *every* poll cycle, not only once at startup, so a quick restart is still caught once the stuck threshold elapses; a job that already exhausted `MaxAttempts` before a crash is recovered straight to `Failed` rather than looping forever. `BackgroundJobHostedService`'s poll loop wraps recovery *and* processing in the same guarded try/catch, so a database outage during recovery logs and retries instead of crashing the whole host.
  - **R03: concurrent-enqueue idempotency race fixed.** `BackgroundJobQueue.EnqueueAsync` previously checked-then-inserted, which is not atomic under two simultaneous callers using the same idempotency key. It now attempts the insert unconditionally and, on a genuine SQL unique-constraint violation (`DbUpdateException` wrapping SQL error 2601/2627), clears the change tracker and re-queries the row the other caller committed — both callers converge on the same single persisted job, proven by a test that fires two concurrent `EnqueueAsync` calls for the same key and asserts they return the same job id with only one row ever persisted.
  - **R03: PHI-safe logging leak fixed.** The failure path previously risked persisting/logging the raw `Exception.Message`, which can embed caller-supplied (potentially patient-identifying) text. Failure handling now records only `SafeErrorSummary(ex, jobId) = "{ExceptionTypeName} ({correlation token})"` — never the message text — both to the persisted `LastError` column and to the injected `ILogger`. A dedicated test (`BackgroundJobPhiSafeLoggingTests`) throws an exception containing synthetic patient-like text and asserts the configured logging sink never receives it, only the safe summary; a second test asserts the same for the persisted column.
  - **R03: migration-failure rollback now actually proven, not merely asserted.** The prior failure-migration test used a migration whose *only* statement failed, so it could not distinguish "the migration never ran" from "the migration ran and was genuinely rolled back." `FailureTestBrokenMigration.Up()` now performs a real, observable schema change first (`ALTER TABLE ... ADD COLUMN`) and only then fails on a second statement; the test explicitly queries `INFORMATION_SCHEMA.COLUMNS` afterward and asserts the added column does **not** survive — proving SQL Server's per-migration transaction rolled back a *partially executed* migration, not just an immediately-failing one.
  - **Self-discovered regression, also fixed in R03:** an earlier version wrote the job's `Failed` status *inside* the still-open transaction that the exception had just interrupted, so the failure write was itself silently rolled back along with the failed effect. Fixed by calling `transaction.RollbackAsync()` as the first line of the catch block, then writing the failure status via a separate `ExecuteUpdateAsync` outside any transaction.
  - `Measurement/MeasurementEvent.cs` — versioned (`SchemaVersion >= 1`), privacy-minimized operational events; `MeasurementEventValidator` checks not just the top-level property key against a small allow-list but also each value's JSON kind (string/number only, never a nested object/array), bounded string length, and — for categorical keys (`outcome`, `role`, `release`, `category`) — a fixed set/pattern of accepted values, so a PHI-shaped or free-text payload can't be smuggled through a "safe-looking" key either. `EventName` must match a bounded `dotted.lowercase-segment` pattern.
  - `Logging/PhiSafeLog.cs` — correlation-token convention (entity type + id only, never a free-text field) for ordinary diagnostic logs.
