## Scope delivered
- **Intake.** `POST api/import-batches` takes one CSV file (our own parser: quoted fields, embedded newlines and quotes, a byte-order mark, CRLF or LF; size, row and column limits) for one kind (patients, appointments, opening balances), refuses a malformed file whole with its place in the file and stores nothing, and stores a sound file byte for byte in an `imports` folder (separate from the document store) with its SHA-256. The same file twice returns the same batch.
- **Mapping and dry-run.** A suggested mapping, a saved and confirmed mapping, and a dry-run that applies the real rules without writing: the front desk's registration validation and duplicate comparison for patients, the scheduler's availability and conflict rules for appointments (patient by first name, last name and date of birth; provider, operatory and type by name; future only), the ledger's empty-account rule for balances (a positive amount, one balance per patient). Every row is Valid, Rejected (with fixed messages, never a value from the file), Skipped (already present) or Unresolved (a likely duplicate patient).
- **Duplicates.** A likely duplicate is held in a queue for a person to decide (register anyway or skip), never auto-merged; the decision is audited and the row is judged again at commit.
- **Commit.** An explicit confirmation names the policy and the number of valid rows shown; a stale screen is refused (409 `results_changed`). Policy per batch, visible before the commit: all-or-nothing (patients only, one transaction, at most a configured number of rows) or commit the valid rows only (the default for appointments and balances, each row in its own transaction). The work runs on the durable job queue with idempotency keys per row (`import-{batch}-{row}`, `import-appt-...`, `import-bal-...`). Appointments go through the scheduling service, so a clash is rejected and reported, never resolved by the import. An opening balance is an `Adjustment` appended through `BillingService.RecordOpeningBalanceAsync` as the first ledger entry of an empty account, with the batch id as its correlation id and a fixed reason; the ledger stays append-only.
- **Retry.** A commit that stopped (no live job of the current round) is shown as stopped and can be retried; the retry starts a new round, never repeats a row done before, and the confirmer becomes the retrier (audited).
- **Reports.** The reconciliation (rows by status, the records the batch made, the ledger total for balances, named problems: `row_count_mismatch`, `accepted_result_missing`, `unexplained_records`, `valid_rows_left`, `counters_mismatch`, `amount_mismatch`), a row-level CSV error report (fixed messages, formula cells neutralised, a byte-order mark) and an orphan-file sweep (on request, 24 hours' grace, a batch's own file never touched).
- **Permissions and audit.** New permission `BulkImportData` (Administrator by default, grantable); committing or retrying a balance batch also needs `ManageBilling`; the duplicate queue is shown only to a person who also holds `ViewPatientRecords`. Ten import audit events (the batch, the file refused, mapping, dry-run, a decision, commit started, completed or refused, retried, files swept) plus the ledger's `BillingOpeningBalanceRecorded`; no name, date of birth, phone or file value in any import audit entry (the ledger's own audit amount and a balance batch's total are the only amounts).
- **Screens.** `/admin/data-import` (batch list, upload) and `/admin/data-import/:batchId` (mapping, dry-run, rows, duplicate queue, commit with confirmation and policy, progress polling every 3 seconds for at most 10 minutes, retry, reconciliation, error-report download, sweep), light and dark, axe-clean.
- **STORY-018 unchanged.** Its import, export and tests are untouched and still pass (see `R01-evidence/PARENT_REGRESSION.md`).

## Decisions and deviations
1. **Our own CSV parser**, no new dependency (owner decision).
2. **Policy per batch**: all-or-nothing is the default and is offered only for patients; appointments and balances are committed row by row ("valid rows only") because each row has its own transaction through its own service. The screen says so.
3. **The upload is kept in an `imports` folder**, separate from the document store.
4. **Appointment conflicts are rejected and reported only**; there is no workflow that resolves one.
5. **Ledger provenance deviation.** The first decision was a separate provenance table. It was implemented as the ledger entry's correlation id (the batch id) plus a fixed reason; the owner agreed when slice 5b was scoped. A migration-origin entry is therefore distinguishable by that reason and correlation id, not by a dedicated column.
6. **Balances: positive amounts only, empty ledgers only**, so an opening balance is always entry number 1 and is never added to a history. The as-of date is validated but not stored.
7. **`ManageBilling` as well as `BulkImportData`** to commit or retry a balance batch.
8. **The appointment commit does not run on the runner's transaction**: each row commits itself through the scheduler, so a mid-batch failure leaves the earlier rows booked; the retry finishes the rest.

## Findings in shared components
- `SchedulingConfiguration.CheckProviderAvailabilityAsync` takes an optional `AvailabilityLookups` cache (null keeps the original queries), so a dry-run does not query the provider's windows once per row. The rules are unchanged and the original callers pass nothing.
- `PatientDuplicateDetector` has its comparison extracted as a pure function used by the front desk's check and by the dry-run, so both apply identical rules.
- `PatientRegistrationService` has patient staging extracted (`StagePatient`), used by `RegisterAsync` and the import commit.
- `ExportDomainCatalog` lists `ImportBatches` and `ImportBatchRows` in the technical-bookkeeping exclusion, so a patient package does not carry import batches. The three refactors are covered by the existing tests (62 STORY-018 tests and the 928 `*ApiTests` pass; their unit tests run in Stage 2).
- `docs/PATIENT_PORTABILITY.md` had three statements corrected (it said bulk import was not available).
- `.colaberry/` platform files were not edited.

## Limitations / debt
- **Untested:** the rollback guards 51263, 51267 and 51268; restoring a backup that contains import files; ambiguous and merged patients in a file; a start time passing into the past between dry-run and commit (untestable with the real clock); a conflict or a 503 leaving a row Valid; a non-Administrator holding `BulkImportData` without `ManageBilling` over HTTP (service level and the walkthrough cover it); a half-done retry (simulated with a pre-made ledger entry); stray-file removal on a real disk in the walkthrough (the runner does not pass the storage folder).
- `ImportBatchRows.ResultRecordId` has no foreign key (the result may be a patient, an appointment or a ledger entry).
- The sweep runs only when someone calls it; nothing schedules it.
- A committed batch cannot be undone as a batch; a mistake is corrected through the normal patient, schedule or ledger workflows.
- CSV only; no vendor adapters; no appointment conflict-resolution workflow; no credit (negative) balances; no balance for a patient who already has any ledger entry.
- The screens show "Unknown staff member" for a user without a staff profile (existing behaviour).
- The mocked browser suite has 2 skipped tests (a data-driven test in `architecture-map.spec.ts`).
