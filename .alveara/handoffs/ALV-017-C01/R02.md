## Review findings and how each is answered
**ALV-017-C01-R01-01 (the Stage 2 runner wrote the patients walkthrough output into the repository).** The new frozen runner `R02-evidence/stage2/run_stage2.sh` uses `PATIENT_E2E_OUT`, sends every walkthrough output to the run's out-folder outside the repository, and **proves it before running anything**: `verify_runner_outputs.py` reads every walkthrough config and spec, checks that the variable the runner passes is the one the spec reads, and checks that the out-folder is outside the repository; a mismatch stops the run (exit 3) with nothing started. The evaluator has a new criterion for that proof. Proof: `R02-evidence/artifacts/runner-proof/` (all five OK; the R01 defect `PATIENTS_E2E_OUT` is reported as a PROBLEM; an out-folder inside the repository is reported as a PROBLEM). The evaluator validation has a new scenario that rejects a wrong-variable proof (10 of 10 scenarios behave as stated). The patients and permission-policy walkthroughs were run with the corrected variable and an out-folder outside the repository: 7 and 7 passed and the worktree stayed clean.

**ALV-017-C01-R01-02 (a fixture teardown could not drop its database: SQL error 3702).**
- **Diagnostic (instruction item 2):** `TestDatabaseFixture` now logs, on every 3702, one line per session holding the database with only session id, program name, host name, host process id and status (control characters stripped, at most 128 characters); never a connection string, statement text or request data (asserted by tests).
- **Failure mode established from evidence:** a broad focused run on a tree that already stopped its hosts reproduced the failure in the same class (`PermissionPolicyPipelineTests`), and the diagnostic named the holder: session 53, program `EFCore/10.0.12`, the test host's own process, status sleeping. The cause is in the application, not only the harness. When the stored policy has invalid rows or is degraded, `PermissionPolicyStore.Report` starts the audit report as a background `Task.Run` after the response (it opens the database through `AuditingPolicyObserver`). Nothing tied it to the host lifecycle, so a host disposed right after such a request still used the database while the fixture dropped it. Both tests that failed (R01 run 2 and this reproduction) put the policy into exactly that state. My first theory (a hosted background service still running at dispose) was not the cause; the harness change alone did not prevent the failure.
- **Fix (item 3):** `PolicyReportDrain` (a hosted service) waits at host stop for the reports in flight (bounded by the shutdown token; a timeout is logged). `SchedulingApiHarness` now stops every host it started and waits (30 s limit, reported if exceeded) before disposing, in both the asynchronous and the synchronous `Dispose()` (all 42 callers).
- **3702 as a bounded transient (item 4):** 3702 joins the deadlock and the pool timeout in `IsTransientDropFailure`. The bound is the existing 4 attempts; when they run out the original exception is thrown unchanged (tested). Recovery is proven against a real 3702, not assumed.
- **Regression coverage (item 5):** `TestDatabaseInUseTests` (5 tests):
  - A real 3702 from a plain DROP against a held session is retried to success; the database and its files are gone, the holder is named by program, and nothing sensitive is logged.
  - A holder that never leaves fails after exactly 4 attempts with the original 3702 and is named on every failure; the test then removes the database it left.
  - The classifier accepts only the SQL error number.
  - Disposing the harness returns only after a slow background service has stopped.
  - A policy report still running when the host is disposed is finished first and the database drops with no 3702 (the test fails without the drain registered).
