## Scope delivered
- **Explicit confirmation:** a merge needs `confirmed: true` from the caller (the screen's own control), and records that look like different people (a different date of birth, or a first name that is not within a nickname's distance) need a second, separate confirmation. The audit entry names the fields decided and how, never their values.
- **Duplicate-review queue:** the scan excludes merged records and dismissed pairs; an administrator can dismiss a pair as "not a duplicate" with a reason and bring it back; a dismissal is never deleted or edited (database triggers), is audited on both records, and one is in force per pair in either order.
- **Retired-record guard and lineage:** the database refuses a new row for a patient who was merged away (error 51235, answered 409 `patient_merged`); the retired record is read-only on its page and links to the survivor; the survivor's page shows what was absorbed and when (`GET api/patients/{id}/merge-history`).
- **Cross-domain preservation:** one merge of a real chart (appointment, medical history and allergy, tooth finding, perio session, diagnosis, plan with a completed procedure, charge and payment, prescription, document, referral, follow-up task, household and guarantor) moves every registered patient-owned column with nothing lost, and every foreign-key edge still agrees.
- **Recovery:** a merge that fails at any of four points changes nothing and the same request then succeeds; a record changed after review stops the merge; an already-merged record is refused.
- **Undo ("unmerge"):** every merge now keeps a ledger of the rows it moved; the undo is previewed by doing the work in a transaction that is rolled back, needs a reason and the same confirmation and version rules, refuses when newer records depend on moved rows or a ledger row is not where it was, keeps fields edited since, restores the retired record to active with its own lineage and audit, and can be repeated safely. A merged record may be merged away only once at a time.
- **UI:** Possible duplicates queue (dismiss, restore), side-by-side review with the identity warning, the merge log with Undo, the undo review, and a banner on both records.

## Architecture, schema, API, UI, security, configuration, measurement changes
- **Schema** (migrations `20261025195735_AddPatientDuplicateDismissals`, `20261025200612_GuardRetiredPatientRecords`, `20261025202141_AddPatientUnmerge`): `PatientDuplicateDismissals`, `PatientMergeMovedRows` (the ledger), `PatientUnmerges`, `PatientMerges.HasLedger`; triggers 51240 to 51243 (dismissals), 51235 (a new row for a retired patient) on each table that owns a patient id, 51236/51237 (ledger and undo records immutable), 51238 (an undo only for a merge that holds), 51244 (a record merged away once at a time), 51245 and the Down guards (rollback refused over data). The merge-scope triggers and the immutable-table triggers gain the allowances the undo needs (`alveara.patient_unmerge` session value, only the active flag, merged mark and who/when columns of the retired record). Registered in the migration inventory.
- **API:** nine routes on `PatientMergesController` (duplicates, preview, log, merge, dismissals, restore, unmerge-preview, unmerge) and one read on `PatientMergeHistoryController`; writes need CSRF and an Idempotency-Key; changes carry row versions; stable error codes. See `docs/PATIENT_MERGE.md`.
- **Security:** the existing `MergePatients` permission (administrator only) covers every route; the patient's merge-history read needs `ViewPatientRecords`. No new permission.
- **Configuration:** none. No secrets.
- **Observability:** three new audit event types (`PatientDuplicateDismissed`, `PatientDuplicateRestored`, `PatientUnmerged`); the existing `PatientMerged` entry gains the field decisions.

## Decisions and deviations
The plan was put to the owner and approved before building, including the undo ("where practical and safe" was read as: build it, with a ledger). Assumptions: "looks like a different person" is a different date of birth or a first name more than two edits apart; a dismissed pair is hidden until restored, and a new dismissal after a restore is a new row; the undo restores a field only if the survivor still holds the value the merge put there; a guarantor link cleared by a merge is not restored.

## Defects found by own verification
- The first guard migration failed on tables with no patient id column (messages, notifications); it now selects tables by column existence.
- Negative controls: 2 backend mutations survived the first pass (the undo not checking that ledger rows are where they were; the retired-record check also running inside a merge); two tests were added; one mutation of mine produced invalid C# and was rewritten; all re-run and killed.
- The real-backend walkthrough found an ambiguous status selector, a link failing colour contrast in the red notice (fixed in `merge.css`), and the retired record still offering Save and Reactivate (now read-only, 409 `patient_merged`).
- The identity derivation found one baseline id that this story renamed; it is declared as retired rather than silently dropped.
- A STORY-017 record said "no ESLint configuration"; the project lint is oxlint and exits 0. Corrected in `docs/testing/STORY-017_TEST_RESULTS.md`.

## Limitations and debt
- No full backend regression was run (Stage 1). The frozen Stage 2 contract is in `R01-evidence/stage2/`.
- A merge made before ledgers existed (that is, one made by STORY-017 before this story) cannot be undone, and neither can a merge whose survivor was merged away since.
- An undo does not restore a guarantor link a merge cleared, and does not overwrite a field edited since.
- Lint reports 3 `set-state-in-effect` warnings in this story's screens, the same rule as 38 already in the project.
- One scratch test database (`AlveraTest_14dc6e152f1548529b2138ccb83bbfe4`, created 2026-10-25 12:37) was left by an interrupted backend test run and was not dropped; see `R01-evidence/TEST_RESULTS.md`.
- Probabilistic matching and auto-merging are out of scope, as the plan says.
