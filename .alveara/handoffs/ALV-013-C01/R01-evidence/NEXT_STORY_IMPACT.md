# Next-story impact - ALV-013-C01 R01

Next scheduled item: **item 27 - `ALV-N005`** (Production Procedure and Fee Catalog Foundation; dependencies `ALV-N003`, `ALV-002-C01`). It does not depend on this attempt and no interface here constrains it. Later stories that do touch this work: `STORY-015` and `ALV-015-C01` (treatment plans) and any story that adds procedures, notes or imaging.

- **The treatment-plan forward reference is the hand-off to `ALV-015-C01`.** `Diagnosis.TreatmentPlanReference` (and every `DiagnosisVersion`) holds opaque text; `TreatmentPlanReferenceStates.Unresolved` is the only state; nothing looks it up. `ALV-015-C01` creates real plan identities and reconciles eligible references with same-patient validation, idempotency, history preservation and visible handling of unresolved or invalid references. The reconciliation can read the reference from the diagnosis row and its history; it must record its own provenance (this attempt left no place that treats the reference as resolved, and the API refuses any request that tries to).
- **Interfaces added:** `DiagnosisService` (now partial: `DiagnosisService.Structure.cs` holds amend, resolve, reactivate, link), `DiagnosisAmendment`, `DiagnosisLinkView`, `DiagnosisLink` (entity), `DiagnosisCodingSystems`, `DiagnosisSources`, `DiagnosisRegions`, `DiagnosisLinkTypes`; endpoints `POST /api/diagnoses/{id}/amend`, `/resolve`, `/reactivate`, `/links`; `DiagnosisException` codes `link_target_not_found` and `diagnosis_withdrawn` (also used for the new operations); problem codes `unsupported_system`, `coding_incomplete`, `unsupported_source`, `source_required`, `unknown_region`, `conflicts_with_tooth`, `unsupported_link_type`, `not_supported`.
- **Triggers and migrations:** trigger numbers 51071 to 51074 (STORY-013) and **51075 and 51076** (this attempt) are used; **51077 and up are free**. Migrations `AddDiagnoses` (STORY-013) and `AddDiagnosisStructure` (this attempt).
- **Links are one-way and permanent.** `DiagnosisLinks` has no unlink; a treatment-plan or procedure link is not a link type (a plan is a reference on the diagnosis itself). Adding a new link type is a one-line change in `DiagnosisLinkTypes`, its check constraint and `DiagnosisService.Structure.cs`.
- **The periodontal side still holds a diagnosis only as text.** `PerioExamLinks` (ALV-012-C01) can name a `Diagnosis` by plain reference; a diagnosis can now name a periodontal chart by id through `DiagnosisLinks`. The two are independent and are not cross-validated; a story that wants both directions could route `PerioSessionService.LinkAsync` through `DiagnosisService` and validate the id.
- **UI extension points:** `DiagnosisChips` (context chips; a new kind of context is a new chip), `DiagnosisStructureFields` (record and amend share it), `DiagnosisReasonForm` (any further change that needs only a reason), the `Linked records` list.
- **Coding systems are names only.** A terminology integration or a licensed code set can be added without changing a diagnosis's identity or history (the system and code are plain columns with their own check constraints), but would need its own story (and its own licensing decision); the code is never validated against a list today.
- **Unresolved decisions that touch later work:** (1) whether `Resolved` needs its own date fields on the diagnosis (today the history entry carries who, when and why); (2) whether an unlink or a "link recorded in error" correction is wanted; (3) whether a diagnosis should be able to link to an encounter note, a procedure or an image; (4) whether hygienists should be able to amend (they can record and amend today because they hold the clinical-notes permission); (5) whether the oral-region list needs finer values (surfaces, sextants).
- **Prompt changes:** none required for `ALV-N005`. For `ALV-015-C01`, the prompt already describes the reference reconciliation this attempt prepares.
