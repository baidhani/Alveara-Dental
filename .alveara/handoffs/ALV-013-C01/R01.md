## Scope delivered (the prompt's implementation scope)
- **Stable internal diagnosis identity** - unchanged from STORY-013 (a GUID that never changes; neither patient, encounter nor origin can change).
- **Structured fields** - optional coding (system `ICD-10-CM`, `SNODENT` or `Local`, and a code, together or not at all), the label as the display, the clinician's explanatory text (the notes), status, and provenance (`Manual`, `Imported`, `Mapped`, with a note allowed only on the last two).
- **Patient and encounter linkage** - STORY-013's, unchanged.
- **Tooth and oral-region linkage** - a tooth or an oral region (nine fixed values), never both; shown as chips.
- **Finding, odontogram and perio linkage** - append-only links from a diagnosis to a finding or a periodontal chart of the **same patient** (the rule is in the service and in the database), who and when recorded, quiet repeats.
- **Treatment-plan forward reference** - STORY-013's optional opaque reference is preserved with its unresolved state through amendment, resolve, reactivate, withdraw and every history view, each step carrying its own actor and time; a request to mark it as anything but Unresolved is refused on record, correct and amend. No treatment-plan table, record, API, workflow or placeholder was built.
- **Active / resolved / amended status model** - `Active`, `Resolved`, `Withdrawn`; `Amended` is a recorded act (a history entry) rather than a status; resolve and reactivate are reversible and need a reason; withdrawn stays final.
- **Amendment preserving prior value, actor, time and reason** - amend replaces the structure (location, coding, source) as one recorded act; the earlier values stay in the append-only history.
- **No licensed terminology** - only the names of three systems; a code is never checked against a code set and no code list is bundled.
- **UI** - coding, source and region on the record form; context chips and linked records on each diagnosis; Amend, Mark resolved / Make active again and Link actions; amendment, resolve and reactivate steps in the history with a column for region, coding and source; the patient-safety strip stays in view.

## Decisions and deviations from the prompt's wording
1. **Amendment is a separate act from correction.** STORY-013's correction (label, tooth, notes) keeps its history type and tests; amendment is for structure, so the history says which kind of change was made.
2. **Coding systems are names only and the list is closed** (`ICD-10-CM`, `SNODENT`, `Local`). No terminology content is bundled and a code is never checked against a code set (the prompt forbids bundling licensed content).
3. **"Display" is the existing label.** The prompt lists "display/label" as one structured field; adding a second display column would duplicate the label, so the label is the display.
4. **Resolved is not Withdrawn.** Resolved means no longer present and is reversible; withdrawn means entered in error and is final.
5. **Links go to records that really exist** (findings and periodontal charts), with the same-patient rule in the service and the database; a treatment plan is not a link type.
6. **The "resolve the treatment-plan reference" failure path is covered by refusing the attempt**, not by a new endpoint, so no treatment-plan API exists (the user's decision).
7. **The default diagnosis list now shows Active and Resolved** so a resolved diagnosis stays visible; withdrawn ones remain behind "Show withdrawn".
8. **The history table's new column is last** so STORY-013's column positions did not move.
9. **The acceptance total recorded in the status file was 6; the authoritative prompt lists 7**; the record is corrected to 7.

## Limitations / debt
See `docs/DIAGNOSES.md` ("Limits"): the code is never validated against a code set and the coding-system list is closed; the treatment-plan reference is never resolved (reconciliation belongs to a later story); status is Active, Resolved or Withdrawn only; a diagnosis cannot move to another encounter; links are one-way and permanent (no unlink); one tooth or one region per diagnosis; hygienists can record and amend because they hold the clinical-notes permission.

**Verification limits (see `evidence/TEST_RESULTS.md`, "Disclosures"):** the mutation filter did not include `DiagnosisRulesTests` or `DiagnosisSchemaTests`; no `.trx` was captured for the full backend run; the walkthrough screenshots are from a standalone run of the same code. A separate proposal to shorten test runs is with the reviewer and nothing in this attempt depends on it.
