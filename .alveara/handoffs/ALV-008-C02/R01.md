## Scope delivered
All six stop conditions of the prompt (mapped in `R01-evidence/ACCEPTANCE_EVIDENCE.md`), with the eight design decisions implemented as approved:
- **Retirement (D1, D2).** Both legacy routes answer `410 Gone` with `legacy_completion_retired` and the two replacement routes, after the sign-in, role (`ManageTreatmentPlans`) and CSRF checks and whatever the body carries; they look nothing up and write nothing. Each attempt is one PHI-free `legacy_completion_retired_attempt` log event (route, status, trace id). `CompleteItemAsync` and `CompleteAcceptedAsync` are deleted, so no production bypass remains. A repository test (`RetiredCompletionCallerSearchTests`) fails if a production caller or a third route declaration reappears.
- **UI (D3).** The "Complete accepted procedures" group, its confirmation form, the per-procedure "Mark X completed" form and the `completeItem` and `completeAcceptedProcedures` client calls are removed; "Review and complete..." is the only completion action. A new "Adopt earlier completions..." action opens a form listing only the procedures the server says are legacy completions (`legacyCompleted`), saying in words what adopting each will do to the chart and the charge (taken from the server's readiness), and asking for provider, encounter, performed time and a required reason.
- **Adoption (D4, D5, D6, C1).** `POST api/treatment-plans/{planId}/items/{itemId}/adopt-completion` (`ManageTreatmentPlans` plus CSRF) adopts exactly one procedure that is currently Completed, not withdrawn and has no completion record. In one transaction it records a completion set that carries the required adoption reason (item count one), the immutable completed-procedure record, the chart effect through the chart's own rules, and the procedure's one charge through `IProcedureCharging` (an existing manual charge is reused, a zero fee has none), advances the plan's row version and writes one PHI-free `CompletionAdopted` audit entry. It stages no new state row and no `ItemCompleted` event: the legacy state row, event and audit entry stay exactly as they were (proven by `The_legacy_state_row_event_and_audit_entry_are_not_rewritten_and_nothing_is_added_to_them`). The same provider, encounter, performed-time (no exemption for an old acceptance time), chart-ambiguity, billing, idempotency, transaction and concurrency rules as `ALV-008-C01` apply. The request identity is a dedicated hash of a version tag, the operation (`adopt-completion`), the item, the encounter, the provider, the performed time to the millisecond and the trimmed reason (C1), so the same request replays, anything else under the same key, including a key an ordinary completion of the same plan used, is `idempotency_conflict`.
- **Reconciliation (D7, C2).** `GET api/completion/reconciliation` (`ViewAuditLog`; read-only; counts only) reports `legacyCompletedNotAdopted`, `completedMissingCharge`, `completedWithUnexpectedCharge`, `orphanedCharges`, `chartMismatch`, `duplicateCharges` and `clean`. `chartMismatch` reads the finding's own version history at the instant the completion was finalized, so a later legitimate chart change is not a defect (C2); no schema change was needed and the same reading covers `ALV-008-C01` completions.
- **Regression strategy (D8).** A test-only `LegacyCompletionFixture` (built on the shared staging helper, so its rows have the retired code's shape by construction), a committed mapping of every affected test and walkthrough (`docs/testing/ALV-008-C02_PARENT_REGRESSION.md`), and a clearly labelled test-only seed (`e2e/support/legacyCompletion.ts`) for the real-browser specs. Course-portal completion state is untouched.

## Architecture / schema / API / UI / security / config / measurement changes
- **Schema.** Migration `AddCompletionAdoption` (`20261013043201`): `CompletionSets.AdoptionReason` (nvarchar 500, nullable), check `CK_CompletionSets_AdoptionReason` (non-blank, no control characters), trigger `TR_CompletionSets_Adoption` (error **51172**: an adoption set has an item count of exactly one). The rollback is refused (51172) while an adopted set exists, so history is never silently dropped. **51173 and up are free.**
- **API.** New: the adopt route and the reconciliation route (`CompletionController`). Changed: the two legacy routes (410); readiness items gain `legacyCompleted`; completed-procedure results and details gain `adopted` and `adoptionReason`; the completion result gains `adoptionReason` (all additive, with defaults).
- **Services.** New `CompletedProcedureService.Adopt.cs` and `.Reconciliation.cs`; `CompletionRules` gains the adoption request, cleaner and hash; `TreatmentPlanService` loses two public methods (a deliberate contract removal: every consumer was updated in the same commit). **One change outside the completion area** (see "Defects found"): `BillingService.LoadSnapshotAsync` now ignores completion records finalized after a document's instant.
- **UI.** `TreatmentPlanAdoptCompletion`; `TreatmentPlanActions` and `TreatmentPlanStateControls` lose the legacy controls; `completionApi.ts` gains `adoptCompletion` and the new fields.
- **Security.** Adoption: `ManageTreatmentPlans` plus CSRF; reads unchanged; reconciliation: `ViewAuditLog`; no new permission. The 410 stubs keep the sign-in, role and CSRF checks before answering (an anonymous caller still gets 401, a hygienist 403, a missing CSRF token 400). No patient, plan, clinical or SQL detail in any audit text or log line.
- **Config / measurement events.** `legacy_completion_retired_attempt`, `completion_adopted` and `completion_adoption_not_recorded` structured log events (PHI-free: correlation id, error class, duration). The old `legacy_completion_used` event is gone.

## Decisions and deviations from the prompt's wording
- **Approved decisions implemented as written** (D1-D8, C1, C2). Implementation choices inside them: the adoption request's performed time is hashed to the millisecond (the column's precision), so a replay of the same request from a second screen is recognised; the reason is trimmed and limited to 500 characters; a `Draft` or `Finalized` encounter is the only kind that exists, so "same-patient Draft or Finalized encounter" is "one of this patient's encounters", exactly as `ALV-008-C01` checks it.
- **"After an announced transition period" (prompt) was resolved as "now" (D1, approved).** The two routes answer 410 immediately; their stubs stay so that an old client gets a safe, explanatory answer rather than a 404 (see Unresolved questions).
- **The reconciliation's chart evidence is derived, not stored (C2 allowed either).** The latest finding version at or before the completion's finalized instant must be an active Completed state. It does not distinguish "this operation created that version" from "it was already there"; both are valid evidence of a completed chart at that instant.
- **The adopt form offers one procedure at a time**, as the prompt requires ("one procedure at a time"); there is no bulk path.

## Defects found by this attempt's own verification
- **A real defect adoption would have introduced in an earlier story's behaviour (ALV-007-C02): fixed here.** A statement ages a charge from the performed time of the completion record behind it, and the reprint of an issued statement ignored later amendments but not later records. Adoption is the first operation that can create a completion record after the charge it bills (a charge billing made by hand for a procedure completed the old way), so a statement issued before an adoption would have been refused on reprint (`This document can no longer be shown exactly as it was issued`). Reproduced first (`BillingTimelineAgingTests.A_statement_issued_before_a_legacy_completion_was_adopted_...` failed with that message), then fixed by ignoring records finalized after the document's instant; killed by negative control A24; the 44 existing billing-document tests pass unchanged. `ALV-007-C02`'s own NEXT_STORY_IMPACT had warned that anything this story writes that an issued statement reads has to reproduce "as it was"; it named amendments, and this is the case it did not name.
- **A clinical-history UI test file was about to be lost with the retired button.** `TreatmentPlanCompleteAccepted.test.tsx` also held five tests of the clinical history, which this story does not touch; they were moved to `TreatmentPlanClinicalHistory.test.tsx` (the refresh test now refreshes after an adoption).
- **The retired STORY-008 walkthrough held two parent criteria** (revising afterwards keeps the original revision and the completed care; every change is in the plan's log). They were ported into the adoption walkthrough (which also asserts adoption added no `ItemCompleted` event).
- **Mutation testing found three missing tests of my own** (a closed plan was not refused by any test, an ambiguous chart match before an adoption, and a legacy completion on a withdrawn procedure counted as waiting for adoption), all added and killed. Four mutants did not run at first because the source files use CRLF line endings; fixed in the driver.
- **First-run mistakes of my own, none a product defect:** audit-entry counts snapshotted before a sign-in wrote its own audit entries; a mis-escaped SQL instance name in the new seed helper; the idempotency header omitted from a patient create; an expected revision count off by the rename made by an earlier step; a test that clicked into an unstubbed readiness call (an unhandled error); the full-run command for the repository checks pointed at a folder instead of the glob.
- **A pre-existing, clock-dependent fragility in an unrelated walkthrough** (disclosed, not fixed): in the sweep `clinical-companion-real-backend.spec.ts` failed once because its audit-text check forbids the substring `190` and the spec's own `Date.now()` stamp (inside a template name) contained it (the stamp is inside such a window for about 2.8 hours today). It passes 9 of 9 on a rerun with only the spec's clock shifted. The spec and the code it drives are untouched by this story.

## Limitations / debt
- **Adoption defaults the performed time to "now"**; the person must edit it to the real time. The legacy state row's own recorded time is not offered as a default (see Unresolved questions).
- **The reconciliation is computed in memory per call** (it reads the completion, plan-item, state, charge and finding-version rows it needs); fine for a report an administrator runs, not designed for paging or very large tenants.
- **`chartMismatch` is only evaluated for completions that name a finding** (`Updated` and `AlreadyCompleted`); a `NotApplicable` completion has no chart evidence to check.
- **The 410 stubs remain in the controller**; deleting them after a sunset period is a later, one-line decision.
- **The real-browser seed writes the retired code's rows with SQL** (state row, event, audit text); if the retired code's row shape ever had a subtlety the fixture's shared helper preserves, the SQL seed could differ. The backend fixture cannot (it calls the same helper); the walkthroughs prove the screens and the API accept the seeded rows.
- **No mocked-browser (Playwright default config) spec covers adoption**; it is covered by 11 component tests, 21 API tests, the service and hardening tests and the real-backend walkthrough.
- Mutation checks cover 24 rules, not the whole feature; one mutant (the up-front plan-version check) is equivalent and disclosed.
- A completion made the old way and then billed, adopted and then amended behaves as any adopted completion; no test combines adoption and amendment beyond the shared record shape.
