## Corrections made this attempt

### ALV-N004-R03-01 — verify-only promoted a contradictory archive and earned confidence
The review's alternative was taken: **media/contents verification stays a distinct, honestly-labelled state and cannot earn application-recovery confidence; a proven archive defect permanently voids credit.**
- **Restore proof is its own fact.** New `BackupRecord.RestoreProvenAtUtc` (migration `AddRestoreProof`, nullable) is set in exactly one place: a successful restore drill. Trust/probation count (`SuccessfulVerificationCount`, `Trusted`), the "overdue" age, and retention's protection of the newest verified backup are all computed from restore-proven, still-`FullyVerified` backups only. "Verify only" keeps its useful result — status `FullyVerified`, shown as **"Contents verified - restore drill still needed"** — but never counts. It cannot know whether the captured database agrees with the manifest (that needs a restore), so it no longer claims to.
- **A proven defect is permanent.** A drill failing with an archive-intrinsic code (`restore_validation_failed` — which includes the database/manifest agreement, row counts and key/secret coherence — `deployment_asset_matches_manifest`, `deployment_settings_recorded`, `documents_complete`, `components_present`, `component_hashes_match`, `database_backup_damaged`, `manifest_*`, `corrupt_or_tampered`) now marks the backup `VerificationFailed` with that code, clears its restore proof, and is audited. `VerifyFullAsync` on a backup with such a recorded defect is a no-op that is audited and returns the failed record, so a later weaker check cannot erase it. Failures that depend on the recovering server or the supplied key (`wrong_recovery_key`, `deployment_settings_match_this_server`, `incompatible_backup`) do **not** poison the backup.
- A drill of a retained archive whose bytes equal a history row (same file name and SHA-256) is linked to that row, so its result applies to the backup's trust state too.
- Missing/unreadable restored deployment record: covered (the drill fails with the specific check detail and earns nothing).
- UI/API/runbook: `restoreProven` on the history DTO; probation/overdue text and the wizard's verify-only result now say it does not count toward trust; runbook verification-levels table, probation and "a proven defect is permanent" sections updated.

**Required regressions (all in `BackupRecoveryHardeningTests`, real SQL Server, same authenticated-altered-archive mechanism the reviewer used):**
- contradictory archive → verify-only: `Verify_only_never_counts_toward_trust_so_an_unknown_contradiction_earns_no_recovery_credit` (status `FullyVerified`, no proof, count 0, not trusted);
- verify-only → failed consistency drill: `Verify_only_then_a_failed_consistency_drill_leaves_the_backup_failed_with_no_credit`;
- failed consistency drill → verify-only: `A_failed_consistency_drill_then_verify_only_cannot_erase_the_failure_or_earn_credit` (the reviewer's reproduction: now `VerificationFailed`, count 0);
- valid drill / later weaker check / later media damage: `A_valid_drill_earns_credit_and_a_later_verify_only_keeps_it_while_a_later_media_failure_removes_it`;
- missing/unreadable restored deployment records: `A_restored_database_with_a_missing_or_unreadable_deployment_record_fails_the_drill_and_earns_nothing`;
- plus the retained R03 manifest/asset/database agreement tests, valid-media and valid-drill paths, history-free recovery, isolated-target cleanup, non-default time zone and legacy MFA compatibility; `Status_reports_probation_trust_…` updated to assert verify-only does not count.

## Corrections to R03 package claims
R03 stated that a contradictory backup could not become fully verified. That held only for drills; verify-only could still promote it and count. Acceptance for "history truthfully distinguishes verification state" is re-asserted only on this attempt's evidence.

## Scope, decisions, limitations
- **Decision (most worth review):** probation/trust is earned by restore drills only (previously a verify-only also counted). This is stricter than before and matches the story's "verified restore drill" language; administrators must run a drill, not just verify, to leave probation.
- Verify-only cannot detect a manifest/database contradiction (it does not restore); this is now stated in the UI, API semantics and runbook rather than hidden.
- Limitations unchanged: OpenPGP MDC integrity rather than AEAD; GnuPG required to run the crypto suite.
