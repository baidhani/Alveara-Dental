## Corrections made this attempt

### ALV-N004-R04-01 — a file-hash check erased a known archive defect
- **Durable, independent storage.** `BackupRecord.ArchiveDefectCode` / `ArchiveDefectAtUtc` (migration `AddArchiveDefect`, with a backfill from rows already failed for an intrinsic reason) hold an archive-intrinsic defect apart from the mutable latest-check fields. The set of intrinsic codes lives in one place (`ArchiveDefects.Codes`). It is permanent: an archive is immutable.
- **One write path.** Every failure write (hash failure, verify-only failure, drill failure) now goes through `BackupRecord.MarkVerificationFailed`, which (a) records an intrinsic code as the permanent defect, and (b) when a defect exists never replaces it with a weaker or environmental code — status stays `VerificationFailed` with the defect's code, restore proof stays cleared. All other writes are guarded: `VerifyHashAsync` no longer touches status/code when a defect is recorded (a passing byte check is audited as "…the recorded archive defect (<code>) remains"); `VerifyFullAsync` returns early with an audit entry; a later drill success does not credit a defective backup. A review of every assignment to `VerificationStatus`/`VerificationFailureCode`/`RestoreProvenAtUtc` was done (the only remaining direct write is the creation of a new backup row as `HashVerified`).
- **Visible representation.** The history API row exposes `archiveDefectCode`; the history list keeps showing "Verification FAILED" with the defect's reason because the status and code stay failed.
- **Distinctions retained.** Wrong key and recovering-server mismatch are environmental: they do not set a defect and do not poison a good backup (new test: wrong key verify → server-mismatch drill → good drill still earns credit).

**Required regressions (`BackupRecoveryHardeningTests`, real SQL Server, authenticated-altered-archive mechanism), each asserting the durable defect, its history/API representation, zero confidence and no restore proof:**
- failed consistency drill → hash pass → verify-only: `A_failed_consistency_drill_then_a_passing_hash_check_then_verify_only_keeps_the_defect` (the reviewer's reproduction);
- failed consistency drill → hash failure (bytes changed) → file missing → bytes restored → hash pass → verify-only: `A_failed_consistency_drill_then_a_hash_failure_or_environment_error_then_weaker_successes_keeps_the_original_defect`;
- direct failed drill → verify-only: `A_direct_failed_drill_then_verify_only_persists_the_reason_in_durable_state_and_the_api`;
- non-defect distinctions: `A_wrong_key_or_a_server_mismatch_is_not_an_archive_defect_and_does_not_poison_a_good_backup`.
Retained and passing: R04 ordering tests, valid hash/media/drill behavior, media-damage credit revocation (`A_valid_drill_earns_credit_…`), history-free archive recovery, isolated-target cleanup, startup guard, non-default time zone and legacy MFA compatibility.

## Corrections to R04 package claims
R04 claimed the defect was permanent and that a later weaker check could not erase it; that held only for verify-only. The hash path could erase it. Acceptance for history truthfulness rests on this attempt's evidence.

## Scope, decisions, limitations
- Decision: the defect is stored in its own columns rather than inferred; a repaired archive is a different file (a new backup), so there is deliberately no "clear defect" operation.
- Limitations unchanged: OpenPGP MDC integrity rather than AEAD; GnuPG required for the crypto suite; verify-only cannot detect a manifest/database contradiction (stated in UI and runbook); trust is earned by restore drills only.

## Architecture / schema / API / UI / config changes
Schema: migration `AddArchiveDefect` (two nullable columns + backfill). API: `archiveDefectCode` on history rows. UI type updated; no behavior change beyond what the unchanged status/code already display. Runbook: "A proven defect is permanent" now lists every check that cannot clear it.
