## Corrections made this attempt

### ALV-N004-R02-01 — domain requests were allowed before verification
- `DeploymentGuardMiddleware` now serves domain API calls **only in the positively verified `Ok` state**. `Unchecked` (startup, database unreachable, check failing) answers **503 `deployment_unverified`** (with `Retry-After`); `Mismatch` answers 503 `deployment_mismatch`. Health, system status, sign-in and `/api/backup/*` (including archive recovery) stay reachable in every state.
- To avoid refusing a healthy server during its first seconds, `DeploymentInvariantStatus` exposes an on-demand `Verifier` (set by the monitor, serialized with its background loop by a lock): a request arriving before the first check triggers it and waits (5 s bound). Only an exception *kind* is logged (no message); failure leaves the state `Unchecked` and the request is refused. This is not a test-side wait: the middleware itself decides.
- **Proof (`BackupRecoveryHardeningTests`):** `Domain_requests_wait_until_deployment_invariants_are_verified_and_are_refused_while_unverified` (the reviewer's reproduction: fresh status, domain path, downstream never reached; operator endpoints allowed in Unchecked; Ok served; Mismatch refused), `A_request_that_arrives_before_the_first_check_triggers_it_and_is_served_only_when_it_verifies`, `A_failing_or_unreachable_initial_check_keeps_domain_requests_refused…` (throwing verifier, and the **real monitor against an unreachable database**); the earlier monitor/allow-list test and the recovered-app mismatch/ok tests remain.

### ALV-N004-R02-02 — a drill could succeed for a contradictory backup
- **At backup time:** `BackupService.EnsureDeploymentAgreesAsync` (before the snapshot and again after it) compares the running settings with the database's `DeploymentInvariants` record (via a fresh context on the live database). A host configured against its database's record fails visibly with `deployment_mismatch` (Failed history row, notification, nothing written). A legacy database with **no record is recorded from the running settings first** (`DeploymentInvariantStore.EnsureRecordedAsync`, shared with the monitor), so manifest, deployment asset and captured database always carry the same values.
- **At restore time:** two new blocking checks — `deployment_asset_matches_manifest` (inventory, before anything is restored) and `restored_database_deployment_matches_manifest` (post-restore: the restored `DeploymentInvariants` row must equal the manifest; a missing record or unreadable table also fails). A failed check yields `Failed`, removes the target, does not mark the backup `FullyVerified` and does not advance confidence.
- **Proof:** `A_host_configured_against_its_databases_recorded_settings_cannot_produce_a_backup_at_all` (the reviewer's mismatched-host scenario: Chicago record, Tokyo host → the backup itself is refused, no file), `A_contradictory_archive_whose_manifest_disagrees_with_its_captured_database_never_reports_success` (authentic archive crafted with manifest and asset = Tokyo, database = Chicago, recovering server on Tokyo → `Failed`/`restore_validation_failed`, not FullyVerified, target removed), `A_deployment_asset_that_contradicts_the_manifest_is_rejected_before_anything_is_restored`, `A_legacy_database_without_a_deployment_record_gets_one_…_and_the_backup_then_recovers_consistently`.
- **Retained regressions:** non-default-time-zone recovery (`A_recovered_application_resolves_practice_local_times_identically…`), history-free archive recovery, legacy Data Protection compatibility, GnuPG interop.

## Corrections to R02 package claims
R02 described deployment enforcement as complete and a successful drill as proof of recovered-app readiness. Both overstated: unverified state was not refused and manifest/asset/database consistency was not enforced. This attempt's evidence supersedes them.

## Scope, decisions, limitations
- Decision: an unverified check fails **closed** for domain APIs (a server whose database is unreachable could not serve them anyway); operator endpoints are exempt so recovery is never blocked by the guard.
- Decision: a database with no deployment record is treated as owned by the host running the first backup/monitor check (an explicit, logged-by-record `RecordedAtUtc` assumption); recovery of such a backup still requires the recorded settings to match the recovering server.
- Unchanged limitations from R02: OpenPGP MDC integrity rather than AEAD; gpg required for the crypto suite.

## Architecture / schema / API / UI / config changes
No schema change. New behavior: 503 `deployment_unverified`; backup failure code `deployment_mismatch` (HTTP 409 message, mapped in the UI); two new restore checks. System Status text for the unchecked state now says the application refuses data requests until verified.
