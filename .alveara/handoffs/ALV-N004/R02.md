### ALV-N004-R01-01 — recovery no longer needs the lost history
- **New entry point:** `BackupRestoreService.ListArchivesAsync / PreflightArchiveAsync / RestoreDrillFromArchiveAsync`, API `GET api/backup/archives`, `POST api/backup/archives/preflight`, `POST api/backup/archives/restore-drill` (Admin / `ManageBackups`, CSRF, current-password step-up, same lockout boundary). UI: **Backup & recovery → "Recover from a retained backup file"** feeding the same restore wizard (no verify-only shortcut for archives).
- Archives are found in the backup folder and a new **import folder** (`Backup:ImportDirectory`, default `<Backup:Root>/import`), read only by their OpenPGP header (recipient key id, no secret, no database row). An archive is chosen by listed reference `destination:NAME.abk` / `import:NAME.abk`, never by a free path (`archive_unknown` otherwise).
- No hash from the lost database is required: authenticity comes from authenticated decryption + the manifest inside the archive; the archive's SHA-256 is recorded on the drill (`RestoreDrillRecord` gained nullable `BackupRecordId`, `SourceKind`, `ArchiveFileName`, `ArchiveSha256`; migration `AddRecoveryHardening`).
- Restore remains isolated-target only (no overwrite path); promotion is the documented offline procedure.
- **Proof:** `BackupRecoveryHardeningTests.A_retained_archive_is_discovered_preflighted_and_restored_with_no_history_and_the_recovered_app_logs_in_with_MFA_data_intact` — real encrypted backup, all history rows deleted and the original destination emptied, only the imported copy plus externally held key/passphrase remain; the archive is listed with `InHistory=false`, preflighted, restored into an isolated database, and the **recovered application is started**, a restored account signs in, a restored MFA secret decrypts with the restored keys, and restored documents verify. Plus archive-ref safety (6 cases), junk/tampered archive tests, and frontend/Playwright coverage (the real-browser flow now also restores from the listed retained file).

### ALV-N004-R01-02 — no custom cryptographic format
- `BackupCrypto` rewritten: the backup is a **standard OpenPGP message (RFC 4880/9580), AES-256 with SEIPD/MDC integrity, encrypted to an OpenPGP RSA-3072 recovery public key**, implemented with the maintained **BouncyCastle.Cryptography 2.7.0** library. No ALVBK header, chunk framing, nonce counter or application AAD remains; the application only streams through the library (64 KiB buffers, bounded memory) and classifies failures (`not_a_backup`, `wrong_recovery_key`, `corrupt_or_tampered`, `invalid_recovery_key`, `weak_passphrase`; trailing data after the message is rejected; destination write faults surface as I/O errors, not corruption). Externally held recovery material is preserved: the server stores only the public key; the armored secret key block and passphrase are shown once.
- **Disclosed limits:** BouncyCastle has no AEAD (OCB/GCM) generator, so integrity is the standard OpenPGP MDC; its passphrase-to-key derivation is the OpenPGP iterated S2K, so the passphrase is **server-generated with 120 bits of entropy** rather than user-chosen (the UI no longer asks for one). Backups made by R01 (custom format, never released) are intentionally unreadable.
- **Proof (`BackupCryptoTests`, 22):** sizes round-trip (0, 1, 63 KiB … odd); **96 MiB streaming round-trip with deep tamper detection**; real **GnuPG 2.4.9 decrypts our backup with the recovery key, and we decrypt what GnuPG encrypts to our key** (the test fails loudly, not skips, if gpg is missing); OpenPGP packet structure; wrong key / wrong passphrase; public key cannot decrypt; tamper/truncation/append/swap; non-backup and retired ALVBK files rejected; recipient id readable without secrets; destination I/O fault passthrough.

### ALV-N004-R01-04 — deployment invariants are part of "full state"
- New asset class `deploymentConfiguration` (`ManagedAssetClasses.All` now has 4): an **allowlisted, non-secret** `deployment-settings.json` (`PracticeTimeZone`, effective Data Protection application name, currency) — never the raw configuration/environment; machine paths are rebound by the operator.
- Recovery **blocks** unless the backup records them (`deployment_settings_recorded`) and this server matches (`deployment_settings_match_this_server`), with the exact lines to apply (`Set PracticeTimeZone = … and DataProtection:ApplicationName = …`).

Intentional change: one-shot `Deployment:AdoptCurrentSettings=true` (logged).
- Coverage/status report a backup lacking the class as incomplete (`MissingAssetClasses`).

## Scope, decisions, limitations
- Unchanged from R01 and accepted by the reviewer: SQL Server `BACKUP`/`RESTORE`, isolated-target-only restore with deliberate offline promotion, tiered verification, probation, durable idempotent scheduling, retention, notifications, audit/permission/CSRF/step-up boundaries.
- Decision: archive restore is offered only for restore drills (no "verify only"), because verification state is a property of a history row.
- Limitation: MDC-based integrity rather than AEAD (see R01-02). Limitation: gpg is required on the machine running the crypto test suite (Git for Windows ships it).
- `deployment_settings_match_this_server` also applies to "Verify only"/drills of ordinary history backups on the same server; on the original server it always passes.
