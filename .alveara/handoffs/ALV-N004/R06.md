- **The flaky test, fixed at its cause.** First attempt (rejected by evidence): raising the Testing Library wait budget to 10 s and the test timeout to 30 s. Under load that did not cure it - 2 of 16 loaded runs still failed, and now after the full 10 s, proving the expected element never appears rather than appears slowly (`test-runs/stress-summary.txt`, `after-timeout-attempt-failing-run-example.txt`); that change was reverted. Root cause, found by reading the failing DOM (the form was back at its original value, no "Unsaved changes", "Save settings" disabled) and `BackupRecoveryPage.tsx`: `load` depended on `canManage` (from the auth context, false while the permission set is still loading), so when the permission set arrived after the first load, `load` changed identity, the effect re-ran `load(true)`, the page showed its loading state and **unmounted the settings form, discarding what the user had typed**. The form could even appear for an instant from the first load's data and vanish. `src/alveara-client/src/pages/BackupRecoveryPage.tsx`: `load` now reads `canManage` through a ref (stable identity, so the blocking initial load runs once) and a permission change after the first load triggers an in-place refresh (`load(false)`), which never unmounts the page.
- `src/alveara-client/src/pages/BackupRecoveryPage.test.tsx`: one new deterministic test, "keeps an edit in progress when the permission set arrives after the first load" (the permissions answer only after the first status load is served, the follow-up status request is held until the test releases it; it asserts the form is the same element with the edit intact while the follow-up load is in flight). **It fails 3 of 3 against the old page**, each time differently (element detached, label not found). The existing tests are unchanged.
- No markup, component API, behaviour, token or backend change.
