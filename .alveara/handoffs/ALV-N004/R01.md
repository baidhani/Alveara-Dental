## Scope delivered

**Encryption and recovery-material strategy** (`BackupCrypto`): AES-256-GCM (platform `AesGcm`) for content; a fresh random data key per backup wrapped with RSA-3072/OAEP-SHA256 (platform `RSA`) to a **recovery public key**. The server stores only the public key, so it can create every unattended backup but can never decrypt one. The private half is generated once, exported already passphrase-encrypted (platform PBES2/PBKDF2-SHA256 600k + AES-256), shown to the administrator once for **offline custody**, and never stored, logged, audited, echoed, or placed in any backup. No home-grown primitive, KDF, or cipher exists; the only code written is the minimal chunk framing for applying AES-GCM to large files (the standard STREAM construction: per-chunk nonce = random prefix‖counter, AAD binds header hash, chunk index, length and a final-chunk flag, so reorder/truncate/extend/header-tamper all fail authentication).

**Backup set** (`BackupService`): one `.abk` file = ZIP (SQL Server `BACKUP DATABASE`, every registered `IBackupAssetSource` — documents and Data Protection keys — and `manifest.json` with per-file SHA-256, schema migration, app version, table row counts before/after the snapshot) encrypted as above; written to `.partial` and atomically moved, so a crash never leaves a file under the real name. A new asset class registers a source and a name in `ManagedAssetClasses`; the UI/API report whether the last backup covers every currently managed class.

**History and truthful state** (`BackupRecord`/`RestoreDrillRecord`/`BackupNotificationRecord`, migration `AddBackupAndRecovery`): success, verification (`NotVerified`/`HashVerified`/`FullyVerified`/`VerificationFailed`) and failure are separate facts; a failure is the page headline even if an older success exists; history rows are never deleted (retention marks `Purged` and deletes the file; the newest fully-verified backup is never purged).

**Scheduling, retry, idempotency**: `BackupScheduler` enqueues a durable job per schedule slot (key `backup:scheduled:{h}h:{slot}`) so polling twice/two servers/a restart yield one job; `ScheduledBackupJobHandler` runs the backup in its own scope with the job's key as the `BackupRecord` idempotency key (a Succeeded row is a no-op, a Failed/stale row is retried in place) — the documented external-effect contract. `RecoverInterruptedAsync` marks abandoned runs Failed(`interrupted`) and removes scratch.

**Verification and restore** (`BackupRestoreService`): preflight (backup/file/hash/recovery-material match), hash verification (no key), full verification (decrypt + inventory + `RESTORE VERIFYONLY`), and a **restore drill** that restores **only into a new, differently-named database plus private folder** (`SqlServerRestoreProvider` refuses an existing database; there is no live-overwrite code path or endpoint), then validates: format and schema compatibility (a schema newer than this build is rejected before anything is restored), document completeness, component hashes, restored schema, row counts within the snapshot window, representative records, and that the **restored key ring decrypts the restored MFA secrets**. A failed drill removes everything it created, records a stable code, audits and notifies.

**Notifications**: every success/failure/verification failure/drill failure creates a notification record and is delivered through `IBackupNotifier` (default: a drop file in a local folder). Delivery failure is recorded on its own and never changes a backup's status; a test endpoint proves the channel.

**API** `api/backup/*` (`BackupController`): `ManageBackups` (Admin) for settings, recovery key, manual backup, verification, preflight, drills, remove-target, test notification; `ViewBackupStatus` (Admin, OfficeManager) for status/history/notifications. Setting up the key, preflight, verification, drills and removing a target additionally require the caller's **current password** through the shared lockout boundary (`AccountService.ReauthenticateAsync`, a wrong password audited as `SensitiveActionStepUpFailed`). Recovery material is accepted only in request bodies. Failures return stable codes with fixed messages, never exception text or paths. Every sensitive action is audited through the shared audit path.

**UI** (`/admin/backup`, nav "Backup & Recovery", gated on `ViewBackupStatus`): status panel (last success/failure, schedule, storage target, verification, probation, overdue, asset coverage; prominent failure), manual backup, recovery-key setup (shown once, acknowledgement required, cleared, never stored), settings form (validation, unsaved protection, conflict banner), history (separate success/verification columns), the **restore wizard** (explicit target, compatibility and recovery-material checks, verify-only or isolated restore, session-bound, material cleared on close), drills list with password-protected target removal, notifications.

**Runbook**: `docs/operations/BACKUP_AND_RECOVERY.md` — what is backed up, key strategy, setup, verification levels, probation, the restore drill procedure, starting the recovered application, offline promotion for disaster recovery, failure reference.

## Architecture / schema / API / UI / security / config / measurement changes

- **Schema:** one migration (4 tables: `BackupSettings`, `BackupRecords` with unique idempotency key, `RestoreDrills`, `BackupNotifications`). **Config:** optional `Backup:Root|Directory|StagingRoot|RestoreRoot|NotificationDirectory`. **Permissions:** `ManageBackups`, `ViewBackupStatus` appended. **Audit events:** `BackupCreated/Failed/HashVerified/FullyVerified/VerificationFailed/PurgedByRetention`, `RestoreDrillCompleted/Failed`, `RestoreTargetRemoved`, `RecoveryKeyConfigured`, `BackupSettingsChanged`, `BackupTestNotificationSent`, `SensitiveActionStepUpFailed`.
- **Data Protection application name is now fixed** (`Alveara.Dental`). Without it the framework isolates keys by install path, so a backup restored to another folder/server could not decrypt its MFA secrets. **Consequence for any pre-existing development database:** MFA secrets protected before this change used the old (path-derived) discriminator and would need re-enrollment; no production data exists yet. The restore validation and the full-state drill prove the restored key ring works.
- **Measurement events:** none (no agreed success metric depends on backups).

## Key decisions

1. **Public-key envelope, not a server-held secret.** The user story requires unattended scheduled backups *and* that recovery material not exist only inside the backups. A server-held key would make unattended backups easy but would mean the server (and anyone who compromises it) can read every backup and that losing the server loses the key; instead the server can only encrypt. Cost: nobody — including the developers — can recover a backup without the offline key file and passphrase, which the UI and runbook state prominently.
2. **Restore only ever creates an isolated copy; promotion to production is an offline, documented procedure.** The story says restore must not overwrite active data "without an explicit protected workflow". I interpreted the protection as *not offering an in-app overwrite at all* (the safest reading); the "explicit workflow" is the runbook's deliberate offline promotion, which needs the offline recovery key. This is the interpretation most worth the reviewer's attention.
3. **What "verified" means is tiered and never overstated** (see runbook): hash-only is labelled as such; only decrypt + inventory + SQL media check, or a real drill, is "fully verified" — and only those count toward probation.
4. **Row-count validation is a window, not equality**: counts are taken immediately before and after the SQL snapshot, and a restored table must fall between them, so a live system writing during a backup does not cause false failures.
5. **Schema policy:** a backup from a schema unknown to this build (newer) is rejected before restore; an older one restores and is upgraded by the application's normal migrations when promoted.
6. **Manual backup runs inside the request** (single practice, modest database); scheduled backups run through the job mechanism. Both use the same idempotent service.
7. **Failure notifications are per failed attempt** (a retrying scheduled backup can notify more than once); delivery failures are recorded separately.

## Review-relevant limitations / unresolved questions

- **Custom framing around platform cryptography.** The story forbids "custom cryptographic formats". Every primitive is platform AES-GCM/RSA-OAEP/PBES2, but applying AES-GCM to multi-gigabyte files needs a chunk framing, which I had to write (documented in `BackupCrypto`, with tamper/truncate/extend/reorder/wrong-key tests). If the reviewer requires an off-the-shelf container format instead, that is a contained change behind `BackupCrypto.EncryptAsync/DecryptAsync`.
- Restore targets live on the same SQL Server instance as production (isolated by database name and folder); restoring onto a different server is the offline runbook procedure.
- **Off-site targets** and cloud DR are out of scope as specified; the destination is a local folder.
- **Staging/restore folders must be readable and writable by the SQL Server service account** (LocalDB runs as the user, so tests pass trivially; a service-account SQL Server needs the folder permissions noted in the runbook).
- Notifications are a local drop-file channel; email/Windows Event Log are future channels behind `IBackupNotifier`.
- The Data Protection application-name change is a breaking change for any pre-existing development MFA secrets (see above).
