# Decisions requested from the reviewer - ALV-N016 R02 (read this first)

R01 was returned `CHANGES_REQUIRED` for one reason: the formal Stage 2 backend run took 3,466 s against the 3,300 s ceiling. R02 is a Stage 1 package that corrects that. **Three things need the reviewer's decision, one of them before anything else.**

## 1. May the 13 rollback classes start from a clone? (needs approval: it relaxes a rule the reviewer set)

The approved prompt says to keep an explicit named inventory of migration and rollback tests that bypass the template and retain the real create-and-migrate path. R02 changes that for the 13 classes whose subject is rolling the schema back and forward, **because it is the only lever that measured large enough** (the others measured nothing, see the experiments below).

- **What stays on the real create-and-migrate path (6 classes, named in `RealMigrationInventory`):** `MigrationTests` and `MigrationUpgradeTests` (the migration pipeline from an empty database) and `TestDatabaseInitFailureCleanupTests`, `TestDatabaseLocationTests`, `TestDatabaseTeardownTests`, `TestDatabaseTransientRetryTests` (the fixture itself).
- **What changes (13 classes, still named and guarded):** `BillingRefundMigrationTests`, `CompletedProcedureMigrationTests`, `CompletionAdoptionSchemaTests`, `CompletionChartEvidenceTests`, `DiagnosisMigrationTests`, `DiagnosisStructureMigrationTests`, `DocumentLibrarySchemaTests`, `DocumentSchemaTests`, `OdontogramCatalogueMigrationTests`, `PerioMigrationTests`, `PrescriptionSchemaTests`, `PrescriptionWorkflowSchemaTests`, `TreatmentPlanRevisionMigrationTests`. Their database now starts as a clone of the run's template. **Every rollback and upgrade they perform still runs the real Down and Up migrations through `IMigrator`** (the inventory guard fails if a class stops calling the migrator).
- **What is still proved from empty with real migrations:** the template itself is built from an empty database by the real migrations at the start of every run and verified (ordered history, `READ_COMMITTED_SNAPSHOT`); the migration pipeline classes above still create and migrate their own database.
- **A direct equivalence proof:** `A_clone_can_be_rolled_back_through_the_real_migrator_and_forward_again_to_exactly_the_same_schema`: a clone rolled back ten migrations through the real migrator and forward again has exactly the schema (every column, index, check constraint, trigger body, foreign key, migration-history row and seed row count) it had before, and exactly that of a real create-and-migrate database.
- **Measured effect, same 250 tests of those 13 classes:** 666 s on the real path (2.66 s per test) and **184 s on clones** (0.74 s per test), all 250 passing, 0 fallbacks, leak counts unchanged (`artifacts/rollback-on-clones-ab/`): a saving of 482 s (8.0 min). Applied to R01's 3,466 s that projects to about 2984 s (49.7 min).
- **If the reviewer does not approve this**, R02 has no other correction measured to be large enough and the 55-minute ceiling is unlikely to be met inside this boundary (see the experiments).

## 2. A flaky failure in production billing code (the reviewer may want it handled before Stage 2)

During the unplanned full run (section 3) one test failed: `GateDHistoryIntegrityTests.D5_financial_history_survives_duplicate_submissions_corrections_stale_edits_and_direct_overwrite`. It starts two simultaneous payments from the same account version and asserts that exactly one succeeds and one gets a `ConcurrencyConflictException`; this time one of the two threw `KeyNotFoundException` from `BillingService.Ledger.MathAllocations` (`BillingService.Ledger.cs`): `LoadLedgerAsync` reads the ledger entries, the allocations and the releases in three separate queries with no shared snapshot, so an allocation committed by the other request between the first and second query refers to an entry the first query did not see. It is a production race, not a test-infrastructure problem: the same test passed 25 of 25 runs in isolation and in every earlier full run (this was the first failure in five full runs on this machine). It could fail the formal Stage 2 at random ("zero failures" is a frozen criterion). **Fixing it is a production change (billing, high risk) outside this story's boundary**, so R02 does not touch it. The reviewer is asked how to treat it: for example a separately reviewed billing correction first, or a stated rule for how a Stage 2 failure confined to this one test is judged.
