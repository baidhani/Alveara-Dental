## Corrections made

### ALV-001-C01-R02-01 — durable, atomically-consumed MFA challenges

New `MfaChallenge` entity (`Id`, `UserAccountId`, `SecurityStamp`, `ExpiresAtUtc`, `ConsumedAtUtc`) is now the authoritative, durable record of an in-flight challenge. `IssueMfaChallenge` (renamed from `IssueMfaChallengeToken`, now private — `LoginAsync` is its only caller) inserts this row in the same transaction as the login's audit entry; the protected token carries the challenge's `Id` (plus a stamp/expiry copy for a fast, DB-free rejection of an obviously tampered or clock-expired token — defense in depth, not the authority).

`CompleteMfaChallengeAsync` verifies the submitted code *first* (so a wrong guess never burns the challenge — a user can still retry after a typo), then atomically marks the challenge consumed via a single conditional `ExecuteUpdateAsync` (`WHERE ConsumedAtUtc == null`, via the new private `TryConsumeChallengeAsync` helper) before granting the session. A losing racer in a concurrent duplicate submission affects zero rows and is rejected (`InvalidOrExpiredMfaChallengeException` — the same exception as any other invalid/expired/replayed case, never distinguishing *why*). This applies identically to both the TOTP path and the recovery-code path — replaying a consumed challenge with a *different* valid recovery code also fails, since the challenge itself, not just the individual code, is what's spent.

New tests: `Replaying_the_exact_same_successful_TOTP_challenge_submission_is_rejected`, `Two_concurrent_submissions_of_the_same_successful_challenge_produce_exactly_one_success` (a real two-`DbContext` race), `Replaying_a_challenge_already_completed_via_a_recovery_code_is_rejected`, `An_expired_challenge_cannot_be_completed_even_with_the_correct_code`, `A_revoked_challenge_row_cannot_be_completed`. Also a new real-backend Playwright test, `replaying the exact same successful MFA challenge submission is rejected, not accepted twice`, directly reproducing the reviewer's own live HTTP-level reproduction against a real API and database.

### ALV-001-C01-R02-02 — step-up password check shares the login lockout boundary

Extracted two private helpers from `LoginAsync`'s previously-inline lockout logic — `RearmAndCheckLockoutAsync` (clears a stale lock and reports current lockout state) and `RecordFailedAuthenticationAttemptAsync` (atomically increments the shared `FailedLoginAttempts` counter and locks the account if the threshold is crossed) — and refactored `LoginAsync`'s own failure path to use them (behavior-preserving; all existing lockout tests still pass unmodified). `BeginMfaEnrollmentAsync`'s step-up check now calls both: a currently-locked account is rejected before even attempting the password comparison, and a wrong step-up password counts toward (and can trigger) the exact same lockout a wrong login password would, audited under a distinct `MfaStepUpFailed` event type so a reader can still tell the two apart. A correct step-up password resets the counter, matching a successful login's own convention. `POST /api/auth/mfa/enroll` also gained `[EnableRateLimiting("AuthAttempts")]`.

New tests: `Repeated_wrong_current_passwords_during_MFA_replacement_lock_the_account_like_a_failed_login_would`, `Failed_login_attempts_and_failed_MFA_step_up_attempts_share_the_same_lockout_counter`, `A_currently_locked_account_cannot_use_MFA_replacement_step_up_either`, `A_correct_step_up_password_resets_the_shared_failed_attempt_counter`, plus an HTTP-level `Repeated_MFA_replacement_step_up_attempts_past_the_limit_are_also_throttled` in `AuthRateLimitTests.cs`.

### Incidental fix (test-only, not production code)

While building the concurrent-replay test, hit the same "two independently-constructed `EphemeralDataProtectionProvider` instances can't decrypt each other's data" pitfall already fixed once in R01/R02 for a different concurrency test — fixed identically, by sharing one provider instance across the racing service instances (matching production, where the provider is a real DI singleton).
