## R05 review decision being corrected

`CHANGES_REQUIRED`, two findings, both P1 evidence gaps (full text in `.alveara/reviews/ALV-001-C01/R05.md`):

1. **ALV-001-C01-R05-01** (P1, evidence gap) — the step-up concurrency test started two uncontrolled tasks and accepted either outcome, with no barrier controlling whether the fifth failure locked before or after the step-up's conditional reset, and no assertion proving both branches actually ran. Repeated uncontrolled runs could all take the same benign step-up-first path without ever exercising the stale-success rejection.
2. **ALV-001-C01-R05-02** (P1, evidence gap) — the recovery-code rollback tests could pass without executing the rollback branch: the deterministic reproduction marked the code used via a raw write *before* calling the service, which the service's own `UsedAtUtc == null` query then silently excluded (so it never attempted that code at all); the two-context race test had no coordination forcing both requests to observe the code as unused before either consumed it, so the losing side could likewise bypass the branch and still show a compatible final state.

## Corrections made

Both findings are evidence gaps, not production-code defects - the review's own "non-blocking observations" explicitly noted "the production changes for both findings are consistent with the required design on source inspection." The correction adds the deterministic proof the reviewer required, per their explicit authorization to "use a narrow test seam/interceptor... do not redesign the identity system."

### Three new test-only coordination seams on `AccountService`

All three are `internal Func<Task>?` properties, visible to `Alveara.Api.Tests` via the assembly's existing `InternalsVisibleTo`, null (and therefore a complete no-op) unless a test explicitly sets them:

- `TestHook_BeforeStepUpConditionalReset` — awaited in `BeginMfaEnrollmentAsync` immediately before the correct-step-up path's conditional lockout-counter reset.
- `TestHook_AfterRecoveryCodeVerifiedBeforeConsumption` — awaited in `CompleteMfaChallengeAsync`'s recovery-code branch immediately after a submitted code's hash verifies, before either the challenge or the code is consumed.
- `TestHook_AfterRecoveryCodeConsumedBeforeCommit` — awaited immediately after both the challenge and recovery-code conditional updates have succeeded, before the transaction commits.

### ALV-001-C01-R05-01 — step-up race now deterministically forces both orderings

`A_correct_step_up_deterministically_loses_when_the_fifth_failure_locks_the_account_first` uses `TestHook_BeforeStepUpConditionalReset` (a `SemaphoreSlim` pair) to pause the correct step-up immediately before its conditional reset, let a concurrent fifth failing login run to full completion and lock the account, then resume the step-up - proving it observes the lock (zero rows affected, `AccountLockedOutException`, no pending secret or pending recovery codes, `FailedLoginAttempts == 5`).

`A_correct_step_up_that_completes_first_resets_the_counter_and_a_later_failure_is_recorded_fresh` proves the other ordering purely sequentially (no coordination needed - letting one request finish before starting the next is deterministic by construction): the step-up completes and resets the counter first, then the later failure is asserted to land on the fresh counter (`FailedLoginAttempts == 1`, not locked), proving it is genuinely recorded, not lost.

### ALV-001-C01-R05-02 — recovery-code rollback now provably enters the critical branch

`Two_distinct_challenges_racing_the_same_recovery_code_deterministically_leave_one_success_and_the_loser_rolled_back` uses `TestHook_AfterRecoveryCodeVerifiedBeforeConsumption` to pause the loser immediately after it verifies the shared code's hash (before consuming anything), let the winner (a different challenge, same code) run to full completion, then resume the loser - which consumes its own challenge (succeeds, different row) and then the recovery-code update (now provably zero rows), rolling back. Asserts exactly one success, one `MfaChallengeFailed`, one consumed challenge, and confirms the loser's challenge is genuinely still completable afterward with a different code.

`A_failure_between_both_conditional_updates_and_commit_rolls_back_both_challenge_and_recovery_state` uses `TestHook_AfterRecoveryCodeConsumedBeforeCommit` to inject a synthetic exception after both conditional updates succeed but before commit, then asserts both the challenge and the recovery code are still unconsumed afterward (the transaction's own uncommitted disposal rolled both back together) and that the challenge remains completable.

Each of the four new/rewritten tests was run 3 consecutive times locally in isolation before inclusion in the full suite run reported here; all passed identically each time.
