## Scope

### Backend (`src/Alveara.Api`)

- **`AccountService.cs`** (rewritten): `RegisterAsync` no longer accepts a role — self-registration always produces `Role.Unassigned` + `IsDisabled = true`; only an authorized admin action (`ChangeRoleAsync` + `SetAccountEnabledAsync`) makes an account usable. `BootstrapFirstAdminAsync` provisions exactly one admin via a fixed-PK `BootstrapState` singleton row — the database's own primary-key uniqueness (not application check-then-act) makes "exactly once, even under a concurrent race" true. `LoginAsync` rewritten with: a stale-lockout rearm step (atomic conditional `ExecuteUpdateAsync`) that runs before anything else; a wrong-password failure path whose lockout-set is itself conditional on "not already actively locked"; a correct-password success path whose counter-reset/lock-clear is conditional on the same thing, so a concurrent failing request that wins the race cannot be silently overridden by a stale success; and a fixed dummy-hash `Pbkdf2PasswordHasher.Verify` call for unknown usernames so that branch pays the same cryptographic cost a real verification would. MFA methods (`BeginMfaEnrollmentAsync`, `ConfirmMfaEnrollmentAsync`, `IssueMfaChallengeToken`, `CompleteMfaChallengeAsync`) and password-reset methods (`IssuePasswordResetTokenAsync`, `ResetPasswordAsync`) are new. `SetAccountEnabledAsync` and `RevokeAllSessionsAsync` are new.
- **`Totp.cs`** (new): hand-rolled RFC 6238 TOTP (HMAC-SHA1, 30s step, 6 digits, ±1 step clock-skew tolerance) — no external package, no network call at enroll/challenge/verify time, satisfying the story's "at least one MFA factor that works with no public internet" requirement directly.
- **`BootstrapState.cs`, `MfaRecoveryCode.cs`, `PasswordResetToken.cs`** (new entities) plus `IdentityEntities.cs` additions to `UserAccount` (`IsDisabled`, `SecurityStamp`, `MfaEnabled`, `MfaSecretProtected`) and `Role.Unassigned` (appended at the end of the enum so it never disturbs STORY-001's already-persisted ordinals).
- **`Permission.cs` / `PermissionMatrix.cs` / `RequirePermissionAttribute.cs`** (new): a named-permission matrix mapped to the story's seven roles (dentist, hygienist, assistant, front desk, billing, office manager, admin), replacing the single `[Authorize(Roles=Admin)]` gate on every security-administration endpoint. Also names clinical/scheduling/billing permissions no module enforces yet, so a future module authorizes against this same matrix instead of inventing its own role checks.
- **`RequireCsrfTokenAttribute.cs`** (new): double-submit CSRF check via ASP.NET Core's built-in `IAntiforgery`, applied to every `[Authorize]`-protected state-changing endpoint.
- **`AuthController.cs`** (rewritten): `register` (no role field), `bootstrap-admin`, `login`, `mfa/challenge`, `logout`, `whoami`, `csrf-token`, `mfa/enroll`, `mfa/confirm`, `permissions` (new — caller's own role + granted permissions), `permission-matrix` (new — the full role→permission table, itself gated by `ViewPermissionMatrix`), `users` (list), `{userId}/role`, `{userId}/enabled`, `{userId}/reset-password`, `reset-password/complete`, `{userId}/revoke-sessions`. Every unauthenticated auth-attempt endpoint (`register`, `bootstrap-admin`, `login`, `mfa/challenge`, `reset-password/complete`) carries `[EnableRateLimiting("AuthAttempts")]`.
- **`Program.cs`**: `AddDataProtection` (MFA-secret-at-rest protection and self-contained MFA challenge tokens), `AddAntiforgery`, cookie options gained explicit `HttpOnly`/`SameSite=Strict`/environment-appropriate `Secure` plus an `OnValidatePrincipal` handler that rejects any session whose `security_stamp` claim no longer matches the account's current value in the database (real server-side "sign out everywhere" with no server-side session store), and `AddRateLimiter` (sliding window, IP-partitioned, configurable via `AuthAttemptRateLimit:PermitLimit`/`:WindowSeconds`).
- **Migration `20260929173614_AddMfaSecurityAndBootstrap`**: the four new `UserAccount` columns plus the three new tables.

### Frontend (`src/alveara-client`)

- **`services/authApi.ts`** (new): typed client for every endpoint above, cookie-auth (`credentials: "include"`), CSRF-token attachment on state-changing calls.
- **`contexts/AuthContext.tsx`** (new): re-derives session state from `GET /api/auth/permissions` on every mount rather than trusting stale client state (the server's SecurityStamp revocation can invalidate a session this client doesn't know about yet); exposes `hasPermission()`.
- **`pages/LoginPage.tsx`**: distinct, honest messaging for invalid credentials, disabled account, lockout (with expiry), rate-limiting, and a `?reason=expired` session-expired banner.
- **`pages/MfaChallengePage.tsx`**: one field accepts either a live TOTP code or a one-time recovery code.
- **`pages/ResetPasswordPage.tsx`**: completes an admin-issued reset token.
- **`pages/AdminUsersPage.tsx`**: user list (username/role/status/MFA-state columns) with role-change, enable/disable, issue-password-reset, and revoke-sessions actions, each permission-gated via `hasPermission()`.
- **`components/PermissionDenied.tsx`** (new): the story's "clear permission-denied presentation," shown instead of a generic error when a caller's role lacks a required permission.
- **`App.tsx`** / **`app/moduleRegistry.ts`**: new routes wired; Security Administration added to the nav registry unconditionally, matching this repo's existing pre-`ALV-N009` convention (nav-level permission filtering is explicitly that story's job) — `AdminUsersPage` enforces its own permission check regardless of whether the link is shown.
- **`test/setup.ts`**: fixed a real test-infrastructure bug this surfaced — the shared fetch mock reused one `Response` instance across every call, which threw once a second consumer (the new `AuthContext` permissions check, alongside the pre-existing connection-status poll) tried to read its body a second time.

## Decisions

1. **Database PK uniqueness for bootstrap concurrency safety**, not application-level check-then-act — see `BootstrapState.cs`'s fixed singleton `Guid`. This is the only way to make "exactly once, even under a genuine concurrent race" a database-enforced guarantee rather than a race-prone application check.
2. **Hand-rolled RFC 6238 TOTP instead of an external NuGet package** — keeps the dependency surface small for a security-sensitive primitive and makes "no network call anywhere in the MFA path" directly inspectable in this repo's own code rather than trusting a third-party package's behavior.
3. **Admin-issued password reset instead of email/SMS** — the release has no configured email delivery and the story explicitly requires at least one recovery path that works with no public internet; an admin-issued, one-time, out-of-band token satisfies both constraints without inventing an email integration this release doesn't otherwise have.
4. **SecurityStamp-claim-validated-on-every-request instead of a server-side session store** — real "sign out everywhere" without adding new infrastructure; consistent with this repo's existing preference for stateless-where-possible services (see `BUILD_STATE.md`'s architecture notes).
5. **A genuine named-permission matrix, not a role-string rename** — `RequirePermissionAttribute` reads the matrix and enforces it at the API boundary; `AuthControllerPermissionMatrixTests` proves both an allowed and a denied case at the HTTP level, not just that the mapping data structure looks right in isolation.
6. **Security Administration added to the nav registry unconditionally** — matches this repo's own documented pre-`ALV-N009` convention (`moduleRegistry.ts`'s existing comment already states nav-level permission filtering is `ALV-N009`'s job); `AdminUsersPage` enforces its own permission check server-side and client-side regardless of the nav link's visibility, so this is not a security gap in the meantime.

## Limitations/debt

- The permission matrix's clinical/scheduling/billing permissions (`ViewPatientRecords`, `ManageClinicalNotes`, `ManageAppointments`, `ManageBilling`, etc.) are named now but not yet enforced anywhere, since no clinical/scheduling/billing module exists yet in this release. This is intentional — see Decision 5 — but means those specific permission assignments are currently unverified against real usage and may need adjustment once the modules that actually consume them land.
- Rate limiting is a blunt per-IP sliding window (default 10 requests/60s, configurable), not a more sophisticated per-account or adaptive scheme. Sufficient to satisfy the story's "rate-limit or throttle... as appropriate" requirement; a future story could tighten this if real-world usage shows it's too loose or too strict.
- `AdminUsersPage`'s "issue password reset" action surfaces the one-time raw token via an in-page toast notification (5s auto-dismiss) rather than a persistent, copy-friendly UI element. Functionally correct (the token is genuinely shown exactly once and never logged/stored), but a follow-up UI polish pass could make it easier for an admin to reliably capture the value before relaying it out-of-band.
- No dedicated Playwright/real-browser test was added for the new auth pages in this attempt; coverage is vitest/jsdom (unit/component level) plus the full backend API-level test suite. The existing real-browser accessibility/responsive suite (`e2e/`) was not extended to the new routes.
