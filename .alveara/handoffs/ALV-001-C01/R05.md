## Corrections made

### ALV-001-C01-R04-01 — step-up race test now genuinely reaches the lockout threshold

`A_correct_step_up_password_cannot_proceed_past_a_concurrent_failure_that_crosses_the_lockout_threshold` (`AccountServiceMfaTests.cs`) now primes exactly 4 failed attempts (asserted directly: `FailedLoginAttempts == 4`, `LockedOutUntilUtc == null`) and races the correct step-up against the genuine 5th failing attempt - the one that must be capable of actually crossing the threshold. Assertions were expanded beyond the prior attempt's pass/fail-shape check to the full outcome-specific invariants the R04 review asked for: when the step-up wins, the account has exactly 10 pending recovery codes, is not locked, and shows `FailedLoginAttempts == 1` (the fifth failure landing on the freshly-reset counter); when the lock wins, no pending secret or pending recovery codes exist and `FailedLoginAttempts == 5` with a non-null lockout. The fifth failing login's own result is also asserted to be exactly `InvalidLoginException` or `AccountLockedOutException` (never anything else), confirming it is a genuine, correctly-shaped participant in the race rather than a bystander. Ran 3 consecutive times locally with no flake before inclusion.

### ALV-001-C01-R04-02 — losing challenge in a two-challenges-one-code race is rolled back, not silently burned

`CompleteMfaChallengeAsync`'s recovery-code branch (`AccountService.cs`) now calls `transaction.RollbackAsync` - rather than committing - when the recovery-code conditional update affects zero rows. This undoes that specific attempt's own challenge consumption along with the no-op recovery-code update, so a losing request in a two-challenges-one-code race is never left with a silently-consumed challenge that has no owning success or failure audit. The loop then continues to the next candidate code (if any); if none match, the pre-existing final `failureTransaction` records exactly one `MfaChallengeFailed` audit for the loss, and the losing challenge remains genuinely unconsumed and reusable with a different valid code afterward.

New tests: `Two_distinct_challenges_racing_the_same_recovery_code_leave_exactly_one_success_and_the_losing_challenge_unconsumed` - a real two-`DbContext` race between two independently-issued challenges submitting the same recovery code, asserting exactly one success (`MfaRecoveryCodeUsed`/`LoginSucceeded`), exactly one `MfaChallengeFailed`, exactly one consumed recovery code, and exactly one consumed / one unconsumed `MfaChallenge` row afterward. `When_a_recovery_code_race_is_lost_the_losing_challenge_can_still_be_completed_afterward_with_a_different_code` - a deterministic (non-racing) reproduction of the losing branch, proving the challenge is genuinely rolled back to a completable state, not merely audited-then-abandoned.
