## Corrections made

### ALV-001-C01-R03-01 — correct step-up path now checks its conditional reset's affected-row count

`BeginMfaEnrollmentAsync`'s correct-password branch (`src/Alveara.Api/Architecture/Identity/AccountService.cs`) now captures the row count of its conditional `FailedLoginAttempts`/`LockedOutUntilUtc` reset (the same `ExecuteUpdateAsync`, `WHERE u.LockedOutUntilUtc == null || u.LockedOutUntilUtc <= UtcNow`, that already existed) and, if it affected zero rows, reloads the authoritative lock state and throws `AccountLockedOutException` — exactly mirroring `LoginAsync`'s own success path (`rowsCleared == 0` check). No pending MFA secret or recovery-code set is generated or persisted on this path; the method returns before reaching that code.

New test: `A_correct_step_up_password_cannot_proceed_past_a_concurrent_failure_that_crosses_the_lockout_threshold` — a real two-`DbContext` concurrency test. It primes the account to three failed attempts (one below the five-attempt threshold), then races a correct-password step-up (`serviceA`) against a wrong-password login (`serviceB`) that crosses the threshold. It asserts only the two permitted outcomes: the step-up completed (no exception, and a pending MFA secret now exists), or the lock won the race (`AccountLockedOutException`, and no pending MFA secret was created).

### ALV-001-C01-R03-02 — challenge consumption, code consumption, and audit are now one transaction; replay rejection is audited

`CompleteMfaChallengeAsync` now opens its transaction *before* calling `TryConsumeChallengeAsync`, so the conditional challenge-consumption `ExecuteUpdateAsync` participates in the same ambient transaction as the audit write that follows — a rollback undoes both together. This applies to both the TOTP path and the recovery-code path (where challenge consumption, recovery-code consumption, and the audit write are now all inside the one transaction opened for that attempt).

When `TryConsumeChallengeAsync` returns false (the challenge was already consumed, expired, or revoked), the method now writes a new `MfaChallengeReplayRejected` audit entry (`AuditLogEntry.cs`) before throwing the same public `InvalidOrExpiredMfaChallengeException` it always threw — the audit entry's message never includes the token or the submitted code, and is worded identically regardless of which of the three causes applied, matching the exception's own refusal to disclose why.

New tests: `Replaying_a_consumed_TOTP_challenge_writes_a_privacy_safe_rejection_audit_entry_with_no_extra_success_audit` (sequential replay — asserts exactly one success audit, one `LoginSucceeded`, and one `MfaChallengeReplayRejected`, and that the rejection's `Details` never contains the code or token), `Two_concurrent_submissions_of_the_same_successful_challenge_leave_exactly_one_success_audit_and_one_rejection_audit` (concurrent replay — same assertions, against two real racing `DbContext`s), and `Replaying_a_challenge_already_completed_via_a_recovery_code_writes_a_rejection_audit_entry` (recovery-code path — also confirms the second, unused recovery code is never consumed by the rejected replay).
