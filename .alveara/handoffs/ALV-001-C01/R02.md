## R01 review decision being corrected

`CHANGES_REQUIRED`, five findings, all P1 (full text in `.alveara/reviews/ALV-001-C01/R01.md`):

1. **ALV-001-C01-R01-01** — `BeginMfaEnrollmentAsync` replaced the active TOTP secret and deleted all recovery codes before any replacement factor was confirmed; an authenticated session could disable a confirmed MFA factor just by starting re-enrollment and abandoning it.
2. **ALV-001-C01-R01-02** — the MFA challenge payload wasn't bound to the account's `SecurityStamp`, so a challenge issued before a password reset or explicit session revocation remained usable to mint a new session for up to 5 minutes afterward.
3. **ALV-001-C01-R01-03** — `Totp.cs` was a hand-rolled TOTP/Base32 implementation, contrary to the project's proven-cryptography rule.
4. **ALV-001-C01-R01-04** — MFA/recovery lifecycle events weren't audited, and `LoginSucceeded` was recorded before the second factor was actually verified.
5. **ALV-001-C01-R01-05** — no MFA enrollment/replacement UI, no permission-matrix UI, no authorized session-timeout configuration UI/API, and no live-browser demonstration of the security-administration UI.

## Corrections made

### ALV-001-C01-R01-01 — pending-enrollment model, atomic promotion

`UserAccount` gained `PendingMfaSecretProtected`; `MfaRecoveryCode` gained `IsPending`. `BeginMfaEnrollmentAsync` now writes only to the pending fields (via `ExecuteUpdateAsync` — see the tracking note below) and never touches `MfaSecretProtected`/`MfaEnabled`/the active recovery-code set. `ConfirmMfaEnrollmentAsync` verifies the submitted code against the *pending* secret, then atomically promotes it (`ExecuteUpdateAsync` gated on `PendingMfaSecretProtected` still equalling the value read at the start of the call — a losing racer's zero-row update is treated as "nothing pending," so two concurrent confirmations apply at most once), deletes the previously-active recovery codes, and promotes the pending ones. Replacing an already-active factor additionally requires the caller's current password (`BeginMfaEnrollmentAsync(userAccountId, currentPassword, ct)`; `CurrentPasswordRequiredToReplaceMfaException` / `InvalidCurrentPasswordException`). New tests: `Starting_re_enrollment_does_not_disable_the_already_established_factor`, `Replacing_MFA_requires_the_current_password_and_the_wrong_password_is_rejected`, `Confirming_a_replacement_atomically_swaps_the_factor_and_recovery_codes_and_rotates_the_security_stamp`, `Two_concurrent_confirmations_of_the_same_pending_enrollment_apply_at_most_once`.

### ALV-001-C01-R01-02 — challenge bound to SecurityStamp

`MfaChallengePayload` gained `SecurityStamp`; `IssueMfaChallengeToken` now takes it as a parameter and `LoginAsync` passes the account's current stamp; `CompleteMfaChallengeAsync` rejects (with the same `InvalidOrExpiredMfaChallengeException` as any other invalid/expired case — never revealing *why*) if the account's current stamp no longer matches. Since `ChangeRoleAsync`, `SetAccountEnabledAsync`, `ResetPasswordAsync`, `RevokeAllSessionsAsync`, and now `ConfirmMfaEnrollmentAsync` (on a replacement) all rotate the stamp, every one of those operations implicitly invalidates any outstanding challenge. New tests: `An_MFA_challenge_issued_before_an_explicit_session_revocation_is_rejected_afterward`, `..._before_a_password_reset_is_rejected_afterward`, `..._before_a_role_change_is_rejected_afterward`.

### ALV-001-C01-R01-03 — Otp.NET replaces hand-rolled crypto

`Totp.cs` is now a thin wrapper over `Otp.NET` 1.4.1 (`Otp.NET` package, MIT-licensed, widely used, actively maintained — added via `dotnet add package Otp.NET`). Secret generation (`KeyGeneration.GenerateRandomKey`), Base32 encode/decode (`Base32Encoding`), and TOTP compute/verify (`OtpNet.Totp`) are all delegated; this file no longer implements HMAC-SHA1 dynamic truncation, RFC 4226 counter windowing, or Base32 encoding itself. Existing MFA tests continue to pass unmodified in behavior against the new wrapper.

### ALV-001-C01-R01-04 — MFA/recovery lifecycle audit, corrected LoginSucceeded timing

New `AuditEventTypes`: `PasswordVerifiedMfaPending`, `MfaChallengeSucceeded`, `MfaChallengeFailed`, `MfaRecoveryCodeUsed`, `MfaEnrollmentStarted`, `MfaReplacementStarted`, `MfaReplaced`, `SessionTimeoutChanged`. `LoginAsync`'s MFA branch now writes `PasswordVerifiedMfaPending` instead of `LoginSucceeded`; `LoginSucceeded` is written only by the paths that actually complete authentication (immediate non-MFA success, or `CompleteMfaChallengeAsync`'s TOTP/recovery-code success branches). A failed challenge writes `MfaChallengeFailed`. New tests: `Beginning_enrollment_writes_an_MfaEnrollmentStarted_audit_entry`, `Consuming_a_recovery_code_writes_an_MfaRecoveryCodeUsed_audit_entry_and_the_final_LoginSucceeded_only_fires_after_MFA`, `A_failed_MFA_challenge_writes_an_MfaChallengeFailed_audit_entry`.

### ALV-001-C01-R01-05 — MFA/permission-matrix/session-timeout UI, real-browser evidence

Three new pages: `MfaSettingsPage` (enrollment/replacement — the displayed secret/recovery codes are visibly inert until the confirmation code is submitted, matching the pending-enrollment model; step-up reauthentication is prompted when replacing an active factor), `PermissionMatrixPage` (the full role → permission table read directly from `GET /api/auth/permission-matrix`), `AdminUserDetailPage` (a real per-user detail view at `/admin/users/:userId`, reachable from a new "View" link on `AdminUsersPage`, including the new session-timeout control). New backend: `AccountService.SetSessionTimeoutAsync` (validated 5–1440 minutes, audited) and `PUT /api/auth/{userId}/session-timeout`.

**Real-browser, real-backend evidence** (the review's explicit requirement — component tests and route-mocked Playwright specs don't satisfy it): `e2e/auth-real-backend.spec.ts` + `playwright.auth.config.ts` (see `docs/testing/REAL_BACKEND_E2E.md` for exact run instructions) make genuine network calls from a real Chromium instance to a real running `Alveara.Api` process backed by a real migrated LocalDB database — no `page.route()` mocking anywhere in this file. All 5 tests pass against a freshly-provisioned database: registration-cannot-select-a-role, real bootstrap+login, real TOTP enrollment+confirmation+challenge completion (the confirming code is computed independently in the test via the Web Crypto API, not by calling into the app's own code — proving standards interoperability, not self-agreement), security-administration list/detail/session-timeout, and the permission-matrix page. See `R02-evidence/artifacts/playwright-real-backend/run-output.txt` for the raw run output.

**A genuine bug this real-backend run caught that no earlier test had** (worth naming directly, since it's exactly the class of defect the review's finding predicted mocked tests would miss): `authApi.ts`'s `request()` called `res.json()` unconditionally on any non-204 success response, but `POST /api/auth/mfa/confirm` and `POST /api/auth/logout` return `200` with an **empty** body (`Ok()`, not `Ok(someObject)`), which threw `SyntaxError: Unexpected end of JSON input` in the browser. Fixed by reading the response as text first and parsing only if non-empty. This is a direct, concrete demonstration of why the review's finding was correct to require real-browser/real-backend evidence.

### Incidental fixes made while correcting the above

Two "stale tracked entity" bugs in `AccountService`, both surfacing only when a `DbContext` is reused across multiple calls (every test in this project does exactly that, and would in principle affect any future code that reuses a scope — production's per-request scoped `DbContext` wouldn't normally hit this, but the fix is correct regardless): `BeginMfaEnrollmentAsync` and `CompleteMfaChallengeAsync` now load their account via `.AsNoTracking()`, matching `LoginAsync`'s existing convention, since their mutations go through `ExecuteUpdateAsync` (raw SQL, bypassing the change tracker) — a tracked copy left in the identity map by an earlier call (e.g. `ChangeRoleAsync` during test setup, or `BeginMfaEnrollmentAsync` itself before this fix) would otherwise shadow a later read with stale field values. Discovered directly by these fixes' own new tests failing with `MfaEnabled: False` immediately after a successful confirm, and by a `SecurityStamp` mismatch that shouldn't have been possible.
