## Root cause
`LoadLedgerAsync` read the entries, the allocations and the releases in three separate queries, each seeing what was committed at that moment. A payment committed by another request between the first and second query produced an allocation whose entry the first query did not return, and building the lookup threw `KeyNotFoundException`.

## Scope delivered
- **Correction:** every recorded change moves the account's row version in the same transaction, so the three reads are one coherent picture exactly when the version is equal before and after. The loader now compares the two and repeats the read (at most 4 attempts, then the existing `ConcurrencyConflictException`); the version query is one extra indexed read each side.
- **Deterministic proof:** 5 tests force the window (a competing payment commits between the queries). They fail 4 of 5 on the old code with `KeyNotFoundException` and pass on the fix.
- **Descendant revalidation** per reviewer point 4 and `HANDOFF_SCHEMA.md` section 7: `REVALIDATION_ASSESSMENT.md`; the eight listed descendants are marked `REVALIDATION_REQUIRED`; targeted evidence 409 of 409 and 1,379 of 1,379.

## Decisions and deviations
1. **Version bracketing rather than a transaction isolation change.** SNAPSHOT isolation needs a database option (a schema-level change) and REPEATABLE READ takes locks that can deadlock writers; the row-version bracket needs neither and uses the mechanism the ledger already relies on.
2. **A read can now end in `ConcurrencyConflictException`** only under sustained concurrent writes (4 consecutive changed reads); it maps to the existing 409.
3. **No full regression in Stage 1**, per the binding policy; the frozen contract counts 4,324 tests (4,300 baseline + 19 ALV-N016 + 5 new).
