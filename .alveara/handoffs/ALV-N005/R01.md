## Scope delivered (the prompt's implementation scope)
- **Stable internal procedure identity** - a GUID that never changes; the code system and code are the procedure's natural identity and are fixed once it exists (service refuses with `identity_fixed`; database trigger 51078).
- **Procedure code plus explicit code system/source, optional source/version metadata, effective period** - code systems `Local`, `CDT`, `External`; `SourceName` (required for any non-local system) and `SourceVersion` on each version; `EffectiveFrom` and optional `ValidThrough` on each version.
- **Description, fee, category** - on each version. Fee is US dollars, 0 to 1,000,000.00, at most two decimals (service and database). Ten generic categories.
- **Tooth/surface applicability** - a scope (whole mouth, arch, quadrant, tooth, tooth surface) and, for tooth-level scopes, a dentition (permanent, primary, both). A particular surface is not stored (see limitations).
- **Active/inactive and effective status/date strategy** - `Active`, `Inactive`, `Scheduled` (no version has started) and `Expired` (past its last valid date), as of any date; a fee scheduled for a future date waits for that date.
- **Historical fee preservation** - versions are immutable (database trigger 51079); a change appends a version that cannot start before the one it follows (51081, 51082) and cannot start in the past. A consumer copies a snapshot by date or by exact version id.
- **CDT-ready structural fields without bundling licensed CDT descriptions** - a `CDT` code is `D` plus four digits, the practice enters its own wording and names the licensed source and edition it holds; nothing licensed ships. A `Local` code that looks like CDT is refused by the service and the database, so a local code never passes for CDT.
- **Source/version/provenance without changing identity** - a new edition of a code set is a new version of the same procedure.
- **Reusable service/API for planning, completion and billing** - `ProcedureCatalogService` (read side: list, get, history, usage, active-for-planning, snapshot by date, snapshot by version id) and `ProceduresController`. Usage is read through `IProcedureUsageSource` so planning and billing can register their own sources.
- **UI** - `/procedures` ("Procedures & fees"): list with search and filters (category, code system, active/inactive), add, change (code fixed, reason required), inactivate (reason, usage warning and confirmation), reactivate, fee and effective-state presentation, and a version and change history.
- **Security and audit** - billing-manager/admin permissions (below); every create, revise, inactivate and reactivate writes an audit entry and an append-only event with actor and time.

## Architecture / schema / API / UI / security / config / measurement changes
- **Schema:** migration `20261008050255_AddProcedureCatalog` adds `ProcedureDefinitions`, `ProcedureVersions`, `ProcedureEvents` with unique indexes, check constraints and triggers 51077-51082 (**51083 and up are free**). Non-destructive; no existing table changed.
- **API:** `GET api/procedures`, `/active`, `/{id}`, `/{id}/history`, `/{id}/usage`, `/{id}/snapshot`, `/versions/{versionId}` (`ViewBilling`); `POST api/procedures`, `/{id}/revise`, `/{id}/inactivate`, `/{id}/reactivate` (`ManageBilling` + CSRF + row version where a record is changed). Stable error codes: `validation_failed` (400, `fieldErrors`), `identity_fixed` (400), `procedure_exists` (409), `usage_confirmation_required` (409, `usage`), `procedure_not_found` (404), shared concurrency conflict (409).
- **UI:** `ProcedureCatalogPage`, `procedures/ProcedureForm`, `procedures/ProcedureRow`, `procedures/procedureText.ts`, `services/proceduresApi.ts`; route `/procedures` guarded by `ViewBilling`; nav entry "Procedures & fees".
- **Security:** read needs `ViewBilling` (Dentist, FrontDesk, Billing, OfficeManager, Admin); change needs `ManageBilling` (Billing, OfficeManager, Admin). Hygienist and Assistant cannot see the catalog. All checked on the server; the screen only decides which controls are drawn. No new permission was added.
- **Config:** none.
- **Measurement events:** none emitted. This story does not affect a defined success metric on its own; adoption of the catalog by planning/billing is where a measurement event would belong.

## Decisions and deviations from the prompt's wording
- **Permissions (decision):** "Billing-manager/admin permissions" is implemented with the existing `ManageBilling` (Billing, OfficeManager, Admin) for change and `ViewBilling` for read. A new permission would be a governance change.
- **Version model (decision):** identity + immutable versions + events, rather than a mutable row and a separate fee table; it gives one mechanism for fee, description and source-edition history.
- **No backdating (decision):** a new version cannot start before today or before the version it follows; creation accepts any date from 2000-01-01 to three years ahead.
- **Dentition (decision):** only meaningful for tooth-level scopes; stored as `Both` otherwise.
- **Usage warning (decision):** counts odontogram procedure links only, because that is the only record that refers to a procedure today; the seam (`IProcedureUsageSource`) is where planning and billing add theirs. If the usage check fails on screen, inactivation is not offered rather than guessed.
- **No deviation** from the prompt's scope, UI, security or required tests.

## Defects found and fixed by this attempt's own verification
- The first test run showed the database check `CK_ProcedureDefinitions_CodeShape` rejecting every valid code: the character class `[^A-Z0-9.-]` is read by SQL Server so that `LOCAL-100` fails. Fixed to `[^-A-Z0-9.]` in the model, migration, designer and snapshot and confirmed directly in SQL (valid code accepted, code with a space still refused). 11 of 25 first-run tests failed from this one cause; all passed after.
- Two mistakes in my own tests (long surface names and `O` on an incisor instead of the repository's letters) were fixed in the tests; the catalog correctly refused them.

## Limitations / debt
- **No consumer yet:** no treatment plan, completed procedure or charge reads the catalog, so the requirement that existing plan/charge history is not rewritten is proven at the catalog only. Snapshot by version id is the mechanism consumers must use.
- **Usage counts odontogram links only.**
- **A particular surface is not stored:** applicability is the class (whole mouth, arch, quadrant, tooth, tooth surface) and the dentition, not "occlusal only".
- **Untested screen paths:** the loading state and the "connection dropped" message (typed values kept) exist on the page but no test asserts them.
- **No mutation checks** were run on the new rules (earlier attempts ran them); coverage rests on 84 tests including database-level tests that bypass the service.
- **No seed data and no licensed code-set import** (out of scope); the catalog starts empty. Quality gate C6 stays `NOT YET EVALUABLE` until planning consumes the catalog.
- **The page shows the catalog as of today;** the API accepts `asOf` but the screen has no date picker.
- Timestamps on screen use the browser's locale.
