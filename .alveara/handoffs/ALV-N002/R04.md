## Corrections made

### N002-R03-01 — clean publish output now serves the shell (partial; infrastructure requirements still open)

`Alveara.Api.csproj` gained `BuildClientForPublish` (runs `npm ci && npm run build` for the client) and `CopyClientBuildToPublishOutput` (copies the client's `dist/` into `$(PublishDir)wwwroot`) MSBuild targets, both wired to run automatically on `dotnet publish`. `Program.cs`'s default static-file path now resolves to `wwwroot` under the content root — matching what a real publish output actually contains — with a repository-layout dev fallback so nothing about local development changes. Reproduced the reviewer's exact clean-publish check (`dotnet publish` to a fresh temp directory, run the executable directly with no repo context) and confirmed `/`, `/system-status`, and `/api/health` are all now `200`, with the real shell HTML in the `/` response body. See `R04-evidence/TEST_RESULTS.md`.

**Honestly still not addressed, not claimed as resolved:** a real LAN hostname with a certificate a genuinely separate client trusts (not `localhost` resolved to another machine), disabling public internet while preserving LAN reachability, and a provisioned least-privilege OS service identity with storage-root filesystem ACLs. These require physical/VM infrastructure and system-level configuration this sandboxed repository environment doesn't have. The user is provisioning a VirtualBox Windows VM for exactly this; the concrete step-by-step plan (bridged networking, a local root CA + LAN-hostname certificate, a reversible firewall-based internet-disable procedure, and a least-privilege service account with ACL-based negative tests) is recorded in `R04-evidence/NEXT_STORY_IMPACT.md` for the follow-up work, not fabricated as already done. `EXECUTION_STATUS.json`'s acceptance block for this attempt honestly reports acceptance items 1 and 7 as `NOT ESTABLISHED` (matching the reviewer's own stricter categorization, not softened to `PARTIAL`), and lists both as explicit `blockingIssues` rather than an empty array — directly correcting the R03 package's `blockingIssues: []` inconsistency the reviewer flagged.

### N002-R03-02 — framework/database logging now suppressed at the category level, plus a global safe exception boundary

`appsettings.json` and `appsettings.Development.json` now set `Microsoft.EntityFrameworkCore`, `Microsoft.EntityFrameworkCore.Database.Command`, `Microsoft.EntityFrameworkCore.Update`, and `Microsoft.AspNetCore.Diagnostics` to `None` in `Logging.LogLevel` — none of these categories can emit a log record through any registered provider regardless of pipeline structure. A new `SafeExceptionHandlingMiddleware`, registered first in the request pipeline (before `MapOpenApi`, HTTPS redirection, CORS, or authorization), catches any unhandled request exception, logs only `ex.GetType().Name` plus a correlation id, and returns a generic 500 — so even an exception type not covered by the category suppression above (e.g. a future non-EF exception) cannot leak its message through the default hosting/diagnostics logging path.

New `FrameworkLoggingPhiSafetyTests.cs` reproduces the reviewer's exact scenario as a codified test: a real `WebApplicationFactory` host using the actual, fully-configured logging pipeline (not a bare-bones test logger — the real `appsettings.json` filters are in effect), a capturing `ILoggerProvider` registered alongside the existing providers, a genuine SQL Server duplicate-key violation via `UserAccount.Username`'s unique index with a synthetic patient-like value, and an assertion that the value never appears in any captured log record across any category. See `R04-evidence/DEMO_EVIDENCE.md` for the full reproduction.
