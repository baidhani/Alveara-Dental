## Corrections made

### N002-R02-03 — atomic idempotent enqueue under concurrent callers

`BackgroundJobQueue.EnqueueAsync` now attempts the insert unconditionally and, on a genuine SQL unique-constraint violation (`DbUpdateException` wrapping SQL error 2601/2627 on the `IdempotencyKey` unique index), clears the change tracker and re-queries the row the other caller committed, returning it instead of throwing. New test `Two_concurrent_enqueue_calls_for_the_same_idempotency_key_both_succeed_and_return_the_same_job` fires two real, synchronized calls against LocalDB and confirms both return the same job id with exactly one row ever persisted — the reviewer's exact scenario, now converging cleanly.

### N002-R02-02 — PHI-safe failure diagnostics, persisted and logged

Failure handling now records only `SafeErrorSummary(ex, jobId) = "{ExceptionTypeName} ({PhiSafeLog.Correlate("BackgroundJob", jobId)})"` — never `ex.Message` — both to the persisted `LastError` column and to a newly-added optional `ILogger<BackgroundJobRunner>?` constructor parameter. Two new tests reproduce the reviewer's exact scenario with the opposite (fixed) result: `A_handler_exception_containing_synthetic_patient_like_text_never_reaches_persisted_LastError` (persisted side) and `BackgroundJobPhiSafeLoggingTests.The_configured_logging_sink_never_receives_the_raw_exception_message_only_the_safe_summary` (logging side, via a `CapturingLogger<T>` fake that records every formatted message string). The `IBackgroundJobHandler.ExecuteAsync` doc comment's unsafe check-marker-then-act suggestion for external effects was also removed, per the reviewer's explicit note that a local pre-check alone is not sufficient for a non-transactional external action.

### N002-R02-04 — migration-failure rollback, genuinely proven

`FailureTestBrokenMigration.Up()` now performs a real, observable schema change (`ALTER TABLE [Rows] ADD [AddedByPartialMigration] INT NULL`) before its second, deliberately-failing statement. The test — renamed `A_partially_executed_failing_migration_is_fully_rolled_back_not_left_half_applied_and_does_not_destroy_existing_data` — queries `INFORMATION_SCHEMA.COLUMNS` afterward via a new `ColumnExistsAsync` helper and asserts the added column does **not** survive, proving SQL Server's per-migration transaction rolled back a partially-executed migration, not just an immediately-failing one.

### N002-R02-01 — LAN production shell, genuine TLS validation, proven storage isolation

- `Program.cs` now serves the built React client (`npm run build`'s `dist/`) as static files from the same Kestrel process, with `MapFallbackToFile("index.html")` for SPA client-side routing. This is gated on the build directory actually existing, so it never interferes with the Vite dev workflow.
- Verified with the dev certificate genuinely trusted (`dotnet dev-certs https --trust`) and the server bound to `0.0.0.0`, using `curl --resolve localhost:<port>:192.168.1.180` — simulating a properly-configured LAN client whose hostname (matching the cert's `CN=localhost`) resolves to the server's real LAN IP — to achieve genuine, non-bypassed certificate validation, directly answering the reviewer's objection to `curl -k`. A direct raw-IP request (no `--resolve`) correctly fails TLS validation (`SEC_E_WRONG_PRINCIPAL`), confirming validation is actually active. Confirmed 200 responses with correct content for the shell, `/api/health`, the SPA-fallback route, a built static asset, and the same-origin `/api/systemstatus` call.
- New `StorageIsolationTests.cs` proves the blob storage root is never web-reachable via HTTP even with static file serving active (checking response *bodies*, not just status codes, since the SPA fallback returns 200 for any unmatched path), plus a structural check that the default storage root and client build path are disjoint directories.
- **Honestly still not established, and explicitly documented as such rather than claimed solved:** a genuinely separate physical/virtual LAN client machine, a real production Windows Service account, CA/AD-CS-issued certificate deployment, and disabling public internet on this machine. These require infrastructure or system-level changes outside this story's sandboxed scope and explicit user authorization — they remain `ALV-N013`/`ALV-N014`'s job. `EXECUTION_STATUS.json`'s acceptance block for this attempt is corrected to `passed: 7`, `partial: 2` (items 1 and 7), not the R02 package's overclaimed `9/9` — see `ACCEPTANCE_EVIDENCE.md`.

### Regression found and fixed during R02's own development (carried forward, unchanged in R03)

The exception-path failure-status write was previously happening inside the still-open transaction that the exception had just interrupted, so the failure write was itself silently rolled back. Fixed with an explicit `transaction.RollbackAsync()` as the first line of the catch block, before writing the failure status via a separate `ExecuteUpdateAsync` outside any transaction. Unchanged in R03; still covered by the retry/failure test suite.
