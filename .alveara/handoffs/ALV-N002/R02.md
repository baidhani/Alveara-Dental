## R01 review decision being corrected

`CHANGES_REQUIRED`, six findings (five P1, one P2), five independently reproduced by the reviewer against a real database or real process:

1. **N002-R01-01 (P1)** — background-job claiming was read-then-write (two runners could both claim the same job); a handler's effect could commit separately from the job's completion status, so a crash between the two could duplicate the effect on a recovered retry. Reviewer reproduced a duplicate effect (count 2) with a synthetic crash-boundary harness.
2. **N002-R01-02 (P1)** — recovery ran only once at startup; a job claimed just before a quick restart (within the 5-minute stuck window) was never re-checked. Reviewer reproduced 0 recovered / job stayed InProgress.
3. **N002-R01-03 (P1)** — an unhandled exception from startup recovery crashed the whole host on a database outage; the client status hook had no timeout/overlap-guard/shape-validation. Reviewer reproduced a real process shutdown ("Application is shutting down...") by launching the unchanged API against a missing database.
4. **N002-R01-04 (P1)** — the measurement-event validator checked only top-level property key names; a nested object under an allowed key, or `schemaVersion: 0`, both bypassed it. Reviewer reproduced both bypasses directly.
5. **N002-R01-05 (P1)** — LAN/no-internet/least-privilege evidence was a source-scan and a loopback request, not a real network/permissions proof; `localhost` is loopback, not LAN.
6. **N002-R01-06 (P2)** — migration coverage never exercised an actual upgrade of a populated database or a failing migration; blob writes could leave a partial file under a real blob id if interrupted. Reviewer reproduced one orphaned partial file via a synthetic interrupted write.

## Corrections made

### N002-R01-01 — atomic claim + transactional effect+receipt+completion

- `TryClaimAsync` replaced the read-then-write claim with a single conditional `UPDATE ... WHERE Status = Pending` (EF Core's `ExecuteUpdateAsync`) — two concurrent runners can never both succeed in claiming the same job.
- A new `BackgroundJobEffectReceipt` entity (new migration `AddBackgroundJobEffectReceipts`) is written in the **same database transaction** as a handler's local-database effect and the job's `Succeeded` status. `IBackgroundJobHandler.ExecuteAsync` now receives the runner's own `AlveraDbContext` (`transactionalDb`) and must write any local effect through it without calling `SaveChangesAsync` itself — the runner commits effect + receipt + status together, once, or not at all.
- Recovery checks the receipt table first: if a job's effect already committed (receipt exists) but a crash happened before the status could update — structurally impossible now that they're one transaction, but kept as defense-in-depth for a future handler whose effect isn't a plain row in this database — the handler is not re-invoked.
- New tests: `A_handler_s_effect_and_the_job_s_completion_commit_atomically_in_one_transaction`, `Recovery_does_not_re_invoke_the_handler_when_an_effect_receipt_already_exists_for_the_job`, `Two_concurrent_attempts_to_claim_the_same_job_result_in_exactly_one_execution`.

### N002-R01-02 — recovery on every poll, MaxAttempts respected on recovery

- `BackgroundJobHostedService`'s loop now calls `RecoverStuckJobsAsync` **and** `ProcessOnceAsync` on every iteration, not just once before the loop starts.
- `RecoverStuckJobsAsync` now marks a stuck job `Failed` (not `Pending`) if it has already reached `MaxAttempts`.
- New tests: `Recovery_marks_a_job_that_already_exhausted_MaxAttempts_as_Failed_instead_of_looping_forever`, `Hosted_service_style_recovery_runs_on_every_poll_not_only_once_at_startup`.

### N002-R01-03 — contained startup failures, sustained truthful degraded status, hardened client hook

- Startup recovery is no longer a separate unguarded call before the loop; it is inside the same `try/catch` as processing, so a database exception there is logged and retried next interval instead of propagating and stopping the host.
- `useSystemStatus.ts` rewritten to mirror `ALV-N001`'s `useConnectionStatus`: 4s per-request timeout (`AbortController`), an in-flight guard, and response-shape validation. Added an explicit `"stale"` state (distinct from `"loaded"`) carrying the last-confirmed status and timestamp, so a page that starts failing after a prior success visibly says so instead of silently keeping old data. `SystemStatusPage.tsx` renders a warning banner for this state.
- **Independently reproduced and confirmed fixed** with a real, separate OS process (not `WebApplicationFactory`) launched via `dotnet <built dll>` with `ConnectionStrings__Alveara` pointed at a nonexistent database: the process stays alive, and `/api/systemstatus` reports `database.reachable: false` consistently across multiple requests spanning more than one poll interval (sustained, not one-off). Codified as `RealProcessDatabaseOutageTests.cs`.

### N002-R01-04 — strict per-key type/shape/bounded-value validation

- `MeasurementEventValidator` now rejects any property value that is a JSON object or array outright (closing the exact `{"category":{"patientName":"..."}}` bypass), enforces a max string length (40 chars), and validates each allow-listed key against its expected type and — for `outcome`/`role`/`release`/`category` — a fixed accepted-value set/pattern.
- `ValidateSchemaVersion` rejects any value `< 1`; `ValidateEventName` requires a bounded `dotted.lowercase-segment` pattern.
- New tests reproduce the reviewer's exact bypasses: `Rejects_a_nested_object_smuggled_under_an_allow_listed_key`, `Rejects_schema_version_zero`, plus array/oversized-string/negative-count/out-of-range-outcome/malformed-event-name cases.

### N002-R01-05 — real LAN/HTTPS reachability and real least-privilege enforcement

- Started the API bound to `0.0.0.0` (both HTTP `:5072` and HTTPS `:7180`) and confirmed real reachability over this machine's actual LAN interface, `192.168.1.180` — genuinely non-loopback, unlike the R01 evidence's `localhost` request — over both HTTP and HTTPS, including a real TLS handshake against the ASP.NET Core development certificate (`curl -v` output confirms the SSL/TLS negotiation, not just a 200 status).
- Added `LeastPrivilegeAccessTests.cs`: creates a real SQL Server login scoped to only `db_datareader`+`db_datawriter` on a live test database, proves ordinary EF Core CRUD succeeds through it, and proves `CREATE TABLE` and `BACKUP DATABASE` are both genuinely rejected by SQL Server for that login — the application identity does not need, and cannot exercise, elevated rights.
- **Honestly documented, not claimed as proven:** a second physical/virtual LAN client machine was not available in this environment, so cross-machine reachability was proven via this machine's own real network interface rather than a truly separate device. Production Windows Service account configuration and CA-issued TLS certificate trust deployment for LAN clients remain out of this story's scope (`ALV-N013`/`ALV-N014`), not established here. This is recorded as a limitation, not silently converted into a claimed pass.

### N002-R01-06 — real migration upgrade/failure coverage, atomic blob writes

- `AddBackgroundJobEffectReceipts` (needed for finding 01 anyway) is a genuine second migration; `MigrationUpgradeTests.cs` seeds data on a database migrated only to the first migration, upgrades it to the second, and confirms the seeded data survived and the new table is queryable — an actual upgrade, not a re-run no-op.
- `MigrationFailureTests.cs` uses a small throwaway `DbContext`/migration pair (its own database, never touching the real Alveara schema) where the second migration deliberately references a non-existent column; confirms the failure is surfaced, the failing migration is **not** recorded as applied, and pre-existing seeded data survives — proving SQL Server's per-migration transaction behavior actually protects the schema.
- `LocalDiskBlobStorage.StoreAsync` now writes to a temp file and atomically moves it into place only on success, deleting the temp file on any failure; `An_interrupted_write_leaves_no_partial_or_orphaned_temp_file_behind` reproduces the reviewer's exact interrupted-stream scenario and confirms zero files remain in the storage root afterward.

### Regression found and fixed during this attempt's own development

While testing the new transactional runner, the exception-path failure-status write was itself getting silently rolled back — it ran inside the still-open `await using` transaction, which then rolled back on disposal and undid it. Fixed with an explicit `transaction.RollbackAsync()` before writing the failure status. Caught by the suite's own `A_job_that_keeps_failing_is_retried_up_to_its_max_attempts_then_marked_Failed_not_lost` test, not shipped.
