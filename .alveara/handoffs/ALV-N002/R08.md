## Corrections made

### N002-R07-01 — implementation identity, fixed by construction

This attempt has exactly one implementation commit, `02a8c98533cc604fce4ac9f27c46f119f5b9065f`. There is no second implementation commit for this attempt, so the specific failure mode R07 exhibited — a ledger/manifest/ZIP-filename identity that diverges from the tree that actually produced the evidence — cannot recur.

### N002-R07-02 — the harness performs and verifies every check itself, in one unattended run

`ops/deployment-verification/Invoke-ServerVerification.ps1` was rewritten so the service-account write/read check and the ordinary-account denial check are both executed by the script itself via `Start-Process -Credential -Wait`, waiting for genuine completion rather than printing a manual instruction. Each child process records its own actual runtime identity via `[Security.Principal.WindowsIdentity]::GetCurrent().Name` — not a string the parent script assumes — making each result file self-authenticating about who really ran it. The summary is computed only after every check has completed, so its `capturedAtUtc` can never precede a result it reports. Run against the real server VM in a single pass: no result file was opened, edited, or completed by a human afterward. See `R08-evidence/DEMO_EVIDENCE.md` for the timestamp-by-timestamp proof this ordering is now correct.

### N002-R07-03 — the running API's actual SQL session, correlated to its own PID

The script now forces a real request to the API's own `/api/systemstatus` endpoint (retaining the full response body) and immediately queries `sys.dm_exec_sessions` for a live session under the configured least-privilege login, correlating its `host_process_id` against the API process's own PID captured earlier in the same run. The captured evidence shows `host_process_id=7172` matching `Alveara.Api.exe`'s own PID exactly, with `program_name` confirming it's the real EF Core client — proving the running API's actual database traffic goes through the tested least-privilege login, not merely that such a login exists somewhere with the right roles.

### Incidental fixes made while rewriting

A latent bug in the role-membership comparison (an invalid `-join` parameter passed to `Sort-Object`, which would have thrown at runtime despite parsing cleanly) was found and fixed with a `Compare-Object`-based comparison. The script's `.EXAMPLE`/parameter docs were corrected to use the API's own HTTP endpoint for the internal self-check, since an HTTPS request to `localhost` would fail on a certificate name mismatch unrelated to what that check verifies (the server's cert is issued for its LAN hostname, not `localhost`; certificate trust itself is already proven by the client-side evidence).
