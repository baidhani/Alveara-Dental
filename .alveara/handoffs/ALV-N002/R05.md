## Work performed

See `.alveara/handoffs/ALV-N002/R05-evidence/DEMO_EVIDENCE.md` for the full transcript. Summary:

1. **Bridged LAN client**: a VirtualBox Windows VM's network adapter set to Bridged, confirmed on the same subnet as the host (`192.168.1.216` vs. host `192.168.1.180`) with genuine bidirectional reachability — the first attempt across all of ALV-N002 to test from a client that isn't the server's own network interface.
2. **Real LAN-hostname certificate trust**: a local root CA and a leaf certificate for `alveara-server.local`, the root trusted only on the VM (not the host), Kestrel configured to serve the leaf cert. Validated genuinely (no `-k`, no `--resolve localhost` trick) from the VM for `/`, `/api/health`, `/system-status`, `/api/systemstatus`, and a static asset — and proven non-universal by the host's own certificate validation *failing* against the same server.
3. **Public internet disabled, LAN preserved**: a Windows Firewall outbound rule (`-RemoteAddress Internet`) blocked the host's public-internet access, paired with a self-reverting Scheduled Task (a dead-man's-switch, since the operator's own remote tooling on that host also depends on its internet connectivity). Dry-run tested first; the real test then confirmed the host's own ping to `8.8.8.8` failing while the VM's requests to the shell kept succeeding, simultaneously.
4. **Least-privilege service identity + storage ACLs**: two local Windows accounts (`svc-alveara-api`, `test-ordinary-user`) created on the VM; NTFS ACLs on a storage-root-equivalent folder reset and re-granted only to the service account; a genuine write/read success as the service account and a genuine access-denied failure as the ordinary account.
