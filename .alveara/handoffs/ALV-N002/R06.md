### N002-R05-01 and N002-R05-02 — corrected topology: real server, genuinely separate client, client's own internet blocked

Both findings shared a root cause: R05's client/server roles were assigned to the wrong machines for what each check needed to prove. R06 corrects this with a proper two-VM topology (see `.alveara/handoffs/ALV-N002/R06-evidence/DEMO_EVIDENCE.md` for the full transcript):

- **Server VM**: runs the real, unmodified, previously-published Alveara API (the same R04 build, with the client bundled into `wwwroot`) under a dedicated least-privilege local account (`svc-alveara-api`), connected via a real SQL Server login (`alveara_app_login`, verified scoped to only `db_datareader`+`db_datawriter`) against a real migrated database, with the real storage root (`App_Data/blobs`, resolved exactly as `LocalDiskBlobStorage` computes it from `ContentRootPath` — not a stand-in) protected by real NTFS ACLs. An unrelated local account is genuinely denied access to that real path.
- **Client VM**: a fresh clone, renamed to avoid a duplicate-computer-name conflict, with its own bridged LAN IP. It reaches the server with genuine (non-bypassed) TLS validation, cannot reach the database's TCP port or a storage-root file share directly, and — the specific N002-R05-01 fix — had **its own** public internet blocked via a real firewall rule (not the server's), confirmed failing (`ping 8.8.8.8` → `General failure`) while its LAN requests to the full shell/API surface kept succeeding, all at the same time. The block self-reverted cleanly via the same Scheduled Task safety net used previously.
- **Host**: untouched by any of this attempt's infrastructure changes — no accounts, ACLs, firewall rules, or certificates were added to it.
