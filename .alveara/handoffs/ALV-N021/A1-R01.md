## What changed
1. **Date-only values shown as the same day everywhere (F-107).** New `components/dateOnly.ts` `formatDateOnly` builds the day from its parts instead of parsing `"1985-03-14"` as midnight UTC. Used by the prescription print's date of birth (the F-107 root cause, `PrintPreview.tsx`) and by `documentText.formatDate`.
2. **Date-of-birth limit (new site, same kind as F-107).** Found while classifying every client date site (`A1-R01-evidence/DATE_SITE_CLASSIFICATION.md`): `PatientFieldsForm` took the latest allowed date of birth from `toISOString()` (the UTC day: tomorrow on a Chicago evening, yesterday on a morning east of UTC). Now `todayDateOnly()`, the viewer's own day. Not in the finding register; the owner approved fixing it within A1 (2026-11-14).
3. **Server dates that named the UTC day (F-118, perio label).** The billing timeline's "Completed procedure performed <date>" and the diagnosis link label "Periodontal chart of <date>" now use the practice day (`clock.ToPracticeLocal`).
4. **When an answer was entered (F-184, F-218).** Treatment-plan state rows are append-only; the view showed the latest row, so scheduling or completing an item replaced the "Entered by ... on" name and time of the patient's answer. `PlanItemView` gains `AnswerRecordedByName` / `AnswerRecordedAtUtc` from the row in which the acceptance last changed (a repeat answer writes no row, so this is exact), and `DecisionRevision` comes from that row. The client shows "Entered ... on" from it and a separate "Last changed by ... on ..." when a later change exists.
5. **Statement aging in practice days (A1-DECISION-01).** A deliberate policy change from the documented UTC-day rule of ALV-007-C02, with a compatibility fix (not a correction of an accidental rule):
   - `FinancialDocumentBuilder.CurrentTemplateVersion = 2`; supported versions 1 and 2; any other version raises `UnsupportedTemplateVersionException` and the API answers `document_template_unsupported` (never a silent fallback).
   - Version 2 subtracts practice-local calendar dates of the as-of and service instants, each converted at its own offset (`TimeZoneInfo.ConvertTime`), clamped at zero; thresholds 0-30 / 31-60 / 61-90 / over 90 unchanged.
   - The basis (`DocumentAgingBasis`: policy, zone id, as-of instant and local date, per-charge service local dates) is frozen in the existing `EnvelopeJson` and repeated in the statement content, so the content hash binds it. A rebuild validates the basis against the document's cut-offs (policy, instant, every open charge covered) and uses it instead of the current zone.
   - Version 1 is unchanged byte for byte: new fields are omitted when null, the v1 path keeps UTC-day aging, and both v1 statements and v1 receipts rebuild to their stored bytes and hashes.
   - Reprint and export rebuild with the **stored** `TemplateVersion`; preview uses the current version; issue refuses a token whose version is not current as stale, after the existing prior-key replay check, so an already-issued v1 request retried with its key still returns the original document.
   - Live aging in `BillingService.Timeline.cs` uses the current policy (`PracticeBasis`), so live and new-statement aging agree.
