## Scope delivered
All seven stop conditions of the prompt (mapped in `R01-evidence/ACCEPTANCE_EVIDENCE.md`; the control file counted 6, the prompt lists 7, and all 7 are evidenced):
- **Phases and revisions.** Every change to a plan's content (create, add or withdraw a procedure, rename, or an explicit revise) saves the next numbered revision, a copy of the latest with the change applied. Earlier revisions can never be edited (database trigger). A revision holds the title, the clinical rationale, the patient-facing explanation, the phases (1-12: name, planned-visit words, optional target date) and where each procedure sits. Revisions can be listed, opened as saved and compared (title, words, phases, procedures added, withdrawn or moved, and the estimate on each side).
- **Answers, scheduling, completion.** A procedure's state is an append-only row per change. Accept or decline per procedure and for the whole plan (refused as `partial_acceptance_conflict` when it would overwrite an opposite answer); a decline needs a reason; the signed-in account is recorded as who entered it and an optional name as who gave the answer; the answer carries the plan's version. Accepted procedures can be scheduled (a state and an optional date) and completed; Completed is final and a completed procedure cannot be re-answered, rescheduled or withdrawn.
- **Estimate.** The practice's catalog fee total, labelled by the server on every plan, revision, comparison and patient copy as not an insurance estimate and not a guaranteed patient cost; the screen adds its source and limits.
- **Patient copy.** A plain-language page without staff-only detail that prints alone in black on white.
- **Reconciliation.** A plan reference code (set once, unique per patient); old free-text diagnosis references matched to the same patient's plans by code or id (preview, then apply) or chosen by a person; unmatched, ambiguous and withdrawn-diagnosis cases stay unresolved with the reason; another patient's plan is never matched or accepted; the tie is a row beside the diagnosis, which keeps its text and history, and the reference is then locked.

## Architecture / schema / API / UI / security / config / measurement changes
- **Schema.** Migration `AddTreatmentPlanCompletion` (`20261009050158`): `TreatmentPlanRevisions`, `TreatmentPlanRevisionPhases`, `TreatmentPlanRevisionItems`, `TreatmentPlanItemStates`, `DiagnosisPlanResolutions`; `CurrentRevision` and `ReferenceCode` on `TreatmentPlans`; `TreatmentPlanEvents` widened (nine new change types, a revision number, `ChangeType` 13 to 20 characters); a backfill gives every existing plan its first revision; 13 triggers using error numbers **51099-51117** (**51118 and up are free**); `Down` verified on a scratch database (the new tables, triggers and columns are removed and the history column and constraints restored; it cannot succeed once a new kind of history entry exists, because history is append-only; noted in the migration).
- **API.** 11 endpoints: `GET .../revisions`, `.../revisions/{n}`, `.../revisions/compare`; `POST .../revise`, `.../decision`, `.../items/{id}/decision`, `.../items/{id}/schedule`, `.../items/{id}/complete`, `.../reference-code`, `POST api/patients/{id}/treatment-plans/reconcile-references`, `POST api/diagnoses/{id}/resolve-plan-reference`. Plan and diagnosis views gain fields (all additive). New stable error codes are listed in `docs/TREATMENT_PLAN_COMPLETION.md`.
- **UI.** The Treatment plan tab: builder grouped by phase, revise form, answer forms, scheduling and completion, revision history and comparison, patient copy with print styles, old-reference panel; the Diagnoses screen shows a tied reference.
- **Security.** No new permission: read `ViewClinicalDocumentation`, change `ManageTreatmentPlans` + CSRF. Audit entries carry the user and time and no patient name or clinical wording; a failed audit write stores nothing (503 `save_failed`).
- **Config / measurement events.** None.

## Decisions and deviations from the prompt's wording
- Acceptance is entered by staff on the patient's behalf (the prompt says patient-portal acceptance is out of scope); attribution is the signed-in account plus an optional name of who answered.
- Revisions are stored as whole copies rather than as diffs, so any version reads as saved and any two compare without replaying history.
- Procedure state is its own append-only table so the STORY-015 triggers that make procedures immutable are unchanged.
- A decision needs the plan's current version; scheduling and completion do not.
- A tie of an old reference is final and one per diagnosis; the reference text is then locked in the service and by trigger 51116 (a trigger declaration on `Diagnoses`, a STORY-013 table; see shared components).
- **Deviation:** the control file's acceptance total for this story was 6; the prompt lists 7 stop conditions; the record is set to 7.

## Limitations / debt
- **The procedure catalog's "in use" warning does not count plan procedures.** Only the odontogram link source is registered; inactivating a procedure that plans use gives no usage warning (the plans themselves are protected: fees are copied, and an inactive procedure cannot be added). A `IProcedureUsageSource` for plan procedures is a small follow-up (recommended; not done here because it changes the catalog's behaviour and would need a new full evidence run).
- Billing, FrontDesk and OfficeManager cannot read plans (STORY-015); no insurance estimate; a schedule is not an appointment and completion posts no charge; a tie of an old reference cannot be undone.
- The print layout is verified by a screenshot under print media and a check that the rest of the page is hidden, not by a unit test or a physical printer.
- Frontend: the first two full `vitest` runs had 5 and 1 timeouts (5000 ms) in the existing periodontal grid tests, which this attempt does not touch (details and measurements in `R01-evidence/artifacts/test-runs/frontend-gates.txt`); the third run passed 1308 of 1308. A larger timeout for those tests changes files outside this story and is recommended to the owner.
- Mutation checks cover five rules (service and database), not the whole feature.
- The loading state of the revision history is covered by a test only for the failure path.

## Unresolved questions

- Whether a tie of an old reference should ever be undoable (it is final here, because the original text is kept beside it and the reference is locked).
