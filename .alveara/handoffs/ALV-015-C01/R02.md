## The finding and what R02 changes (only that)
**Finding:** the catalog's inactivation guard (`GET api/procedures/{id}/usage`, 409 `usage_confirmation_required`) counted only odontogram links, so a procedure used by treatment plans reported zero uses.

**Reproduced first, before any fix** (`R02-evidence/artifacts/correction/reproduction_before_fix.txt`): with the new tests and the production wiring, the usage answer gave no "Treatment plans" source (`Tuple (0, -1)` where a count was expected) and inactivation of a used procedure went through without acknowledgement.

**Fix:**
1. `src/Alveara.Api/Architecture/Treatment/TreatmentPlanProcedureUsageSource.cs`: a read-only `IProcedureUsageSource` named "Treatment plans" counting every persisted `TreatmentPlanItems` row for the procedure, withdrawn and completed included, for every patient's plans. It returns a number only.
2. `Program.cs`: registered beside `FindingLinkProcedureUsageSource`.
3. The existing usage response, 409 and catalog page warning carry the count with no new endpoint or contract change. The page already rendered `bySource` generically; one frontend test proves it ("Treatment plans: 2" named, zero-count sources hidden, confirmation still required).
4. One existing STORY-015 test (`A_retry_still_returns_the_plan_after_the_procedure_has_been_inactivated`) now acknowledges the use when inactivating, because the plan uses the procedure. This is the intended behaviour change, not a regression.

Nothing else in the R01 design, schema (no migration), API contract or UI changed.
