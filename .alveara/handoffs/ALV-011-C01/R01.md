## Scope delivered (implementation scope of the prompt, item by item)
- **Scheduled, confirmed, arrived/check-in, ready, seated, in treatment, checked out, completed, cancelled, no-show** — `Scheduled → Confirmed → CheckedIn → Ready → Seated → InTreatment → CheckedOut → Completed` in the `FlowState` column STORY-011 added (its four values unchanged); **cancelled and no-show stay the booking `Status`**, so they cannot be mistaken for completed.
- **Provider assignment / operatory assignment** — `VisitProviderProfileId` / `VisitOperatoryId` (null = as booked): where the patient actually is, kept apart from the booking so the calendar and conflict rules never move; visible on every card next to the booking.
- **Valid transition rules** — `VisitStateMachine`, one pure function tested on all 64 state pairs; a superset of STORY-011's rule (a test compares every original pair); forward only, check-in cannot be skipped, Completed is final, repeats are no-ops. **Operatory already occupied where enforced**: one patient per room (Seated/InTreatment), checked under an application lock.
- **Timestamped state history** — an `AppointmentEvent` per move and per assignment change (who, when, `from -> to`; where the patient WAS), in the same save as the change, plus a PHI-free audit entry.
- **Current-day live flow** — `GET api/visits/board?date=` (default today; cancelled/no-show included; visits still open from an earlier day carried onto today's board because they still hold a room).
- **Check-in readiness surfaces incomplete/complete required forms/consents from ALV-N010; viewing a form does not silently mark it complete/signed** — `FormTemplate.RequiredAtCheckIn` (practice-controlled, audited, publishes no version) and `CheckInReadinessService`: Complete only for a Signed form **with its signed copy on the template's current version**; otherwise started / signed an earlier version / not done; read-only; informational (never blocks a check-in).

UI deliverables: **live flow board** with a column per state, patient/provider/operatory cues and **elapsed-time indicators** (server clock); **fast transition actions with confirmation only where needed** (one press; "Complete visit" asks because it is final); **visible required-form readiness cues at check-in**; no invented clinical safety flags (ALV-N011 will add a minimal indicator once a safety model exists).

## Architecture / schema / API / UI / security / config / measurement changes
- **Schema** — migration `AddVisitWorkflow`: `CK_Appointments_FlowState` widened to the eight states and made **case-sensitive** (`COLLATE Latin1_General_CS_AS`; the database's default collation would accept `completed`); `Appointments.VisitProviderProfileId` / `VisitOperatoryId` (Restrict FKs); index on flow state/start; `FormTemplates.RequiredAtCheckIn` (default false). The rollback fails loudly if a visit is already in a new state.
- **API** — new `VisitsController` (`api/visits`): `GET board`, `POST {id}/state`, `PUT {id}/assignment`; `FormsController`: `PUT api/forms/templates/{id}/required-at-check-in` and `GET api/patients/{id}/forms/check-in-readiness`. STORY-011's endpoints on `api/appointments` are untouched. New stable codes: 409 `operatory_occupied` (with `conflictingAppointmentId`), `visit_completed`, `provider_inactive`; `validation_failed` for an unknown target.
- **Security** — two new permissions, appended: `UpdateVisitFlow` (front office: confirm, check in, check out — front desk, office manager, admin) and `UpdateChairsideFlow` (ready, seat, start treatment, complete — dentist, hygienist, assistant, office manager, admin); either may reassign (`RequireAnyPermission`, new). Reading the board needs `ViewSchedule`; the form cue only for callers who may see form status. Every change needs CSRF and the row version; the server re-checks everything the UI hides. STORY-011's endpoints keep `ManageAppointments`.
- **Audit** — `PatientConfirmed`, `PatientReady`, `PatientSeated`, `PatientCheckedOut`, `VisitAssignmentChanged`, `FormTemplateRequirementChanged` (with STORY-011's three): user and time in the same save as the change; details never contain names, times or notes. If the log cannot be written the change is not stored.
- **Measurement** — `appointment.flow` (category = the target state or the refusal code) and `appointment.assignment` (outcome), through the shared privacy-safe sink; a failure to record never changes a decision.
- **UI** — route `/flow` (nav "Visit board", `ViewSchedule`): `pages/flow/*` (`FlowBoardPage`, `VisitCardView`, `AssignPanel`, `ReadinessCue`, `visitLabels`, `visitTime`); the calendar drawer keeps STORY-011's three buttons (a confirmed appointment can still be checked in) and points to the board for the rest; the form templates page has a "Require at check-in" toggle.

## Decisions and deviations from the prompt's wording
1. **One state column, extended, and a superset rule.** STORY-011 stored its flow in `Appointment.FlowState` and froze its rule with tests; this story keeps that column and its four values, adds four states, and puts the full rule in a new `VisitStateMachine` that provably agrees with the old one on the original pairs. STORY-011's shortcuts (checked in → in treatment, checked in → completed, in treatment → completed) stay legal, so the receptionist-only flow it shipped still works.
2. **Cancelled and no-show are not visit states.** The prompt lists them with the states; they are kept as the booking `Status` (where they already live and drive the conflict rules). The board shows them as their own group; the database refuses them as a flow.
3. **Confirmed has not arrived.** A confirmed appointment can still be rescheduled, cancelled or marked no-show (cancelling resets the flow; the Confirmed event stays in the history). From check-in on those are refused.
4. **Front-office and chairside permissions are separate** ("role-based transition permissions where appropriate"). My reading: confirm, check in, check out are front-office work; ready, seat, start treatment, complete are chairside. Front desk cannot seat or complete from the board; clinicians cannot confirm or check in. Either may reassign where the patient is seen. This is a policy choice — see question 1. STORY-011's own endpoints keep `ManageAppointments` (its tests pin that).
5. **Readiness means "signed on the current wording".** The prompt asks that readiness be accurate and not fabricated; a signature on an older version is shown as "signed an earlier version" and does **not** count as complete. It is informational only: it never blocks a check-in. Only active templates the practice marked required count. The "required" flag lives on the template row (not on a version), so changing it publishes nothing.
6. **Live = refreshed, not pushed.** The board re-reads every 15 seconds, when the tab becomes visible and after every action; a failed or >10-second read keeps the last good board and says so. No websockets or server push (new infrastructure, not asked for).
7. **A visit left open from an earlier day is shown on today's board.** The room rule is about who is in the room now, so a visit left seated overnight would block its room with nothing on screen to say why; it is shown, marked "carried over".
8. **Confirmation only where needed.** Every move is irreversible (no undo), but only completing a visit is final in the sense of closing it, so only "Complete visit" asks first.
9. **Occupancy includes STORY-011's check-in-straight-to-treatment**, which enters InTreatment without seating: that patient is in a room too.
10. **The booking never moves.** Assigning a provider/operatory during the visit changes where the patient is seen, never the booked slot, so the calendar and `SchedulingGuards` are unaffected.
11. **STORY-011's service was generalised, not forked.** `AppointmentFlowService` keeps its three methods and now calls `TransitionAsync`; one code path means STORY-011's tests exercise the new rules.
12. **No clinical safety flags** (per the prompt; ALV-N011 owns them).

## Defects found and fixed by this attempt's own verification
- **Cancelling or marking a *confirmed* appointment no-show failed at the database** (found by a service test): the flow stayed `Confirmed` on a cancelled appointment, which STORY-011's own constraint rightly refuses. The flow is now reset and the Confirmed event kept.
- **The database's case-insensitive collation accepted `completed`** (found by a schema test; STORY-011's original constraint had the same gap, never tested): the check is now case-sensitive.
- **My first race test did not detect a missing lock** (found by a mutation check): the window between check and write was too small. Each contender now pauses between the two (`SlowSaveContext`); without the lock six patients are seated in one room.
- **Board layout** (found only by looking at the screenshots): waiting patients read "Starts in 28794 h 50 min" (long durations now read in days) and four empty columns took as much room as the busy ones (empty columns now shrink).
- **A board mutation survived** (showing another day's board under this day's heading while it loads); a test that holds the next day's board back was added.
- A regression run on a stale, deliberately-mutated binary was discarded and redone on a verified rebuild (process error of mine, not a product defect). Mistakes in my own tests/fixtures are listed in `R01-evidence/TEST_RESULTS.md`.

## Limitations / debt
- **Polling, not push** (decision 6); **no undo** and no "back" moves; **no "too early to check in" rule** (inherited from STORY-011); **no queue optimisation or patient-facing arrival status** (the prompt's out-of-scope).
- At desktop width the eight columns scroll sideways when many states are busy (empty ones shrink to a strip); on a phone they stack.
- The board builds each card with a few queries (a day's schedule, capped at 500 appointments and 100 carried-over visits).
- The front-office / chairside split and the "current version is the one that counts" readiness rule are policy choices a practice may want different (both are local changes).
- There is still no patient filter on the appointment list and no "close open visits" flow for a visit left open.
- `F2` workaround on the board (above); the real-browser "left open" arrangement uses one declared SQL UPDATE (the API correctly refuses to book in the past).
