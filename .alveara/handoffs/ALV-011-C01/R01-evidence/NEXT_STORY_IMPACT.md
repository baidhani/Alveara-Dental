## What Gate B (and later stories) can rely on
- **The visit has one rule and one place.** `VisitStateMachine` (pure, all 64 pairs tested) is the only decision about which move is allowed; `AppointmentFlowService.TransitionAsync` is the only way a visit moves; STORY-011's `PatientFlowRules` is kept as the compatibility oracle (a test compares every original pair) and must not be edited without reviewing that test.
  A story that adds a state (for example a "Waiting for results" step) edits `VisitStates` + the edge table, the database check constraint (`CK_Appointments_FlowState`, case-sensitive) and `VisitStateMachineTests`' written-out move list — the exhaustive test will fail until all agree.
- **Cancelled and no-show are not visit states.** They are `AppointmentStatuses`; a cancelled/no-show appointment has `FlowState = Scheduled` and no moves. `VisitStates.HasArrived` (true from check-in on) decides whether an appointment can still be rescheduled/cancelled/no-showed.
- **Where the patient actually is** is `VisitProviderProfileId` / `VisitOperatoryId` (null = as booked), read through `VisitOccupancy.EffectiveProvider/EffectiveOperatory` and the view's `visitProviderName`/`visitOperatoryName`. The booking (`ProviderProfileId`, `OperatoryId`) is untouched by visit changes; the calendar and `SchedulingGuards` keep using it.
- **One patient per room** (`VisitOccupancy`, lock resource `visit:operatory:<id>`, `operatory_occupied`) looks at visit state only (Seated/InTreatment), not at booked time — a visit left open from an earlier day still holds its room, which is why the board shows it ("carried over"). A future "end of day" or "close open visits" story should resolve such visits through a real transition (there is no undo and no force-close here), not by editing rows.
- **Check-in readiness** (`CheckInReadinessService`): Complete only for a Signed form with its signed copy on the template's *current* version; informational; read-only; `FormTemplate.RequiredAtCheckIn` is the practice's switch. **ALV-N011** (clinical safety indicator) can add a second cue to the same board card; this story deliberately invented no clinical flags. A "re-sign on new wording" policy (or treating an older signature as acceptable) is a practice decision not made here: today an older signature is reported as `SignedEarlierVersion`, never complete.
- **Permissions**: `UpdateVisitFlow` (front office: confirm, check in, check out) and `UpdateChairsideFlow` (ready, seat, start treatment, complete) are new and separate; either may reassign; office manager and admin hold both; STORY-011's endpoints still need `ManageAppointments`. If a practice wants the front desk to seat patients, change `PermissionMatrix` (and `VisitPermissionTests`), not the controller.
- **Board** (`/flow`, `api/visits/board`): built only from stored data, re-read every 15 seconds and after each action, last good board kept on failure, elapsed time from the server's clock. `VisitBoardService` builds each card from `AppointmentViewBuilder`; a later patient-workspace "visits" tab can reuse `VisitCard`/`CheckInReadiness`. There is still **no patient filter on the appointment list**.
- **Audit/history**: new audit events `PatientConfirmed`, `PatientReady`, `PatientSeated`, `PatientCheckedOut`, `VisitAssignmentChanged`, `FormTemplateRequirementChanged` (alongside STORY-011's three); new history event types `Confirmed`, `Ready`, `Seated`, `CheckedOut`, `AssignmentChanged`. Details stay PHI-free in the audit log.
- **Measurement**: `appointment.flow` (category = the target state or the refusal code) and `appointment.assignment`.
- **Test support for races**: `SchedulingTestSupport.SlowSaveContext(pause)` pauses before every save; a rule that checks first and writes after is only proven race-safe if the test pauses between the two (without it the first transaction finishes before the others even check). Use it for any new lock.
