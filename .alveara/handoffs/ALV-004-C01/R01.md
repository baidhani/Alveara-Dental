## Scope delivered (implementation scope of the prompt, item by item)
- **Multiple providers/hygienists/operatories** — the calendar's day view has one column per provider; appointments carry provider and operatory; filters by both.
- **Appointment type and configurable duration** — the type's default is shown and used when the duration is blank; an explicit duration overrides; a reschedule keeps the booked duration unless a new one is given.
- **Provider availability and blocked time** — STORY-004's rule (ALV-N003's availability check) is applied to every booking and every reschedule; the calendar draws each provider's real weekly hours.
- **Provider, operatory and patient-overlap conflict detection** — one shared rule (`SchedulingGuards`), checked in the order provider, operatory, patient, naming the appointment in the way; patient overlap is new and applies to booking as well as rescheduling.
- **Reschedule** — in place (the appointment keeps its identity), with the previous start/provider/operatory kept in its history.
- **Cancel with reason** — the reason is required; the appointment stays on the record and in the calendar and stops holding time.
- **No-show** — only once the start time has passed; stays on the record and in the calendar, distinct.
- **Appointment notes/status metadata** — a working note (≤ 1000 characters, never in the audit log); statuses `Scheduled`/`Cancelled`/`NoShow`; who and when for a cancellation or no-show; an append-only history.
- **Concurrency-safe schedule edits** — every change carries the row version read (stale = the shared 409); conflict checks run under database application locks on provider, operatory and patient.

UI deliverables: **day/week calendar** (provider/operatory filters; practice working hours; week lanes for overlaps); a **create/edit drawer** with a plain-words **conflict explanation** naming what is in the way and when; **distinct cancelled/no-show presentation** (outline style, struck-through name for a cancellation, and the status written in the block); **fast patient lookup** (the shared picker) and **appointment-type defaults**; **reschedule by the drawer** — drag-and-drop was left out deliberately ("only if safely validated", see Decision 4).

## Architecture / schema / API / UI / security / config / measurement changes
- **Schema** — migration `AddAppointmentLifecycle`: `Appointments` (+`Notes`, `CancelReason`, `StatusChangedAtUtc`, `StatusChangedByUserId`, index on status/start), new table `AppointmentEvents` (Restrict FK, index on appointment/time).
- **API** (`AppointmentsController`) — existing: `POST /api/appointments`, `GET /api/appointments`, `GET /api/appointments/{id}` (unchanged contracts; the booking body accepts an optional `notes`, the list an optional `includeAll=true` for every status). New: `PUT …/{id}/reschedule`, `POST …/{id}/cancel`, `POST …/{id}/no-show`, `PUT …/{id}/notes`, `GET …/{id}/history`. New error codes: `patient_double_booked` (409), `appointment_not_found` (404), `appointment_not_scheduled` (409), `no_show_too_early` (409), `reason_required` / `reason_too_long` / `invalid_notes` (400), `row_version_required|invalid` (400), plus the shared `concurrency_conflict` (409).
- **Security** — no new permission: `ManageAppointments` (front desk, office manager, admin) for every change, `ViewSchedule` for reading; every change needs CSRF; the server re-checks everything the UI hides.
- **Audit** — `AppointmentRescheduled`, `AppointmentCancelled`, `AppointmentNoShow`, `AppointmentNotesChanged` (and STORY-004's `AppointmentScheduled`/`AppointmentRejected`, now also for refused reschedules): actor and time in the same save as the change; details never contain names, times, reasons or notes. Those live in the appointment's own tables behind `ViewSchedule`.
- **Measurement** — `appointment.rescheduled`, `appointment.cancelled`, `appointment.no-show` (schema v1, `outcome` only), through the shared privacy-safe sink; a failure to record never changes a decision.
- **UI** — route `/calendar` (nav "Calendar", `ViewSchedule`), `pages/calendar/*` (`CalendarPage`, `CalendarGrid`, `AppointmentPanel`, `NewAppointmentPanel`, `PlacementFields`, `calendarLayout.ts`, `explainRefusal.ts`). `/schedule` (STORY-004's page) is unchanged.
- **Config** — none new; `playwright.calendar.config.ts` for the real-backend walkthrough (excluded from the default mocked run).

## Decisions and deviations from the prompt's wording
1. **No manual overrides.** The prompt says audit "manual overrides" and, for patient overlap, "unless an explicitly authorized future policy says otherwise". No such policy exists, so nothing can override a conflict and there is nothing to audit; the refusals themselves are audited. If a policy is ever authorized it needs its own permission, audit event and tests.
2. **A new page, not a replacement.** The calendar is `/calendar`; STORY-004's `/schedule` booking page stays exactly as it was so the parent's tests and walkthrough keep proving the parent's contract.
3. **No-show only after the start time.** An appointment cannot be marked as a no-show before it has started (`no_show_too_early`); the control is disabled with an explanation and the server refuses anyway. A cancelled appointment cannot become a no-show and vice versa.
4. **Reschedule through the drawer, not by dragging.** A drag would need the same server validation and refusal explanation before it could be trusted, and the drawer already provides both with a keyboard path. Not done; documented as a limit.
5. **Patient overlap also protects bookings.** Applying the rule only to reschedules would let a booking do what a reschedule may not. STORY-004's tests are unaffected (the check comes after the provider and operatory checks and none of them overlaps a patient with themselves).
6. **Only `Scheduled` holds time.** A cancelled or no-show appointment never blocks a provider, operatory or patient; they remain visible and are included only in the calendar's all-status list.
7. **Cancel/no-show/notes/reschedule are idempotent** (repeating changes nothing) and **check the row version first**, so a stale request is reported as "someone changed this" rather than as a confusing consequence of the change.
8. **The cancel reason lives in the appointment's own record and history**, not in the audit log (the audit log stays PHI-free); likewise notes.

## Limitations / debt
- No drag-and-drop, recurring or multi-resource appointments, printing/export, or manual overrides.
- Blocked time is enforced and explained but not drawn on the grid (the scheduling read model lists weekly hours only).
- A past start cannot be booked or rescheduled to; the no-show demonstration in the real browser moves one appointment's times in the database to look long past (declared in the spec), and service-level tests use a controllable clock.
- Availability is read before the locks are taken: blocked time added in the same instant as a booking may not be seen by that booking (inherited from STORY-004).
- The week view's side-by-side lanes get narrow when many providers overlap (full details are in each block's label/tooltip and the drawer); at most 500 appointments are returned for a range.
- F2 workaround in the drawer (above).
- No patient filter on the appointment list yet (a patient-workspace appointments tab would need one).
