## Prior attempt decision

R02 repaired R01's five findings but was returned `CHANGES_REQUIRED` with one reproduced defect:

- **ALV-N003-R02-01 (P2):** write completions in `AvailabilityTab` were bound to the *provider id*, which cannot tell two editing sessions of the same provider apart. Sequence: edit A and submit (response held after the server commits revision 2) → switch to B → switch back to A (fresh read: revision 2) → type a new draft → the old response lands and its `setRows`/`setSaved` replace the new draft with the old values, with no confirmation. Blocked-time add/remove success and error completions shared the pattern. The review also required that an in-flight save must not replace edits typed after its submitted snapshot, and that the package's claims ("every completion is protected", "all R01 findings closed") be corrected.

## Correction of the R02 package's claims

R02's handoff/evidence said request responses and saves were protected against being applied to a different selection and that R01-01 was closed. That was too broad: R02 protected *loads* (numbered generations) and compared *writes* only against the currently selected provider id. It did **not** protect against an abandoned session of the same provider becoming "current" again. R02 is immutable and left as submitted; this attempt states the accurate position: R01-01's original A-load/B-load sequence was repaired in R02, and the return-to-same-provider write-completion sequence is repaired here. R02's `NEXT_STORY_IMPACT` pattern ("target the identity the data was loaded for") is superseded by the session-identity pattern below.

## Corrections made this attempt

### ALV-N003-R02-01 — completions are bound to an editing session

`AvailabilityTab` now keeps `sessionRef`, an *editing-session generation* that advances every time an editor is (re)populated — choosing a provider and every successful (re)load, including conflict-recovery reloads. Every write captures the session at submit time; its completion — success, error, notification, and the follow-up blocked-time refresh — is discarded unless that session is still current. Request identity (`loadSeq`, `sessionRef`) is independent of domain identity (the provider id), so `A → B → A` produces three different sessions and an old response cannot become current again.

Pending-write policy inside a session:

- **Weekly save:** a draft counter is captured at submit. If the user kept typing during the in-flight save, the response advances the saved baseline and revision but **keeps the newer rows** (they remain dirty and saveable at the new revision); if nothing changed, the server-normalised rows replace the editor as before. The Save button is disabled while saving (`Saving…`), so two saves cannot race on the same revision.
- **Blocked-time add:** the form is cleared on success only if it was not edited after submit.

The same class of defect was audited elsewhere and fixed proactively rather than waiting for a reviewer probe:

- **`ConfigEntityPanel`:** an editing-session generation guards save and conflict-reload completions (a reload that completes after the user closed or switched the form never reopens or repopulates it; an abandoned session's committed save refreshes the list but gives no form feedback), and an explicit pending-write policy disables the form fields, the other rows' Edit buttons and Add while a save is in flight.
- **Practice information form:** inputs are disabled while saving, so the response cannot overwrite newer typing.
