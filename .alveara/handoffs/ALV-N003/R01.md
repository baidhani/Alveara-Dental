## Scope delivered

**Data model / migration** (`20261001035949_AddPracticeConfiguration`): `PracticeSettings` (singleton), `PracticeLocation`, `Operatory`, `AppointmentType`, `ProviderWeeklyAvailability`, `ProviderBlockedTime`; `StaffProfile` gains `IsActive`/`JobTitle`; `ProviderProfile` gains `IsActive`/`RowVersion`. Database-enforced rules: unique location/operatory(per location)/appointment-type/staff names, one staff link per login account (filtered unique index), one provider profile per staff member, **at most one active location** (filtered unique index `UX_PracticeLocations_SingleActive`), and every foreign key into configuration is `Restrict`.

**Services** (`Architecture/Configuration/`): `PracticeConfigurationService` (practice, location, operatories, appointment types), `StaffProviderService` (staff, providers, account linkage, weekly availability, blocked time), `SchedulingConfiguration` (the read model scheduling consumes), and `ConfigurationWrite`/`ConfigurationException` (the reusable write pattern: audit staged in the same `SaveChanges`, caller-supplied row version, unique-violation → stable 409).

**API** (`Controllers/ConfigurationController`, `api/config/*`): list/get/create/update/`active` for each entity, availability replace, blocked-time add/remove, linkable-accounts picker, `GET scheduling` snapshot and `GET scheduling/availability-check`. Reads/writes need the new `ManagePracticeConfiguration` permission (Admin, OfficeManager); the scheduling read model needs only `ViewSchedule`. Writes require CSRF. **There is deliberately no DELETE route** for staff, providers, operatories, locations or appointment types.

**UI** (`/admin/configuration`, nav "Practice Configuration", route-guarded on `ManagePracticeConfiguration`): Admin Configuration hub with Practice (+ the single location), Staff, Providers, Operatories, Appointment types, Availability (weekly hours + blocked time) and Scheduling preview tabs, built on the reusable `ConfigEntityPanel`.

## Key decisions

1. **Time zone and currency are reflected read-only, not stored.** They are deployment invariants owned by ALV-N002 (`IPracticeClock`, `Money.Currency`). A second editable copy in a table could only ever disagree with the clock that actually converts every stored local time. The Practice tab shows them read-only.
2. **Practice-local semantics.** Weekly availability is stored as `DayOfWeek` + `TimeOnly` wall-clock (so "Tuesdays 09:00–17:00" means the same hours across DST). Blocked time is entered as practice-local time, converted once through `IPracticeClock.FromPracticeLocal` with the *Reject* policy (a DST gap or ambiguous time is a 400 `invalid_local_time`, never a guess), and stored as UTC instants.
3. **Never delete; inactivate.** No DELETE routes; FKs are `Restrict`; list endpoints hide inactive rows by default but every `GET by id` resolves them; scheduling's read model excludes them. Dependent-state rules: a location with active operatories, and staff with an active provider profile, cannot be inactivated; a provider/operatory cannot be reactivated under an inactive staff/location.
4. **Identities stay distinct but linkable.** Login account, staff profile and provider profile are separate records; the account link is an optional, validated FK (existing + enabled + not linked elsewhere). An *existing* link to an account that is later disabled is kept, not silently severed, and only a *changed* link is re-validated.
5. **Names are unique** (staff display name, operatory per location, appointment type, location) — which also makes a retried create idempotent rather than duplicating.
6. **Optimistic concurrency on every editable record** (rowversion round-tripped as base64; required on update). This is the first real adopter of the ALV-002-C01 conflict UI: a stale save returns the real HTTP 409 and the panel renders `ConcurrencyConflictBanner` with a reload that refetches the current version.
7. **One reusable pattern.** `ConfigEntityPanel` takes fields/columns/API calls and supplies states, search, show-inactive, inline validation, unsaved-change protection, conflict banner, server-error mapping and inactivate/reactivate. Later domain stories add their own settings by supplying those, not by copying a page.

## Review-relevant limitations / unresolved questions

- **No scheduling module exists yet**, so "immediately consumed by scheduling" is demonstrated through the read model/availability-check the scheduling story will call (`SchedulingConfiguration`, `GET api/config/scheduling*`) and the in-product preview, not a booking screen.
- **One active location** (service + filtered unique index); multi-location/overrides are future work per the story. Operatories attach to the single active location automatically.
- **Weekly availability is replaced as a whole** (atomic, audited) and is not individually version-tokened; two administrators saving different schedules for the same provider is last-writer-wins on that schedule. Blocked-time removal is a hard delete of a schedule constraint (audited), not a historical record.
- **Staff display names are unique** by decision; a practice with two people of the same name disambiguates the display name.
- Existing databases containing duplicate staff display names would fail the new unique index on migration; no such data exists in this build (no prior staff API), noted for any data-bearing environment.
- Unsaved-change protection is the browser `beforeunload` prompt plus an in-app confirm on cancel/row switch/tab switch (the app uses `BrowserRouter`, not a data router, so route-transition blockers are unavailable).
- `AuditLogEntry.TargetUserAccountId` carries the configuration entity's id (the column predates generalized auditing; `EntityType` says what it is), as already established by ALV-002-C01.
