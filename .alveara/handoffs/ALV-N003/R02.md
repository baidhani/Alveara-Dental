## Corrections made this attempt

### ALV-N003-R01-02 — the weekly schedule is a versioned aggregate (backend, UI, tests)

`ProviderProfile` gains `AvailabilityRevision` (migration `AddProviderAvailabilityRevision`), configured as an EF concurrency token and deliberately separate from the provider's `RowVersion` (editing a specialty never conflicts with editing hours). `ReplaceAvailabilityAsync` now **requires the revision the caller read**, compares it against the stored revision and increments it in the *same* `SaveChanges` as the row replacement and the audit entry — so two replacements that both read the same schedule (even an empty one) cannot both commit: the second's UPDATE matches zero rows and is rejected as the shared 409 `concurrency_conflict` (`entityType: "ProviderAvailability"`), with its audit entry rolled back. `GET …/availability` now returns `{ revision, windows }`; `PUT` takes `{ windows, revision }`; a missing revision is `revision_required` (400). The availability tab stores the revision it loaded, sends it, and on a 409 renders the shared `ConcurrencyConflictBanner` with reload-to-current recovery.

Proof: `AvailabilityConcurrencyTests` — real SQL Server races using a `SaveChanges` interceptor barrier (the reviewer's own technique) that forces both replacements to finish reading before either commits: initially-empty schedule and populated schedule each yield exactly one winner, exactly one conflict, a single valid final schedule (never the union), the matching revision, and exactly one audit entry; a stale editor is rejected with schedule and audit trail unchanged; a missing revision is refused; revisions advance and specialty edits do not disturb them. I also verified these tests **fail** with the revision check removed (both race tests red), so they genuinely guard the fix. API round-trip test: revision in GET, stale PUT → 409 problem, missing → `revision_required`.

### ALV-N003-R01-01 — editor state bound to the provider it was loaded for

`AvailabilityTab` numbers every schedule load; a response for a superseded request is discarded. Choosing a provider immediately clears and hides everything bound to the previous one (rows, revision, blocked time, errors) and invalidates in-flight loads, so stale rows can neither be displayed nor saved. Save, blocked-time add and remove always act on the provider the rows were loaded for and ignore completions that arrive after the user moved on. Dirty-change confirmation when switching providers is retained.

Proof (`ConfigurationHubPage.test.tsx`, deterministic hand-completed responses): out-of-order completion (A pending, B selected and completed, A completes last) still shows B's 13:00 and a save submits B's rows to B at B's revision; the previous provider's editor is hidden while the next loads; switching with a dirty schedule still prompts. Also verified red without the discard check.

### ALV-N003-R01-03 — unsaved-change protection covers main navigation and back/forward

Blocking a route transition requires a data router, so `App` now uses `createBrowserRouter`/`RouterProvider` (routes, guards and tests otherwise unchanged; the connectivity banner moved into the root layout). A new app-wide `UnsavedChangesProvider` registry receives dirty state from every editor through `useUnsavedChangesWarning`, and a router-level `NavigationGuard` (`useBlocker`) asks `confirm` before any pathname change while something is dirty; declining resets the navigation and leaves the page and draft intact. Sign-out now asks first too. **Authorization loss is never held hostage:** the guard only blocks a *signed-in* session, so a 401/expiry redirect to sign-in goes straight through, clearing the protected UI and the draft with no prompt; an unmounted editor also clears its own registry entry.

Proof (`App.unsavedNavigation.test.tsx`, 5 tests): shell link with decline/accept; no prompt when clean; browser back declined stays put with the draft; sign-out decline; a 401 during a dirty draft redirects with no prompt and no retained draft. A new real-browser Playwright test uses a real dialog (dismiss → still on the page with the typed text; accept → navigates). Verified red with the guard removed.

### ALV-N003-R01-04 — DST-safe availability check

`CheckProviderAvailabilityAsync` no longer infers containment from two local endpoint inequalities. It now compares the UTC offset at the slot's first and last instants and **refuses a slot whose elapsed time spans a UTC-offset change** (`crosses_dst_transition`) — conservative, and it never guesses an ambiguous local boundary. For slots with a constant offset it evaluates wall-clock arithmetic from the start (so a slot ending exactly at the transition instant is judged on its own wall clock). Blocked-time overlap remains a UTC-instant check.

Proof (`SchedulingConfigurationTests`, real database): the reviewer's exact reproduction (Sunday 01:30–02:00 window, 2026-11-01 06:50Z 30 min) is now unavailable with reason `crosses_dst_transition`; the same window a week earlier is available; a spring-forward-crossing slot is refused while slots wholly before/after it are available; a slot ending exactly at the fold instant is available; blocked time is still detected across the transition date.

### ALV-N003-R01-05 — failed conflict reload keeps the draft

`ConfigEntityPanel.reloadAfterConflict` replaces the draft only after a successful read. A failed read keeps the form, the draft and the conflict banner and shows a retryable error; the record being absent is now distinguished from a read failure — if it is not in the active list it is looked up among inactive records (it may have been inactivated by the other editor and is then loaded for editing), and only a successful read that finds it nowhere closes the form (with a notice). The same failed-reload rule applies to the availability schedule recovery.

Proof (`ConfigEntityPanel.test.tsx`): failed reload keeps the draft/conflict then recovers on retry; record inactivated elsewhere is found; genuinely missing record closes the form only after a successful read; the availability tab has the equivalent failed-reload-then-retry test.

### A related defect found while fixing R01-05 (not in the review)

`ConcurrencyConflictBanner`'s "Reload current version" button had no `type`, so inside a form it defaulted to *submit* and re-submitted the stale edit on every click (R01's reload test passed only because of timing). It is now `type="button"`, with a test asserting the stale `update` is called exactly once across a reload.

## Review-relevant limitations / unresolved questions

- The DST rule is deliberately conservative: a bookable slot that spans the transition hour is refused rather than evaluated. Offices rarely operate through 01:00–03:00 on a transition Sunday; if that ever matters, a future scheduling story can evaluate such slots piecewise.
- Blocked-time add/remove are not revision-checked (each is an independent, audited row; they cannot produce an invalid union). Blocked-time removal remains a hard delete of a schedule constraint.
- No scheduling module exists yet; the read model, availability check and in-product preview remain the consumer seam.
- One active location (service + filtered unique index); multi-location remains future work.
- The router migration is behavior-preserving but touches `App.tsx`; the same `RequireAuth`/`RequirePermission` guards and every existing test are unchanged.
