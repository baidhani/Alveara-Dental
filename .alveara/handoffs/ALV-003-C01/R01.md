## Scope delivered (implementation scope of the prompt, item by item)
- **Family/household relationships** — `Household` + `Patient.HouseholdId` / `HouseholdRelationship`; join an anchor patient's household (created on demand), leave it, change the relationship label; one household per patient; an empty household is removed.
- **Separate guarantor/responsible party** — `Patient.GuarantorPatientId`, independent of household. Rules (each refusal is `invalid_relationship`): guarantor must exist, be active and be self-responsible (so no chains and no cycles); a patient who guarantees others cannot be given a guarantor.
- **Active/inactive state** — `IsActive`; inactivate/reactivate (never delete; every relationship is `Restrict`); an ordinary edit never reactivates; a guarantor of active patients cannot be inactivated (`guarantor_in_use`).
- **Duplicate candidate warning before create** — exact match (same normalized name + birth date) is refused outright with the existing record offered (STORY-003's rule, unchanged); likely matches (all require the same birth date: same last name; same first name with a last name 1–2 typos away; same phone; same email) are shown side by side with the reason and registered only if the user acknowledges every flagged patient (verified server-side). No merge exists anywhere.
- **Safe edits with history/concurrency** — `PUT` with the row version read (stale = shared 409 `concurrency_conflict`); one `PatientHistoryEntry` per changed field (old/new, who, when); PHI-free audit entry in the same save; a save with nothing changed is a no-op.
- **Patient search and identity summary** — name words (prefix, any order), birth date, phone in any formatting; inactive hidden unless asked; capped at 50; detail with age (on the practice calendar date), guarantor, "guarantor for", household members; history endpoint.
- **Persistent patient-context workspace/header/navigation extension point** — `PatientContextProvider` (shell), `PatientHeader` replacing the shell's placeholder, `/patients/:patientId/...` workspace with tabs from `src/app/patientWorkspaceTabs.ts` (the extension point), documented in `docs/PATIENT_WORKSPACE.md`.
- **Patient switching clears or reloads patient-scoped state** — the previous patient is dropped synchronously on select; a response applies only if it is still the latest request; the workspace renders nothing for a patient other than the URL's and is keyed by patient id.
- **Validation appropriate to configurable practice requirements** — a practice-level setting (`PatientRegistrationSettings`, page `/admin/patient-registration`) may additionally require email and/or sex; enforced by the server on registration, edit and the early duplicate check, reflected in the forms.

UI deliverables: fast registration workspace (required fields marked, errors focused), household/guarantor editor, duplicate comparison panel, header identity card reused on every screen (shows only real data — no balances, diagnoses, alerts or counts), keyboard-first throughout.

## Architecture / schema / API / UI / security / config / measurement changes
- **Schema** — migration `AddPatientIdentityWorkspace`: `Patients` (+`IsActive`, `HouseholdId`, `HouseholdRelationship`, `GuarantorPatientId`, `UpdatedAtUtc`, `UpdatedByUserId`, indexes), `Households`, `PatientHistory`, `PatientRegistrationSettings` (unique `Singleton` index → exactly one row even when two first saves race). - **API** (`PatientsController`) — `POST /api/patients` (now with optional `acknowledgedDuplicateIds`), `POST /api/patients/duplicate-check`, `GET /api/patients?q&includeInactive&take`, `GET /api/patients/{id}`, `GET /api/patients/{id}/history`, `PUT /api/patients/{id}`, `PUT …/active`, `PUT …/guarantor`, `PUT …/household`, `GET|PUT /api/patients/registration-settings`. Stable error codes: `validation_failed` (+`fieldErrors`), `duplicate_patient`, `possible_duplicate` (+`candidates`), `invalid_relationship`, `already_in_household`, `guarantor_in_use`, `row_version_required|invalid`, `concurrency_conflict`, `patient_not_found`.
- **Security** — new permission `EditPatients` (front desk, office manager, admin). **Front desk now also holds `ViewPatientRecords`** (it must find and open the patients it registers); clinical roles and billing already held it, so they can now search/read patients but still cannot register or edit. - **Measurement** — `patient.duplicate-check` (schema v1; `category` ∈ `exact_refused|likely_warned|likely_overridden`, `count`) through the shared privacy-safe sink; failure to record is logged and never alters the registration.
- **UI** — routes `/patients`, `/patients/:patientId` (+ `household`, `history`), `/admin/patient-registration`; nav entries Patients and Patient Registration Settings; the shell now hosts the patient header and the requirements provider. Shared pieces: `PatientFieldsForm`, `DuplicateComparisonPanel`, `PatientPicker`, `SafeLink`.

## Decisions and deviations from the prompt's wording
1. **Exact duplicates are refused, not "warned".** The acceptance item "Likely duplicate is warned without silent merge" is met for *likely* duplicates. A same-name-same-birth-date match stays STORY-003's hard refusal (its tests and the unique index require it), with the existing record shown. I earlier told the user (in the STORY-003 enrichment) that a later story "will have to relax" the unique index; **that turned out to be unnecessary** and the index is unchanged.
2. **Likely-duplicate rules all require the same birth date.** An earlier draft also flagged a shared phone+surname or email+surname; the parent regression showed that would warn on STORY-003's own father/son case (and on any normal family), so those rules were dropped.
3. **"Configurable practice requirements"** is interpreted as practice-selectable required email/sex (the master plan says nothing more specific). It lives in its own table and page so completed `ALV-N003` files are not modified.
4. **Household "relationship" semantics**: each member carries a label (Self, Spouse, Parent, Child, Sibling, Grandparent, Grandchild, Other) relative to the household; the anchor of a newly created household is labelled `Self`.
5. **Guarantor is a registered patient** (see limitations).
6. **No success toasts**: saves are confirmed inline (see finding F1).

## Defects found and fixed by this attempt's own verification
- **StrictMode load loop** (found only by the real-browser run): in development, React StrictMode's mount/unmount/remount aborted the first patient request and the "already selected" guard skipped the reload, so a directly opened patient URL showed "Loading patient…" forever. Fixed (an aborted load is not "loading"; an unmounted provider forgets its selection) with a regression test that fails against the old code.
- **Simultaneous-retry race** (found by repeated test runs): a retry could pass the replay check, lose a race, and be reported as a duplicate; fixed in registration and covered by the existing simultaneous-registration tests, run repeatedly.
- Several test-data mistakes in my own new tests (documented in `TEST_RESULTS.md`), none in product code.

## Limitations / debt
- A guarantor must be a registered patient; a responsible party who is not a patient is not modelled.
- Likely-duplicate detection requires the same birth date (a misspelt name with the same birth date is caught; a wrong birth date is not). Search matches name *prefixes*, not fuzzy spelling; phone search normalizes spaces, hyphens, parentheses, dots and `+` only.
- Changing a practice requirement does not invalidate existing patients; an edit of a patient who lacks a newly required field will prompt for it.
- Patient history values (including contact details) are stored in the database and visible to everyone holding `ViewPatientRecords`.
- Patient search returns at most 50 rows with no paging.
- The patient header shows no indicators beyond identity/status/guarantor (by design until later stories produce real ones).
- Accessibility scans are representative of the states exercised, not every control state.
- Not yet scheduling/appointment aware (STORY-004).
