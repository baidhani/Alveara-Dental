## Proof (raw output in `R04-evidence/artifacts/`)
1. **Real forced pruning, not an injected exception.** `SqlClientPoolPruner` finds SqlClient's `_pruningTimer` / `PruneConnectionPoolGroups` by name and calls the same callback every 20 ms while a real fixture lifecycle runs (restore of a clone from the run's template, then the owner's first pooled open). A mechanism test fails loudly if a SqlClient upgrade renames it.
2. **Control arm (warm-up OFF): 800 forced cycles, 154 authentic first-open `Timeout expired ... obtaining a connection from the pool` failures** (19%), 0 initialisation failures (`preflight/control.jsonl`).
3. **Treatment arm (warm-up ON): 60 iterations x 15 cycles = 900 cycles, 900 of 900 first opens succeeded; 39 warm-up races were recovered by the bounded retry; fixture databases left and files left are 0 after EVERY iteration** (independent read-only `sys.databases` and folder check per iteration in `preflight/treatment.jsonl`). `preflight/SUMMARY.txt` is written by the preflight script after it re-verifies the raw files itself.
4. **Owner failure cleanup, both observed paths:** a direct owner and a `SafetyTestBase` derivative whose setup fails after the clone exists: the original exception propagates (same object), 0 databases and 0 files are left; a forced cleanup failure is logged distinctly (class only, no message) without replacing the original; a successful setup is untouched; the owner's own setup is never retried, even with pool-timeout text.
5. **Narrow classification:** the warm-up retry does not retry a product exception, a different `InvalidOperationException`, a `TimeoutException`, an assertion failure, an `IOException`, a look-alike message from another exception type, or a real `SqlException` (error 8134); it retries only the pool-acquisition timeout, up to 3 attempts, rethrowing the first exception.
6. **Negative controls** (`negative-controls/`): warm-up removed: the treatment arm FAILS; owner cleanup removed: 4 of the 5 owner tests FAIL; classifier widened: the classification tests FAIL (3 failures in the two classes). Each mutation was reverted and the files are byte-for-byte restored (the restored tree passes 15 of 15).
7. **Other checks:** the 18 new ids pass 18 of 18; all `TestDatabase*` fixture classes plus a sample of every owner family (including both R03 failure classes, the multi-class owners and `LeastPrivilegeLoginCleanupTests`) **325 of 325 passed, 11 m 30 s, no leftover database or file** (`sample-filter.txt`); `node --test tests/*.test.mjs` 49 of 49; the build has 0 errors and the same 32 warnings as before (no new warning). Client gates are untouched (no client file changed).

## Decisions and limits (stated, not hidden)
1. The warm-up reduces but cannot prove away the race for a connection opened much later in a long test (idle connections are trimmed after minutes; these tests run seconds). The preflight proves protection of the real first-open path; only the final Stage 2 proves the whole system.
2. The forcing is statistical per cycle (19% in the control arm), not certain; that is why the control arm runs 800 cycles and must show at least one authentic failure, and the treatment arm runs 900.
3. During the owner-cleanup negative control, three isolated `AlveraTest_*` databases leaked on purpose (that is what the broken code does). I removed them after verifying each name matched `^AlveraTest_[0-9a-f]{32}$` and every file sat under `Test-Data\Database`; only `AlveraDev` remains and the folder is empty.
4. I ran focused proof tests while building (before showing the product owner the diff summary I had promised). Nothing outside the test project and the preflight script changed.
5. The preflight script needed three fixes during this attempt (the `[ ]` in this repository's folder name is a wildcard to several PowerShell cmdlets); none of those runs executed any test, and the raw files in the package come from the final run only.
