## Scope

Established the production Alveara application as a structurally separate project from the course Command Center:

- **Technology stack decision** (made explicitly with the product owner, not silently): ASP.NET Core Web API (C#, .NET 10) + React 19 + TypeScript (Vite) client. Chosen over Blazor Server/WASM for JS-ecosystem accessibility/offline-tooling maturity and a structurally enforced client-independent API boundary.
- **`src/Alveara.Api`** — minimal ASP.NET Core Web API with one endpoint, `GET /api/health`, and a CORS policy scoped to the local Vite dev server origin only (no wildcard).
- **`src/alveara-client`** — React + TypeScript application shell:
  - Design-token system (`src/styles/tokens.css`): semantic colour (light + dark), typography scale, spacing scale, radius, elevation/shadow, icon sizing, density (comfortable default, compact variant defined), focus-ring tokens.
  - `AppShell` component: responsive sidebar navigation (module-registry-driven, `src/app/moduleRegistry.ts`), patient-context placeholder region, theme toggle (persisted), skip-to-content link, disconnected-state banner wired to a health-check polling hook (`useConnectionStatus`).
  - Reusable components: `Button` (3 variants), `PageHeader`, `FormField` (labelled, hint/error, ARIA-wired), `LoadingState`/`EmptyState`/`ErrorState`, `DisconnectedBanner`, `Notification` (toast) system with a context provider.
  - Pages: `DashboardPage` (honest empty state — no feature exists yet), `ShowcasePage` (demonstrates every reusable control built so far), `NotFoundPage` (unknown-route handling).
  - Routing via `react-router-dom`, with a catch-all `*` route to `NotFoundPage`.

## Architecture/schema/API/UI/security/config/measurement changes

- **API surface:** one endpoint, `GET /api/health` → `{ "status": "ok" }`. No other endpoints, no database, no persistence yet.
- **UI:** new application shell as described above. No existing UI was modified (none existed).
- **Security:** no authentication/authorization exists yet, and none is claimed. `moduleRegistry.ts` explicitly documents (in-code comment) that it performs no permission filtering, to prevent a later story from mistaking the unconditional list for "current-user-authorized modules."
- **Config:** CORS policy added, scoped to `localhost:5173`. No secrets or environment-specific config introduced.
- **Measurement events:** none emitted — this story does not affect any defined success metric.

## Decisions

1. React + TypeScript over Blazor (WASM/Server) — see `HANDOFF_SCHEMA.md`-referenced Standard Production Prompt Rules; decision made explicitly with the product owner (not silently), recorded durably in `BUILD_STATE.md` so later stories don't re-litigate it.
2. Module registry lists all modules unconditionally rather than an empty list or a fake "admin-only" placeholder — an empty registry would fail acceptance criteria in a different way (no modules to demonstrate navigation), and a fake-permission-filtered registry would violate the explicit "do not pretend current-user permissions already exist" requirement. An unconditional, clearly-commented list satisfies both constraints honestly.
3. Component showcase built as a real route (`/showcase`) inside the shell rather than a separate Storybook-style tool — keeps the "acceptance items demonstrated, not just described" requirement satisfiable with the existing test/browser tooling, and avoids adding a second toolchain for a shell this small.
