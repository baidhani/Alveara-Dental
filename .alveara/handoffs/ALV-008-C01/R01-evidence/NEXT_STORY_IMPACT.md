# ALV-008-C01 R01 - Next-story impact

The next scheduled items are 35 `ALV-007-C02` (statements, receipts, refunds, corrections, account UX) and 36 `ALV-008-C02` (retire the legacy completion paths and adopt historical completions), then 37 `STORY-016`. Gate D (after item 38) criteria D2 and D5 depend on this story and on `ALV-008-C02`.

## For ALV-008-C02 (retire legacy completion; adopt historical completions)
- **What to retire.** Backend routes `POST api/treatment-plans/{planId}/items/{itemId}/complete` and `POST .../complete-accepted` (`TreatmentPlansController`; `TreatmentPlanService.CompleteItemAsync` and `CompleteAcceptedAsync`), and the UI: the "Complete accepted procedures" button and its group (`TreatmentPlanActions.tsx`, `TreatmentPlanCompleteAccepted.tsx`) and the per-procedure "Mark X completed" button (`TreatmentPlanStateControls.tsx`, `completeItem` in `treatmentPlansApi.ts`).
- **Callers to map test by test** (searched): backend tests `TreatmentPlanCompleteAcceptedTests`, `TreatmentPlanCompleteAcceptedApiTests`, `TreatmentPlanStateServiceTests`, `BillingTestBase` and through it `BillingSchemaTests`, `BillingServiceTests`, `BillingResponsibilityServiceTests`, `BillingLedgerSchemaTests`, `BillingLedgerServiceTests` and `BillingProcedureChargeContractTests` (each builds a billable plan with a procedure completed the old way), `CompletionTestBase` and the ALV-008-C01 tests that make a "completed the old way" fixture on purpose; frontend tests `TreatmentPlanCompleteAccepted.test.tsx`, `TreatmentPlanAnswers.test.tsx`, `TreatmentPlanReviewComplete.test.tsx` (the legacy disclosure); walkthroughs `treatment-plans-complete-real-backend.spec.ts`, `treatment-plans-complete-accepted-real-backend.spec.ts`, `completion-real-backend.spec.ts` (the LEGACY step), and the two billing walkthroughs (they complete items first). Tests that only need a completed procedure can use a test-only fixture that writes the same state; the course portal's STORY-008 verification must not be altered.
- **HTTP callers found by searching the backend tests for the route:** `BillingApiTests`, `BillingLedgerApiTests`, `TreatmentPlanCompleteAcceptedApiTests`, `TreatmentPlanCompletionApiTests`, `TreatmentPlanProcedureUsageApiTests` and `CompletionApiTests` (the legacy step). `PatientFlowApiTests` and `VisitsApiTests` also match a `/complete` path, which may be the visit's own completion; they were not checked and `ALV-008-C02` must confirm which route they call.
- **Usage evidence.** Each use of either route is logged as `legacy_completion_used` (route, outcome, status, trace id; no PHI) since this story; use it to decide when the routes can return `410 Gone`.
- **Adoption** can reuse what this story built: `CompletionRules` (the time rules and the canonical hash), `CompletedProcedureService.PerformedTimeProblem` (one rule for completion and amendment), `ResolveChartAsync` / `StageChartAsync` (the chart resolution and the staged move), `ChargeAsync` (the billing contract call and its error mapping), the completion-set and completed-procedure tables (an adopted procedure's record would need its own set or a nullable set, which the current `SetId` and trigger 51147 do not allow: a new migration or a set per adoption), and the readiness's provider and encounter choices. A procedure completed the old way has a Completed state row, an `ItemCompleted` event and an audit entry, and no record, no chart move and possibly no charge (billing's manual charge may already exist, which `IProcedureCharging` reuses).
- **Triggers 51157 and up are free.** The performed-time triggers (51153, 51154) compare with the recorded acceptance and the plan's creation; an adoption of old data must satisfy them or be given an explicit reviewed exception.
- **Gate D2 reconciliation** is straightforward from the data: a completed plan item with no `CompletedProcedures` row is a legacy completion; a `CompletedProcedures` row for a fee above zero must have exactly one `BillingEntries` charge naming its plan item; a no-fee row must have none; a finding whose `ChartOutcome` is `Updated` must be Completed.

## For ALV-007-C02 (statements, receipts, refunds, corrections, account UX)
- Charges made by a completion carry the set's correlation id (`BillingEntries.CorrelationId` equals `CompletionSets.CorrelationId`) and name the plan item, so a statement can show which visit, provider and performed time a charge belongs to by joining `CompletedProcedures` (current values are the latest amendment's where given). The charge itself is never changed by an amendment.
- A completion can create several charges in one transaction and opens the account if it does not exist; account views must cope with an account whose first entries share one correlation id.
- A charge reversal does not undo the completion or the chart move; a reversed charge is still the procedure's one charge (the unique index on `PlanItemId`).
- A no-fee procedure completes with no ledger entry; statements must not expect one per completed procedure.

## Shared infrastructure and conventions
- Trigger error numbers **51157 and up are free**; this story owns 51144-51156, billing 51118-51143.
- `CompletedProcedureService` is a partial class (operation, checks, chart, charge, readiness, amendments, reads, history). Adding behaviour should add a partial, not grow the existing files (the size rule: a file near 300 lines is split before it is extended).
- Test helpers: `CompletionTestBase` (a provider, a finding, a linked tooth plan, the snapshot of everything a completion writes, the rows of the three tables written straight to the database); `HookedClock` (in `CompletedProcedureServiceTests.cs`) runs an action at the Nth time the clock is asked, to prove a guard inside a save deterministically.
- `SchedulingApiHarness.ConfigureLogging` lets an API test see what the host logs.

## UI extension points
`TreatmentPlanActions` composes the plan's actions; the review is `TreatmentPlanReviewComplete` (data from `getCompletionReadiness`, request from `completeProcedures`). A later screen that lists completed procedures or their corrections can use `listCompletedProcedures` and `amendCompletedProcedure` (typed, tested through the API but with no screen yet: corrections are made through the API in this story).

## Unresolved decisions to carry
Whether to add an explicit "agreed on" date to acceptance so the performed-time rule compares with the patient's agreement; whether the screen should let the clinician choose among several matching chart findings; how adoption treats old data whose times predate its recorded acceptance; and whether a screen for correcting a completed procedure belongs in `ALV-008-C02` or later.

## Prompt changes recommended for the next scheduled items

- `ALV-007-C02`: note that a no-fee completion has no ledger entry and that charges made by a completion share a correlation id.
