## Scope delivered
All seven stop conditions of the prompt (mapped in `R01-evidence/ACCEPTANCE_EVIDENCE.md`), implemented as the reviewer's approved decisions D1-D8, R1a-R4 and the six mandatory constraints require:
- **One authoritative operation.** `POST api/treatment-plans/{id}/complete-procedures` completes a selected set of one plan's procedures in **one explicit transaction**: the plan's version, each procedure's Completed state, history event and audit entry, an immutable completion set, one immutable completed-procedure record per procedure, the chart finding that moves, and one charge per billable procedure through `IProcedureCharging`. Any failure (a charge, the chart, an audit write, either save) rolls back the whole submitted set.
- **Plan-level stale protection.** The request carries the plan's version. It is checked before anything is staged and again, atomically, by the save that advances the plan's row version (the plan row is touched in the same transaction, because item-state inserts do not move it). Two overlapping sets end with exactly one winner.
- **Idempotency.** A non-empty, duplicate-free item list; a canonical request hash (sorted item ids, encounter, provider, performed time in UTC milliseconds). The same key and request replays the saved result with no writes (even from a stale screen); the same key with a different request is `idempotency_conflict`; the same procedures under a new key after success are refused as already completed.
- **Exact linkage and attribution.** Each record names the plan, the exact plan **revision**, the plan item, the catalog version, tooth, surface, encounter, provider, performed time, chart outcome and finding, and who finalized it. The encounter may be Draft or Finalized and is never changed.
- **Chart.** Plan item to its diagnosis to an explicit diagnosis link to a finding of the same patient on the same tooth (and surface). One eligible finding moves to Completed through the same rules, history and audit as a manual change; an already completed finding is reported; no match is `NotApplicable`; more than one match refuses the whole set (`ambiguous_chart_finding`). Never inferred from tooth and surface alone.
- **Charge.** Billable means a stored fee above zero; a zero-fee procedure completes with `charge: none` and no ledger entry. Billable procedures call `IProcedureCharging` in the same transaction and context with the set's correlation id and no caller amount; an existing charge is reused.
- **Finalization and amendments.** A completed-procedure record is final when created (database triggers refuse any change or delete). Amendments are append-only, numbered, with a required reason, and may correct only the provider, performed time and encounter; concurrency uses the amendment last seen (no row version), plus an amendment key and request hash; identical retries return the original; racing corrections leave one winner. Amendments never touch the plan, the chart or the charge.
- **Readiness.** `GET .../completion-readiness` reads only and uses the same refusal rule and chart resolution as the completion, so the review screen shows server data and does not reimplement matching in the browser; it also offers the active providers and the patient's encounters.
- **Clinical history.** The STORY-008 history now adds the provider, performed time, encounter, charge and chart outcome for a procedure completed this way; the fields are null for one completed the old way.
- **Legacy routes.** Unchanged (D1). The only change is the approved internal `legacy_completion_used` structured log (R1a): route, outcome, status and trace id, no PHI, no header, no change to any response or stored data.
- **UI.** **Review and complete...** is the primary action: a table of each procedure's tooth and surface, chart effect and charge (from the readiness), provider, encounter and performed time, a live summary, an explicit confirmation, a result shown only after the server confirmed the whole set with links to the clinical history, the odontogram and the ledger, and a failure state that always says nothing was completed. The old button keeps its exact name (so the STORY-008 tests and walkthrough are untouched) in a group labelled **Legacy completion** that says it records no provider, encounter, chart change or charge.

## Architecture / schema / API / UI / security / config / measurement changes
- **Schema.** Migration `AddCompletedProcedures` (`20261012020128`): `CompletionSets`, `CompletedProcedures`, `CompletedProcedureAmendments`; check constraints; unique indexes (one completed procedure per plan item, one set per plan and key, one amendment per procedure and number or key); **six triggers using error numbers 51144-51156 (51157 and up are free)**: append-only for all three tables (51144-51146), the set's patient (51156), the completed procedure's plan, patient, revision, set, item, catalog version, tooth, surface, encounter and finding (51147-51149), only for a completed and not withdrawn item (51150), not before the plan existed (51153) or before the acceptance in force (51154), and the amendment's patient and encounter (51151), contiguous numbering (51152) and time rules (51155).
- **API.** New `CompletionController`: `POST .../complete-procedures`, `GET .../completion-readiness`, `GET api/patients/{id}/completed-procedures`, `GET api/completed-procedures/{id}`, `POST api/completed-procedures/{id}/amend`. `GET api/patients/{id}/clinical-history` now returns the enriched entries (fields added at the end).
- **Services.** `CompletedProcedureService` (partials for the operation, the checks, the chart, the charge, readiness, amendments, reads, history), `CompletionRules` (pure rules), `CompletionViews`; `TreatmentPlanService.CompletionSupport.cs` (shared staging with STORY-008's completion) and `OdontogramService.CompletionSupport.cs` (shared state-change staging).
- **UI.** `TreatmentPlanReviewComplete`, `CompletionReviewTable`, `CompletionResultPanel`, `completionReviewRules.ts`, `completionApi.ts`; the history section shows the added detail.
- **Security.** No new permission: `ManageTreatmentPlans` plus CSRF for completing, amending and the readiness; `ViewClinicalDocumentation` for reads. No charge amount is accepted from a caller. Audit text carries no patient name or clinical wording; logs carry only error class and SQL error number on failure.
- **Config / measurement events.** None.

## Decisions and deviations from the prompt's wording
- **Approved decisions implemented as written** (D1 legacy routes unchanged; D2 quick button kept and labelled; D3 amendments with an expected-latest-amendment sequence and request hash and no row version; D4 zero fee is not billable; D5 chart linkage only through the diagnosis link; D6 Draft or Finalized encounter, never changed; D7 provider and time rules with a five-minute inclusive clock tolerance, tested at the boundary; D8 permissions and one plan per set; R1a internal log only; R2 acceptance rule with an explaining message; R3 server readiness; R4 adoption left to `ALV-008-C02`).
- **The legacy button keeps its exact accessible name** and is labelled by an enclosing group ("Legacy completion") and a description rather than by changing its text, so the verified STORY-008 UI tests and walkthrough stay unchanged (the reviewer allowed keeping it only if parent regression needs it). Disclosed here because it is a choice between two ways of "labelling clearly".
- **A second legacy control was found late and labelled.** The per-procedure "Mark X completed" button (ALV-015-C01) also calls the legacy state-only route. Its confirmation form now says "Legacy completion. This records only that the procedure is completed: no provider, encounter, chart change or charge. Use Review and complete on the plan instead."; the button's name and the existing tests are unchanged, and a unit test covers the disclosure. Retiring both controls is `ALV-008-C02`.
- **Provider and encounter are chosen explicitly** (no default) so attribution is never an accident; the performed time defaults to now.
- **Readiness carries the providers and encounters** so the screen needs only one permission and no calls to the configuration endpoints.
- **Completion failure message** is the completion's own ("The completion could not be saved, so nothing was completed"); a failed save in either of the two saves, or a failed charge, uses it.
- **Two saves inside one transaction** (state rows first, then the records, chart and charge): the database trigger for a completed-procedure record needs the item's completed state row to exist, and EF does not order inserts across tables with no foreign key between them. The transaction makes it atomic.

## Defects found by this attempt's own verification
- **A survivor in the negative controls.** Removing the atomic plan-version check from the completion's save left all 18 service tests passing (the earlier non-atomic check and the unique constraints already caught every case the tests used). A deterministic test was added (a clock hook renames the plan after the version check and before the save) and kills the mutant. See `R01-evidence/artifacts/test-runs/negative-controls-c008*.txt`.
- **A real bug in the new component**, found by its unit tests: the "first load" flag was read inside a state updater after it had been cleared, so nothing was preselected.
- **A colour-contrast failure** in the result panel's links in one theme, found only by the real browser (axe), fixed by using the app's theme-aware link class.
- **The failure message** said "treatment plan could not be saved"; the real browser showed it, and it now speaks about the completion.
- Several first-run failures were mistakes in the new tests (performed times before the plan existed, an occlusal surface on an incisor, a replay with a changed time, comparing entities by reference, a ledger count); none was a product defect.

## Limitations / debt
- **Legacy completions** (the STORY-008 routes) still exist and record only a state; the new operation refuses such a procedure as already completed and it cannot be amended. `ALV-008-C02` (item 36) retires the routes and adopts those completions; Gate D2 cannot honestly pass before that.
- **The acceptance rule compares with the time staff recorded the answer**, not when the patient agreed; a completion dated before a late-entered acceptance is refused (the message says what it compares with). An explicit "agreed on" date is future work.
- **A performed time equal to a recorded acceptance can be refused by a fraction of a millisecond**: the request's time is cut to whole milliseconds, the stored acceptance time is exact, and the service and the database trigger compare exactly (they agree).
- **An ambiguous chart match refuses the whole set;** the person unticks that procedure or corrects the diagnosis links. The review screen shows the server's readiness before submitting.
- Completed is final: no undo; a reversed charge keeps its procedure billed (ALV-007-C01).
- One request completes items of one plan; a visit spanning plans is several submissions.
- Mutation checks cover fifteen rules, not the whole feature.
- The closing "unmutated tree" line of the mutant-1 rerun script reported 18 of 19; eight consecutive reruns of that class and the whole completion set (173 of 173) on the restored tree passed. The cause was not identified; it is most likely that the closing run used the mutated build.
