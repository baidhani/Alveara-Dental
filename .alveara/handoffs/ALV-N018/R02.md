## Scope delivered
- **Write API (Admin-only where stated).** `PUT /api/permissions/overrides` (grant, revoke or revert one cell of a working role), `PUT /api/permissions/delegations` (the closed delegation table), `POST /api/permissions/delegated-grants` (a delegate allows or stops a delegated permission), `GET /api/permissions/delegations` and `GET /api/permissions/my-delegations`. Every write needs CSRF, an `Idempotency-Key`, the policy `expectedVersion` the caller was shown (stale: `policy_changed` 409, nothing stored), a bounded required reason (1 to 500 characters), `confirmed: true`, and for the high-impact list a typed confirmation of the permission name. One transaction moves the version, changes the rows and writes the immutable history row, the audit entry and two idempotency receipts; any failure changes nothing. Stable error codes (see `docs/PERMISSION_POLICY.md`).
- **Protected rules enforced on write.** Protected permissions, the Administrator and Unassigned columns, a role in repair, a change that leaves the cell as it is (`no_change`, `matches_default`). Delegation: only the office manager may be a delegate, only for delegable permissions (never the two assignable ones), only for Dentist, Hygienist, Assistant, FrontDesk and Billing; the delegate must itself hold the permission and the row must be in the delegation table.
- **Opened user list.** `GET /api/auth/users` accepts `ManageUsers`, `ManageAccountStatus` or `RevokeSessions`. An administrator sees all accounts; any other holder sees only accounts whose role is not Admin and whose permissions are a subset of the holder's. Every other caller keeps the existing 403 body.
- **Screens.** Editable Admin permission matrix (source, enabled-account counts, reason, revert, typed confirmation, stale-write recovery, protected and fixed cells locked, refresh every 25 seconds, within the required 30), policy health and repair panel, delegation-table editor, change history for `ViewAuditLog` holders, the office manager's "Who may import documents" card, and the account administration page for holders of the status permissions. Read-only matrix for everyone else.
- **Tests and tooling.** `PermissionPolicyWriteTests` (58), a restore proof for API-written changes, Vitest screens and guards, a real-backend walkthrough (8), and 13 negative controls.
- No migration: the N017 tables carry everything.

## Decisions and deviations
1. **Typed confirmation is the permission name** (the high-impact list in `PolicyWriteRules.HighImpact`, which includes `ManageAccountStatus` and `RevokeSessions`). Matched exactly, never case-folded.
2. **Delegation rules are edited as a simple add/remove list** (a full-table write), not a matrix.
3. **Non-admin holders of the status permissions** are limited to the existing enable/disable and sign-out screens behind the target rules; the screen explains which accounts are shown.
4. **Administrator keeps access during a policy outage** (accepted by the reviewer in ALV-N017).
5. **Policy-wide `expectedVersion`** is the concurrency token (any policy change moves it), checked in the same transaction as the writes. A caller who is one version behind gets a 409 even if the cell they edit did not change; the screen offers a reload.
6. **One N017 test was retired, not renamed silently.** `PermissionPolicyPipelineTests.The_user_list_has_the_same_status_and_body_for_every_role_before_and_after_the_two_assignable_permissions_are_granted` asserted ALV-N017's "the user list is unchanged"; this story changes it by design. It is replaced by a test with a new name that asserts the new rule. The frozen Stage 2 declares it in `stage2/retired_ids.txt`, the evaluator accepts exactly that one missing baseline id and rejects it if it still runs; this is a change to the comparison contract, validated by `stage2/evaluator-validation.txt` (11 of 11 scenarios).
7. **Delegated grants may revoke as well as grant.** A delegate says whether the role may hold the permission; the stored change is whatever moves the cell from the default to that state (grant, revoke or revert), so allowing and stopping use the same endpoint.

- The existing `PermissionMatrixPage.test.tsx` rendered the page outside an auth provider after it started asking who is signed in; the test now mocks the auth context.
- Two N017 pipeline tests asserted a closed user list; updated by design (decision 6).
- The negative-control run found no surviving mutant (13 of 13 killed).

The client has a new `RequireAnyPermission` route guard and `anyPermission` navigation entries.

## Limitations / debt
- The concurrency token is policy-wide (decision 5).
- The two-host proof was not extended to the write endpoints; the next-request revoke and revert are proven in-process (`PermissionPolicyWriteTests`) and on screen against a real host (walkthrough). Two hosts reading one database after a write are covered by the N017 two-host tests, which are unchanged and pass.
- The write path has no new performance budget; the existing evidence tests are unchanged.
- The status-permission holder screens add no new actions; only the existing disable/enable and sign-out screens exist.
- The backend focused and ApiTests runs are from the R01 product commit `41c44ab`; R02 changed no backend file (empty diff). The comment-only edit in `41c44ab` itself came after those runs and was built but not re-tested.
- The refresh is one measurement per run (25.1 s), taken at the worst phase of the polling cycle; the guarantee rests on the 25 s interval plus the measured request and render time, not on a statistical sample.
