## The review finding and how R02 closes it
**ALV-006-C01-R01-01 (P1):** the absent-tooth rule was not preserved when a finding becomes absent, and was not atomic for concurrent writes. Concretely, Planned Missing -> Caries -> Missing Completed persisted an active completed absence beside an active caries, and two writers could both pass the pre-read.

| Required correction | What R02 does |
|---|---|
| 1. Serialize and validate every operation that can create or activate an Absent finding **and** every operation that records a non-presence finding against the same patient/tooth state, atomically | A database trigger `TR_ToothFindings_ToothPresence` (migration `AddToothPresenceInvariant`) fires on every insert and relevant update of a finding. For each (patient, tooth) it touches it first takes an application lock (`sp_getapplock`, exclusive, owned by the transaction) named for the patient and tooth, then checks both directions of the rule. Two writers on one tooth queue; the second sees the first's committed row. It covers recording, moving a finding forward, and any other writer including raw SQL. The service also checks first so the ordinary case gets a clear message. |
| 2. Decide and implement the correction path when a transition would make a tooth absent while other active clinical findings exist | **Refuse, non-destructively, with a stable clinical conflict**: `tooth_has_findings` (409). Nothing is withdrawn, rewritten or moved for the person; the response says "Nothing was changed" and names the way out (withdraw the findings that no longer apply, with a reason such as the extraction, or keep the missing tooth as Planned). This applies when a missing-tooth finding is recorded as Existing or Completed **and** when an existing one is moved to Completed. The database refusal of a concurrent loser maps to the same code (`tooth_absent`, `tooth_has_findings`, or `tooth_busy` if the lock is not granted within ten seconds). |
| 3. Real-SQL tests: (a) Planned Missing -> Caries -> Missing Completed cannot persist; (b) concurrent Missing and Caries cannot both succeed; (c) a permitted replacement/implant stays possible; plus API-level behaviour and regression of the original STORY-006 workflow | `ToothPresenceInvariantTests` (21): (a) the exact sequence through the service and in raw SQL; (b) sixteen simultaneous Missing/Caries pairs, eight simultaneous move-versus-record pairs, and **two real transactions racing on one tooth with one held open** (the second demonstrably waits, then is refused), the reverse order, a different tooth not held up, and the busy refusal; (c) implants and other replacements in every order, withdrawn findings not counting, planned extractions allowed. `ToothPresenceApiTests` (4): the sequence over HTTP, both stable codes, the way out, a replacement, the parent's workflow, and a dentist-versus-hygienist HTTP race. The original STORY-006 classes and walkthrough pass unchanged. |
| 4. Update the handoff acceptance and limitations to state the final proved invariant; remove the simultaneous-write disclaimer | The invariant is stated in `docs/ODONTOGRAM.md`, this handoff and `evidence/ACCEPTANCE_EVIDENCE.md`; the old "not transactional" limitation is removed. |

**The proved invariant.** For every patient and tooth at every moment there is never an active finding whose condition has the `Absent` effect in state `Existing` or `Completed` together with an active finding whose condition has effect `None`; findings with the `Replacement` effect (an implant) or another `Absent` condition may stand beside an absence; a `Planned` or `Diagnosed` absence does not yet make the tooth absent. The trigger judges only what a statement changes, so a withdrawal is never refused and rows written before this migration are not re-judged (they are put right by withdrawing, which is always allowed).

## Decisions and deviations from the prompt's wording (R02 additions first)
1. **The database holds the invariant, under a per-tooth lock taken inside the trigger.** A pre-read in the service cannot be atomic; a lock row or aggregate revision in the application would protect only callers that use it. The trigger takes the lock itself, so it covers every writer and needs no cooperation from the service, which keeps its own check only to give a clear message first.
2. **The correction path is a refusal, not an automatic transition.** The reviewer allowed either. Automatically withdrawing or superseding a person's findings when a tooth is marked missing would change clinical records they did not ask to change; a refusal that names the way out keeps the person in control and loses nothing.
3. **Pre-existing rows are not re-judged.** A database that already holds an absence beside another active finding (R01 could have produced one) is not rewritten by the migration; the trigger checks only changed rows, so such a state can be put right by withdrawing, never blocked by the rule.
4. **Retained from R01:** dentition is a view not a stored mode; a condition's effect on the tooth is data; condition definitions are immutable; `ManageClinicalTemplates` governs the catalogue; links by reference with no creation screen; one history per finding with a read-only tooth timeline; the numbering preference remains unowned.

## Defects found and fixed by this attempt's own verification
- **The review finding itself** (above).
- **A collation conflict in the new trigger** - its staging table took the database default collation, which cannot be compared with the case-sensitive condition code; found when the test fixture applied the migration; fixed by declaring the column with the matching collation.
- **Test-side mistakes** (not product defects): recording the same implant twice in different states, an occlusal surface on front teeth, a misspelled user-event method, and a mutation script that ran against stale binaries after one mutation failed to compile.
- **Mutation checks** (see `evidence/TEST_RESULTS.md`): with only the trigger disabled 10 of 21 fail; with only the service checks removed all 21 pass (the database alone enforces it); with both removed (the R01 behaviour) 16 of 21 fail.

## Limitations / debt
See `docs/ODONTOGRAM.md` ("Limits"): no numbering preference; supernumerary teeth and area findings not covered by the FDI key; absence only through an Absent-effect condition; making a tooth missing needs the other findings dealt with first (deliberate, no one-step "extract and retire" action); rows written before the invariant are not re-judged; no screen to add a link; completing a finding creates no charge; condition definitions immutable; Complete is one click; reads are not audited. **The R01 limitation "the absent-tooth check is not transactional" no longer applies.**
