## Scope delivered (implementation scope of the prompt, item by item)
- **Anatomical tooth identity independent of display numbering** - already the case from `STORY-006` (FDI string stored, display-only mapper); this attempt adds a test that the server holds no numbering column or field anywhere (`OdontogramHistoryAndLinksTests.Numbering_is_not_part_of_a_teeth_stored_identity`, and the real-browser `TRUST AND NUMBERING` step).
- **Permanent, primary and mixed dentition** - the chart has three views over the same findings (Permanent, Primary, Mixed with four arches); switching is a view only (no stored mode, no request); a patient with a primary-tooth finding opens as Mixed; findings on teeth a view does not draw are listed, never hidden; primary teeth have their own Universal letters A-T and Palmer letters.
- **Universal numbering/lettering default with an abstraction for FDI/ISO** - delivered in `STORY-006` and extended to the primary arches; the preference setting is still not built (no story owns it; see "Unresolved questions").
- **Surface selection and tooth-state validation** - surfaces that exist on each tooth (primary included); a condition must apply to the tooth's dentition (an implant is refused on a primary tooth); a tooth recorded as missing takes no other finding except an implant or another absent condition; withdrawing the missing entry makes it present again.
- **Structured caries, restorations, crowns, missing, implants, root canals and extensible condition types** - a `ConditionTypes` catalogue seeded with the six; a person who manages clinical templates can add, retire (with a reason) and reactivate conditions; definitions are immutable once created.
- **Existing, diagnosed, planned and completed lifecycle** - unchanged from `STORY-006`, now on every dentition.
- **Longitudinal event/history model** - a per-tooth timeline (`GET .../odontogram/teeth/{toothKey}/history`) reading every version of every finding ever recorded on the tooth, withdrawn ones included, with who, when and why; a condition's own history; the screen's Tooth history.
- **Link findings to diagnosis/treatment/completed procedure where applicable** - `ToothFindingLink` (append-only, unique per finding, type and reference, recorded in the history, does not change the finding); API, display beside the finding and in the timeline. The targets do not exist yet, so the reference is opaque text and there is no screen to add a link.
- **Preserve historical events when teeth/conditions change** - findings and history are never deleted (triggers), a retired condition keeps its label and stays listed, a condition's meaning cannot be edited, links are append-only.
- **UI/UX** - interactive permanent/primary/mixed chart with legend and lifecycle distinctions (word plus border style); tooth detail with surfaces, findings and longitudinal history; arrow-key navigation; the safety strip stays in the patient header.
- **Security, audit, integrity** - clinical permissions (read `ViewClinicalDocumentation`, write `ManageClinicalNotes`, catalogue `ManageClinicalTemplates`); every change audited with user and time in the same save and PHI-free text; concurrency-safe (row version, unique indexes, six-way race tests); history cannot be silently deleted.
- **Failure paths** - invalid tooth/surface combination (400 `validation_failed`), condition invalid for the dentition (400, field named) or the tooth state (409 `tooth_absent`), stale update (409 `concurrency_conflict`, banner naming a "tooth finding" or "condition type"), unknown condition (400) and retired condition (409 `condition_inactive`), switching representations without losing history (a view, tested).

## Decisions and deviations from the prompt's wording
1. **Dentition is a view, not a stored mode.** The prompt's failure path "switch between mixed/permanent representation without losing recorded history" is met by construction: nothing is stored about it, so nothing can be lost. The default (Mixed when a primary finding exists, else Permanent) is a screen convenience, not a clinical inference from the patient's age.
2. **A condition's effect on the tooth is data** (`None`, `Absent`, `Replacement`), not code that knows the words "Missing" and "Implant", so a practice's own condition (for example "Extracted") can take part in tooth-state validation.
3. **A tooth is absent only through an Existing or Completed finding with the Absent effect.** The chart never infers absence from age or from a primary tooth that should have exfoliated; a Planned or Diagnosed extraction does not make the tooth absent.
4. **Condition definitions are immutable.** The prompt asks that history not be rewritten when conditions change; a mistaken label or scope is corrected by retiring and adding a new condition.
5. **The catalogue is changed with `ManageClinicalTemplates`.** Item 22 names "extensible condition types" without saying who may extend them; this is the permission that already governs the practice's clinical configuration (standard rule 13). It is a decision for the reviewer to confirm.
6. **Links are by reference and have no creation screen.** The targets (diagnosis, treatment plan, completed procedure) are later stories; the model, API, display and history exist, and the later stories call `LinkAsync`.
7. **No new "event table" for the longitudinal model.** Each finding already has an append-only history; the tooth timeline is a read over those histories, so there is one source of truth and nothing to keep in step.
8. **The numbering preference remains unowned.** Not built here; restated in `docs/ODONTOGRAM.md` for the master execution plan.

## Defects found and fixed by this attempt's own verification
- **A code-shape check accepted lowercase** - in the dictionary-order collation `[A-Z]` also matches lowercase letters, so "fracture" passed the database check; fixed with a binary comparison and tested.
- **A column too short** - `TreatmentPlan` (13 characters) exceeded the 12-character link-type column; found by the schema test, fixed to 16.
- **A foreign key that would accept the wrong spelling** - the default collation made the new foreign key accept "caries" for "Caries"; found by the original `STORY-006` schema test, fixed with a case-sensitive collation on both columns.
- **Test-side mistakes** (not product defects): wrong expected counts, a strict-mode locator, a list counted before it loaded, and a stale-change scenario built on a case the system correctly treats as a quiet repeat.
- **Mutation checks** on every new rule (see `evidence/TEST_RESULTS.md`).
