## Failure paths required by the prompt
- Invalid tooth/surface combination - 400 `validation_failed` naming the field (service, API, screen, schema).
- Condition invalid for selected dentition/tooth state - an implant on a primary tooth (400, field `condition`), a finding on a missing tooth (409 `tooth_absent`); screen shows the server's words; real-browser `TOOTH-STATE VALIDATION`.
- Conflicting/stale update - 409 `concurrency_conflict`, the conflict banner (naming a "tooth finding" or "condition type") with a reload that refreshes in place.
- Unknown/inactive condition type - unknown or misspelled code (400), retired (409 `condition_inactive`), not offered by the form; existing findings still read as they did.
- Switch between mixed/permanent representation without losing recorded history - a view, tested to change nothing and ask the server for nothing (service test and frontend test) and shown in the real browser.
