## The three corrections
**C01-3 (30-image cap) and C01-2 (select versus inactivate): one mechanism.** New `LoginBackgroundCatalogGuard` (a transaction-scoped `sp_getapplock`, the repository's existing pattern from `AdminAvailabilityGuard`). `LoginPresentationService` now runs every catalog mutation - add an image, make one available, make one unavailable, choose the shown background - inside one transaction that first takes the lock (`InCatalogTransactionAsync`), then reads the active count and the selection and writes. Two requests that both see 29 can therefore no longer both succeed, and a selection can no longer race an inactivation on stale reads. The refusals are the existing ones (`background_catalog_full`, `background_in_use`, `background_unavailable`, all 409). If the lock cannot be had within 5 s the answer is a clear 409 `catalog_busy` and nothing was written. A derivative file written by an upload that does not commit (refused, failed or rolled back) is removed again. **Triggers 51276-51279 are untouched** and remain the independent backstop; no migration was needed (the review allowed "a serialized guarded operation").

`LoginBackgroundCatalogConcurrencyTests` (3 tests; each competing operation has its own database context and service instance and is released by a `Barrier`):
1. select versus inactivate of the same image, 6 rounds: exactly one succeeds; the loser gets `background_in_use` (select won) or `background_unavailable` (inactivate won); the persisted state never selects an unavailable image; the audit counts for `LoginBackgroundSelected` and `LoginBackgroundInactivated` increase only for the operation that won.
2. two uploads at 29 available images: exactly one succeeds, the other gets `background_catalog_full`; 30 available; exactly one derivative file in the store (the refused upload left none); one `LoginBackgroundAdded` audit entry.
3. an upload against a reactivation at 29 available (+1 unavailable): exactly one succeeds, the other `background_catalog_full`; 30 available; the file and audit counts match whichever won.

**Negative control:** with the lock disabled (temporarily; restored, `cmp` identical) test 2 fails (1 of 3 failed). Test 1 still passes without the lock because the 51277/51279 triggers (read with READCOMMITTEDLOCK) already make the database refuse the bad outcome; that is the backstop working as designed, and is why the review kept it. Test 3 passed by timing in that one run; with the lock the three are deterministic.

**C01-1 (accessibility modes): real browser (`e2e/login-presentation-access.spec.ts`).**
- **200% zoom** is a 640x400 (of 1280x800) and a 960x540 (of 1920x1080) CSS viewport, each in light and dark (4 tests): no horizontal scrolling; Tab order Username -> Password -> Sign in; Sign in and the footer notice scrolled to and verified not covered by anything (`elementFromPoint`); the sign-in failure message visible and not covered; axe, all rules, clean. Screenshots kept.
- **Forced colours** (Chromium's real forced-colours emulation, `forcedColors: "active"`, asserted active by `matchMedia`) at 1280 and 375 px (2 tests). **Finding:** the first run failed 2 of 2 - a real browser does **not** drop a `url()` background in forced colours, so the R01 comment in `LoginLayout.css` ("Forced-colours mode drops the background image by itself") was wrong. Fix: a `@media (forced-colors: active)` rule removes the backdrop image (the inline style needs `!important`) and gives the panel a 2 px `CanvasText` edge in place of its shadow. After the fix: the backdrop computes `background-image: none`; the panel keeps a visible edge; labels, fields, the Sign in button, the notice and the error message have distinguishable system colours and field/button borders; focus outlines are visible on Username, Password and Sign in; the failure message appears; no horizontal scroll. Screenshots (`R02-evidence/artifacts/focused-proof/a11y/`, and the failing run's in `a11y-before/`) show it readable.
