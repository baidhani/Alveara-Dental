## What was built (plan item 57a, acceptance in `R01-evidence/ACCEPTANCE_EVIDENCE.md`)
- **Account-scoped permission `ManageLoginPresentation`.** A separate `AccountPermission` type with its own grant table (`AccountPermissionGrants`), checked by `RequireAccountPermission` against the signed-in ACCOUNT. Because it is not a `Permission` value, the Admin role (which holds every `Permission`), role overrides and the role matrix can never reach it. A **new** installation's bootstrap grants it to the first administrator in the same transaction (audited; the bootstrap response states it: `presentationAdministrator: true` and a plain notice); an **existing** installation gets no holder by inference; a ManageUsers holder grants or revokes it for an enabled named account through `PUT api/auth/{id}/presentation-administrator` (CSRF, audited, idempotent; disabled/Unassigned refused). `/api/auth/permissions` reports it as `accountPermissions`.
- **Managed local catalog.** Five bundled owner backgrounds (`teal-doodle` default, `blue-doodle`, `blue-operatory`, `violet-operatory`, `neon-doodle`) plus administrator-added images. Uploads (5 MB cap) are checked by content (PNG/JPEG only; SVG, GIF, WebP, BMP and anything else refused before decoding; extension must agree), by header dimensions (256-4,096 px per side), total pixels (16,777,216) and frames (an APNG `acTL` chunk is refused, not flattened), then decoded and **re-encoded by SkiaSharp 4.156.0** into a clean derivative (no EXIF/XMP/IPTC/PNG text chunks; long side capped at 2,560 px). Only the derivative is stored, under a server-generated name in `StorageRoot/login-backgrounds`; the original and its file name are never kept. Duplicate (by derivative hash) and a 31st active image are refused. Added images are inactivated, never deleted; the current selection cannot be made unavailable (409 `background_in_use`), backed by database triggers that read with `READCOMMITTEDLOCK`.
- **Display modes** Tile / Stretch ("May distort the image") / Fill ("Recommended for photographs").
- **Anonymous endpoints.** `GET api/public/login-presentation` (`no-store`; background reference, mode, notice or null) and `GET api/public/login-background/{sha256}.{png|jpg}` (only the current selection; 404 otherwise; fixed type, `nosniff`, `Cross-Origin-Resource-Policy: same-origin`, `Content-Security-Policy: sandbox`, server-controlled file name, immutable cache because content-addressed); both rate-limited per address. Missing/unreadable/inactive/invalid selection falls back to the teal default.
- **Footer notice.** Deployment default in `appsettings.json` (`LoginPresentation:DefaultFooterNotice`, the owner's USA text, deployer-editable); custom text up to 1,000 characters and 10 line breaks; no tabs/control characters, `<`, `>` or URL forms; rendered as a text node with `pre-line`; when display is off it is not sent and not rendered.
- **Backup.** New asset class `loginBackgrounds` (excluded from the documents class) and restore check `restored_login_backgrounds_have_their_files`.
- **Client.** `LoginLayout` on `/login`, `/mfa-challenge`, `/reset-password` (owner mockup: page background, full-height solid panel, approved cleaned logo v2, the unchanged form with visible Username/Password labels and the Sign in button, the footer); Practice configuration -> Sign-in screen tab (holders only); the add-background form with the required public-image warning and acknowledgement; the presentation-administrator control on the account page.
- **Audit events:** `AccountPermissionGranted/Revoked`, `LoginBackgroundAdded/Inactivated/Reactivated/Selected`, `LoginFooterNoticeChanged/Reset` (no image bytes, uploaded file names, credentials or full notice text).
- **Migration** `20261112210440_AddLoginPresentation`: three tables, seed, triggers 51276-51279; down refused once a grant or added image exists.

## Decisions and deviations (disclosed)
1. **Account permission as its own type** (`AccountPermission`), not a new `Permission` enum value as the briefing's section 6 worded it: the enum is what the Admin role, the role matrix and role overrides iterate, so a separate type makes "never role-assignable, never inherited by Admin" true by construction with a smaller change. Behavior is exactly as approved.
2. **Bundled tiles are 624 x 624 JPEG (quality 90, 4:4:4)**, not 627 px PNG: 627 px PNG at 256 colours was 277-322 KB (over the 250 KB target); 624 is a multiple of the JPEG block size so the repeat edges carry no block artefacts (measured: edge differences unchanged from the source). They were prepared with Pillow (resize + fresh encode, no metadata written), not with the SkiaSharp upload pipeline; `LoginBackgroundCatalogTests` proves each asset has no APP1/APP13 segment and is within its size target. Logo: the owner-approved cleaned v2, cropped to its letters + 24 px margin, 560 x 251 PNG, no metadata chunks.
3. **Source files:** the owner renamed the tiles (`dentalKeep-background-tile-00` to `-04`) and replaced the neon tile with a reworked version (`tile-04`, SHA-256 `b5d062ca1b275c0cfb1d...`, edges 0.3/0.3 vs 1.9); tiles 00-03 are byte-identical to briefing T1-T4.
4. **Shared test infrastructure:** `BackupTestEnvironment` gains the `loginBackgrounds` source (mirrors production; otherwise every test backup reports the class missing).
5. **Updated expectations caused by the new backup class** (not loosened): `BackupServiceTests` (an old backup's missing-class list) and the auth walkthrough (the history row's class list).
6. The sign-in layout is applied at the route level in `App.tsx`, so the page components and their own tests are unchanged.

## Limitations (stated, not hidden)
0. **Run order:** the negative controls, the chain and the first auth walkthrough ran on `94bcee0`; the auth walkthrough re-run on `5bec8ef`; `65c234b` only adds two fields to the bootstrap response (existing readers ignore them) and was proven by the 29 bootstrap-reader tests; the chain (whose stage 0 bootstraps and checks only the status and user count) was not re-run for it.
1. **200 % zoom and forced-colours mode** were not exercised by a test (the briefing listed them); the layout uses relative sizes and no text over the background, and forced-colours drops background images by browser design, but neither is proven here.
2. **The concurrent select-versus-inactivate race** is guarded by triggers reading with `READCOMMITTEDLOCK`; the triggers are proven with direct SQL (51277, 51279), but no test forces two concurrent transactions.
3. **A holder without practice-configuration access** cannot reach the Sign-in screen tab (it lives in Practice configuration, as briefed); the API itself only requires the account permission.
4. **The owner's development database** does not yet have this migration or a holder: after a deploy the operator applies the migration (`Initialize-DevDatabase.ps1`) and grants the permission to `admin` through Security administration (audited), per the approved existing-installation rule.
5. The added-image thumbnail endpoint for administrators returns any added image (active or not) to the permission holder only; it is not anonymous.
