## The review finding and its correction (R02)
**Finding ALV-016-C01-R01-01.** The required full serial backend regression of R01 reported 3675 passed / 1 failed of 3676: `CompletedProcedureServiceTests.Two_overlapping_sets_submitted_at_once_leave_exactly_one_winner_and_each_procedure_completed_once` ended with SQL Server deadlock error 1205 escaping through `ConcurrencySaveGuard.SaveOrThrowConflictAsync` and `CompletedProcedureService.RecordAsync` as an `InvalidOperationException`. The reviewer's reading, which R01's handoff understated by calling it an intermittent test, is correct: it is a fault in how the completion service handles a deadlock. R01 disclosed the failure but offered isolated reruns as the answer; the review rightly refused that.

**Reproduced first, with a real deadlock.** `CompletionDeadlockTests` engineers a genuine, deterministic SQL Server deadlock (a second session holds an exclusive lock on the billing accounts table while the completion is blocked inside its transaction, then closes the cycle at a moment the test controls; the second session runs at higher deadlock priority so the completion is the victim). On the unchanged code the completion ended with `InvalidOperationException > DbUpdateException > SqlException(1205)`, exactly the reviewer's chain (`R02-evidence/artifacts/reproduction/reproduction-before-fix.txt`).

**Root cause.** `TreatmentPlanService.SaveAsync` already turns a `DbUpdateException` into the documented `save_failed` (503). But EF Core's default SQL Server execution strategy wraps a *transient* provider error (a deadlock is one) in an `InvalidOperationException` ("likely due to a transient failure"), so the handler's `catch (DbUpdateException)` never saw it and the exception left the service raw. Ordinary save failures were handled; the one failure SQL Server tells you to simply run again was not.

**Correction** (`Architecture/Concurrency/DeadlockRetry.cs`, `CompletedProcedureService.Deadlock.cs`, two public methods delegating to it):
- `DeadlockVictim.Is` finds error 1205 anywhere in an exception chain (raw, inside a `DbUpdateException`, inside EF's `InvalidOperationException`, inside an `AggregateException`) and nothing else. Timeouts and lost connections are deliberately not classified: after them it cannot be known whether the work committed. A deadlock victim is the one transient failure that is always safe to run again, because the server has already rolled its whole transaction back.
- `DeadlockRetryPolicy` runs the whole operation again at most **3 attempts in all**, with a short pause that grows with each failure and carries jitter. Each attempt clears the change tracker and starts from scratch (it re-reads the plan and re-checks the caller's row version and key), so an attempt that runs after the competing request committed meets that request's outcome (a **replay** of its own key, a `concurrency_conflict` because the plan's version moved, or `items_not_completable`) instead of recording anything twice.
- `CompleteAsync` and `AdoptAsync` (the two operations that record a set inside one transaction) run through the policy. After the last attempt the caller gets the documented `save_failed` (503): "The completion could not be saved because the database was busy, so nothing was completed" (adoption: "... adopted"), logged by error class only. Everything else (domain refusals, conflicts, cancellation, any other failure) passes through exactly as before, on the first attempt.
- **The all-or-nothing completion-set invariant is untouched**: each attempt is still one explicit transaction that commits or rolls back whole.

**Proof.** `CompletionDeadlockTests` (10 tests, all with real deadlocks or a real captured 1205): a completion victimised once is retried and succeeds exactly once and replays on the same key; victimised on all three attempts it ends in `save_failed` 503 with the plan, states, events, audit and ledger exactly as before; after a deadlock an overlapping winner that commits during the pause leaves exactly one winner and no duplicates; after a deadlock an identical double submit replays instead of recording twice; adoption is retried and exhausts the same way; a domain refusal is not retried; the classifier recognises a real 1205 however wrapped and rejects a different SQL error, a timeout and null; the policy retries only deadlock victims, within its bound, and wraps the last failure when it gives up. Each retry test also asserts that a retry was logged, which proves a deadlock really happened. The class passed on three further runs in a row. The full serial backend regression passed **3686 of 3686**, including the test that failed in R01.

**Effect on ALV-008-C01's (and ALV-008-C02's) completion contract.** The contract is unchanged, so the completed story is **not reopened**: no request or response shape, route, status code (apart from a deadlock victim now ending in the already-documented `save_failed`), schema, rule or message changed. ## Decisions and deviations from the prompt's wording
- All R01 decisions stand (a second Prescription composer tab beside STORY-016's quick entry; amendment as a superseding record; the allergy-conflict policy is STORY-016's review-note rule; printing as a logged read; typing-error ceilings).
- **The retry is at the operation level, not inside the save.** A retry inside `SaveAsync` would re-run a save in a transaction that the server has already rolled back, with a tracker that still holds the failed attempt's entities; re-running the whole operation re-reads and re-checks everything, which is what makes it idempotent.
- **Attempts and pause.** 3 attempts in all, a pause of 40 ms times the failure number plus up to 40 ms of jitter (growing, so two victims do not collide again in step). These are typing-and-latency judgements, not clinical or legal limits; they are constants of the policy and the tests inject the pause.
- **Amendments and plan edits are not covered** (see limitations); the finding concerns the completion race.

## Defects found by this attempt's own verification
- The reproduction itself: my first engineered scenario asked for a shared table lock, which did not conflict with what the completion held, so no deadlock formed and the test passed vacuously (I did not establish why; an exclusive table lock does conflict, and that is what the tests use); a deadlock-counter assertion meant to catch that does not exist on LocalDB (no such performance counter). Both were replaced by an exclusive table lock and by proving the deadlock through the exception chain that actually escaped (before the fix) and through the retry log and the policy's retry count (after it). A vacuous reproduction would have proved nothing.
- Three mistakes of my own in the first draft of the new tests (a performed time that differed between a request and its replay, an array compared by reference inside a tuple, a missing `using static`), none a product defect.
- Negative controls found no test gap: 12 of 13 killed on the first run; the 13th (D08, clearing the change tracker between attempts) is an equivalent mutant, documented.
- No defect in earlier stories' code beyond the finding itself was found by this attempt.
