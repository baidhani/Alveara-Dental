## Scope delivered
- **Recall:** pure next-due calculation (`RecallCalculator`: practice-local date of the last completed visit plus whole days at 09:00 practice time, lead time, lapse after a maximum visit age, opt-out, open recall and future booking, with a fixed verdict order); practice settings (**off by default**, default interval 180 days, lead 30, maximum visit age 24 months, due-soon 7 days, all with limits) and per-patient interval/opt-out with reset; a scheduler that only enqueues durable jobs and a handler that re-checks the world and makes the one unassigned recall task.
- **Unscheduled accepted treatment:** a scheduler and handlers that make one task per accepted-and-unscheduled state of a plan item (due 7 days after acceptance) and close it, as the system with the reason in its note, when the treatment is scheduled, completed, declined or withdrawn.
- **Durable reminders:** STORY-009 reminder delivery now runs as one job per task, due time and channel on the ALV-N002 queue (survives restart, not duplicated by retry; a job that fails all attempts gets fresh ones after a cool-down while the reminder is owed); the old entry point stays as an inline wrapper so the STORY-009 tests pass unchanged; unassigned tasks remind the office managers.
- **Work queue and task operations:** `GET /api/work-queue` (filters overdue, due soon, unassigned, mine, all; narrowing by priority, kind, owner or none; counts; paging), claim, assign/reassign (or return to the unassigned queue for system tasks), set priority, link an appointment, each with the row version and an audit entry and history event; patient follow-up timeline; recall settings and patient recall endpoints; new permission `ManageRecallSettings` (Admin, Office Manager).
- **UI:** Work queue page (chips with counts, narrowing, table, Take, Owner and priority, Complete, Cancel, 60 s refresh paused while a form is open), recall card and follow-up timeline on the patient's follow-ups page, Recall settings page; priority and overdue are said in words as well as shown.

## Architecture, schema, API, UI, security, configuration, measurement changes
- **Schema** (migration `20261024060516_AddWorkQueue`): `FollowUpTasks` gains Priority, Kind, AppointmentId, SourcePlanItemId, SourceKey (unique when set), ClosedBySystem, and nullable AssigneeUserId/CreatedByUserId with shape check constraints; new `RecallSettings` (one row) and `PatientRecallPlans`; follow-up triggers altered for the new columns; event and delivery checks widened. Old rows backfill to Manual/Normal. Rollback is covered by the existing migration inventory (`RealMigrationInventory` lists the rollback test classes).
- **API:** see `docs/RECALL_AND_WORK_QUEUE.md`. All writes are CSRF-protected and versioned; 409 `task_changed`, `plan_changed`, `settings_changed` for stale changes.
- **Security:** `ViewFollowUps` reads the queue and timeline; `ManageFollowUps` acts; `ManageRecallSettings` changes the practice settings; billing and anonymous callers are refused (tested).
- **Configuration:** `FollowUps:WorkPollSeconds` (default 300; 0 off). No secrets introduced.
- **Observability:** each pass that did something logs one structured line (`followup_work_pass ...`); failures log the error class only.

## Decisions and deviations
Five decisions were put to the user before building and approved: (1) move STORY-009 reminder delivery onto the job queue behind an inline wrapper; (2) recall OFF by default with a 30-day lead and a 24-month window; (3) unscheduled accepted treatment as stored tasks reconciled by jobs (not a computed view); (4) defaults 180-day recall, 7-day due soon, `ManageRecallSettings` for Admin and Office Manager; (5) unassigned reminders go to the office managers. Other assumptions: "last completed visit" means an appointment with status Scheduled and flow state Completed; system tasks have no creator and no owner; source keys use colons because the notification source-key check refuses hyphens; email or SMS reminders are out of scope (the channel seam exists).

## Limitations and debt
- A recall task is not closed by the system when the patient books (only an open recall blocks a new one); a possible refinement, not in scope.
- A recall or unscheduled-treatment job that fails all its attempts stays `Failed` for triage; unlike reminder jobs it is not reset automatically.
- The browser demo seeds the year-old visit in SQL and does not include accepted-but-unscheduled treatment or a killed API process (see `DEMO_EVIDENCE.md`); those behaviours are proven at the service and database level against a real SQL Server.
- No full backend regression was run (Stage 1). The frozen Stage 2 contract is in `R01-evidence/stage2/`.
- Size: every new production file is under the 500-line ceiling (largest: the migration, 465 lines, apart from its generated designer); the new test classes `WorkQueueApiTests` (583 lines) and `WorkQueueSchemaTests` (374) are the large ones. `FollowUpService.cs` was touched but not split.
