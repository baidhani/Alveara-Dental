## Prior attempt decision

R01 was reviewed and returned `CHANGES_REQUIRED` with three blocking findings, all in the client:

1. **ALV-N009-R01-01 (P1):** passing the known session expiry left protected UI mounted and the caller marked signed in — the expiry poller only cleared the `sessionExpiringSoon` warning flag, it never transitioned `AuthContext` state to `signed-out`.
2. **ALV-N009-R01-02 (P1):** a permission/role change made elsewhere during a signed-in visit was not revalidated — `refresh()` ran only on mount and after login/MFA, not on any bounded interval or activity signal, so stale nav/protected state could persist indefinitely while the caller moved among routes that don't fetch protected data.
3. **ALV-N009-R01-03 (P2):** the validated deep-link return destination was dropped when reauthentication required MFA — `MfaChallengePage` always navigated to `/` after a successful challenge instead of the location `RequireAuth` originally captured.

## Corrections made this attempt

All three corrections are isolated to the client; no backend change was required or made.

### ALV-N009-R01-01 — expiry now ends the signed-in state

`AuthContext.tsx`'s expiry-poll effect (`src/alveara-client/src/contexts/AuthContext.tsx:85`-`108`): when `remainingMs <= 0`, the effect now calls `refresh()` instead of just clearing the warning flag. This re-asks the server rather than assuming signed-out locally, deliberately — the review itself flagged that the app uses sliding-expiration cookies, so a session the caller kept actively using may already have been renewed server-side past the timestamp this client captured at the last refresh. `refresh()` reconciles against current server truth either way: a genuinely expired cookie 401s and clears to `signed-out` (which `RequireAuth` turns into an immediate redirect, unmounting protected UI); a transparently renewed one returns a fresh `sessionExpiresAtUtc` and the effect re-arms against it.

### ALV-N009-R01-02 — bounded revalidation while signed in

A new effect in `AuthContext.tsx` (`:70`-`84`) runs only while `state.kind === "signed-in"`: a 30-second interval calls `refresh()`, and `window`/`document` listeners call it again on `focus` and `visibilitychange`. The server's `SecurityStamp` rotation on any role/permission change makes a stale cookie fail this call the moment it fires, so this both narrows/widens the caller's effective permission set and clears state outright if access was revoked. `AuthProvider` still sits outside `BrowserRouter` (unchanged from R01), so this is the poll/focus option the review itself offered as an alternative to a route-navigation trigger, not a partial fix.

### ALV-N009-R01-03 — MFA deep-link redirect survives the extra hop

`LoginPage.tsx` now passes the already-computed `redirectTo` (the location `RequireAuth` captured, or `/` if none) into `navigate("/mfa-challenge", { state: { challengeToken, redirectTo } })`. `MfaChallengePage.tsx` reads `redirectTo` from `location.state` (defaulting to `/` if absent, e.g. a direct visit to `/mfa-challenge` with no prior redirect) and navigates there — not to `/` unconditionally — after a successful challenge.
