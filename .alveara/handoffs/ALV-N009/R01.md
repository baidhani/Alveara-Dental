## Implementation scope delivered

Per the authoritative prompt (`GPT Docs/Alveara_Dental_Execution_Plan_v4.md`, item 6):

- **Bind shell/navigation module registry to server-authoritative permissions/capabilities** — `moduleRegistry.ts` gained an optional `requiredPermission` field; `AppShell` filters the rendered nav against it via `useAuth().hasPermission()`, which is itself now defensive against a malformed/missing permissions array.
- **Signed-in account identity/context presentation** — the sidebar footer shows the signed-in caller's username and role, sourced from `GET /api/auth/permissions`'s response (extended this attempt to also return `username`).
- **Session timeout/expiry UX and re-authentication path consistent with `ALV-001-C01`** — `GET /api/auth/permissions` also now returns `sessionExpiresAtUtc` (the real cookie expiry, read from the authentication ticket, not client-guessed). `AuthContext` exposes `sessionExpiringSoon`, true within a 2-minute window before that real expiry; `AppShell` shows a warning notice when true. The existing `?reason=expired` convention on `LoginPage` (already built in `ALV-001-C01`, previously only reached by `MfaSettingsPage`'s own ad hoc redirect) is now the single, centralized re-authentication path every protected route uses via `RequireAuth`.
- **Permission-denied route/action states** — `RequirePermission` (new, `RouteGuards.tsx`) renders the existing `PermissionDenied` component at the route level, before a protected page's own data fetch starts, for any route whose module entry declares a `requiredPermission`.
- **Direct URL/deep-link authorization behavior** — `RequireAuth` (new, `RouteGuards.tsx`) wraps the entire authenticated shell in `App.tsx`; an unauthenticated direct/deep-link request is denied (redirected to `/login?reason=expired`, preserving the intended destination) before `AppShell` or any child route ever mounts. `RequirePermission` does the equivalent for a signed-in-but-under-permissioned caller. Neither guard is the actual access-control authority — the server continues to re-check every protected endpoint via `[RequirePermission]` regardless of what the client renders or hides.
- **Global sign-out/account menu** — the sidebar footer's account block includes a keyboard-reachable "Sign out" button, calling the `logout()`/`POST /api/auth/logout` path that already existed end-to-end in `ALV-001-C01` but had no UI trigger until now.
- **Navigation extension contract for later modules** — `ModuleDefinition.requiredPermission` is optional and permission-named (not role-name branching), so a future module opts into gating by adding one field; an entry with no `requiredPermission` is visible to every signed-in caller by default.

## UI/UX deliverables delivered

- Role/capability-aware navigation (module registry filtering, above).
- Session-expiry warning (`alv-shell__session-warning`, shown only to the signed-in caller it concerns — computed entirely from that caller's own `sessionExpiresAtUtc`, never another user's).
- Permission-denied page/action state (`RequirePermission` → existing `PermissionDenied` component, reused not reinvented).
- Keyboard-accessible account/session menu (plain focusable `<button>` elements in normal tab order, positioned after the nav links so existing keyboard-navigation regression coverage is unaffected).

## Security, audit, and data-integrity requirements — how each was met

- **Server/API enforcement remains authoritative** — no client-side check in this story ever substitutes for `[RequirePermission]`; `RequireAuth`/`RequirePermission` only ever deny earlier/more gracefully than a 401/403 would, never grant more than the server would.
- **Hidden navigation is not treated as authorization** — confirmed by the real-backend Playwright test and `App.routeGuards.test.tsx`: a direct URL to a hidden route is independently denied by `RequirePermission`, not merely omitted from the nav.
- **Session transition clears protected UI state appropriately** — signing out (or a reactive 401) transitions `AuthContext` to `signed-out`, which `RequireAuth` turns into an immediate redirect away from any protected route; no protected component instance survives that transition on screen.

## Failure paths handled

- **Permission changes while signed in** — the next `GET /api/auth/permissions` refresh (on any subsequent navigation) reflects the new permission set; `hasPermission` and nav filtering are always derived from the current `AuthContext` state, never cached from the original sign-in.
- **Session expires during edit** — proactively warned via `sessionExpiringSoon`; reactively, any authenticated call that now 401s (via the new `setUnauthorizedHandler` hook in `authApi.ts`) immediately transitions to signed-out, and the next route render (or an in-flight guard) redirects to `/login?reason=expired`.
- **Direct URL to unauthorized module** — denied by `RequirePermission` (signed-in, lacking permission) or `RequireAuth` (not signed in at all), covered by both unit and real-backend browser tests.
- **Server denies an action the cached UI thought was allowed** — any `authApi.ts` call that 401s now reactively signs the caller out via the same `setUnauthorizedHandler` hook, rather than leaving a stale "still signed in" UI on screen indefinitely.

## A genuine bug this story's own guard surfaced and fixed

Confirming MFA enrollment (`ConfirmMfaEnrollmentAsync`, built in `ALV-001-C01`) rotates `SecurityStamp` by design, to invalidate every *other* outstanding session — but the `mfa/confirm` endpoint never re-issued the *confirming caller's own* cookie, so that caller's own session became invalid too, immediately. This was invisible before `ALV-N009`: nothing reacted to the now-stale cookie client-side, so `MfaSettingsPage`'s own locally-tracked "confirmed" UI state kept showing success regardless. The moment `RequireAuth` started reacting to `AuthContext`'s real state, this surfaced as "confirm MFA, instantly get redirected to a session-expired sign-in screen" — caught by this attempt's own real-backend Playwright run before it ever reached a human. Fixed: `mfa/confirm` now re-signs-in with the fresh account state (including the new stamp) immediately after confirming, exactly like login/bootstrap already do. `ConfirmMfaEnrollmentAsync` now returns the updated `UserAccount` instead of `void` to make this possible. Covered by a dedicated real-HTTP backend test (`AuthControllerMfaConfirmSessionTests.cs`, both the first-enrollment and replacement-factor paths) and exercised live by the real-backend Playwright suite's existing MFA-enrollment test, which now passes end to end again.
