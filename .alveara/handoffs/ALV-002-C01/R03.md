## Prior attempt decision

R02 was reviewed and returned `CHANGES_REQUIRED`. The review closed three of the four R01 findings (conflict presentation, genuine audit-INSERT failure test, test accounting/timestamps) and left the audit viewer's data presentation incomplete, with two new P2 findings, both confined to the audit API/viewer contract:

1. **ALV-002-C01-R02-01 (P2):** `GET /api/auth/audit-log` projected only `Id, EventType, TargetUserAccountId, PerformedByUserAccountId, Details, TimestampUtc`. It never serialized the shared `EntityType`, `Reason`, `CorrelationId`, so the viewer's entity column rendered a dash even for brand-new events whose entity type had been recorded. The R02 handoff's statement that the endpoint "now return[s] the richer entity/reason/correlation metadata" was **wrong** — the controller had not been extended; R02's component test fed the page a mocked response the real endpoint could not produce, and the real-browser test checked event names only.
2. **ALV-002-C01-R02-02 (P2):** the viewer's description said "the most recent 500" events, but `getAuditLog()` sent no `take` parameter, so the server default of 100 applied.

## Corrections made this attempt

### ALV-002-C01-R02-01 — the real audit API now returns the shared metadata

`AuthController.GetAuditLog` now also projects `EntityType`, `Reason`, `CorrelationId` (one added block, original fields, ordering, bound, and `[RequirePermission(Permission.ViewAuditLog)]` gate all unchanged). Rows written before the metadata existed — or by callers that supply no reason/correlation — honestly serialize those fields as `null`; nothing is invented.

Proof, at each layer the review named:

- **API contract test** (`AuthControllerPermissionMatrixTests.GET_audit_log_round_trips_entity_type_reason_and_correlation_id`): stages two events through the actual shared `AuditService.Record` path inside the real `WebApplicationFactory` host (one with reason + correlation id, one without), reads them back over authenticated HTTP, and asserts `entityType`/`reason`/`correlationId` round-trip exactly, and stay `null` where none was supplied. This is the same shape of probe the reviewer used, now a permanent test.
- **Real-browser test strengthened** (`auth-real-backend.spec.ts`, test 7): in addition to the existing event-name assertions, the row for the real `SessionTimeoutChanged` event this session produced must visibly contain `UserAccount` (not a dash).

### ALV-002-C01-R02-02 — the viewer requests the window it claims

`authApi.ts` exports a single `AUDIT_LOG_WINDOW = 500`; `getAuditLog()` requests `/api/auth/audit-log?take=${AUDIT_LOG_WINDOW}`, and `AuditLogPage` generates its description text from the same constant, so the claim and the request cannot drift apart. The server's own 500 clamp is unchanged.

Proof:

- **Frontend request-contract test** (`AuditLogPage.test.tsx`): asserts the actual fetch URL contains `take=500` and the visible description names that same number.
- **Backend window test** (`AuthControllerPermissionMatrixTests.GET_audit_log_defaults_to_100_rows_and_honors_take_up_to_500`): with 130 events staged, the default request returns exactly 100, `take=500` returns all 130 staged events, and `take=9999` is clamped to at most 500 — proving both why the client must ask explicitly and that the server bound is intact.
