## Why this story exists

STORY-002 proved role-change auditing works. This story generalizes that into reusable primitives (audit event model, optimistic concurrency, idempotency, record-lifecycle vocabulary) so later clinical/financial domain stories adopt a shared trust mechanism instead of each inventing their own — without declaring which lifecycle pattern applies to a domain record that doesn't exist yet.

## Implementation scope delivered

- **Reusable audit service/event model** (`Architecture/Auditing/AuditService.cs`) — a static `Record(db, eventType, entityType, entityId, performedByUserAccountId, details, reason?, correlationId?)` method covering actor, timestamp, action, target/entity identity, reason/context, and correlation metadata. `AccountService.AddAudit` (the single private helper all 22 of its existing audit-write call sites already funneled through) now delegates to it — **zero call-site changes**, so STORY-002/ALV-001-C01's own passing tests are untouched. `AuditLogEntry` gained nullable `EntityType`, `Reason`, `CorrelationId` columns; historical STORY-001/ALV-001-C01 rows simply predate them (left `null`, not backfilled with a guess).
- **Append-only/immutable-to-ordinary-users audit semantics** — reused, not reinvented: STORY-002's existing `AlveraDbContext.SaveChanges`/`SaveChangesAsync` guard (throws `AuditLogImmutableException` on any `Modified`/`Deleted` `AuditLogEntry`) already covers every write through the new shared service, since both write to the same table. Doc comment updated to describe it as the shared primitive.
- **Optimistic concurrency/version-token primitives** (`Architecture/Concurrency/`) — `ConcurrencyConflictException` (stable, domain-level conflict type with a `ToProblem()` → `ConcurrencyConflictProblem(Error, EntityType, EntityId)`, the shared conflict-result shape usable by any future API/UI) and `ConcurrencySaveGuard.SaveOrThrowConflictAsync`, which wraps EF Core's own `DbUpdateConcurrencyException`. Demonstrated against `StaffProfile.RowVersion` (SQL Server `rowversion`, `IsRowVersion()`), the representative currently-existing mutable record — see "A genuine conflict found and resolved" below for why `UserAccount` was rejected as the demonstration target.
- **Idempotency/correlation primitives for consequential commands** (`Architecture/Idempotency/`) — `IdempotencyReceipt` + `IdempotencyGuard` (`AlreadyProcessedAsync`/`MarkProcessed`), generalizing `BackgroundJob.IdempotencyKey`'s pattern (already established by `ALV-N002`) beyond background jobs to any consequential command. A real database unique index on `(CommandType, IdempotencyKey)` is the actual duplicate-command guarantee, not an application-level check-then-act race.
- **Reusable record-lifecycle interfaces/patterns** (`Architecture/Lifecycle/RecordLifecycleGuard.cs`) — `RecordLifecycleAction` enum (`Finalize`, `Amend`, `Addendum`, `Void`, `Reversal`, `Inactivate`) and `RecordLifecycleGuard.EnsureAllowed(requested, allowedFromCurrentState)`, throwing `UnknownLifecycleTransitionException` otherwise. Deliberately the only thing shipped for lifecycle semantics — no domain record, no state machine, no rule about which actions apply to which record type; each owning domain story defines its own record type and allowed-transition set later.
- **Audit failure policy** — explicit and tested: a consequential action's business change and its coupled audit write live on the same `DbContext` and commit via the same `SaveChangesAsync` call (unchanged from STORY-001's original design, now formalized as policy for the shared service too), so a required audit write failing takes the business change down with it, atomically. Proven by a new test (see below) that deliberately invalidates the audit side of a single `SaveChangesAsync` call and shows the business change never persisted either.

## Security, audit, and data-integrity requirements — how each was met

- **Audit read permissions separated from business write paths** — unchanged from STORY-002: `GET /api/auth/audit-log` requires `Permission.ViewAuditLog`; no business write path requires or grants that permission.
- **Ordinary users cannot modify/delete audit events** — unchanged from STORY-002, now proven to cover every write through the new shared `AuditService` too (same table, same guard).
- **No secrets or unnecessary PHI logged** — `AuditLogEntry.Details`/`Reason` carry only the same kind of operational summaries STORY-001/ALV-001-C01 already wrote (role names, event descriptions); no new field introduces a secret or PHI risk.
- **No invented clinical/financial lifecycle states** — `RecordLifecycleAction`/`RecordLifecycleGuard` are tested only against synthetic allowed-sets in the test file itself, never against any real domain record.

## Failure paths handled

- **Required audit write fails** — any `AuditLogEntry` mutation attempt (the closest analogue to "the audit write side of a transaction goes wrong" available without inventing a fault-injection seam) throws `AuditLogImmutableException`, which takes the whole `SaveChangesAsync` call — and the coupled business change — down with it. See `A_business_change_cannot_commit_if_its_coupled_audit_write_is_invalid`.
- **Stale concurrent update** — `ConcurrencyGuardTests.Saving_a_stale_read_of_the_same_staff_profile_is_rejected_as_a_concurrency_conflict`.
- **Duplicate command/correlation key** — `IdempotencyGuardTests.A_duplicate_command_key_is_rejected_by_the_database_s_unique_constraint`.
- **Unauthorized audit access** — unchanged from STORY-002 (`GET_audit_log_is_allowed_for_a_role_holding_ViewAuditLog_and_denied_for_one_that_does_not`).
- **Unknown lifecycle transition requested by a domain** — `RecordLifecycleGuardTests.A_requested_transition_outside_the_allowed_set_throws_UnknownLifecycleTransitionException`.

## A genuine conflict found and resolved during this attempt

The first implementation added `RowVersion` directly to `UserAccount` (the obvious "representative currently-existing mutable record" — it's mutated by `ChangeRoleAsync`, `ResetPasswordAsync`, `RevokeAllSessionsAsync`, etc.). The full backend regression run caught **three genuine `ALV-001-C01` test failures** (`An_MFA_challenge_issued_before_a_role_change_is_rejected_afterward`, `...before_an_explicit_session_revocation...`, `...before_a_password_reset...`), each throwing a real `DbUpdateConcurrencyException`.

Root cause: `UserAccount` already has its own deliberate, already-approved concurrency-safety design — several methods (`LoginAsync`'s lockout-counter increment and success-path reset, among others) use atomic `ExecuteUpdateAsync` bulk updates specifically to stay race-safe *without* a load-modify-save cycle, and these bypass EF's change tracker entirely. Adding a generic change-tracker-based `RowVersion` column meant any `UserAccount` entity already tracked earlier in the same `DbContext` (common in these multi-step tests) held a stale version token after one of those bulk updates silently advanced the real row's version — so a later, entirely legitimate, non-concurrent update on the *same* context raised a false-positive conflict.

This is exactly the kind of case where "a required architectural change would invalidate a verified course criterion" — caught before packaging, not after. Resolution: moved the demonstration to `StaffProfile.RowVersion` instead. `StaffProfile` has no competing bulk-update path anywhere in the codebase (confirmed by search), so it demonstrates the primitive cleanly without touching `ALV-001-C01`'s already-approved concurrency design at all. The migration was regenerated accordingly (`StaffProfiles.RowVersion`, not `UserAccounts.RowVersion`).
