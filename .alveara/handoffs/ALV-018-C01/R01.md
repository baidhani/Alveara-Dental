## Scope delivered
- **Package.** One ZIP per patient or for every patient: `README.txt`, `manifest.json` (written last, SHA-256 and size of every other file), `data/<domain>.json` for the 19 domains, the readable record (`readable-record.html`, or one page per patient under `readable-records/`) and, by default, the document files under `documents/<patient folder>/<document id>/<file>`. Manifest format `alveara.patient-data-package` version 1 with schema version (last migration), application version, export id, time, actor, scope, result `Complete` or `Partial`, included and excluded domains with the reason for each exclusion, file list, document statuses with the recorded and the found hash, patient-folder map, read consistency, and a `problems` list with stable codes. FHIR is reserved (`null`).
- **Domains and exclusions.** Registration (with its change history), appointments, forms, visits and notes, medical history, safety alerts, dental chart, diagnoses, periodontal charting, treatment plans, completed procedures, billing, prescriptions, documents, messages, follow-up, recall, referrals and lab cases, and merge history. Excluded and said so: accounts and staff identities, credentials and one-time codes, the access policy, the audit log, practice configuration, technical bookkeeping. A completeness test fails if a table is added to the database without being placed in a domain, a lookup or an exclusion.
- **Readable record.** One function used inside the package and stand-alone (its own permission, history row and audit event): a self-contained page (no script, no outside file, content-security policy), times in the practice time zone with the UTC offset, empty sections say so.
- **Endpoints** `api/patient-exports`: `POST patients/{id}/package`, `POST all-patients/package`, `POST patients/{id}/readable-record`, `GET history`, `GET overview`. POST with CSRF; no-store; stable error codes (`patient_not_found`, `patient_merged`, `too_many_patients`, `package_too_large`, `export_in_progress`, `permission_revoked`, `permission_policy_unavailable`, `invalid_folder_naming`, `invalid_limit`, `export_failed`).
- **Permissions.** `ExportPatientData`, `ExportAllPatientData`, `ExportPatientReadableRecord`: Administrator only by default, grantable (not protected) through the permission policy.
- **History and audit.** New table `DataExportHistory` (one migration, `AddDataExportHistory`): a row is written as `Started` before anything is read and finished once; the database refuses delete and change of what was recorded. Audit events `PatientDataPackageExported`, `AllPatientDataPackageExported`, `PatientReadableRecordExported`, `DataExportFailed`, written in the same save as the finish and before anything is sent. No patient name, no content, only ids, counts, sizes and hashes.
- **Limits and failure paths.** 5,000 patients and 2 GB (configurable `DataExport` section), explicit read timeout, temp files deleted on every path, a second all-patients export refused while one runs, permission rechecked on a fresh scope before reading, after every domain, every 250 patients and before delivery, a document missing or with a different hash listed in the manifest and the package marked `Partial`, a domain that cannot be read listed `Unavailable`.
- **Snapshot read.** The all-patients export reads inside one snapshot transaction when the database option `ALLOW_SNAPSHOT_ISOLATION` is on, otherwise table by table; the manifest says which. The one-patient export reads table by table. The option is set by the database scripts (`Initialize-DevDatabase.ps1`, the walkthrough runner), never by the application.
- **Screen** `/admin/exports` ("Export patient data"): scope and format choices shown by permission, document files on or off, patient folder naming with a warning, counts against the limits, what a package holds and leaves out, cancel while running, a plain "incomplete" warning for a Partial package, and the history with results in words and times in the practice time zone. A "Download readable record" button on the patient's page.
- **STORY-018 unchanged.** Its `alveara.patient-export` v1 file, the "Export patient file" button and the import are untouched and still pass (see `R01-evidence/PARENT_REGRESSION.md`).

## Decisions and deviations
1. **One ZIP, no new dependency** (`System.IO.Compression`). FHIR is not included (manifest `fhir: null`), by decision with the owner.
2. **Three permissions, all Administrator-only by default and grantable**: one patient, every patient, the stand-alone readable record. The history shows a person their own exports unless they hold `ExportAllPatientData`.
3. **Document files travel by default**, with a manifest-only option; the manifest lists every document either way with its recorded hash.
4. **Patient folders** by id (default) or `Last-First_<id>`, chosen per export or by `DataExport:DefaultFolderNaming`; the manifest maps every patient to its folder.
5. **The audit log is excluded** from the package; disclosures are in the export history.
6. **Snapshot isolation only for the all-patients export**, with fallback and a manifest field. The database option is set by scripts, never by the application (owner decision).
7. **Downloads are POST with CSRF** (each writes a history row and an audit entry).
8. **A merged-away patient's readable record returns 409** (the surviving record carries it).
9. **The command-center test fix (`1de9de5`)** touches an existing test outside this story's scope. It is test-side only, small, and disclosed: the portal's own sync put `STORY-000` in `progress.json` without adding it to `plan.json`, so the screen shows 18 verified stories and the test expected 19.

## Limitations / debt
- **The package is not encrypted.** It holds personal health information; whoever holds the file holds the data. The README says so.
- No progress while an export runs (one synchronous request; a proxy with a short time limit could cut a large export off).
- Not covered by a test: one patient's readable page failing while others succeed (handled in code: that patient is a problem, the rest continue); the history table's rollback guard (error 51253).
- The history proves the server produced and sent a package, not that the browser received it.
- History rows show "Unknown staff member" for an account with no staff profile.
- `scripts/Initialize-DevDatabase.ps1` (which turns the snapshot option on) has not been run on the `AlveraDev` database; a database without the option reads table by table and says so.
- No FHIR copy; no import of a package (`ALV-018-C02`).
- The mocked browser suite has 2 skipped tests: a data-driven test in `architecture-map.spec.ts` skips itself when every planned portal story already shows progress.
