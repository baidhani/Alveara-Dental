## 3. Leaks, processes, ports (snapshots before and after every step: `gate2_runs/snapshots.txt`)
- `AlveraTest_` databases 49 at the start of Gate 2 and 49 after every canary run and after each of the three full runs. `AlveraRestore_` 56 and `AlveraMigrationFailureTest_` 1 constant throughout. No orphan dotnet/gpg/testhost process and port 5193 free in every snapshot.
- **Test logins grow by 2 per full run (226 to 240 over this evidence set).** This is NOT caused by parallelism or by the retry work: it reproduces on the unchanged baseline code in serial mode (Phase 1a baseline `1b92fcf`: `LeastPrivilegeAccessTests` alone, 224 to 226). Root cause found: `LeastPrivilegeAccessTests.DisposeAsync` runs `DROP USER ...; DROP LOGIN ...` inside `try { } catch { /* best-effort */ }`; the test's own restricted connection is still pooled and logged in as that login, so SQL Server refuses the drop and the failure is swallowed (the "never swallow an error" rule). It is a pre-existing leak, listed here because the review requires zero leaks. **Proposal, not implemented:** clear the restricted pool before the drop and log (not swallow) a failure, with a test that counts logins before and after.
- Leftovers are never deleted (standing rule). During the walkthrough step 18 more databases appeared (17 `alveara_p2_*` walkthrough databases plus 1 `AlveraRestore_` created by the running API's own scheduled restore drill; the two perio reruns added 2 more walkthrough databases), see section 6.

## 4. Mechanism of the two earlier failures, and the fix (details in `findings/MODEB_INVESTIGATION_REPORT.md`)
- Teardown deadlock (SQL 1205) between the fixture drop and an EF session of a still-running in-process host: bounded retry of the drop (4 attempts, 250/500/750 ms).
- Pool-open timeout in `MigrateAsync`: SqlClient 7.0.0's pool-pruning timer (due 4 min, period 30 s) shuts down an empty pool while EF polls for the new database ("Pool is shutting down; abandoning wait", surfaced as "Timeout expired"): bounded retry (3 attempts) with cleanup of the half-created database before each retry; the drop (master connection open included) also retries this classification.
- **Controlled hammer on the final code** (`hammer_final/`, a thread calls SqlClient's prune method every 20 ms, about 1,500 times the natural tick rate): 800 fixture cycles, 16,000 results all passed, 0 init failures, 0 dispose failures; the fixture made 23 retries (20 pool-acquisition timeouts at initialisation, 3 SQL 1205 at the drop), every one recovered on the first retry, none gave up. `AlveraTest_` 49 before and 49 after. Without the retry the same hammer produced 15 failures in 798 cycles. Supporting evidence only: the hammer is an accelerator.

## 7. What is not claimed
- Three consecutive green full runs on one machine are a strong signal, not proof of absence of rare races; the natural failure rate before the fix was about 1 in 4,000 to 5,000 fixtures, so three runs (about 4,000 fixtures) could not by themselves distinguish the fixed from the unfixed code; the hammer runs and the mutation tests carry that burden.
- The retry recovers from the two observed transient failures; it does not prove host shutdown is race-free, and the pool-acquisition classifier can also match genuine pool exhaustion (then the retries exhaust and the first exception is rethrown).
- The `LeastPrivilegeAccessTests` login leak and the `perio_sessions` single failure are open items for the reviewer's decision (section 3 and 6).
- Nothing was pushed. If the work is not approved, the P2 runner configuration is reverted and the suite stays serial.
