## 1. Intended result
**User-visible:**
1. **One receipt per payment.** A payment that has a receipt offers "View receipt N", not a new preview. A second receipt is issued only through "Issue a replacement", which needs a reason. The replacement gets the next number. The original then shows "Superseded by receipt M" in the list, in its opened view and on paper, and the replacement shows "Replaces receipt N".
2. **Documents say what happened since they were issued.** The documents list marks a receipt whose payment was later reversed or refunded (F-115). A statement marks each reversed line "reversed by N" (F-117). Printed documents carry their own number (Q-5av).
3. **Statement CSV.** The CSV carries a header block (practice, patient, statement number, as-of time in the practice's zone) and a ReversedBy column. Times are practice-local, and the zone is named (F-119).
4. **The balance reconciles on screen.** The Billing tab and the statement show an "Adjustments not applied to a charge" line, so that open charges - unapplied payments + those adjustments = balance owed (F-116/F-175, Q-5ay). The Balances report is checked for the same gap.
5. **Payer (PD-18).** "Who paid" offers the patient, the patient's registered guarantor and the members of the patient's household. It is always shown when anyone besides the patient qualifies, and it defaults to the party now responsible for the account (F-209, F-205). There is no free patient search.
6. **Responsibility.** It can be recorded before the first charge (Q-5bf). Recording the party that is already responsible says "Nothing changed" and adds no row (F-197). Guarantor messages name the people (F-204). Set guarantor explains up front when it cannot be used (F-203).
7. **Small items:**
   - The preview and an opened document scroll into view and take focus (F-113).
   - "Zelle already exists" replaces a second "is available" (F-120).
   - A field's error clears when the field changes (F-121), and the "Nothing was recorded" wording is the same in every billing form (F-122).
   - The panel's status line clears when another billing action starts (F-207).
   - Money is formatted as "$264.00" everywhere (F-208).
   - The checkbox lines up with the other fields (F-196).
   - The responsibility table names people consistently, and "From" is labelled as an effective date (F-198).
   - One sentence each explains Account history versus Timeline (F-195).
   - A procedure charge shows "performed by" (Q-5ag).
   - A refunded payment's row says why it cannot be reversed or corrected (Q-5ax).

**Technical:** one migration (section 4), with database guards for the replacement rule and the widened payer rule. Template version 3 for statements (the F-116 and F-117 content changes); version-1 and version-2 documents keep rebuilding with their own builders (the ALV-N021 A1 pattern). Focused proof only (section 9).

## 2. Itemized changes
### 2.1 Server
- **S1** `FinancialDocument`: add `ReplacesDocumentId` (nullable, self-reference) and `ReplacementReason` (nullable, at most 500 characters). These are set only on the **new** row. The table stays append-only (51169), and the original is never updated: "superseded" is derived as "some row replaces me".
- **S2** `BillingService.Documents.cs`:
  - `PreviewDocumentAsync` refuses a receipt preview for a payment that already has a live receipt (`receipt_exists`, 409, naming the receipt), unless the request says `replaces: <documentId>` with a reason.
  - `IssueDocumentAsync` carries the replacement fields inside the signed preview token, so what was reviewed is what is issued. It is audited as `FinancialDocumentReplaced` with the reason.
  - `ListDocumentsAsync` adds a status to each row: `supersededBy`, `replaces`, `paymentReversed` and `paymentRefunded` (an amount).
- **S3** `FinancialDocumentBuilder`, template version 3:
  - Each statement line carries `ReversedByNumber`.
  - The statement totals add `UnappliedAdjustmentTotal` and the aging block names it.
  - `StatementCsv` writes the header block and the ReversedBy column, with practice-local times. The CSV is rebuilt from the document's own content and version, so a v2 statement's CSV gains the header block but no ReversedBy data. The reviewer is asked to confirm this in OQ-3.
- **S4** The account view (`BillingService.Queries.cs`) adds `unappliedAdjustmentTotal`. A reconciliation rule enforces open - unapplied + adjustments = balance; it is asserted by a property test.
- **S5** Payer rule:
  - `BillingService.cs:111` and `BillingService.Corrections.cs:138` check the payer against the PD-18 set: the patient, `Patient.GuarantorPatientId`, members with the same `Patient.HouseholdId`, and anyone ever recorded as responsible (kept so that existing data stays valid). A payer outside the set is refused with `payer_not_eligible` (400).
  - A new read, `GET /api/patients/{id}/billing/payers`, returns that set with names and the default (the party currently responsible).
- **S6** `BillingService.Responsibility.cs`:
  - Recording the implicit default (the patient, with no row yet) is "nothing changed" and adds no row. Both "nothing changed" cases return `changed: false`.
  - Recording before the first charge stays allowed. The server already opens the account then, with no entry and no document.
- **S7** `CurrentStatusAsync` notes: amounts become numbers that the client formats (F-208).
- **S8** The ledger row view adds `performedByName` for procedure charges, read from the completed procedure (Q-5ag). It adds `cannotReverseBecause` for refunded payments (Q-5ax).
- **S9** `BillingService.Methods.cs`: the add answer says `created: true` or `false` (F-120).
- **S10** `FinancialReports` (Balances): the report shows the same unapplied-adjustment figure if it has the same gap (checked in Step 0; changed only if confirmed).

## 4. Schema design, for the reviewer's explicit approval
### 4.1 `FinancialDocuments`: two columns
- `ReplacesDocumentId uniqueidentifier NULL`, a foreign key to `FinancialDocuments(Id)`.
- `ReplacementReason nvarchar(500) NULL`.
- CHECK `CK_FinancialDocuments_Replacement`: the two columns are both null or both set; the reason is not blank; and `DocumentType = 'Receipt'` when set (OQ-2).
- A filtered unique index on `ReplacesDocumentId WHERE ReplacesDocumentId IS NOT NULL`: a document is replaced at most once, though a chain of replacements is allowed.
The `INSTEAD OF UPDATE, DELETE` immutability trigger (51169) is unchanged. Adding nullable columns does not update rows.

### 4.2 Database guards (verified unused at `e2a50ad`: the highest in use is 51293)
- **51294:** a replacement belongs to the same account, the same document type and the same payment as the document it replaces.
- **51295:** a receipt for a payment that already has a receipt nobody has replaced must name, in `ReplacesDocumentId`, the **latest** such receipt (the highest number). This makes a silent second receipt impossible even if the service check is bypassed, and it still lets a legacy unlinked pair (OQ-4) be replaced deliberately through its latest receipt.
- **51296:** `Down` is refused once any replacement row exists, so nothing is lost (the ALV-N023 51293 pattern).
- **51142, widened:** `TR_BillingEntries_Reversals` is re-created with the payer condition "the patient, OR recorded responsible (as today), OR the patient's `GuarantorPatientId`, OR a patient with the same non-null `HouseholdId`, as read at insert time". Its message becomes "A payment is made by the patient, their guarantor, a household member or someone recorded as responsible for the account." `Down` restores the old body. This is safe because the trigger checks inserted rows only, so rows already stored are not re-checked.

### 4.3 "Verified household member" (PD-18; OQ-1 DECIDED 2026-11-18)
There is no "verified" flag in the data. Household membership (`Patient.HouseholdId` with a relationship) and the guarantor (`Patient.GuarantorPatientId`) are recorded on the patient record by staff through the audited household and guarantor actions (`PatientHouseholdChanged`, `PatientGuarantorChanged`). **Proposed meaning:** "verified" = recorded on the patient record by an authorised user through those audited actions, as read at the moment of payment. **Owner's decision (OQ-1):** "Here, 'verified' means the relationship was formally recorded through the existing audited patient-record workflow - not an extra financial or identity-verification claim. No new schema or workflow is needed."

### 4.4 Upgrade
No backfill. Existing duplicate receipts (such as the walkthrough's Receipts 1 and 2 for payment 5) are not rewritten. Rule 51295 applies only to new inserts. **Owner's decision (OQ-4):** "Do not alter historical receipt data or invent a supersession relationship retroactively. Show a neutral read-only notice such as: 'Multiple legacy receipts exist for this payment.' The new replacement/supersession rule applies only to newly issued receipts." So the list and the opened view show that notice on every receipt of a payment that has more than one receipt with no replacement link between them. This is derived at read time and stores nothing. For such a payment, the preview refusal names the latest receipt, and a replacement replaces that one.

## 7. Permissions, audit, data, integrations, accessibility, recovery, performance, release
- **Permissions:** unchanged. Issuing and replacing need ManageBilling; reading needs ViewBilling; recording a payment needs the existing payment permissions. The payer read needs the same permission as recording a payment.
- **Audit:** `FinancialDocumentReplaced` (the original and new numbers, the reason) and the existing issue row. Responsibility "nothing changed" writes no audit row. Audit details carry no clinical text.
- **Data:** no PHI is added to documents beyond what they already carry; the payer name is already in the ledger view.
- **Accessibility:** focus moves to the preview heading; the replacement form uses the "Say why." pattern; the reconciliation line is text, not colour.
- **Recovery:** every write is idempotent by key (unchanged pattern); the migration `Down` is refused once a replacement exists.
- **Performance:** the list status adds one ledger read per list (already loaded for the opened view); the payer read is small.
