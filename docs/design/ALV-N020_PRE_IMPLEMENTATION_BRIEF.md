## 1. Intended result

### 1.1 User-visible
1. **Patient context belongs to the person who opened it (F-037).** After sign-out, session expiry or a change of user, no patient name, page or cached patient data from the previous user is shown. A new sign-in always lands on the dashboard (never on the previous user's patient page). Refresh keeps a same-user selection only.
2. **Honest session and outage messages (F-007, F-012, F-014, F-155).** A first visit shows a plain sign-in page. "Your session expired" appears only after a real expiry or a 401 after being signed in. A server or network failure (502, 503, no connection) shows a "cannot reach the server, reconnecting" state, keeps the signed-in screen and any unsaved form, and recovers by itself when the server returns; only a genuine 401 signs the user out. With the API down, sign-in says the server is unavailable (never "Invalid username or password"); a 500 gets a server-problem message; 429, disabled and locked keep their current messages. A signed-in user who opens `/login` goes to the dashboard.
3. **Sign-in polish (F-151/F-166, F-156).** Surrounding spaces in a typed username are removed before sign-in and in the audit line. The sign-in page uses the saved light/dark theme.
4. **Leaving staff cannot sign in (F-021).** Deactivating a staff profile disables its linked login and ends its open sessions in the same step, with an audit entry. Reactivating the profile does not re-enable the login; only an administrator re-enables it in Security Administration. An administrator can unlink a login from an inactive profile with a reason, and the account list shows each account's linked staff profile. If the account step fails, nothing changes, the person gets a clear result, a durable operational record is written and an Urgent notification goes to administrators and office managers.

### 1.2 Technical
- Client: `AuthContext` distinguishes `signed-out` (no session / genuine 401) from `unreachable` (network, 502, 503) and keeps the last signed-in identity while reconnecting; `RequireAuth` redirects a never-signed-in visitor to `/login` without a reason and adds `?reason=expired` only when the session ended after being signed in; `LoginPage` maps errors by status and code; the patient context and the post-login return destination are scoped to the signed-in identity and cleared on identity loss or change; the theme is applied before the shell mounts.
- Server: `AccountService.LoginAsync` trims the username before lookup and audit; `StaffProviderService.SetStaffActiveAsync` (inactivate) disables the linked account and rotates its security stamp in the same transaction via the existing `SetAccountEnabledAsync` rules; new admin unlink-with-reason operation; account list exposes the linked staff profile; new audit events and an operational failure record.
- No schema change is expected except possibly a version column on the staff-account link if none exists (it does: `StaffProfile` already uses `ConfigurationWrite.ApplyExpectedVersion`, so none is planned; see 8.4).

## 7. Design of each part

### 7.1 Identity-scoped patient context and return destination (Group A, F-037)
`AuthContext` exposes `identity` (username + role) and an `identityEpoch` that increments on sign-out, genuine 401 and every change of username. `PatientContextProvider` clears when the epoch changes. `RequireAuth` stores `from` together with the epoch; `LoginPage` uses `from` only if the epoch at sign-in equals the stored one **and** the signed-in username equals the one that left (same user returning after expiry); otherwise it goes to `/`. Explicit sign-out never stores `from`. Two tabs: each tab re-derives identity from the server; a tab that discovers a different identity on revalidation clears its patient context and goes to `/`. Refresh: the URL keeps the patient for the same user (acceptable, owner's F-034/F-035 evidence line), re-fetched under the current identity.

### 7.2 Session and outage states (Group B, F-007, F-012, F-155)
State machine: `loading -> signed-in | signed-out`; `signed-in -> signed-in(connection lost) -> signed-in` on recovery; `signed-in -> signed-out(reason: expired | revoked | signed-out-by-user)`. Only a server 401 (or the server's own expiry answer) produces `expired/revoked`. Network errors, 502, 503, 504 produce `connection lost` and never unmount the shell. The expiry notice on `/login` shows only for `expired/revoked` and is hidden while the connection is lost.

### 7.3 Sign-in errors (F-014) and signed-in visitor on /login
`LoginPage` mapping table: 401 `invalid_credentials` -> invalid; 401 other -> invalid (unchanged); 403 `account_disabled` -> disabled; 423/`account_locked` -> locked (unchanged codes as the server sends them today, verified in 9.1); 429 -> rate limited; 502/503/504/network/timeout -> "The server cannot be reached. Try again when it is back."; other 5xx -> "The server had a problem. Try again; if it continues, contact your administrator." A signed-in visitor to `/login` is redirected to `/`.

### 7.4 Username normalization (F-151, F-166)
`Trim()` the username at the server boundary of login, MFA-challenge start, registration and bootstrap (consistent for every entry point); audit `account.Username`. The client also trims before sending (defense in depth, not relied on).

### 7.5 Staff deactivation and login lifecycle (PKG-03, F-021)
Transaction boundary: `StaffProviderService` and `AccountService` share the scoped `AlveraDbContext`. The deactivation runs in one database transaction: load staff (version check), check active provider (existing rule), load and lock the linked account, apply the account-disable rules (target rules, last-admin guard, security stamp, `AccountDisabled` audit), set the profile inactive, write `StaffLoginDisabledOnDeactivation`, commit. A refusal (last admin, admin-guard busy, target not allowed) or any exception rolls back everything; the API returns 409 with the specific code (e.g. `staff_login_last_admin`) or 500 with a correlation id; a durable `StaffLoginDeactivationFailed` record is written in a separate, short transaction after the rollback, and an Urgent notification is attempted (its failure is logged, never thrown). Concurrency: the staff row version and the account lock make a concurrent edit fail cleanly (409 conflict). Idempotency: deactivating an already-inactive profile is a no-op (existing early return); disabling an already-disabled account is a no-op (existing check). Unlink: admin-only, inactive profile only, reason required (1-500 chars), versioned, audited. Re-enable stays in Security Administration (`ManageUsers`).

### 7.6 Chain stage 1, minimal stage 2 and the outage step (R05 "built here")
New chain spec beside `chain/stage-0.spec.ts`: stage 1 = cases 1.01-1.06, 1.10, 1.11 (objective part), 1.12 (short per-user timeout), staff deactivation (F-021) and the patient-context check with two accounts (F-037); minimal stage 2 = two synthetic patients; runner step 13.05 = stop the chain API, assert the reconnecting state and a kept form, restart, assert recovery without sign-in. It uses the stage-0 runner, its owned throw-away database and the injected clock only for test data (PD-32: never for authentication expiry; case 1.12 uses a real short per-user timeout). Under the deferred policy these specs are **built and focused-proven once in this story; their repeated execution belongs to the ALV-N028 consolidated run.**

## 13. Risks and mitigations
- **Keeping the UI during an outage could show stale data.** Mitigation: mutations still fail visibly; the banner says the server cannot be reached; a 401 on recovery signs out immediately.
- **Changing the return-destination rule could break the ALV-N009 deep-link behavior.** Mitigation: same-user deep links still return to the page (tested); only a different user or explicit sign-out is redirected to `/`.
- **Disabling a login from a configuration screen widens that screen's power.** Mitigation: decision 10.3 (require `ManageUsers`), confirmation dialog, audit.
- **Shared DbContext transaction across two services.** Mitigation: one explicit transaction owned by the staff operation; the account rules are called through an internal method that does not open its own transaction (refactor of `SetAccountEnabledAsync` into a transaction-free core plus the existing public wrapper, behavior unchanged and covered by its existing tests).
