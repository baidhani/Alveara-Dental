## 0. Answers to BRIEFING-R01 (revision 2)
- **BR-01 (session expiry):** the "readable sid on an expired ticket" mechanism is withdrawn. Section 4 now uses a durable, **audit-only** session lifecycle record created at sign-in. A server-owned processor writes `SessionExpired` at the known deadline unless the session ended earlier, and an explicit sign-out closes the record first. Every transition is a single conditional write, so each session ends exactly once. The record is never read for authorization and never renews the fixed authentication deadline. The schema, retries, idempotency, retention and proofs are in sections 4, 6 and 8.
- **BR-02 (History link):** section 4a states the permission boundary. The audit API returns no old or new values, no patient name and no contact detail: only an opaque history-entry reference and the patient id. Resolving the reference goes through the existing `GET /api/patients/{id}/history`, which independently requires `ViewPatientRecords`. The screen withholds the link and says "History is available to staff who may see this patient" when the viewer lacks that permission. The proofs cover the authorized path and a `ViewAuditLog`-only account denied the content, by direct API and by direct navigation (sections 4a and 8).

## 1. Intended result
**User-visible:**
1. **Every "who did it" names a person.** This covers the audit page, permission change history, fee history, document history, encounter history and follow-ups. The rule: the staff profile's display name; if the account has none, the account's username; never a bare id or a generic "Staff member". Auditors keep the id (tooltip and API). Answers F-029, F-087, F-138, F-149, F-172, F-214 and U-011.
2. **The audit page.**
   - The heading says what it holds (F-150, F-174, O-G2k).
   - It filters by event type and date range.
   - It shows "Performed by" and "About" as names (F-149).
   - A patient edit names its fields and links to the patient's History row, where the old and new values already live (F-041, owner).
   - Guarantor and household entries name the other party by id and the relationship (F-040, O-G2j).
3. **Registering a near-duplicate.**
   - "Register anyway" needs a short reason.
   - The audit records the matched patient ids and the reason (D-02a, F-036, owner).
   - A same-name patient with a **different** birth date but the same phone, email or address is flagged as a possible duplicate, in registration, import and the Duplicate patients page (F-145, F-210).
   - The guarantor picker shows enough to tell two people apart (F-211).
4. **Not-a-duplicate** has a visible, required reason with one line of instruction (F-148).
5. **Patient number (MRN).** Every patient has an 11-digit MRN, shown in the header and search results and in the patient exports, and searchable exactly (PD-21, section 5).
6. **Demographics.**
   - Sex is a list: Female, Male, Other, Unknown/unspecified.
   - There is a Country field (ISO 3166-1 alpha-2, defaulting from the practice).
   - For the USA, State is a list stored as the 2-letter code; elsewhere it is free text labelled "State / Province / Region".
   - Existing values that cannot be mapped are listed for staff review, never changed silently (F-032, F-033, owner).
7. **Import.**
   - The patient-import page says exactly which file it takes (the single patient file) and that the package export is for reading and archiving, not re-import (F-147, owner).
   - The bulk-import dry run filters by several statuses at once (F-144).
8. **Household and dialogs.**
   - A household left with one member is dissolved, with an audit row (F-202, Q-5bd).
   - Inactivating a patient and leaving a household use the app's own confirm dialog (F-042).
9. **Merge.** The comparison shows every field that differs, and the person chooses each (Q-5cb, if confirmed in Step 0).
10. **Patient-access trail (PD-20, section 4).**
    - Opening a patient record (once per patient per session), every export and download, and sign-out and session expiry are recorded.
    - The audit-log readers can see them.
11. **Permission Matrix (Q-5cl access).** The screen offers a manager no change, which matches the API (proven by test).

**Technical:**
- **Observability:**
  - Abandoned requests are logged as information, not errors (F-126, F-010).
  - SQL failures log the method, path and SQL error number, never the message or any data (F-127).
  - Measurement categories are normalised on every path (F-128).
  - Console log lines carry a UTC timestamp (F-212).
- **Schema:** one migration for MRN, Country, the access-session table and the guards (section 6).

## 4. PD-20 design: patient-access trail (compliance; for explicit approval)
- **Purpose:** to answer "who opened, exported or downloaded which patient's record, and when", and "when did that person's session end".
- **Readers:** holders of `ViewAuditLog` (Admin, OfficeManager today). No new permission.
- **Events (PHI-free details, entity = Patient id; actor = the account):**
  - `PatientRecordOpened`;
  - `PatientRecordExported` (export file, package, readable record);
  - `PatientDocumentDownloaded` (existing `DocumentOpened` kept);
  - `UserSignedOut`;
  - `SessionExpired`;
  - `SessionRevoked` (BR-01);
  - `PatientMaterialPrinted` (OQ-1).
- **"Once per patient per session":**
  - At sign-in the cookie gains a random session-id claim (`sid`; no schema change for the cookie).
  - The first `GET /api/patients/{id}` (the workspace load) in a session inserts a row into a new table `PatientRecordOpens (SessionId, PatientId, UserId, FirstOpenedAtUtc)` with a unique key on (SessionId, PatientId), and writes the audit row in the same save. A repeat in the same session finds the row and writes nothing.
  - Other reads (tabs, lists, searches) are **not** logged: no indiscriminate page-view logging.
- **Sign-out:** see the session lifecycle record below (the event is written only when sign-out closes the record).
- **Session lifecycle record (BR-01; audit-only):**
  - **At sign-in** a row is written to a new table `AuditSessions`: `SessionId` (a random GUID, also put in the cookie as the `sid` claim), `UserId`, `IssuedAtUtc`, `ExpiresAtUtc` (the same fixed deadline the cookie ticket carries), and `EndedAtUtc`, `EndKind` (`SignedOut` | `Expired` | `Revoked`) and `EndAuditWritten`, all null or false at first. It is written in the same save as `LoginSucceeded`.
  - **Explicit sign-out** (`POST /api/auth/logout`, which is authenticated, so only before the deadline): one conditional update, `SET EndedAtUtc = now, EndKind = 'SignedOut' WHERE SessionId = @sid AND EndedAtUtc IS NULL`, plus `UserSignedOut` in the same transaction **only if the update changed a row**. A second sign-out, or a sign-out racing the processor, changes nothing and writes nothing.
  - **Expiry processor:** a hosted background service (the same pattern as the follow-up pass) runs every minute. For each row with `EndedAtUtc IS NULL AND ExpiresAtUtc <= now` it issues the same conditional update with `EndedAtUtc = ExpiresAtUtc, EndKind = 'Expired'` and, only when the update changed the row, writes `SessionExpired` (occurredAt = the deadline) in the same transaction. Rows are processed in batches of at most 500 per pass. A crash between passes loses nothing: the next pass finds the same rows. A row already closed is skipped by the `WHERE`, and a retried pass cannot write a second event.
  - **Revocation:** when an account's security stamp rotates (password change, disable, the existing server-side revocation), that account's open rows are closed in the same save with `EndKind = 'Revoked'` and one `SessionRevoked` event each, so a revoked session is never later reported as expired.
  - **Exactly once:** the event is written only by the transaction whose conditional update closed the row. A guard (**51301**) refuses any change to a row whose `EndedAtUtc` is already set, and any change to `SessionId`, `UserId`, `IssuedAtUtc` or `ExpiresAtUtc`.
  - **Not a session store:** authentication keeps using the cookie ticket and the security stamp exactly as today. Nothing reads `AuditSessions` to accept or refuse a request, and nothing in it extends `ExpiresUtc`. A missing or failed lifecycle write at sign-in is logged (`audit_session_write_failed`) and does not block sign-in; that session then has no expiry event, which the help text states.
  - **Retention:** as the audit log (no purge exists; none is added).
  - **Help text:** "Sign-out and session expiry are recorded; expiry is recorded within about a minute after the session's fixed end time."
- **Prints (OQ-1, owner 2026-11-19):** every in-application **Print** button first calls `POST /api/patients/{id}/print-events` with the material type (for example `TreatmentPlanPatientCopy`, `Statement`, `Receipt`, `Prescription`, `ReadableRecord`) and the resource id. The server records `PatientMaterialPrinted` with the actor, patient id, material type, resource id, timestamp and outcome `requested`, PHI-free. It records the print **request**, not that paper came out. Browser printing outside the app's buttons (for example Ctrl+P) is outside this guarantee, and the audit page's help text says so. Then the screen opens the browser's print dialog. If the call fails, printing still proceeds and the failure is logged (`print_event_failed`), so recording never blocks care.
- **Retention:** as the audit log (no separate purge exists; none is added).
- **Noise controls:**
  - one open row per patient per session;
  - opens are not recorded for the patient-search list or for background reads;
  - the audit page's event-type filter can hide or show them.
- **Volume estimate:** a small practice of 40 patients a day with 5 users is about 200 rows a day.

## 4a. The History link from the audit (BR-02; permission boundary)
- **What the audit API returns:** for a patient-edit row, the patient id, the changed field names and an opaque `historyEntryId`. **Never** old or new values, the patient's name or any contact detail, for any caller. This is unchanged by the viewer's permissions, because the audit row itself holds no such data (PHI-free, as today).
- **Resolving the link:** only through the existing `GET /api/patients/{id}/history` (`PatientsController.cs:128`), which requires `ViewPatientRecords` on its own. The audit API never resolves or embeds a History row. No new route returns History content.
- **The screen:** the audit page shows "View in patient history" only when the signed-in account holds `ViewPatientRecords`. Otherwise it shows "History is available to staff who may see this patient" with no link. Navigating directly to the patient History URL without the permission shows the app's existing "not permitted" state, and the API answers 403 with no content.
- **Who is affected today:** `ViewAuditLog` is held by Admin and OfficeManager, both of whom also hold `ViewPatientRecords`. The boundary matters for any account later granted `ViewAuditLog` without patient access (grantable permissions, ALV-N017). The proof builds exactly that account (section 8).

## 5. PD-21 design: Medical Record Number (data model; for explicit approval)
Implements the owner's decision (decision record, quoted in full there).
- **Column:** `Patients.Mrn bigint NOT NULL`, unique index. The value is UTC whole seconds since 0001-01-01 (`Ticks / TicksPerSecond`): **11 digits** in 2026.
- **Generation on registration** (also import and bulk import, which all go through `StagePatient`):
  1. The candidate is `now` seconds.
  2. While a patient has that MRN, add 1 second.
  3. Insert. On a unique-index violation (a concurrent registration took it), add 1 and retry, up to 60 attempts, then 503 `mrn_busy`.
  4. Never wait; never a suffix.
- **Immutable and never reused:**
  - Guard **51298** refuses any UPDATE of `Mrn` (INSTEAD OF / AFTER UPDATE check).
  - Patients are never deleted (inactivated and merged records stay in place), so the unique index keeps every MRN reserved, including a merged-away record's. Unmerge restores the record with its own MRN.
- **Backfill (migration, deterministic):** existing patients are ordered by (`CreatedAtUtc`, `Id`). Each takes the seconds of its `CreatedAtUtc`, moved forward past any MRN already given. A rerun gives the same result. New registrations after the migration start from the current second and step past any backfilled value.
- **Merge:** the surviving patient keeps its MRN; the merged-away MRN stays on its retired row.
- **Display and search:**
  - Shown in the header, search results, patient summary and the patient exports (export file, package, readable record), subject to existing permissions.
  - An exact 11-digit search finds that patient first, before the phone rule.
- **Not in this story:** printed clinical and billing documents (treatment-plan patient copy, statements, receipts, prescriptions). Adding the MRN to them changes their content, and for statements and receipts their template version. Proposed for ALV-N026 (documents and printing) as OQ-2.
- **Not identity:** it is a lookup reference; nothing authenticates with it.

## 6. Schema and guards (migration `AddMrnCountryAndPatientAccess`; highest guard in use 51297)
- `Patients.Mrn bigint` (backfilled, then NOT NULL, unique index); **51298** MRN immutable.
- `Patients.Country char(2) NOT NULL DEFAULT 'US'`.
- `PracticeSettings.DefaultCountry char(2) NULL`.
- `PatientRecordOpens` (SessionId uniqueidentifier, PatientId, UserId, FirstOpenedAtUtc; PK (SessionId, PatientId); append-only **51299**).
- `AuditSessions` (SessionId PK, UserId, IssuedAtUtc, ExpiresAtUtc, EndedAtUtc NULL, EndKind NULL CHECK IN ('SignedOut','Expired','Revoked'), EndAuditWritten bit; CHECK: EndedAtUtc and EndKind are both null or both set; an index on (EndedAtUtc, ExpiresAtUtc) for the processor); **51301** a closed row and the identifying columns never change; no delete (INSTEAD OF DELETE, 51301).
- **Down** is refused (**51300**) once any patient was registered after the migration (their MRN would be lost); otherwise it removes the columns and both tables.
- No change to stored Sex and State values: unmappable ones are surfaced for review (owner), not migrated.
