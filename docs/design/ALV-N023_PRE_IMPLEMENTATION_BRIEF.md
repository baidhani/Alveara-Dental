## 1. Intended result (user-visible and technical)
1. **A plan item is "booked" only by a real appointment.** The front desk or office manager can name the patient's accepted, not-yet-booked procedures while booking an appointment (OQ-1, owner 2026-11-18), and a dentist can link an existing appointment from the plan item. The item shows that appointment's current date, time and provider, read live from the appointment, so a move is followed automatically; if the appointment is cancelled or marked no-show the item says so and is no longer booked. Only a linked, not-cancelled, not-no-show appointment - or a terminal item state (completed, declined, withdrawn, plan withdrawn) - closes the "accepted treatment is not scheduled" follow-up. A cancelled or no-show link reopens it.
2. **A target date is only a target.** The existing planned date becomes an optional "target date" (PD-15): a past target date needs a confirmation and is shown "overdue"; a target date never looks like a booking and never closes the follow-up. A blank target date is simply "no target date" (F-188).
3. **The plan's state tells the truth** (PD-14, derived, no stored field): Proposed / In progress / Completed / Closed (no remaining procedures, not all completed). A Completed or Closed plan is read-only except history, the patient copy and a warned "Revise anyway".
4. **History is visible.** A plan "Activity" list shows every recorded event (answers, links, target dates, reference code, renames, completions) with who and when; each item can show its answer history (F-181, F-190). A rename needs a reason and reads "Renamed from <old> to <new>" (DR-5).
5. **Buttons only where they act:** bulk answers act on unanswered items only and report the count (DR-4), and are hidden when nothing is unanswered; "Adopt earlier completions" only when an old-style completion exists.
6. **Display and audit corrections:** Before/After on separate lines; a patient copy with the practice's name, address and phone, "Completed" wording, one disclaimer and a labelled "Plan reference" (DR-6); "$0.00 accepted so far"; the create-form message only where it belongs; an enabled Withdraw that explains an empty reason; "account entry N" linked to the account; a less crowded plan card; every item gap listed at once; richer PHI-free audit rows (DR-7); a visible note when a completion's performed date is after its encounter's date (DR-8).

## 4. Schema design (DR-1) - for the reviewer's explicit approval
### 4.1 Table `TreatmentPlanItemAppointmentLinks` (append-only)
`Id` (PK), `PlanId` (FK TreatmentPlans), `ItemId` (FK TreatmentPlanItems), `PatientId`, `AppointmentId` (FK Appointments, no cascade), `Sequence` (int, per item, starts at 1, unique `(ItemId, Sequence)`), `Action` (`Linked`/`Unlinked`, CHECK), `Reason` (nullable; required for Unlinked, CHECK), `RecordedByUserId`, `RecordedAtUtc`. The **current link** of an item is its highest-sequence row when that row is `Linked`.
- One item has at most one current link; one appointment may be linked by several items (a visit often covers several procedures).
- The appointment row is never changed by a link; moves are followed because the item reads the appointment's live start/provider/status.

### 4.2 Database guards (numbers verified unused at `7a8b64e`: highest in use 51290)
- `TR_TPItemAppointmentLinks_SamePatient` (AFTER INSERT): `PatientId` = the item's patient = the appointment's patient; otherwise THROW **51291**.
- `TR_TPItemAppointmentLinks_AppendOnly` (INSTEAD OF UPDATE, DELETE): THROW **51292**.
- Down: refused (THROW **51293**) while any row exists, so no link history is lost; otherwise drops triggers, indexes and the table.
- The service checks first (same patient, appointment not cancelled/no-show at link time, item accepted and not completed); the triggers back the same-patient and append-only rules if anything bypasses the service.

### 4.3 What "live" means
Current link exists and the appointment's `Status` is `Scheduled` (not `Cancelled`, not `NoShow`). A past appointment that was kept (status Scheduled, flow done) stays live; the procedure still needs completion through the completion workflow to become Completed.

### 4.4 Follow-up keying
Today the task key is `unscheduled:{item}:{stateSequence}`. A cancelled appointment does not change the item's state sequence, so the old key would block a new task. New key for new tasks: `unscheduled:{item}:{stateSequence}:{linkSequence}` (link sequence 0 when the item has never been linked). `JudgeAsync` returns both numbers; the close check compares the full key; an existing open task with an old-format key is treated as `...:0` (so open tasks are not churned on upgrade). Effects: link -> the open task closes ("A linked appointment is booked: <date>."); cancel/no-show/unlink -> a new task (new link episode); completion/decline/withdrawal -> closes as today. All through the existing durable jobs (idempotent keys); timing is the existing background pass (not instant), stated in the UI as today.

### 4.5 Upgrade of existing data
No row is changed. Items whose latest state is `Scheduled` and that have no link become "waiting" on the next pass: their (closed) old-key task stays closed and history-true; a new task is created with the new key. The brief's Stage 1 includes an upgrade test on a database seeded with such items.

## 7. Permissions, audit, data, integrations, accessibility, recovery, performance, release
- **Permissions (OQ-1 decided):** link/unlink: `ManageAppointments` (Front desk, Office manager, Admin) **or** `ManageTreatmentPlans` (Dentist, Admin) - an administrative scheduling relationship, not a plan edit; target dates, answers and every other plan change: `ManageTreatmentPlans` only. The bookable-treatment read exposes no clinical text. Reading the linked appointment on the plan needs `ViewSchedule` for time/provider; without it the item shows only "Booked". Tests prove a front-desk account can link/unlink but cannot answer, rename, revise, set a target date or read the plan.
- **Audit:** new audit actions `TreatmentPlanItemAppointmentLinked/Unlinked`, `TreatmentPlanItemTargetDateSet/Cleared`; DR-7 detail text; plan events as history.
- **Data/migration:** one migration (section 4); no data rewritten; upgrade behaviour section 4.5.
- **Integrations:** follow-up jobs (section 4.4); calendar (read; a link to it). No external service.
- **Accessibility:** new controls labelled; status words, not colour alone, for Booked/Cancelled/Overdue; the warned "Revise anyway" is a confirmation dialog with focus management.
- **Recovery:** link/unlink are reversible by appending; a failed save changes nothing (one transaction); the follow-up pass is idempotent.
- **Performance:** the plan read adds one join to appointments per plan load (indexed by `ItemId`, `AppointmentId`).
- **Release:** ALV-N013 installer applies one more migration; Down refused once links exist.
