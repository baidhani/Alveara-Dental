## 1. Intended result (user-visible and technical)
1. **A plan item is "booked" only by a real appointment.** The front desk or office manager can name the patient's accepted, not-yet-booked procedures while booking an appointment (OQ-1, owner 2026-11-18), and a dentist can link an existing appointment from the plan item. The item shows that appointment's current date, time and provider, read live from the appointment, so a move is followed automatically; if the appointment is cancelled or marked no-show the item says so and is no longer booked. Only a linked, not-cancelled, not-no-show appointment - or a terminal item state (completed, declined, withdrawn, plan withdrawn) - closes the "accepted treatment is not scheduled" follow-up. A cancelled or no-show link reopens it.
2. **A target date is only a target.** The existing planned date becomes an optional "target date" (PD-15): a past target date needs a confirmation and is shown "overdue"; a target date never looks like a booking and never closes the follow-up. A blank target date is simply "no target date" (F-188).
3. **The plan's state tells the truth** (PD-14, derived, no stored field): Proposed / In progress / Completed / Closed (no remaining procedures, not all completed). A Completed or Closed plan is read-only except history, the patient copy and a warned "Revise anyway".
4. **History is visible.** A plan "Activity" list shows every recorded event (answers, links, target dates, reference code, renames, completions) with who and when; each item can show its answer history (F-181, F-190). A rename needs a reason and reads "Renamed from <old> to <new>" (DR-5).
5. **Buttons only where they act:** bulk answers act on unanswered items only and report the count (DR-4), and are hidden when nothing is unanswered; "Adopt earlier completions" only when an old-style completion exists.
6. **Display and audit corrections:** Before/After on separate lines; a patient copy with the practice's name, address and phone, "Completed" wording, one disclaimer and a labelled "Plan reference" (DR-6); "$0.00 accepted so far"; the create-form message only where it belongs; an enabled Withdraw that explains an empty reason; "account entry N" linked to the account; a less crowded plan card; every item gap listed at once; richer PHI-free audit rows (DR-7); a visible note when a completion's performed date is after its encounter's date (DR-8).

## 4. Schema design (DR-1) - for the reviewer's explicit approval
### 4.1 Table `TreatmentPlanItemAppointmentLinks` (append-only)
`Id` (PK), `PlanId` (FK TreatmentPlans), `ItemId` (FK TreatmentPlanItems), `PatientId`, `AppointmentId` (FK Appointments, no cascade), `Sequence` (int, per item, starts at 1, unique `(ItemId, Sequence)`), `Action` (`Linked`/`Unlinked`, CHECK), `Reason` (nullable; required for Unlinked, CHECK), `RecordedByUserId`, `RecordedAtUtc`. The **current link** of an item is its highest-sequence row when that row is `Linked`.
- One item has at most one current link; one appointment may be linked by several items (a visit often covers several procedures).
- The appointment row is never changed by a link; moves are followed because the item reads the appointment's live start/provider/status.

### 4.2 Database guards (numbers verified unused at `7a8b64e`: highest in use 51290)
- `TR_TPItemAppointmentLinks_SamePatient` (AFTER INSERT): `PatientId` = the item's patient = the appointment's patient; otherwise THROW **51291**.
- `TR_TPItemAppointmentLinks_AppendOnly` (INSTEAD OF UPDATE, DELETE): THROW **51292**.
- Down: refused (THROW **51293**) while any row exists, so no link history is lost; otherwise drops triggers, indexes and the table.
- The service checks first (same patient, appointment not cancelled/no-show at link time, item accepted and not completed); the triggers back the same-patient and append-only rules if anything bypasses the service.

### 4.3 What "live" means
An item's **current link** is its highest-sequence link row when that row is `Linked`. The current link is **live** when its appointment's `Status` is `Scheduled`. `Cancelled` and `NoShow` are terminal for an appointment (verified at `7a8b64e`: nothing sets an appointment back to `Scheduled` after creation; `AppointmentManager` writes an append-only `AppointmentEvent` of type `Cancelled` or `NoShow` when it changes the status). A kept past appointment (status still `Scheduled`, visit done) stays live; the procedure still becomes Completed only through the completion workflow.

### 4.4 Follow-up episode algorithm (CR-2)
**Waiting** (eligible for the unscheduled-treatment follow-up): the item is not withdrawn, its plan is not Withdrawn, its latest state row is Accepted and NotStarted (not Completed, not Declined), and it has **no live current link**. A target date never affects this. (The plan-state matrix in 4.6 restates this per row.)

**Episode identity.** Every waiting period is identified by three values read only from immutable data:
- `s` = the sequence of the item's latest state row (state rows are append-only);
- `l` = the sequence of the item's latest link row, or 0 if it was never linked (link rows are append-only);
- `e` = `ended` when the latest link row is `Linked` and its appointment is `Cancelled`/`NoShow` (terminal, so it can happen only once per link row), otherwise `open`.

**Task key (versioned):** `unscheduled:v2:{itemId:N}:s{s}:l{l}:{e}`. Old tasks keep their old keys `unscheduled:{itemId:N}:{seq}` unchanged (history is never rewritten).

**Legacy equivalence (one rule only):** an old key `unscheduled:{item}:{seq}` is treated as the same episode as `unscheduled:v2:{item}:s{seq}:l0:open`, for both the "already has a task" check and the close check. Why this is safe: old tasks were only ever created for a state row that was Accepted + Unscheduled + NotStarted, and that row was the item's latest at the time; every later change of the item (schedule, completion, decline) appended a new state row with a higher sequence. So an old closed task can only match a v2 episode whose `s` is that same, still-latest row with no link - which is the same waiting period (closed by hand by staff); any new waiting period after upgrade has a higher `s` or a non-zero `l` and therefore a different key.

**Create pass:** for each waiting item compute the v2 key; if no task with that key (or its legacy equivalent) exists, enqueue the existing durable create job (idempotent key = the task key). **Close pass:** an open UnscheduledTreatment task is closed when its item is not waiting, or is waiting under a different key (the waiting period it was about has ended and another has begun). The closure note says why: "A linked appointment is booked for <date>.", "The treatment has been completed.", "The patient declined the treatment.", "The treatment is no longer proposed.", or "Continued in a new follow-up: <reason>." Closed tasks are never reopened; a new waiting period always gets a new task.

| Path | Rows written | Task identity afterwards | Prior task | Why the prior closure cannot suppress the new task |
|---|---|---|---|---|
| **1. Legacy Scheduled item, closed old task, no link (seeded upgrade)** | none (upgrade writes nothing) | the item's latest state row is the old `Scheduled` row, sequence N; now waiting -> `unscheduled:v2:{i}:sN:l0:open`, created on the next pass | old task `unscheduled:{i}:M` (M < N, the Accepted row it was made for) stays closed, unchanged ("The treatment has been scheduled.") | its equivalent v2 key is `...:sM:l0:open`; M != N |
| **2. Link, then the appointment is cancelled** | link row 1 (`Linked`); the appointment's own `Cancelled` event (no plan row) | after link: not waiting -> the open task `...:sN:l0:open` is closed "A linked appointment is booked for <date>."; after cancel: waiting -> `...:sN:l1:ended`, new task | the link-closed task stays closed | key differs in `l` and `e` |
| **3. Link, then no-show** | link row 1; the appointment's `NoShow` event | as path 2 -> `...:sN:l1:ended` | as path 2 | as path 2 |
| **4. Explicit unlink (reason required)** | link row k (`Unlinked`, reason) | waiting -> `...:sN:lk:open`, new task. If the item was already waiting under `...:l(k-1):ended` (unlinking a cancelled appointment), that open task is closed "Continued in a new follow-up: the cancelled appointment was unlinked." and the new one opens - the follow-up is never absent | closed with the note above, history kept | key differs in `l` |
| **5. Relink to a later appointment** | link row k+1 (`Linked`) to the new appointment | not waiting -> the open task is closed "A linked appointment is booked for <date>."; if that appointment is later cancelled -> `...:l(k+1):ended`, a new task | closed | a later waiting period always has a higher `l` |

Also covered by the same rule: a state change (decline, completion, plan withdrawal) closes the open task as today; a re-acceptance after a decline appends a state row (`s` grows) and starts a new episode. Timing is the existing background pass (not instant), unchanged.

**Tests (direct, one per path, plus the seeded upgrade):** `RecallJobTests` gains `Path1_legacy_scheduled_item_gets_a_new_v2_task_and_the_old_closed_task_is_untouched` (seeded: an old-format closed task and a Scheduled state row, no link), `Path2_cancelled_linked_appointment_reopens_with_a_new_task`, `Path3_no_show_reopens_with_a_new_task`, `Path4_unlink_opens_a_new_task_and_continues_a_cancelled_episode`, `Path5_relink_closes_and_a_later_cancel_opens_again`, plus `An_open_legacy_task_is_kept_as_the_same_episode_after_upgrade` and `A_target_date_never_closes_the_follow_up`; each asserts the exact keys, the open/closed statuses and the closure notes, and that running the pass twice changes nothing (idempotency).

### 4.5 Upgrade of existing data
No row is changed or deleted. On the first pass after the migration: items whose latest state row is `Scheduled` (old label) and that have no link are waiting under `...:s{N}:l0:open` and get a new task (path 1); items that already had an open old-format task keep it as the same episode (legacy equivalence); old closed tasks stay closed. The UI shows the old `Scheduled` rows as a target date (or "no target date"), never as a booking.

### 4.6 Derived plan state matrix (PD-14, CR-4)
Definitions: an item is **withdrawn** if withdrawn from the plan; every other item is **remaining**. A remaining item is **unanswered** (no answer), **accepted** (accepted, not completed), **completed**, or **declined**. "Live link" as in 4.3. The rules are evaluated in order; the first that matches gives the state.

| # | Plan situation | Displayed state | Allowed actions | Follow-up eligibility (per item, rule 4.4) |
|---|---|---|---|---|
| 1 | Plan withdrawn | **Withdrawn** (unchanged) | Activity, revision history, patient copy (as today, read-only) | none |
| 2 | No remaining items (all withdrawn) - "empty plan" | **Closed** ("No procedures remain") | Activity, revision history, patient copy, Revise anyway (warned) | none |
| 3 | Every remaining item completed (any number withdrawn) | **Completed** | Activity, revision history, patient copy, Revise anyway (warned) | none |
| 4 | No remaining item unanswered or accepted, and not row 3 (all remaining are completed/declined with at least one declined, or all declined) | **Closed** ("All remaining procedures are completed or declined" / "All procedures declined") | Activity, revision history, patient copy, Revise anyway (warned) | none |
| 5 | At least one remaining item accepted or completed, and at least one remaining item unanswered or accepted | **In progress** | full open-plan set: add procedure, rename (reason), revise, set code (once), withdraw item, withdraw plan, item answers (unanswered and accepted items; not completed), bulk answers when >= 1 unanswered, target date and appointment link/unlink on accepted items, review and complete (accepted items), adopt (only if `hasAdoptable`) | each accepted item without a live link is waiting (with or without a target date, past or not); an accepted item with a live link is not; unanswered, declined, completed items are not |
| 6 | Otherwise (remaining items are unanswered, possibly some declined, none accepted or completed) | **Proposed** | the same open-plan set as row 5 (no review and complete: nothing accepted) | none (nothing accepted) |

The reviewer's listed cases map as: all unanswered -> row 6 Proposed; accepted with no link/target -> row 5 In progress, waiting; accepted with target date only -> row 5, waiting (overdue label if past); accepted with live link -> row 5, not waiting; some completed while others remain unanswered/accepted -> row 5; every remaining completed -> row 3 Completed; every remaining declined/withdrawn, or completed mixed with declined -> row 4 Closed (completed + withdrawn only -> row 3); empty plan -> row 2 Closed; withdrawn plan -> row 1. The server computes `planState` and the allowed-action flags from this one function; the client, the follow-up job and the browser tests read the server's values (the job uses rule 4.4, which matches the eligibility column), so no layer re-derives it differently. A unit test asserts every row (and the listed mixtures) against the function.

## 7. Permissions, audit, data, integrations, accessibility, recovery, performance, release
- **Permissions (OQ-1 decided):** link/unlink: `ManageAppointments` (Front desk, Office manager, Admin) **or** `ManageTreatmentPlans` (Dentist, Admin) - an administrative scheduling relationship, not a plan edit; target dates, answers and every other plan change: `ManageTreatmentPlans` only. The bookable-treatment read exposes no clinical text. Reading the linked appointment on the plan needs `ViewSchedule` for time/provider; without it the item shows only "Booked". Tests prove a front-desk account can link/unlink but cannot answer, rename, revise, set a target date or read the plan.
- **Audit:** new audit actions `TreatmentPlanItemAppointmentLinked/Unlinked`, `TreatmentPlanItemTargetDateSet/Cleared`; DR-7 detail text; plan events as history.
- **Data/migration:** one migration (section 4); no data rewritten; upgrade behaviour section 4.5.
- **Integrations:** follow-up jobs (section 4.4); calendar (read; a link to it). No external service.
- **Accessibility:** new controls labelled; status words, not colour alone, for Booked/Cancelled/Overdue; the warned "Revise anyway" is a confirmation dialog with focus management.
- **Recovery:** link/unlink are reversible by appending; a failed save changes nothing (one transaction); the follow-up pass is idempotent.
- **Performance:** the plan read adds one join to appointments per plan load (indexed by `ItemId`, `AppointmentId`).
- **Release:** ALV-N013 installer applies one more migration; Down refused once links exist.
